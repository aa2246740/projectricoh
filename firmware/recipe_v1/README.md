# GXR recipe v1

这是独立的 C 原型：读取、写回 16 槽配方库，选中一条即覆盖原厂 Setting1、两轴白平衡，并设选择值 `04`，写完后请求预览更新。按用户决定，原 Setting1 不备份、不恢复。Setting2 不由 apply 写入；`recipe_core/` 没有改动。

原型已经通过电脑测试和 m32r 编译。原厂文件与预览 ABI 桥接、ADJ 菜单尚未安装。输出文件不能通过原厂 My Settings 菜单加载；object 和测试 ELF 也不是升级包。

## 复跑

在项目根目录运行：

```sh
sh firmware/recipe_v1/run_tests.sh
python3 -I research/stage1_data/analyze.py
python3 -I research/stage1_data/audit_delivery.py
```

第一条使用现有 Apple Clang、GCC 13.4.0 m32r-elf 和项目内 Binutils。它只写本目录的 `build/` 和 `protected-inputs.json`。后两条只写 `research/stage1_data/`。

测试读取真机样本 `captures/a12-50/2026-10-13/A0-baseline/MYSET01.IFO`，检查其固定 SHA-256 和原厂加权和。真实 Setting1/2 的 13 字节和白平衡 `09 09` 会生成测试 fixture。脚本检查 `recipe_core/`、样本及官方 `ilaunch3` 在前后保持相同哈希。

当前结果是 31 项用例分别通过普通宿主执行和 ASan/UBSan。Python 另行核验每条记录的 CRC、真实色彩字节，以及 apply 后全部 4096 字节的内存范围。结果在 [`build/verification.json`](build/verification.json)。

## 文件格式

每个文件包含完整的 16 槽库，长 1056 字节。所有多字节整数按大端保存，禁止直接把 C struct 写进文件。

| 文件头偏移 | 字节数 | 内容 |
| ---: | ---: | --- |
| 0 | 8 | ASCII `GXRRV101` |
| 8 | 2 | 版本 1 |
| 10 | 2 | 文件头长度 32 |
| 12 | 2 | 记录长度 64 |
| 14 | 2 | 槽数 16 |
| 16 | 4 | generation，可从 `ffffffff` 回绕到 `00000000` |
| 20 | 4 | 记录区长度 1024 |
| 24 | 4 | 记录区 `32..1055` 的 CRC-32/ISO-HDLC |
| 28 | 4 | 文件头 `0..27` 的 CRC-32/ISO-HDLC |

第 n 槽在 `32 + (n-1)*64`，n 为 1..16。

| 记录偏移 | 字节数 | 内容 |
| ---: | ---: | --- |
| 0 | 1 | 槽号 1..16 |
| 1 | 1 | occupied，0 或 1 |
| 2 | 1 | 名称长度，已占用槽为 1..32 |
| 3 | 1 | 保留，必须为 0 |
| 4 | 32 | 名称原始字节，名称结束后的字节必须为 0 |
| 36 | 13 | 对比度、锐度、鲜艳度，五色鲜艳度，五色色相 |
| 49 | 2 | 两个白平衡补偿值，二补码 int8，范围 -8..+8 |
| 51 | 9 | 保留，必须为 0 |
| 60 | 4 | 记录 `0..59` 的 CRC-32/ISO-HDLC |

五色顺序为橙、绿、蓝、红、洋红。13 个色彩字节保持原厂枚举编码，合法字节为 `01..09`，它们与界面显示值的顺序不同。显示 1..9 对应 `07 06 01 02 03 04 05 08 09`。白平衡在应用时加 9，写入 `S+0x6dd/+0x6de`。

名称是长度限定的原始字节，可以由电脑端保存 UTF-8；本原型不把它转换为相机字形。相机首版列表可显示 R01..R16。空槽要求记录偏移 2..59 全部为 0，槽号与 CRC 仍存在。

`rv1_decode` 先验证全部 16 槽，再修改输出。损坏、短文件、超长文件、未知版本和越界字段都返回错误。`rv1_encode` 先验证整个库，错误时不修改输出文件缓冲区。

## SD 保存

固定路径为 `/ATA1/RECIPES0.DAT`、`/ATA1/RECIPES1.DAT`，两者都是 8.3 文件名。每个文件长 1056 字节，合计 2112 字节，实际卡占用还取决于簇大小。

`rv1_store_load` 验证两个文件，选择较新的有效 generation，再重读该文件。损坏的新文件会回退到完整的旧文件。两份都损坏时返回 `RV1_CORRUPT`，不会自动重建。两份都不存在返回 `RV1_EMPTY`。未来版本、媒体 I/O 错误和相差半个计数空间的 generation 都阻止保存。

`rv1_store_save` 只写另一个文件，并读回检查 CRC 和内容校验值。回调必须返回真实字节数，检查关闭和刷新失败。一次保存失败后，旧有效文件仍保留；若关闭返回错误但新文件实际完整，后续加载可能选择新文件。这个协议不宣称 FAT 元数据或物理掉电的原子性。

`Rv1Store.read/write` 由平台实现。write 回调应把指定目标替换为精确长度的整份文件，宿主使用 `fopen(..., "wb")`；原厂创建函数的截断语义尚未确认，接入时需核对，或只重建本次指定的另一份文件并检查 delete/create 结果。状态区分缺卡、写保护、满卡、文件不存在及其他 I/O 错误。原厂错误原因未确认时应返回 `RV1_IO`，不能把所有打开失败归为文件不存在。调用方必须独占整个 load/save 操作；单独给每次回调加锁不能阻止两个保存者选中同一文件。

宿主真实文件回调在 `tests/test_recipe_v1.c`。它用 `fread/fwrite/fflush/fclose`，只读写测试目录。缺卡、写保护、满卡、短写和关闭失败由另一个模拟回调注入，未在物理 SD 卡上测试。

## 应用配方

`rv1_apply(port, recipe)` 固定写 Setting1，共 16 个字节：

- `S+0x36f/+0x370/+0x371` 的三个全局项。
- `S+0x8ac..0x8b0/+0x8b1..0x8b5` 的两个五色数组。
- `S+0x6dd/+0x6de` 的白平衡两轴，以及最后写入的 `S+0x36e=04`。

原 Setting1 的色彩数值被当前配方取代，白平衡补偿也随配方改变。apply 不写 Setting2、曝光、对焦和画质字段。没有备份、恢复或持久化遮罩。

```c
/* bank 已成功解析；先确认 slot 为 1..16、occupied=1。 */
Rv1Status status = rv1_apply(&port, &bank.slots[slot - 1].recipe);
```

`Rv1SettingsPort.acquire` 每次取得当前 S 和长度，并防止原厂拍摄、编辑、MY 召回和保存与写入/预览同时发生。GXR 上应读取 `*(u32*)0x200c0dac`，长度来源是 `*(u32*)0x200c0db0`，当前固件初始化值为 4096。核心最低长度要求为 `0x8b6`，电脑测试使用完整 4096 字节模拟内存。

必须提供 `request_preview` 回调。它在全部字段和选择值写好之后，同步桥接到原厂 `0x202d6f38`，传原厂参数 `r4=0`，请求命令 `0x2f03`。原厂返回 0 映射为 `RV1_OK`，-1 映射为 `RV1_IO`。`release(changed)` 只释放所有权，changed=1 表示字段已写、请求已调用。用 UI/设置任务的串行执行保护这段操作，不要关闭中断后调用原厂队列。

缺少回调、非法配方、短对象、空 S 或 acquire 失败时，核心不写 S，也不请求预览。预览队列失败时返回 `RV1_IO`，S 已保留完整配方，release 的 changed 仍为 1。队列成功只表示请求提交；实际预览需真机验证。下一次拍摄继续由原厂发送 `0x2f02`，核心不直接调用拍摄 sender。

关闭 ADJ 列表后继续使用所选配方。重新打开原厂 Setting1 编辑页会从 S 读取当前配方数值，用户修改的也是当前值；SD 库不会随原厂编辑自动写回。应用时原厂编辑页应处于关闭状态，防止旧的临时编辑对象随后 OK 回写。

原厂 `0x20067bb4 -> 0x200997cc` 保存整个 S，并重算 `S+0xffc` 的原厂加和校验，因此这些配方值会进入成功执行的机身保存。apply 不立即调用 flash 保存函数，沿用原厂保存时机。正常关机后保留属于强推测，普通电源键事件、上电恢复和实际 JPEG 仍需真机复核，详见 [研究报告第 4 节](../../research/stage1_data/REPORT.md#4-关机保留与直接占用-setting1)。

原厂保存当前配方的 Setting1、白平衡及选择值；配方名称和 16 槽库保存在 SD。本 API 不持久保存 R01–R16 编号，重启后的 ADJ 高亮由 UI 处理；只凭模式 `04` 无法确定配方编号。

## m32r 产物

最终参数包括 `-m32r -mmodel=large -Os -ffreestanding -fno-builtin`。默认 small model 在假定的 `0x20400000` 地址发生 `R_M32R_24_RELA` 溢出，证据在 `build/layout-small-negative.txt`。large model 已通过该地址的独立链接检查。这个地址只用于检查重定位，未证明那里能放固件代码。

| 项目 | 字节数 |
| --- | ---: |
| `.text` | 2848 |
| `.rodata` | 72 |
| `.data/.bss/.sbss` | 0 |
| 代码与只读数据合计 | 2920 |
| ELF object 文件 | 5012 |
| 目标上的 `Rv1Recipe` | 48 |
| 目标上的 `Rv1Bank` | 788 |
| 目标上的 `Rv1SettingsPort` | 16 |
| caller-owned 文件缓冲区 | 1056 |

库与文件缓冲区共 1844 字节，另加回调结构、UI状态和调用栈。最大的单函数静态栈框架为 60 字节，平台回调、嵌套调用和中断栈不包含在内。

[`build/recipe_v1.m32r.o`](build/recipe_v1.m32r.o) 是 ELF32 大端 M32R，未定义符号为 0。`build/recipe_v1.layout-check.elf` 是电脑端的地址布局检查产物，没有执行。

GCC 的前三个参数在 `r0..r2`，原厂文件函数的参数在 `r4..r6`，预览入口使用 `r4=0`。证据见 `build/gcc-abi-probe.s` 和 [研究报告](../../research/stage1_data/REPORT.md)。必须实现寄存器与栈约定桥接，再调用原厂文件或预览地址；不能直接强转成普通 C 函数指针。
