EXIF 记配方：可行（需 v3.11）

推荐沿用原厂已经存在的 264 B `UserComment`：先锁存本张实际生效的配方身份，再在 JPEG、DNG 各自生成该字段时填入。保留原厂目录、长度、图像数据和保存流程。首版记录配方 ID、目录身份及实际状态摘要，电脑按随版本封存的目录显示配方名。

## 2. 相机何时组装元数据

元数据分成拍摄参数准备、原生照片记录、文件头构造、保存任务几个阶段。JPEG 压缩结束不等于文件头已经定稿，更不等于照片落盘。

| 阶段 | 静态追踪所见 | 对配方标记的含义 |
| --- | --- | --- |
| 准备拍摄参数。 | 原厂读取设置区，包括版权文字，并更新共享元数据缓冲；部分参数另进入本张原生元数据对象。 | 配方应用时改一个共享字符串，不能直接证明它属于以后某次曝光。 |
| 生成本张图像和记录。 | 原生拍摄槽关联元数据对象、主图、JPEG 及 RAW 描述符。当前共有 18 个槽。 | 应绑定槽的本次生命周期和原生拍摄身份，不能只记一个槽地址。 |
| 主 JPEG 编码。 | H40 在主压缩包装器之前，H41 在包装器返回之后。普通路径随后还会构造 JPEG 头。 | H40 没有“最终 EXIF 缓冲区”参数；H41 也不是元数据提交或写卡完成点。 |
| 构造 JPEG 头。 | 读取本张元数据对象、单元信息和若干共享文本来源，构造 EXIF／MakerNote，并重新复制 `UserComment`。 | H40 早写的同名内容可能被后续原厂复制覆盖。 |
| 构造 DNG 头。 | 独立 RAW 路径先把本张元数据复制到原生临时区域，再调用 DNG 构造器。它有独立的 `UserComment` 复制函数。 | RAW-only 不能依赖主 JPEG H40；RAW＋JPG 两份文件必须消费同一张快照。 |
| 交给原厂保存任务。 | 文件封装与存储另有任务和生命周期。 | 标记应在头仍归构造器独占时写完，不在文件已经排队后回头改内存或文件。 |

## 3. 候选路线逐条评估

### a. 配方应用时改原生版权设置

这条路线有真实基础。离线固件更新手册明确写有 `Copyright notice`，说明输入的信息会写进照片 EXIF，回放详情也能查看。原生编辑器、设置区文字、共享版权缓冲、JPEG 与 DNG 内容复制之间已有静态链。

应改的是受控的原生设置，不能只改共享缓冲；原厂准备拍摄参数时会从设置区重填它。当前 DAT 的设置写服务只放行颜色参数和自有记忆记录，尚不放行版权文字。服务代码在 DAT 中，扩展服务本身并不必然要求改机身，但必须保留原生锁、设置代次、补偿及保存规则。

| 项目 | 判断 |
| --- | --- |
| 字节成本。 | 设置 47 B、输出 70 B 均已存在，新增字段容量为 0 B。独立“检查长度并复制 47 B”函数实测 60 B，不含锁、原文保留、应用成功判定、设置校验、失败补偿及生命周期处理。若另存原文，需至少 47 B，按 4 B 对齐为 48 B。完整适配增量未链接，不能将 60 B 报成完整功能。 |
| g159／v3.11。 | 可以继续研究 DAT-only 的版权适配，但现有 test 代码区仅余 8 B，连上述不完整函数都不能直接追加。还须证明原厂排队互斥或增加逐帧机制。本轮不将它评为可靠的 g159 交付路线。 |
| JPEG／DNG。 | 正常拍摄的两个构造器都消费版权缓冲，静态上均可覆盖；RAW-only 也有该字段。非空自定义版权尚无本机实拍样本。 |
| 是否代表本张。 | 仅在已证明的串行拍摄范围内，且文字只在真实应用成功后更新、所有覆盖和失败均撤销旧身份时，才可能成立。当前没有排除“先曝光 A，后准备 B，最后给 A 写头”的完整生产者链。 |
| 风险。 | 会覆盖机主版权，且改动可随设置保存。只改标题、光标或 BOOT 意愿会留下假标签。原文、设置一致性和先前在途照片都要处理；不应新增强制写盘或强制保存设置。 |

它适合先用原生菜单做零代码通路验证，也可作为仅限串行单张的后续小原型；不能省略逐帧身份要求。

### b. 在已有 H40 或新的元数据入口写定长字段

直接在 H40 猜一个 EXIF 偏移不可采用：它没有最终字段地址，后续原厂还会重建头，DNG 有独立路径。推荐的是这条路线的正式版本：保留 H40 观察，另在拍摄身份冻结以及 JPEG、DNG 字段生成时提供受控入口。

| 项目 | 判断 |
| --- | --- |
| 字节成本。 | 推荐的 ID-only 序列化器实测 M32R 代码 324 B、只读常量 36 B，共 360 B；目录 SHA-256 另 32 B。每张规范字节快照 20 B，18 槽共 360 B。合计已量化 752 B，尚未计桥、发布、失效、快照打包、指针验证、重定位及对齐的完整集成增量。照片空间增加 0 B。 |
| g159／v3.11。 | 推荐 v3.11。现有 H09 没有已证明的逐帧 K 身份；现有 H40/H41 不提供两个最终字段。当前 test 代码和主请求也均不足。仅调大 DAT 链接上限无效，运行中的 resident 同样检查代码上限。 |
| JPEG／DNG。 | 可分别覆盖 JPEG-only、RAW＋JPG 和 RAW-only，前提是两个元数据入口消费同一张快照。首版只开放已经验证的普通单张路径。 |
| 是否代表本张。 | 在参数冻结时绑定真实拍摄身份、槽代次、单元及有效状态；写头时只读这份不可变快照。下一张切配方不会改前一张标签。缺失映射时留空或未知，禁止沿用“最近一次配方”。 |
| 风险。 | 指针、所有权或时机错误仍可损坏头。必须验证原字段与长度，只在原厂尚未提交该头时写内容。标记失败时零写并继续原厂保存，不能沿用像素处理失败后跳过编码的合同。 |

首版用 ASCII 十六进制协议包住数字 ID，不添加名字表。推荐原型正文 119 B，连字符集前缀与终止符共占 128 B，保留整个字段 264 B。配方名由同一份封存目录解析；代数、ID、单元、实际状态摘要和目录身份共同区分版本。拍摄序号与槽代次负责本张绑定。摘要不用于从颜色反推配方，也不能单独还原每项微调。

若还要逐项保存 10 个微调值，本轮另测完整编码器 708 B、目录摘要 32 B、48 B×18 槽快照 864 B，已量化合计 1,604 B，正文 200 B；它不是“只记哪个配方”的最低成本。名字直接写入可后续研究，未计入这两份对象。

目录摘要由不含该标记的规范配方目录预先生成；不是把 DAT 自身完整 SHA 填回 DAT。CRC 只检查标记完整性，不能证明相机确实用了某组颜色参数。

### c. 复用 MakerNote 未用字段

没有找到可证明归扩展所有的保留字段。样本中的零值只能说明这些样本没有变化，不能证明所有场景、单元和原生读取者都不用它。

| 项目 | 判断 |
| --- | --- |
| 字节成本。 | 覆盖已有一个 byte／整数只需 1／4 B 文件内容，但完整写入及身份代码未定，不能按 store 指令长度报价。若新增一个 TIFF 项，目录至少增 12 B，4 B ID 可内联；较长 payload 还需额外空间和对齐。当前没有被证明安全的空目录项。 |
| g159／v3.11。 | 现有未用字段路线不放行。v3.11 可设计正式自有标签，但不因换机身版本就获得未知字节的使用权。 |
| JPEG／DNG。 | 两者都有 MakerNote；共同格式不代表原厂所有生成入口相同，仍需各自绑定。 |
| 是否代表本张。 | 与路线 b 一样需要逐帧快照；换到 MakerNote 不会消除身份竞态。 |
| 风险。 | 改 selector／13 参数会伪造原生设置，并可能影响原生回放或后续 RAW 处理；未知枚举可能不被原厂读取者接受。新增项会改变目录／偏移，违反本轮优先保留原文件布局的安全目标。 |

| --- | --- | --- |

## 4. 空间账与版本建议

| 项目 | g158 test | g158 release |
| --- | ---: | ---: |
| DAT 文件。 | 94,952 B | 92,484 B |
| 可执行节，含其常量。 | 69,624 B | 67,392 B |
| 距 69,632 B 代码上限。 | 8 B | 2,240 B |
| BSS。 | 4,360 B | 4,360 B |
| 主请求。 | 106,940 B | 104,472 B |
| 距 107,612 B 工程上限。 | 672 B | 3,140 B |

两包共享的 resident 可用余量为 92 B。它与 DAT 代码余量是独立限制。

按推荐 ID-only 原型做已量化相加，test 主请求为 107,692 B，超 80 B；可执行节增 392 B，超现有余量 384 B。release 主请求为 105,224 B，仍余 2,388 B，但它不提供 test 的 BOOT 策略，且没有解决新的拍摄入口。完整微调版会使 test 主请求达到 108,544 B，超 932 B。

这些是算术投影，不是完整链接结果。ID-only 目标函数栈为 8 B；完整编码器最大单函数栈为 28 B，hex helper 另有 8 B 栈帧。新桥和原 task 的完整栈峰值未验。为安排后续工作，可另外给 DAT 适配与发布暂留 512 B，给 resident 桥接与边界验证暂留 512 B。按推荐版，前者使 test 主请求投影到 108,204 B，需回收 592 B；后者超过当前 resident 余量 420 B。这两个 512 B 都是工程预留，最终按实际链接替换，不能当已测实现大小。

因此建议与 [v3.11 规划](../v311_feasibility_r1/REPORT.md)共用正式拍摄身份和驻留扩展设计。数据压缩只能缓解主请求，不能单独解除 resident 和 DAT 代码上限。若后续专门精简 g159，并证明版权路径的排队互斥，路线 a 仍有 DAT-only 研究价值；本轮没有这些证明。

## 5. 怎样保证标的是实际生效配方

标签发布应跟随已有深层应用与读回成功，不能跟随菜单高亮、待应用记忆记录或开机意愿。手动应用、开机自动应用、预览取消与补偿恢复都有独立出口，必须一起核对。

1. 在深层表与原生参数全部应用、读回成功后，发布一份不可变的有效状态，包含配方引用、单元、10 项实际微调、完整状态摘要及目录身份。预览若已真实改变颜色，也按有效状态处理；不能一律用“上次确认”。
2. 在对应的原生拍摄参数冻结点复制这份状态，并用拍摄序号和槽生命周期绑定本张。H09 只有参数块，不能按 FIFO 或“最后一次 H09”猜 K。
3. JPEG 和 DNG 写字段时消费同一快照，不再读当前 UI、当前全局模板或当前配方。后一张成功切换不应撤销前一张已冻结的身份。
4. 应用失败、恢复未知、单元变化、原生设置覆盖、DAT 退役或缺失映射时，对新拍摄不给有效配方标签；槽复用前撤销旧绑定。标签出错只影响识别，原厂保存继续。

原始 RAW 像素不会因写此标签而变成已烘焙的配方结果。DNG 标签描述本次拍摄关联的相机配方；不能据此声称任意电脑显影器会自动复现机内 JPEG。

## 6. 照片与文件系统的硬边界

推荐路线不新增任何相机文件 I/O，不 open、seek、append、重写照片或记日志。不改变 APP1／IFD 项数、字段类型或长度、MakerNote 大小、RAW strips、JPEG 码流、偏移及文件大小。只在原厂头尚未发布时替换已经存在的字段内容。

以下任一不成立就不得写入：可信原厂调用点、可信且独占的完整头范围、正确的现有标签／类型／264 B 长度、本张身份一致、原有内容为空白或受支持的自有版本。已有用户文字原样保留。缺 DAT、CRC 错、失效和忙状态都原样通过，不能等候、重试、改原厂文件系统状态，不能把标记错误返回成编码错误。

本轮只能验证局部指令、文件格式和空间账，不能证明新 hook 不会在实机损坏照片。目前禁止把研究原型上卡；只有原厂保存零改动、所有写入白名单和完整故障路径通过后，才准备现场候选。

## 7. 最小现场验证方案

本轮未碰相机，下面是后续现场顺序。每一步只做一个动作；每次快门后等保存灯熄灭，再给机主下一步，文件在关机交卡后统一检查。所有样本用可擦除的测试卡，原片由验证者取回分析，机主不用手改文件。

### 先验证原生文字通道，不换 DAT／机身

验证者先记录原版权、准备已备份的测试卡，并确认当前稳定版本。只需当前 MOUNT 和一张 RAW＋JPG。

1. 将保存格式设为 RAW＋JPG。
2. 在原厂“Copyright notice／版权信息”中输入 `GXRT-A`。
3. 退出到拍摄待机。
4. 拍一张普通单张照片。
5. 正常关机。
6. 将测试卡交给验证者。

验证者只读检查这对原件：两份 Copyright 是否完整为 `GXRT-A`、所有图像能否正常解码、已有字段长度是否如本报告。任一不一致先停在原生通路问题，不安装标记原型。核验后用原生菜单恢复原版权；这次手填文字不算自动配方功能通过。

### 再验证已审查的 v3.11 标记候选

验证者先完成刷机／恢复审查、完整链接、逐槽及故障模拟，准备默认关闭、仅普通单张开放的候选，设计不修改单元映像。本轮没有准备这些包。先安排一张原样透传基线，确认成功才开启标记。开启后 MOUNT 再做以下五次快门，A、B 取两个有明显不同 ID 的已验证配方。

1. 将保存格式设为 RAW＋JPG。
2. 应用配方 A。
3. 拍一张照片。
4. 应用配方 B。
5. 拍一张照片。
6. 应用配方 A。
7. 拍一张照片。
8. 正常关机。
9. 正常开机。
10. 不进配方菜单拍一张照片。
11. 将保存格式设为 RAW-only。
12. 拍一张照片。
13. 正常关机。
14. 将测试卡交给验证者。

前三张应为 A→B→A；每张 RAW＋JPG 的身份、状态摘要及拍摄序号必须相同，若启用完整微调版还要核对 10 值。冷启动那张只接受实际 BOOT 成功后的身份；没有成功就应未知，禁止仅从记忆记录写 A。最后一张验证 RAW-only 没有依赖 H40。

两只 A12 后续各补一张 RAW＋JPG，逐次应用后再拍。该最小流程不覆盖连拍、自拍、间隔、SCENE／MY 和拍摄中途切换；这些路径在对应身份／生命周期验证前保持标记关闭。完整交付还需 K 槽复用、失败补偿、保存排队与覆盖模式的故障矩阵，不能靠 A→B→A 三张替代。

出现保存异常时保留第一份原件和错误画面，不在写入中拔卡、强断电或格式化试错。现场“能拍”也不能代替文件结构、图像数据和逐帧身份核验。

## 8. 本机验证与复跑

本轮回执及精确计数见 [static-results.json](local/static-results.json)、[native-results.json](local/native-results.json)、[format-results.json](local/format-results.json)。

- 静态核对 23 个窗口，其中 22 个与当前 v3.10 相同；H09 的预期已有补丁另列，不把原厂序言当成现行执行路径。当前 resident 字节也与最终 ELF 对应。
- 原始 M32R 指令局部重放共 16 例，覆盖 6 例 UserComment 复制、4 例版权设置、4 例 JPEG／DNG 版权内容复制和 2 例 MakerNote 参数复制。共享模板改变的顺序是人工夹具，未执行完整 RTOS 连拍。
- ID-only 和完整微调版各有 128 例主机 C／Python 序列化对照通过；各自 264 个单字节破坏均拒收、3 例无效参数保持零写。M32R 对象用于尺寸和栈报告，未将主机 C 结果称为完整相机执行。
- 从已有 69 个文件读取字段，选择三单元的 3 份 JPEG、MOUNT 和 50mm 的 2 份 DNG，在内存副本替换 UserComment。文件大小、字段位置、其余字节及 9 个已定位图像区域全部相同。本轮没有 28mm DNG 副本试验，也没有任何新标记的机内输出。

以下命令在仓库根串行运行。每项调用 `tools/loadgate.py` 的 `workers()`；返回 0 时以 75 退出并推迟，未另设 load1 门槛。原始 CPU／内存采样保存在 [admissions.jsonl](local/admissions.jsonl)。

```sh
nice -n 15 /usr/bin/python3 -I -B research/exif_recipe_tag_r1/local/static_study.py
nice -n 15 /usr/bin/python3 -I -B research/exif_recipe_tag_r1/local/native_probe.py
nice -n 15 /usr/bin/python3 -I -B research/exif_recipe_tag_r1/local/format_probe.py
```

这些通过只支持离线可行性，不代表相机已输出新标签、完整内存互斥成立或照片安全验收通过。完整集成代码与新桥的准确字节数仍待下一实施任务。

最终输入复核和本目录摘要见 [verification.json](local/verification.json)、[SHA256SUMS](local/SHA256SUMS)。
