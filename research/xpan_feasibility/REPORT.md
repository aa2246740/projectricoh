### 1.4 单元里的裁切能力

- 图像处理中间层的输入结构有 16 位字段 `RawRgbSize_X`、`RawRgbSize_Y`、`RawRgbCropOrigin_LX`、`RawRgbCropOrigin_RX`、`RawRgbCropOrigin_TY`、`RawRgbCropOrigin_BY`、`RawRgbLines`。字符串在 `jlaunch3` 文件偏移 `0x1FA538` 起（VMA `0x20245338..0x20245518`），打印函数 `0x202388C0..0x202389F0`：`struct+12`、`+16` 是行数类字段，`+36/+38` 是 `RawRgbSize_X/Y`，`+40/+42/+44/+46` 是 `CropOrigin_LX/RX/TY/BY`，都是 `lduh`。`qlaunch3`（`CropOrigin_LX` 字符串在文件偏移 `0x1FE036`）、`l08firm3`（`0x1F9456`）里也有同样的字符串。结论：底层可以接任意裁切坐标。
- 谁在拍摄时把这些字段填成 16:9/4:3/3:2/1:1 对应的值，这一轮没有追到。所以"加第 5 种画幅"需要改单元里这张表（或它的调用者），机身这边只是传一个 4 以上的类别，单元会把它夹成 0。
- 单元的传感器/输出尺寸表在 `jlaunch3` 文件偏移 `0x7A1D0` 附近（VMA `0x200C4FD0`）：`10d0 0b2e`（4304×2862）、`10c0 0b20`（4288×2848），后面是镜头名 `RICOH GR LENS A12 50mm F2.5 MACRO`。这是单元自带的"镜头/传感器参数块"，不是画幅表（其他画幅的像素数没有以 16 位常数形式出现，是计算出来的）。

### 1.5 DNG 裁切标签和 JPEG 尺寸

- 写标签的通用函数在 `jlaunch3:0x20166E70`（以标签号、类型 5=RATIONAL、个数 2 调用）。标签号 0xC61F（DefaultCropOrigin）出现在 `0x20161F00`、`0x20161F3C`、`0x201641BC`；0xC620（DefaultCropSize）出现在 `0x20161FFC`、`0x20162044`、`0x20164268`。数值来自写入上下文里的偏移 1244/1256/1320/1336 等字段，这些字段在哪里被填没追到。机身里也有同样的一份写标签代码（`0x20123DF8..0x20123F40`），不能凭此认定"只有单元写"；但拍摄时的 DNG 保存函数名 `MngRecStill_SaveDngFile1/2` 在单元里（`0x2021E262`、`0x2021E299`），所以拍摄 DNG 判断为单元写。
- 现有样本（`captures/` 里 A12/MOUNT 全部 DNG 与 JPEG，统计在 `local/sizes.txt`，脚本 `sizes.py`）：
  - 341 个相机直出 JPEG（手机翻拍图不算）全是 4288×2848；
  - 341 个 DNG（330 个 `GXR A12`，11 个 `GXR MOUNT A12`）全是 4304×2862 的 RAW，且 DefaultCropOrigin = (8/1, 7/1)、DefaultCropSize = (4288/1, 2848/1)，即默认裁切恰好等于 JPEG 尺寸；
  - 样本全部是 3:2 L，**没有任何其他画幅的样本**，所以 16:9、4:3、1:1 的真实像素数和 DNG 裁切值目前未知。
- 结论：JPEG 尺寸和 DNG 默认裁切都由单元在拍摄时一并决定，画幅变了它们跟着变（手册也这样说）。这部分是强推断，用第 5 节上机步骤实测可以确认。
- MakerNote 的 22,880 字节里是否记录 Image Settings 或画幅，本轮对比了 `captures/a12-50/2026-10-20/stage2j-notables-huering` 里的 4 张 DNG（场景和配方都不同，`mn_diff.py`），差异几乎全是场景数据（白平衡、直方图一类），没能分离出配方或画幅字段，仍未知。

### 1.6 取景时的黑边

- 手册只说"显示屏上下/左右变黑"，没有说是谁画。
- 机身侧：访问画幅字节的地方很多（`S+0x3A9` 有数十处读写，`S+0x3F4` 也有三十多处），抽查到的都是设置校验、菜单可用性、保存到快照等（例如 `0x2027B9C0`、`0x2027D914` 在 `S+0x3A9` 为 1 或 2 时才跳过两次状态复位调用 `0x202697BC(0)`、`0x2027164C(0)`，前者写 RAM 标志字节 `0x205D9A6E` 并调用 `0x202B4688`、`0x202B467C`、`0x202729D0`（没有展开，是否与取景绘制有关未知），后者只写 `0x205D9AA2`；`0x20357600` 把它复制进一块 RAM 快照）。没有逐处看完，所以不排除遗漏。没有找到"按画幅往图层上填黑矩形"的代码。

- 因此"黑边由谁画"这轮只能说倾向单元，没有证据排除机身。这个问题只影响路线 (a) 的设计细节（能不能直接沿用现成黑边），不影响结论。

## 3. 推荐路线

1. **先做 (d)+(c) 零固件版**：Studio 提供"XPan 65:24"裁切（可调纵向位置、导出 JPEG 和带裁切标签的 DNG）；拍摄时建议用户把画幅设为 16:9，并让 Studio 把"16:9 文件"默认当作 XPan 候选（可在设置里关掉）。16:9 文件的尺寸本身就是标记，不需要任何固件，也不会丢。
2. **(a) 只作为下一次机身大更新的候选项，不单独刷一次**：前提是先拿到绘制接口的静态证据（找到取景网格 `Grid Guide` 的绘制代码，看能否加第四种"XPan 框"，或另找安全的 OSD 画线口）。没有这个证据之前不要往 v4 预算里记。
3. **(b) 搁置**：它要求改单元并刷单元，恢复没验证，三个单元都要，收益和风险不成比例。

## 4. 剩余未知

1. 画幅类别编号 0..3（或实际存储的 1..4）各对应哪一个比例。
2. 16:9、4:3、1:1 的 JPEG 与 RAW 像素数，DNG 的 DefaultCropOrigin/Size 实际值。A12 的传感器是 3:2，4:3 与 1:1 是否在单元内按传感器裁，16:9 是否 4288×2412，都未实测。
3. 单元里"画幅类别 → 裁切坐标"表在哪里、谁填 `RawRgbCropOrigin_*`。
4. DNG 写入上下文里 1244/1256/1320/1336 偏移字段的来源。
5. 取景时黑边是谁画的（机身还是单元）。
6. 取景网格的绘制代码和它的绘制范围（整个 640×480 屏幕，还是只在有效画面内）。
7. 机内是否有逐张可读的标记通道：JPEG 的 EXIF/MakerNote 和文件名由谁写，预留的 DNG 字段（ImageDescription 64 B、Copyright 70 B、UserComment 264 B）由机身还是单元填，未确认。
8. 28mm 与 MOUNT 单元的同类地址没有逐个核对，只确认了字符串在（`aspect_ratio` 出错字符串、`RawRgbCrop*` 字符串）。

## 5. 上机确认方法（只读，不超过 3 张照片）

目的：解出画幅类别对应的比例，得到 16:9、4:3、1:1 的真实像素数和 DNG 裁切值，并看看取景黑边和网格线的位置。不刷任何东西，不改菜单里的 Image Settings 配方。做完把画幅改回 3:2。

准备：50mm A12 单元，画质设为 RAW。按 ADJ. 拨杆，选"画质/尺寸"（手册说 ADJ. 拨杆默认第 3 项就是 Quality；如果你的 ADJ 键位改过，从设置菜单里找 Picture Quality/Size 也行）。

步骤：

1. 在"画质/尺寸"里选 RAW 的 16:9。对准任意静物，看屏幕：我们预期上下各有黑边。拍 1 张。
2. 选 RAW 的 1:1。预期左右有黑边。拍 1 张。
3. 选 RAW 的 4:3。预期没有黑边、铺满整屏，视野左右比 3:2 窄一点（A12 的传感器是 3:2）。拍 1 张。
4. 把画幅改回 3:2，结束。

可选的小测试（不算相机照片）：先到设置页的"Grid Guide Display Options"选带对角线的 4×4 网格，选 16:9 时用手机拍一张屏幕。假设：网格是画满 640×480 整屏的，那么 16:9 画面（占屏幕高度的中间 360 行）里，上下两条内部水平线会落在画面高度的 1/6 和 5/6 处，围成的高度比约为 66.7%，对应 2.667:1，和 XPan 的 2.708:1 很接近，可以直接当取景辅助线。如果网格只画在有效画面内，线就落在 1/4 和 3/4，围成的是更窄的 3.56:1，不适合。这是假设，没有静态证据，上面的拍屏幕照片可以直接判断。

用户会看到：每次改画幅后，取景画面上下或左右出现不同的黑边；拍完回放能看到对应画幅的图。

我这边读什么：把 SD 卡里新拍的 3 对 JPG+DNG 拷出来，我用 `sizes.py` 读像素数和 DNG 裁切值，对照取景观察，就能填第 4 节的 1、2、5、6 项。

## 6. 复跑和脚本

所有脚本只读。`xref.py`、`ptrscan.py`、`bytesearch.py`、`vdump.py` 借用 `research/hidden_processing/analyze.py` 里的段表解析和线性常量传播（只是读取，没有修改）；`fn.sh` 读 `research/tooling_m32r/disasm/`。

```sh
# 文件偏移转 VMA
/usr/bin/python3 -I -B research/xpan_feasibility/xref.py ilaunch3 vma 0x1d7628

/usr/bin/python3 -I -B research/xpan_feasibility/xref.py jlaunch3 refs 0x2021eec0 0x2021f130

/usr/bin/python3 -I -B research/xpan_feasibility/ptrscan.py ilaunch3 0x20222428
# 找字节串
/usr/bin/python3 -I -B research/xpan_feasibility/bytesearch.py jlaunch3 10d00b2e 24
# 按 VMA 转储数据
/usr/bin/python3 -I -B research/xpan_feasibility/vdump.py ilaunch3 0x203802c0 0x80

research/xpan_feasibility/fn.sh ilaunch3 20270c08 140
# 统计样本像素数和 DNG 裁切标签
/usr/bin/python3 -I -B research/xpan_feasibility/sizes.py captures
# MakerNote 差异
/usr/bin/python3 -I -B research/xpan_feasibility/mn_diff.py <DNG...>
```
