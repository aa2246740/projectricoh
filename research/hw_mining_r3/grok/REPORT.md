# MCR（type 11）静态研究

只读。没有构建，没有连接相机，没有写存储卡。官方包 SHA-256 为 `3705984b…fc898`，`ilaunch3` 为 `da1980e9…`，不是以 `04168d00` 开头的那一份。各单元段表按头部 `0x20` 起、每项 5 个大端 word 单独换算，文件偏移含 `0x200` 头。A12 的打包入口 `0x201123EC` 落在文件 `0x000C75EC`，用来核对换算。

## 结论

MCR 不能当作曲线前的颜色混合来用。六个镜头单元里，控制字节和六个半字的官方脚本值、嵌入默认块、以及打包后的四个镜像 word 都是 0。把这四个 word 写进 `F0318000/8004/8008/800C` 的 type 11 提交函数，在六个单元里都没有调用者。普通 apply 根本不读 F+1C。

另有一条会读 F+1C 的函数，六个单元都有。它把这个指针交给 type 27 的提交，寄存器在 `F034A`，不是 MCR 的四个地址。所以「槽里有数」和「MCR 寄存器被写到」是两件事。

像素方程静态看不出来。软件只把一个字节和六个半字原样拼进四个 word，没有通道、符号或乘加。六个非对角项的猜想和寄存器个数相容，但代码没有体现它，前端地址 `F031` 也不像那块已知的 `F034` 颜色矩阵。把它当成配色矩阵的可能性低。字段、零值和 type 11 没有调用者，这三件事的证据是高的；方程本身未定。

## 1. 六个参数在各单元里都没有被用起来

每个单元只有一处把 `T+25B3` 到 `T+25BE` 当成 16 位位移来读。控制字节用 `ldub`，六个半字用 `lduh`，两两拼成三个 word，再加控制 word，存进镜像。`lduh` 只说明容器是 16 位、位型原样拷贝，不能说明硬件按无符号解释。

| 单元 | 打包 | type 11 提交 | 镜像四个 word | 脚本 UEEF1/X12C0 的 13 字节 | 嵌入默认块 |
| --- | --- | --- | --- | --- | --- |
| A12 jlaunch | `0x201123EC` | `0x201123D4` | `0x20141584` 起，全 0 | 全 0，13 个字节都有写入 | `0x200B81D4`，全 0 |
| 28mm qlaunch | `0x20114FEC` | `0x20114FD4` | `0x20144818` 起，全 0 | 全 0 | `0x200B81FC`，全 0 |
| MOUNT l08firm | `0x2010CE14` | `0x2010CDFC` | `0x2013F95C` 起，全 0 | 全 0 | `0x200B978C`，全 0 |
| S10 nlaunch | `0x201123B0` | `0x20112398` | `0x201430AC` 起，全 0 | 全 0 | `0x200B81F8`，这 13 字节为 0 |
| P10 klaunch | `0x20115810` | `0x201157F8` | `0x2013ABE0` 起，全 0 | 全 0 | `0x200B81C8`，全 0 |
| A16 l06firm | `0x2011055C` | `0x20110544` | `0x2013F2B0` 起，全 0 | 全 0 | 16KiB 拷贝源没有从其他同长度调用里分开 |

T 指针槽的初值都是 `0x20022000`，这段不在已初始化段里，是运行时的 T。A12 槽是 `0x200B2CF0`，MOUNT 是 `0x200B4280`，S10 是 `0x200B2D14`，P10 是 `0x200B2CE4`，A16 是 `0x200B2C2C`，28mm 与 A12 同为 `0x200B2CF0`。五个已分开的默认块在 `+0x2444` 处，A12、28mm、MOUNT、P10 是 `0x0002`，S10 是 `0x0602`。这不影响 MCR 那 13 个字节，它们仍是 0。

脚本里 `0x25A4..0x25B0` 和 `0x25C2` 之后有非零半字。那是相邻字段，不是 `0x25B3..0x25BF`。

打包函数的唯一调用者是构建路径，条件是配置字节 +1 的 bit7。A12 在 `0x2010D548`。它只重写 RAM 镜像，不写 `F0318000`。

type 11 提交的形式是：源指针放进 r5，`ldi r4,#11`，再调用分发器。A12 分发器在 `0x20255600`，类型必须小于 40，描述表在 `0x2029DA8C`。type 11 的描述在 `0x2029C364`，四个地址后跟 0。对提交入口做了 seth/or3 和按 4 对齐的函数指针检索，六个单元都是 0 个调用者。读回入口（A12 `0x201123B0`，固定从 `F0318000` 读 4 个 word）同样是 0。getter 只有初始化在调：A12 `0x201131A8` 以参数 4 调用 `0x20112394`，把返回值存进 `0x20383EB4`，也就是 F+1C（F = `0x20383E98`）。索引表 `0x2012B540` 的第 4 字节是 0，所以返回值就是镜像基址 `0x20141584`。旁边的 word `0x010203` 是这张索引表，不是六个系数。

普通 apply（A12 `0x2010C474`）按配置位提交 F+4、+8、+C、+10、+14、+18，下一项直接是 F+20、+24、+28。六个单元的对应函数都是这个序列，中间没有 F+1C。A12 的三个调用者是 `0x20105408`、`0x201A412C`、`0x201A44AC`。后两个没有定成视频或回放，但它们调用的是这条跳过 F+1C 的函数。

会读 F+1C 的是另一条函数，A12 入口 `0x2010C248`，唯一调用者 `0x201054D8`，并且要 r12 非 0。配置字节 bit1 置位时，它把 F+1C 交给 `0x2011889C`。这个包装的第一条有效操作是 `ldi r4,#27`，不是 `#11`。qlaunch、l08firm、nlaunch、klaunch、l06firm 的对应被调函数头同样是 `ldi r4,#27`。type 27 的描述从 `F034A000` 开始。它的写入函数 `0x20257490` 先把描述指针加 4，跳过第一项，然后循环 4 次，每次把源 word 存到「这项地址 + r2」，r2 从 0 起每次加 4。按这个读法，四次落在 `F034A004`、`F034A008`、`F034A00C`、`F034A010`。无论这个加数是否还被别的指令改过，描述表在 `F034A`，不在 `F0318000`。r12 从哪来，这次没有往上追。

A12 在 `0x2011DFCC` 还有一次读取 F+1C，长度 512，被调函数 `0x2005199C` 是按对齐做的内存拷贝，不是 type 11 的寄存器写入。

机身 `ilaunch3` 在 `0x20409504` 有同样的四个地址，没有这六个半字的打包函数。同族资料里没有这个模块：`research/gr_firmware`、`research/frame_gr2`、`research/gr_complete_pipeline` 共查了 268 个文件，没有 `Dump MCR`，也没有 `F0318000`。`/tmp/gxr_gr_firmware` 不在。GR III 的 `FINDINGS.md` 写的是另一代 ARM 流水线，曲线前的混合是 CCA0 的 9 个系数，后面还有 CCA1，没有这个名字或这组地址。

## 2. 像素方程推不出来

打包过程是：

```text
镜像+0  = 控制字节 T+25B3
镜像+4  = (u16)T+25B4 << 16 | (u16)T+25B6
镜像+8  = (u16)T+25B8 << 16 | (u16)T+25BA
镜像+C  = (u16)T+25BC << 16 | (u16)T+25BE
```

`FFFF0000` 是 `0x10000` 取负之后用来留住高半字，不是窗口坐标，也不是 Q 格式。没有符号扩展（用的是 `lduh` 不是 `ldh`），没有乘，没有按 R/G/B 重排。全零既可能是关闭，也可能是「对角为 1、非对角为 0」的单位变换，代码两边都不支持。

六个半字和「3×3 去掉对角」或「相邻像素的六项串色」在个数上都能对上。现有指令分不出这两种，也分不出加性还是乘性，分不出作用在 Bayer 相邻像素还是 RGB 三元组。没有非零出厂值可以当例子。

## 3. 配置顺序在曲线和白平衡之前，像素顺序没有测到

调试名的顺序是 CAMREG、GRYDEC、REO、CCDIF、CDP、DCLMP、VK、MCR、SCR、SCM，然后才是 AWBCAM、ISPREG、WDR、RLUT、EXIP、AWBIP、LUT、INP、MCM、FLT。A12 初始化把 MCR 的指针放在 F+1C，VK 在 F+18，下一项在 F+20。这是配置结构的顺序。普通 apply 按这个结构往下提交，但把 MCR 这一格跳过了。

寄存器地址是另一套顺序，六个单元的描述表一致：

| 类型 | 描述的第一项 | 已有名称 |
| --- | --- | --- |
| 11 | `F0318000` | MCR |
| 7 | `F0310000` | 与 CCDIF 同一段 |
| 9 | `F0315004` | 与 DCLMP 同一段 |
| 23 | `F0342000` | 曲线 |
| 25 | `F0348004` | AWBIP，白平衡增益 |
| 26 | `F0349000` | 曲线 |
| 27 | `F034A000` | 上面那条 4 word 写入 |
| 28 | `F034C000` | 已知矩阵所在的颜色块；描述本身只列出 C000、C004 |

`F0318` 在 `F0342`、`F0348`、`F0349`、`F034C` 之前。这只说明地址地图把 MCR 和传感器前端放在一起，把白平衡、曲线和已知矩阵放在 `F034`。它不是像素从哪块流到哪块的测量。配置次序和地址次序互相一致，都不能单独升级成像素次序。

## 4. 只改六个参数不会写到 MCR 寄存器

要让 `F0318000` 被写到，得让现有的 type 11 提交被调用，调用时 r4 指向那四个镜像 word。普通 apply 里没有这次调用。这是单元代码上的改动，不是 T 里多写几个数。这里不给出具体改法。

单元代码在已初始化段里，加载地址就是它的执行地址，和 T 指针、X 的窗口基址在同一套 RAM 里。A12 的 X 处理在 `0x20243100`：命令值左移 16 位之后，`0x12C0` 改用 `*(0x200B2CF0)`，`0x12C1` 改用 `*(0x200B2CF8)`，`0x12C2` 再用这个指针加 `0x10000`，其余页号就把「页号 << 16」存成窗口基址。因此现有的 X/V/W 能够写到 `0x2010xxxx` 这段程序 RAM。`UEE00` 提交的是 T 那一块，不是程序映像。程序 RAM 里的半字改动，会在 MAIN 重新装入时消失，断电即回到存储里的官方映像。

现产品 `eng_core.c` 的 `deep()` 只写 GXMP 地图里的行，外加页 `0x12C0`、游标 `0x2444` 的控制字。`pack_v1.py` 里 A12/28mm/MOUNT 的行地址在 `0x2012xxxx` / `0x2013xxxx` 的曲线和矩阵表上，不覆盖 apply，不覆盖 MCR 镜像，也不覆盖 T+`0x25B3`。源码里没有把 `0x2010C474` 或 `0x12C025B3` 写成行地址。所以按现在的 deep() 使用方式，写不到这次需要动的指令，也写不到这六个参数。X/V/W 这套命令本身可以写程序 RAM，deep() 没有把页号指到那里。

风险在普通拍摄这条路上。`0x20105410` 无条件调用普通 apply，`0x201A` 里还有两个调用者。写错这里的半字，前端提交会停在这次调用上，直到程序映像重新装入。方程未知，所以即便 type 11 的四个寄存器被写到，也不能把它当成已经可用的配色控制。只改 T+`0x25B3` 而不调用提交，像素不会变；如果这次改动又随整块 T 被存下去，它会留在下次开机的 T 里，但仍然没有硬件效果。官方 `*8` 脚本会把这 13 个字节写回 0。

## 5. 判断和下一步

作为「曲线前、可按配方改的颜色混合」，MCR 的可能性低。支持这个判断的是：出厂值为 0、type 11 没有调用者、寄存器在 `F031` 前端而不是 `F034` 颜色块、软件没有 3×3 方程。没有被排除的只是「硬件内部把六个半字当成固定对角之外的项」这一种未证实的读法。GR III 上真正的曲线前矩阵是另一块硅片上的 9 个系数，对不上这个模块。

下一步不必改代码。最小的实机核对是：普通静帧前后读 `F0318000` 起的四个 word。若保持上电初值，type 11 在这条路径上就是空的。同时读 `F034A004` 起的四个 word，用来看 type 27 那条条件路径有没有在动。r12 的来源仍然是静态上的缺口。调用检索覆盖的是 seth/or3 和按 4 对齐的指针，不是每一条算出来的间接地址。

证据在同目录 `evidence/`。机器可读的汇总是 `evidence/summary.json`。关键反汇编是 `jlaunch-mcr-window.asm`、`jlaunch-apply-2010c598.asm`、`jlaunch-early-apply.asm`、`jlaunch-mcr-callee.asm`、`jlaunch-type27-writer.asm`、`jlaunch-controller.asm`、`jlaunch3-xhandler.asm`。
