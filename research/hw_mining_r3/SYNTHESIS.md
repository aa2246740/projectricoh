# MCR（type 11）三方独立研究汇总

汇总人：Opus 5.5（编排者），2026-10-27。本文只综合三份报告与电脑价值模型，待 GPT-6.1-Sol 独立核验，以核验为准。

> **核验后修正**（validate-hw-mcr-r1，GPT-6.1-Sol；[VALIDATION.md](validation/VALIDATION.md)，SHA256SUMS 247 项已复核 OK）。与本文冲突时以核验为准：
> - **G1 成立，但需收窄。** 四处驱动按 bit 0 决定清除还是保留 `0xFF700070` 的 bit 21；第五处带有 type 与运行状态条件，改的是保存值，由调用者稍后写回。门控的精确硬件名称未定。
> - **G2 成立。** X/V/W 可以对任意地址读写，高低两个半区采用不同的总线宽度，没有 RAM/MMIO 区域校验。现有产品已核对过的写入地图只指向 RAM。
> - **G3 未证实。** F031 前端分组成立，但不能证明它在 Bayer 域、在 RAW 写入之前，或相对 WB 和曲线的像素次序。
> - **G4**：可以设计一个只写 MCR 与 bit 21 的短试验，前提是先确认门控、记账状态和读回。风险包括花屏、全黑、颜色异常、总线停住或相机停止响应；出现异常就停止、按顺序恢复，必要时取出电池完全断电。像素效果和断电恢复都未实测。
> - **"所有路径都不提交"** 收窄为"有限搜索内未找到调用者"。**"断电必定恢复"** 收窄为"在只写易失寄存器、记账计数为零、没有持久提交这三个条件下成立，未实测"。
> - **建议**：MCR 保留为以后一次短的语义研究候选（单系数 `0000→0001→0000` 的 A→B→A）。当前不值得为它改单元代码，也不纳入产品承诺。

## 1. 一致结论

1. 六个单元的 MCR 参数全部为零，普通拍照路径从不提交它。按现有原厂流程，它不是可用的能力。
2. 像素方程静态无法确定。"混色校正，6 个非对角项"只是与现有证据相容的假说。
3. 价值：如果它是 Bayer 或 RGB 域的非对角混色（H1/H3），在现有目标下收益很小，不值得为此改单元代码。

## 2. 待核点（交给 GPT）

- **G1**：Gemini 所说"五处驱动读 `0xF0318003` bit 0，开关 `0xFF700070` bit 21"，是否成立？`0xFF700070` 是什么（时钟、电源或模块门控）？
- **G2**：X/V/W 能否访问任意 RAM 与 MMIO？请核对 `0x20242B68..0x20243178` 和 `0x2024304C`，以及 `X` 对 12C0/12C1/12C2 的特判。若成立，这对两件事都有影响：
  - 现产品写入路径的安全性：需要确认它不会误写 MMIO；
  - 今后的实机验证：可以直接写寄存器。
  需要说明：哪些寄存器在每次拍摄的配置 apply 中会被覆盖，例如 type 28；哪些不会，例如 MCR。
- **G3**：MCR 的物理位置。前端分组（F031 段）能否证明它在 WB 与曲线之前、在 Bayer 域？
- **G4**：给出一个最小、可逆的实机验证方案，供用户以后决定是否执行（本轮不执行）。要求：
  - 只写 MCR 与门控寄存器，取小系数；
  - 读回核对；
  - 断电即恢复；
  - 写明预期现象：色串扰变化，或无变化；
  - 写明风险：例如门控错误导致花屏或死机，以及恢复办法。

## 3. 建议

按现有目标，不为 MCR 投入改单元代码的工程。如果 G2 成立，就把"直接写 MCR 寄存器的小探针"列为以后某次上机时的可选项，用来低成本确认它的语义；只有在改用模拟器目标、且 MCR 被证明属于 H2 形式时，才值得深入。
