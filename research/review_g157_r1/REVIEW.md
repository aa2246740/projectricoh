## P1

### P1-01：显式套用失败后，半套颜色可以留在无护栏的取景状态

反例来自完整逻辑 S 的新 MAIN，使用有效原厂 Vivid 编码 09、合法的本 DAT HC BW 非默认记忆。首次 BOOT 正确跳过，首次诊断和记忆读回正常。进入列表后只按一次 OK 显式套用，在第八次实际单元写入已经发生后，把该次原厂 RPC 回执声明为失败。实际只注入了一次失败，之后没有额外丢弃回执。

原生 strict_r4 的单次故障复现为 `local/runs/independent-manual-true-once-native/` 和 `local/runs/independent-manual-true-once-release/`。两包均从新 MAIN 启动，使用各自合法绑定的记忆；驱动均正常收尾并观察到以下安全反例。

- 套用前，模型中经原生 RPC 读取的单元九行与 T 完整等于原厂 04。
- 套用失败后，单元 RPC 读回既不等于原厂 04，也不等于目标 HC BW，不能算完整颜色或成功补偿。第一行由目标前缀与旧 04 后缀拼成，并出现非单调点。
- 机身模型回到取景状态。resident 仍为 READY，引擎为 uncertain，DIRTY 和 GUARD 都未置位。
- ERR 留在 DAT 的错误缓存中；这次失败没有停留在一个可见的八行错误页。另一份复现重新打开 ADJ 后才发布 ERR。
- 另存的 test 复现 `local/runs/independent-manual-once-counterexample-r2/` 中，半按未被 H52 拦截，进入后续相机状态。之后模拟器遇到尚未声明的 HSP 报文而停止，没有继续 FULL/H40 或生成 JPEG。本报告不声称已经拍出坏照片。

这已经违反“失败不能留下半套颜色”的上卡门。判断依据是模型中失败后的单元 RPC 读回、取景状态和护栏值，不是模拟器最终是否生成照片。v3.10 H52 的实际指令另由 C 和 Python 指令后端复核：DIRTY/GUARD 为零时不会拦截半按或全按。resident 与 H52 的既有语义没有改变，缺口是这条手动路径没有置位保护。

根因分布在三个位置。

1. `candidate/containers/product/src/firmware/engine/core/eng_core.c` 的 `apply_impl` 收尾调用 `expire_previous`，丢弃非 baseline 事务的 live 验证。`recover_confirmed` 的恢复再次走 `capture_previous`，此时读到的是已经被部分改写的行；结构校验失败后设置 snapshot fault，恢复在完整写回 04 之前停止。
2. 手动事务没有接入 resident 的 DIRTY/GUARD 生命周期。引擎的 uncertain 和 resident 的 RPC 不确定标志都不能代替 H52 所检查的护栏。
3. `adapter.c` 的记忆预选 OK 路径可以在失败时走关闭菜单的 H07 收尾，因此不能依赖错误页阻止继续拍摄。

相关事务函数在 Engine 指针转换后与 g156 相同。本轮没有在 g156 整机上重跑同一输入，尚未证明这是 g157 新引入的缺陷。g157 增加了 Vivid/WB 下的有效读回与显式套用入口；这些入口仍必须满足“失败不能留下半套颜色”，不能用“沿用 g156 算法”代替验证。

修复必须满足：手动颜色写入前进入已有 resident 护栏；只有完整颜色及设置验证成功后才清除；任何无法补偿、对象变化或 DAT 退役都保留保护。纯 04 补偿不能要求已经部分改写的现场行先通过完整有效性校验。修复后用新 SHA 重跑本反例，并验证基础槽、Look、用户项和正常成功路径。当前两个 SHA 不因报告补写或 BOOT 关闭而获得放行。

参考复核已完成，见 `local/runs/independent-manual-standby-reference/`。`validate_p1.py --require-reference` 独立检查了四份完成回执，其中两份 native 使用真正单次注入策略；test 的 native 与参考失败后完整读回相同。旧驱动配置名虽为 persistent，实际也只发生一次故障，已按故障事件和 W 日志核实。release 本轮复现了 native 反例，没有再跑同一反例的 release 参考整机。

## P2

### P2-01：直接降级到 g156，高索引 Look 的记忆会阻止旧版继续保存

已在 g156 test 和 release 的最终指令上分别执行 own-tail 识别及实际 SETTINGS op5，C 与 Python 后端结果一致。g157 保存 MOUNT LowSat 或 Acros 后，g156 不承认该高索引尾部，op5 返回冲突并保持旧尾部。它不是安全清空记忆，也不是无条件可逆的版本切换。随后再换回同一 g157，还可能恢复之前的 Look，而不是降级期间最后手动选择的配方。

g157 读 g156 记录会按 DAT 绑定干净拒收，旧记录仍可被 g157 的新手动选择替换。反方向的安全操作是先在仍能工作的 g157 中保存纯 04，再降级；这个尾部能被 g156 识别和替换。仅在 g156 中改选 04，不能清理已经被它当作外来尾部的高索引记录。

证据为 `local/receipts/downgrade-{c,python}.json`，各八例。它们是最终指令函数探针，使用相同 resident ABI 的声明 UI 上下文，不是一次物理降级或 NAND 验收。

### P2-02：g157 没有放宽 BOOT 模式门，固定 M 不等于明天会自动恢复

g156 与 g157 的模式、原厂选择组合、MY、pending、设置对象、state 和 activity 门等价。g157 改的是读回和诊断，不是物理 M/P/A/S 准入。机主已确认始终使用 M，真实 H51 内部模式和 activity 仍未采到，不能把模型的模式 4 或 activity 6 冒充机身实测。

若仍因模式/原厂选择组合被拒，应显示 B11；若启动 activity 不合格，优先显示 B10；没有合格派发时为 B01。多个失败条件同时成立时，以优先原因显示 B 码，F 行保留其余失败位。初次换代的旧记录还可能引出 B21，原厂图像设定/WB 不符则为 B20。

机主必须先保留开机首拍，再拍首次 ADJ 的完整八行。仅有游标停在 03、Standard 标签或某个 BOOT 返回成功，都不能替代实际颜色。详细码表和一次一个动作的流程见 [机主步骤](OWNER_STEPS_MOUNT.md)。该文件当前明确暂停执行。
