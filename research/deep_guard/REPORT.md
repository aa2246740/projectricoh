NOT_CLOSEABLE_STATICALLY。第 9 个 hook 关不上这道证明：它只能看见机身 `0x2006B9E0`，镜头自己的调整行执行器不经过那里；现有只读 RPC 也不把四个计数交回 ADJ 回调。

本轮只读官方 `ilaunch3` / `jlaunch3` 和 deep 包里的 `ilaunch3`、`payload.bin`。没有编译、链接、改镜像或碰相机。扫描脚本是 `research/deep_guard/analyze.py`，机器可读结果在 `evidence/analysis.json`，指令摘录在 `evidence/EXCERPTS.txt`。

## 计数器本身

【静态确认】四个计数是 `jlaunch3` 已初始化段里的字，不是 BSS。file `0x1FB358` 起 20 字节全是 0，覆盖游标 `0x20246158` 和 `0x2024615C/6160/6164/6168`。装载后的初值是 0。

【静态确认】加一只有四个 leaf：`0x20242B28/B38/B48/B58`。全镜像 `seth+or3` 拼出这四个地址各只有一次，分别在 `0x20241FF8`、`0x20242008`、`0x20242068`、`0x20242078`（file `0x1F71F8/208/268/278`）。对这四个字的 `st` 只出现在这四个 leaf 和消费者 `0x202429C8` 的减一里。`0x20233AAC` 那组 `or3 #0x2b58` 前面是 `seth r0,#0x2023`，目标是 `0x20232B58`，不是计数器。

【静态确认】U 分派 `0x20241DA4` 把参数低 8 位当作索引，半字表在 `0x20245B9C`（file `0x1FAD9C`），基址 `0x20241E10`。表项：

| 索引 | 表半字 | 落点 |
|---|---|---|
| 0 | `0038` | `0x20241E48`，UEE00 提交 |
| 33 | `01E8` | `0x20241FF8`，`0x2024615C++` |
| 34 | `01F8` | `0x20242008`，`0x20246160++` |
| 49 | `0258` | `0x20242068`，`0x20246164++` |
| 50 | `0268` | `0x20242078`，`0x20246168++` |
| 83 | `03C4` | `0x202421D4`，UEE53 导入 |

所以会武装计数的是十进制子命令 33/34/49/50，也就是数值低字节 `0x21/0x22/0x31/0x32`。字面命令 `UEE53` 的低字节是 `0x53`，走到导入，不走到这四个 leaf。

【静态确认】`0x202429C8` 的地址只被拼出一次，调用点是 V 工作者里的 `0x20242CD0`。计数非零时它改 `*0x200B2CF0` 的 `+0x3F0C` 或 `+0x3F10` 再减一。计数为 0 时这四个分支都不写 T，但 V 仍然会进入这个函数。用 V 去“先读计数”本身就会在计数非零时改 T。

## 机身记账

【静态确认】官方 `ilaunch3` 里调用 `0x2009005C` 且当时 `r4=8` 的，只有 `0x2006B9E0`（file `0x20BE0`，`64 08 1e c0`）。同 API 还有另外 42 处 `seth+or3` 拼到 `0x2009005C`，跟踪到的 `r4` 是 3、9、10、15 以及其他 ID，没有第二处是 8，也没有 `r4` 跟踪失败的调用。deep 镜像在这个地址仍是这 4 字节。payload 里的第二处在 `rfw_rpc8_native`：`rfw_rpc8_call` 先拒绝字母 20 和 21..23 以外的值，所以 deep 自己发不出 U 33/34/49/50。

【静态确认】`0x2006B84C` 到 `0x2006B9F4` 没有把“本上电周期已经发送”写进任何绝对地址。它只使用栈，并在 `0x2006B9E0` 发出 RPC。函数入口被很多调用者拿着命令字符串指针调用，包括 `0x2036CC0C` 一带；这些调用者最后都汇进同一条 `jl`。因此观察点必须是这条 `jl`，不能是某一个菜单函数，也不能在 ADJ 打开时去读一个原厂标志。原厂没有这样的标志。

【静态确认】镜头侧不经过这条 `jl` 也能进同一个 U 跳表。`0x202428E8` 只在字母注册里被拼进 `r5` 一次；真正执行它的是调整命令分发。`0x2005AE30` 在 `jlaunch3` 里有两百来处调用。其中 `0x2007B9C0` 把栈上的一行文本交给它：先填缓冲，拒绝以 `#` 或 `;` 开头的行，类型字节是 5 就 `jl 0x2005AE30`。脚本行走 `0x202416BC` 也把记录指针交进去。这两条都不执行 `0x2006B9E0`。

【静态确认】整份 `jlaunch3` 里形如 `U` 加四位十六进制的字面命令只有 `U2000 U4208 UA300 UBE00 UE001 UEE00 UEE01 UF2E0 UF2E1 UF2E2 UF96B`。按 U 处理函数“低 8 位作索引”的规则，它们的低字节都不是 `0x21/0x22/0x31/0x32`。`ilaunch3` 里另有 `UEE71`、`UEE75`，同样不是。没有 `UEE21/UEE22/UEE31/UEE32`。

【未知】`0x2007B754` / `0x2007B880` 填进行缓冲的文本从哪来、普通拍摄会不会走到这个执行器。只要运行时行可以是 `UEE21` 这一类，计数就会在机身 hook 看不见的地方变成非零。这正是用户规定的“还有别的路径则机身记账不够”。固定字面量不够构成这条路径已经发生的证据，但执行器本身是镜像里的路径，不是猜测出来的 DMA。

【推断】DMA 或第二颗 CPU 直接把 RPC 8 包写入链路缓冲，在这两份镜像的调用图里没有对应的发送指令。不能据此宣称电气层不存在，只能说软件发送点已经收拢到 `0x2006B9E0` 和 payload。

所以机身记账即使加上第 9 个 hook，证明的也只是“本机身镜像自从标志被清零后没有执行过 `0x2006B9E0`”。它证明不了四个计数现在是 0。

启动清零也帮不上这个证明。【静态确认】`0x20055000` 在 `0x2005BE50` 返回 0 时，从 `0x2040AF84` 起写 `0x20BBD8` 个 0，范围盖住 `0x2040E084`。返回非零就整段跳过。【未知】什么情况下返回非零，以及镜头 SDRAM 会不会在机身这块 RAM 被清掉之后仍然留着旧计数。

## 只读 RPC

【静态确认】RPC 15 `0x200691D8`、RPC 17 `0x20069420`、RPC 19 `0x20069668` 都不调用 `0x202429C8`，也不写那四个计数。它们各自把地址存进 `0x2033B144`、`0x2033B148`、`0x2033B14C`，读出 byte / halfword / word，交给 `0x2005642C` 打印，然后 `ldi r0,#0` 返回。写兄弟 RPC 16/18/20 接着用这三个全局地址做 store。所以这三次“读”没有消费计数，但改了下一次写原语的目标地址，而且 scalar 返回值是 0，不是读到的数。

payload 的 ADJ 路径只比较 `rfw_rpc8_call` 的有符号返回值。RPC 15/17/19 把这个返回值固定成 0，回调里没有计数可读。shell `md`（`0x20069E98`，RPC 7）同样把输出交给打印，而不是放进这条 scalar 返回。现有回调接不住那次打印。

【静态确认】不存在一条不进入 `0x202429C8` 的 X/V 读。X 只设页基址。V 在设游标之后调用 `0x202429C8`。内部的 `0x20242980` 是一条单纯的 `lduh r0,@r4 -> jmp lr`，但没有注册成返回该 halfword 的 RPC。用 shell `ex` 去调用它不在本设计里：返回值进不了现在的 ADJ scalar 比较，而且 `ex` 能调用任意地址。

因此没有一条现成的、不改计数、又能让 payload 在 ADJ 回调里解析出 `0x2024615C..68` 的读。T 尾 `+0x3F0C/3F10` 同样没有这种读。

## 若仍要做只覆盖机身的缓解

下面这段不是失败关闭，不能拿来放行 deep V。它只让“机身执行过 `0x2006B9E0`”变成拒绝。构建时仍要先收回空间：payload 现在止于 `0x200546F8`，探针从 `0x20054700` 开始，中间只有 8 字节。下面的 trampoline 单独就要 32 字节，加上 ownership 里的判断，大约还要 40 字节，合计约 72 字节，至少再收回 64 字节，并且不能动现有 8 个 hook 和探针文件字节。

第 9 个 hook 打在发送指令上，不打在 `0x2006B84C` 入口。入口的 `addi sp,#-20 -> push r8` 后面紧跟着还要执行的 prologue；发送点才是唯一的 `r4=8`。

| 项 | 值 |
|---|---|
| VMA | `0x2006B9E0` |
| file | `0x20BE0`，segment 1 |
| 原字节 | `64 08 1e c0` |
| 下一条保留 | `0x2006B9E4` 的 `4f 0c 1a 80` |
| 新指令 | BRA24，`FF` 加 24 位字位移，目标 `rfw_adjust_send_hook` |
| 编码 | 与现有 `0x202871D8` 相同。项目模型里 `raw[0]==0xFF` 直接改 PC，不把下一条当延迟槽。该 hook 自己就放在 `bnez r4` 前面，真机路径靠的就是这一点 |

进入 trampoline 时 `r0` 已经是 `0x2009005C`，三个参数已在栈上，`r4` 还不是 8。trampoline 先写标志，再恢复和原指令相同的 `r4`、`lr`，用 `jmp r0` 让 `0x2009005C` 返回到 `0x2006B9E4`，这样 `mv r10,r0` 拿到的仍是 RPC 返回值：

```
21 7f f0 00    push r1 || nop
d1 c0 20 40    seth r1,#0x2040
81 e1 e0 84    or3 r1,r1,#0xe084
64 01 24 41    ldi r4,#1 -> st r4,@r1
21 ef 64 08    pop r1 -> ldi r4,#8
de c0 20 06    seth lr,#0x2006
8e ee b9 e4    or3 lr,lr,#0xb9e4
1f c0 f0 00    jmp r0 || nop
```

标志字是 `0x2040E084`。启动清零循环覆盖它，镜像里没有直接拼出这个地址的指令，也没有它的 BE32 指针。它是 sec0 BSS 的最后一个字，紧挨着 sec1 BSS。【未知】有没有人以别的基址加偏移写到它。hook 在 `jl` 之前写 1。写不进去时，这次原厂发送仍然要完成，否则会弄坏维修调整；payload 不能把“读到 0”当成没发送过。

检查放在现在的 `rfw_deep_ownership`（`0x200528B8`，目前只是 `bra 0x200534B4`）返回之后、`0x20053688` 的第一笔字母 23 之前。`r8` 在 `rfw_deep_transition` 里是 `RfwDeepState`。标志非 0 时走新的几条指令：`stb` 到 `state+1`，语义与 `0x200537A4` 相同，然后进入 `0x2005364C` 的 `ldi r0,#11`。`rv1_apply` 在 `0x20053E0C` 看到 acquire 非 0 就跳到 `0x20053E54`，不会执行 `0x20053E74` 的 S 写，也不会执行 `0x20053E30` 的 preview。preflight 失败而标志仍是 0 时，仍进 `0x2005364C`，但不把 `uncertain` 粘住，避免一次链路未就绪把整个会话锁死。

`rfw_rpc8_call` 在调用 `rfw_rpc8_native` 之前再读一次标志。这样第一笔 X 的等待期间如果另一任务跑了 `0x2006B9E0`，下一笔 V 不会发出。mutex 74 不能在外层握住再调用 RPC，那会自锁。中断恰好夹在“读到 0”和 `jl` 之间仍是【未知】。

主机测试沿 `tests/test_deep.inc` 的 `di_calls`、`di_writes`、`di_letters[21]`、`previews` 和 `state.uncertain`：

- 标志为 1，切到 deep key：`RV1_CONFLICT`，`uncertain==1`，`di_calls==0`，`di_letters[21]==0`，`previews` 不增加，settings 与调用前相同。
- 标志为 0，原有成功用例仍成立，第一笔 RPC 之前标志被改成 1：停在第一笔 V 之前，`di_letters[21]==0`，`uncertain==1`，没有 S、没有 preview。
- `di_ready=0` 且标志为 0：`RV1_CONFLICT`，`uncertain` 仍是 0，`di_calls==0`。
- 模拟 hook：调用 trampoline 后、进入 `0x2009005C` 之前标志已是 1；RPC 返回值仍传到 `r10`。

这些测试证明不了镜头文本执行器。主机 mock 里没有那条路径。

## 构建者下一步

1. 不要为了这道互锁去编译、链接或改 deep payload。静态材料关不上“四个计数现在是 0”。
2. 不要加第 9 个 hook 然后放行 V。hook 看不见 `0x2007B9C0` 和 `0x202416BC`。
3. 不要用 RPC 15/17/19、shell `md` 或一笔 V 当准入。前两者的 scalar 返回是 0，还改写地址全局；V 必经 `0x202429C8`。
4. 保留现在的 preflight 和“失败的 W 才粘住 uncertain”。在有一条不改计数、且把 16 位计数交回 `rfw_rpc8_call` 返回值的读之前，deep 候选不能把计数互锁说成失败关闭。
5. 若只做机身缓解，按上一节的地址和 32 字节 trampoline 做，并在包说明里写明它不覆盖镜头文本执行器；8 字节空隙不够，先从 payload 里收回至少 64 字节，探针 `[0x20054700,0x20054800)` 的文件字节保持 `FF`。
