# 段 0 执行探针：静态清点与实现

候选区仍可用于本次实验。在下述覆盖范围内，未发现它作为栈、缓冲区、表或 DMA 描述符的额外写入/读取证据。已有装载器会把整段初始化字节写到这里；运行时持久性和取指能力尚待真机验证。

日期：2026-10-13。范围均为半开区间。官方 `ilaunch3` SHA-256 为 `da1980e9d6f3996ede4953b8311cf0ce2abeb4bb300b6ee60a38f38e29a3cdf7`。脚本重新核对官方 `ilaunch3`、`ilaunch0` 和已有反汇编每一行的原始字节，未执行目标固件。

## 1. 8 个区外分支与 28 个 BE32 模式

逐项地址、文件偏移、原反汇编行号、原字节和分类在 [MATCHES.md](MATCHES.md)。完整记录为 [branch-matches.json](evidence/branch-matches.json)、[be32-matches.json](evidence/be32-matches.json)。

**静态已确认：8 个分支匹配是图标像素字节。**它们都把 `FF F8 2F EF` 解成 `bra`，来源相隔 `0x188=392` 字节。图标描述表从 `VA 0x2023C224`、文件 `0x1F1424` 开始。第 47–54 项的宽、高、编码分别是 `56,28,3`。初始化函数 `0x201D4FE4..0x201D5094` 按 type=3 将宽度向上对齐到 4，再计算 `宽×高/4`，每项 392 字节；其调用 `0x201D5868` 使用该表。读取函数 `0x201D5794..0x201D5830` 按索引乘 16 读取偏移，并加像素基址 `0x20245CCE`。逐项重放这段偏移算术后，8 个匹配分别落入这 8 项的像素范围。像素按显示路径读取，不会成为指向段 0 的分支目标。这里重放的是原厂静态算术，没有观测相机执行。

**静态已确认：28 个 BE32 匹配均是指令字节巧合。**4 项即使按 4 字节对齐，仍是 `20 05 45 01 = stb r0,@r5 -> addi r5,#1`，并非地址常量。其余跨半字或跨指令的匹配逐项列出真实指令。`0x23BE2` 的 `20 05 2C CC` 横跨 `seth r0,#0x2005` 的立即数与 `ld r12,@r12`；该 `seth` 在 `0x2006E9E8` 配对得到真实函数地址 `0x2005F454`。

图标与格式化代码本身有真实读取用途。这些用途不属于候选区；不能把图标分支匹配或指令拼接当成候选区引用。

**段 0 重装载：未知。**装载器接受索引 0；段 0 启动中实际请求的是 1 和 15。主程序的 `0x20068818` 与 `0x20089158` 将调用者传入的段索引交给 `0x20088358`；没有硬编码排除 0。尚未证明所有上层调用者的索引范围，也未发现可确认“普通回放重新装载段 0”的路径。若从同一修改过的存储镜像重装载，按已恢复装载算法会恢复同一探针和 FF；这仍是真机未验证的条件推断。

段 15 的任务切换在 `0x050022DC`、`0x0500C92C` 设置动态 `SPU`，从 `[0x200D2174 + 4×task - 4]` 保存/读取栈指针。未证明全部任务栈范围；不能用已确认的初始栈替代这项未知。

## 3. 基址加偏移、DMA 与扫描边界

[audit_candidate.py](audit_candidate.py) 对 `ilaunch3` 全部 16 段和 `ilaunch0` 的 1,140,226 个线性指令字运行常量传播，覆盖 `seth/or3/add3/ld24/neg/mv/add/sub` 与带常量基址的内存位移。常量最多跨 64 个指令字，遇分支清除，未知加载不继承文件初值；并行半字读取同一份旧寄存器值。解析到 71,414 个常量地址的读写；候选区地址构造 0 项、已解析读写 0 项。阳性对照能找到已排除区 `0x200D1838`、主装载器调用和邻接的两次 memset。

完整 BE32 任意字节对齐扫描给出的 28 项均已解释；未发现独立的指针表项或 DMA 描述符地址落入候选区。上述扫描也未找到常量基址加偏移后落入候选区的访问。覆盖结果是**未发现额外写入/读取证据**。动态 DMA 描述符、运行期大偏移、指针改写、物理别名、reset ROM、模块主动访问以及跨函数传播仍未覆盖。

REA 当前没有可用深度分析引擎（Ghidra/IDA 未配置，Hopper 可执行文件缺失），见 [rea-availability.json](evidence/rea-availability.json)。使用的是现有 GNU M32R 工具和本项目扫描器，未声称获得完整调用图或 DMA 所有权证明。

## 4. 探针与挂钩

最终 ELF 的入口 `probe_entry=0x200547B0`，文件 `0x99B0`，代码 68 字节、常量 12 字节，恰好结束于 `0x20054800`。它检查 `[0x2005276C,0x200547B0)` 的全部 8,260 字节，碰到首个非 `FF` 即选 `NG %d`，否则选 `OK %d`。探针自身的 80 字节按任务要求排除。

普通回放 `0x20319C7C`（文件 `0x2CEE7C`）和另一份回放 `0x20318464`（文件 `0x2CD664`）的完整指令字均为 `1E C0 F0 00 = jl r0 || nop`。只把这 4 字节改为 `bl.l probe_entry`。前面的 ISO 入栈、格式串入栈和 `r4=0x20234BD0` 参数准备都原样保留；返回仍分别在 `0x20319C80`、`0x20318468`，原厂继续弹出两个栈参数。

原厂普通参数约定是 `r4..r7`，但此格式化函数是可变参数函数：入口 `0x200BBC7C` 保存栈 60 字节，`0x200BBCA4` 从 `sp+60` 取格式，`0x200BBC8C/94` 将 `sp+64` 作为可变参数指针。两份回放调用也直接证明格式与 ISO 在调用时的 `sp+0/+4`。探针使用 `r0..r3`，不改变 `r4..r13`、`lr`、`sp`；只写调用栈 `sp+0` 的格式指针，然后 `jmp 0x200BBC7C`。原格式化函数的缓冲区写入、NUL 结尾和返回值继续执行。没有 GCC ABI 边界，没有新栈帧、堆分配、设置或文件写入。

BL24 的两条距离分别为 `-0x2C54CC` 和 `-0x2C3CB4`，均在有符号 24 位字位移范围内。构建器独立编码/解码并调用 objdump 核对；探针内的 BNE16、BC8、BRA8 也按目标符号核对。最终字节、工具哈希和每个挂钩前后的原参数窗口均写进包 manifest。

`OK` 只能证明探针本次执行并在扫描时看到检查区为 FF。探针自身被覆盖可能导致死机，短暂写入后恢复 FF 可能不被发现；未进入回放的时段也没有连续监测。多种模式后反复看到 `OK` 是本阶段的真机检查目标，不能据此保证所有运行路径永不写入。

## 5. 复跑与完成边界

```sh
python3 -I research/stage1a_probe/audit_candidate.py
python3 -I firmware/stage1a_probe/build_probe.py
python3 -I scripts/verify_build_code_patch.py
python3 -I scripts/build_code_patch.py firmware/stage1a_probe/spec.json
```

有输出路径时，构建器只允许在 `artifacts/stage1a-probe/packages/` 下创建新目录，不覆盖旧包。官方 29 文件哈希、只改 `ilaunch3`、等长、无重叠、原字节和原哈希匹配、CSV 与官方头逐字段一致、相位 0 校验及恢复/落盘复核均保留。ELF 还须无未定义符号、重定位、可写节、孤立节或运行时初始化器，payload 和独立 objcopy 导出相同。

包和测试结果见 [FLASH_AND_CHECK.md](FLASH_AND_CHECK.md) 与 [builder-verification.json](evidence/builder-verification.json)。当前没有连接相机，未写 SD 卡或 `/Volumes`，所有相机验收均为待测。最大风险是探针或挂钩错误导致主程序不能启动或正常升级入口失效；这种状态的救援仍未在本机证明。
