# 镜头通信模型的输入

所有新增业务数据都由模型声明。静态代码确定消息形状、字段宽度和正常分支。光学字段的数值使用零输入，单元侧产生这些数值的流程仍未知。

## 请求和回复

HSP type 12 的前八字节为 `u16 length, u8 type, u8 sequence, u32 queue`，后面紧跟原厂消息。机身收到 type 12 后，由 `0x200941F0–0x20094208` 将 `queue`、消息地址和 `length-8` 交给原厂发送函数 `0x2005E034`。新模型只填 HSP 接收寄存器，由现有 IRQ 87 路径处理。

| 标识 | 方向 | 数据字段 | 依据 |
| --- | --- | --- | --- |
| `0x2F02` | 机身→单元 | 144 B，前八字节 `0090 8000 8400 2F02`。后面保留机身生成的参数。HSP 总长 152 B，queue=15。 | 机身 `0x2017098C`、Task 28 的 `0x20173A10`，实际完整帧保存在各收据的 `unit_events`。 |
| `0x2002` | 单元→机身 | 48 B，前八字节 `0030 8400 8000 2002`。`+12:u32=0` 选择正常结果。HSP 总长 56 B，queue=1，分成两片 32 B 槽。 | 50mm `0x201A67BC`，28mm `0x201A9BC0`，MOUNT `0x201A5FE8`。50mm 发送封装为 `0x2007C894`。 |
| type 13 slot 47 → type 14 | 机身查询→单元返回 | 请求长 12 B，无参数。回复长 12 B，`+4:u32=0`，`+3` 和 `+8..11` 复制请求的序号与 slot 标识。 | 50mm `0x201A84A0→0x200CD984`，28mm `0x201AB8A4→0x200CDF08`，MOUNT `0x201A7CCC→0x200CFB6C`。三个目标函数都直接返回 0。 |
| type 15 slot 38 | 机身→单元 | 本轮只新增参数 `(0)`，无回复。 | 各单元的注册点分别为 `0x201A8340`、`0x201AB744`、`0x201A7B6C`。50mm `0x201C4D10→0x201CDE40` 只改单元局部标志。模型记录请求，不执行单元动作。 |
| type 15 slot 28 | 机身→单元 | 新增 `(1,0,1,0)` 供待机入口使用，新增 `(3,0,0,0)` 供 ADJ 观察使用，无回复。原 `(2,1,0,0)` 沿用 batch。 | 50mm 注册 `0x2021B7D0→0x2021B8C8`。形状由机身实际发送帧约束。模型记录请求，不声明单元采集或显示已开始。 |
| type 15 slot 83 | 机身→单元 | 新增 `(0)`，无回复，供 ADJ 观察使用。原 `(1)` 沿用 batch。 | 50mm `0x2018C094→0x2018C0C0`。形状由机身实际发送帧约束。 |

`0x2002` 的其余字段均明确为零。

| 偏移 | 宽度 | 原厂来源和机身消费点 | 模型值 |
| --- | --- | --- | --- |
| `+8` | 4 B | 该构造函数未赋值，机身 UI 映射不读此字段。 | 0。 |
| `+16`、`+18` | 各 2 B | 单元 getter，机身写入 `0x2037F332`、`0x2037F330`。 | 0、0。 |
| `+20` | 2 B | 单元有符号 getter，机身 `0x20265CA4` 写入 `0x2037F2FC`。 | 0。 |
| `+22..26` | 各 1 B | 单元 getter 和状态结构；机身 `0x202E3B3C` 消费。 | 全部为 0。 |
| `+27` | 1 B | 对齐字节。 | 0。 |
| `+28`、`+32`、`+36`、`+40` | 各 4 B | 单元从四个半字扩展为字，机身按模式保存这些值。 | 全部为 0。 |
| `+44`、`+46` | 各 2 B | 单元参数结构；机身 `0x20266EB8`、`0x20266EE0` 保存。 | 0、0。 |

这些数值不代表实测的光圈、焦距、位置、区域或校准结果；未确认含义的字段不作物理命名。`+12=1` 的另一构造分支以及 `0x1F03→0x1003` 照片链未建模。

## 沿用的传输和启动输入

以下形状在 batch 中已经存在，本轮保留。完整字节及顺序见每次冷启动收据的 `hsp_packets`、`hsp_replies` 和 `board_events`。

| 标识 | 方向 | 数据和模型输入 | 依据 |
| --- | --- | --- | --- |
| type 6→7 | 双向握手 | 回复固件名和 MAIN 头部 `0x12..15` 的版本字节。 | `peripherals.py` 的 hello 分支，机身 `0x2009394C`、`0x200951C8`。新增型号使用各自固件名。 |
| type 8→9，10→11 | 双向短交换 | 保留序号，分别返回 ACK 和结束通知。 | 机身 `0x20094328`、`0x2009433C`，沿用 batch 八步时延。 |
| slot 13，type 18/19/20/37 | 单元信息传输 | 2048 B。前四字节为 `NL1`、`NL5` 或 `NL8`，`+4..11` 为固件名，`+0x30..33` 为版本，末四字节为前 2044 B 的加和。其余字节为 0。 | 机身校验器 `0x200637E0`，原 `fixtures.py` 的 NL1 夹具。NL5、NL8 只替换身份字节。 |
| slot 14，type 18→19 | 机身数据传输 | 允许已声明的 2048 B、4608 B DMA。传输完成后继续短交换。 | `peripherals.py` 中的 DMA 与传输记录。 |
| slot 13，operation=2 | 单元→机身启动通知 | 三个掩码 `0x00800000`、`0x02000000`、`0x04000000`，沿用已有 `Board` 模型。默认延至状态 2 才交付。 | `board.py` 原 `ready_condition`、`advance`，既有冷启动检查使用相同输入。 |
| slot 13 的其他已声明请求 | 机身查询→单元返回 | 维持原 `-1` 返回。 | 原 `peripherals.py` 错误路径夹具，未改为统一成功。 |
| slot 8 | 双向参数读写 | 沿用 X、V、W 逻辑；只读值来自选定 MAIN 的文件区，T 初值仍为 2。 | `unit_peer.py` 提取冻结 `RpcEdge`；本轮没有运行 host harness。 |
| slot 42 | 机身查询→单元返回 | 布尔参数，原返回 0。 | M2d 已有注册点和函数证据，沿用 batch。 |
| slot 30 | 机身查询→单元返回 | 原未初始化返回 `-1`。 | M2d 的 `0x204A37CC=0` 分支，沿用 batch。 |
| slot 24、28、41、82、83 及 type 24 | 机身→单元通知 | 保留 batch 已声明形状，只记录，无业务回复。 | 原 `peripherals.py`，未扩展这些单元动作。 |

## 状态 5 的机身条件

`0x202AFA8C` 将 `0x2002` 映射为事件 131，并在 `0x202AFAFC–0x202AFB04` 将 `0x205D9DF8` 置 1。`+12=1` 会改为事件 132。本模型只提供正常分支 0。

状态 2 的共用表 `0x20378E00` 将事件 131 交给 `0x202E3B3C`，随后调用 `0x202E4004`。机身查询 slot 47 的布尔结果；本模型的三个已核对函数均返回 0。机身继续到状态 32。

状态 32 的事件 1 运行 `0x2029E210→0x2029E490`。`0x2029E728–0x2029E764` 检查 `0x2037F3B1`。值 1 或 2 可选择状态 63。本轮读值为 0，机身走到直接选择状态 5 的分支。状态写入函数为 `0x202B0A74`，最终写入指令为 `0x202B0AD8`。所有记录中的状态变化均来自此指令。

因此当前声明输入得到 `0→2→32→5`，不等同于实机测得的 `0→2→32→63→32→5`。带状态 63 的路径仍待另行解释和验证。
