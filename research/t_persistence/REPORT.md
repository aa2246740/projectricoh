# T 参数块：机身经 X12C0/V/W 只改 RAM 能不能被存下来

2026-10-20。只读静态分析，由 Opus worker 完成，它没有写 `.md` 的权限，本文由主代理删减落盘。没有连相机，没有动 SD 卡，没有改仓库。worker 的草稿在 `/tmp/tpersist/`。

主代理独立核对了以下几点：
- 官方 `jlaunch8` 头部类型是 `05 03`（ADJCOM），`jlaunch3` 是 `02 01`（MAIN）。
- `jlaunch8` 脚本共 10101 行。开头是 `X12C0, X12C0, UEEF1, V0002, W0151`，最后一行是 `UEE00`。
- 脚本第 6990 行在游标 `V2444` 之后写 `W0002`，所以它会把 T+0x2445 写回 2。

## 结论

1. **只改 RAM 能做到（已验证）。**
   - `X12C0` 指向真实的 T 指针，`0x20243100` 处有特判。
   - `V` 设定游标，并返回该处当前的 u16（`0x20242CE4 → 0x20242B68`，用 `lduh`）。
   - `W` 用 `sth` 写入后再读回。
   - 这条路径本身不调用任何提交函数，和 `deep_isp.c` 已经在用的机制相同。
2. **「绝不会被存下来」证明不了**（推断，与既有审计一致：`zero_persistence_proven=false`）。
   - 提交函数 `0x20065DB0` 只有两个固定调用者：UEE00（`0x20241E50`）和 UEE53 文件导入（`0x2006683C`）。普通拍摄、菜单、模式、关机、睡眠、回放、格式化、像素映射和复位路径里都没有。
   - 模块里的工厂缺陷和转换校准流程会自己发 UEE00：`0x2022EDF0` 的成功分支在 `0x2022F140`，`0x2022FE30` 在 `0x20230180`。它们属于 adjust 命令子系统，普通使用到不了，但动态派发没有完全排查完。
   - 机身自己发 UEE00 只在 SD 卡更新的 ADJCOM 路径上（`0x2008E98C`、`0x2008EB24`）。UEE71、UEE75 是版本查询，不是提交。
3. **只重刷 MAIN（`jlaunch3`）不会动 T（已验证）。**
   - T 存在存储描述符 4 里，不在程序镜像里；MAIN 的更新流程也不执行脚本。
   - 只有执行到 ADJCOM（`jlaunch8`）时，T 才会被整块重写并提交，T+0x2445 被拉回 2。
   - 更新器按文件后缀 0..9 扫描清单，再按头部类型处理（`research/unit_recovery/REPORT.md`）。版本相同时会不会跳过 `jlaunch8`，未知。
4. **所以真正的风险在恢复这一侧。**
   - 万一 T+0x2445 = 0 被存了下来，每次开机都会重新载入 0，原厂 04 就会坏。
   - 只刷 MAIN 救不回来。能不能靠官方完整更新重跑 ADJCOM 救回来，未知。
   - 故意发一次 UEE00 能修复，但它会把 RAM 里整块 T 当前的状态一起存下去，包括运行中会变的字段，比如 T+0x233F、T+0x3EE、T+0x3F0C/3F10。

## 读、写、校验的 RPC 序列（已验证，可以直接套进 `deep_isp.c`）

- **进入**（先写 C/D，最后写控制）：`X12C0`；`V2444` 必须返回 `0x0002`；`W0000`；`V2444` 必须返回 `0x0000`。
- **恢复**（先恢复控制，再把 C/D 清零）：`X12C0`；`V2444` 必须返回 `0x0000`；`W0002`；`V2444` 必须返回 `0x0002`。
- 高字节 T+0x2444 一直保持 `0x00`。INP 打包函数 `0x20118F5C` 会读这个字节。
- V 还会调用记账函数 `0x202429C8`：只要计数 `0x2024615C..68` 有一个不为 0，就把读到的值写进 T+0x3F0C/3F10。冷启动时这些计数都是 0，所以没有副作用。

## 安全设计，按优先顺序

1. **首选：矩阵线性近似，完全不写 T。** 分色的线性部分能做到，灰阶 ΔE00 从 3.50 降到 1.65。
2. **一定要逐通道曲线的话：**
   - 每次开机后第一次打开菜单时，读 T+0x2444。如果没有任何 T 配方生效，读到的值却不是 `0x0002`，就只在 RAM 里写回 `0x0002`，并在界面上给出明显的告警。
   - 进入配方时先写 C/D，最后写控制；离开时先恢复控制，再清 C/D。
   - 绝不发 UEE00、UEE53、UEEF1。
   - 上机前必须向用户讲清恢复边界，并取得明确同意。
3. **金丝雀测试做不到证明。** 没有办法证明 T 里的哪个字节无人读取，所以不指定任何偏移。可以用目标字节 T+0x2445 本身做持久化测试：写 0，禁用自愈，冷启动后再读。但这项测试本身就承担同样的风险。
