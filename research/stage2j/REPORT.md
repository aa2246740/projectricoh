## 修正内容

| 项 | 状态 | 要点 |
|---|---|---|
| F1 | 已修 | 颗粒门控增加两个条件：<br>• `S+0x36E == rfw_defaults[entry[0]-1].base_mode`。机身在 `0x20268880` 读这个字节，03 的 base_mode 是 3；<br>• S 至少 `0xC9E` B。<br>在普通菜单改了图像设置，颗粒就关闭。 |
| F2 | 已修 | 门开时写四个字节：<br>• `B+0x1A = 21`；<br>• `B+0x10 = 0`（单色标志，parser `0x20197F98`）；<br>• `B+0x32 = 1`（画面风格，parser `0x20198180`）；<br>• `B+0x6F = S+0xC9D`（1..3，否则为 1；parser `0x20198140`，曲线选择在 `0x20195A14`）。<br>WB（`B+0x0F`）不动。 |
| F3 | 已修 | 读到有效值才置 `t_checked`，失败可以在之后的 refresh 重试。<br>从非 T 配方进入 control-0 配方时，必须先读到 T = 2，才写任何行；读失败或不是 2 就拒绝切换，零写入，不置 uncertain。<br>完成了 `control_of` → `t_bit` 的重构。 |
| F4 | 已修 | 生成器在 `--fit` 和正式集合里拒绝「有 bit 2、没有 bit 1」的条目，只有标明的 t-test 探针例外。<br>README 和上机清单加了一句：after testing a T profile, select 04 before switching modes. |
| F5 | 已修 | 先写 active，经编译器屏障再清 uncertain：`0x2005438C` → `0x20054390`。 |
| F6 | 未修 | 要多用 52 B 早段空间，但早段只剩 8 B。`!` 仍固定标在第 4 槽。 |
| F7 | 未修 | RfwCache 中途丢失时，自检可能把有意设成 0 的 T 当成异常，写回 2 并显示 `!4`，旧行仍留在原处。遇到意外的 `!4`，应断电重启。 |

**B+0x32 的决定：只改 +0x32，+0x33..0x36 保留 03 的值。**

- **不会进覆盖分支。**
  - `0x2019A260` 的覆盖分支要求类别 4，并且 unit+0x0D ∈ {7, 8}。
  - unit+0x0D 由 parser `0x2019804C` 从 B+0x1E 取来，而门控要求 B+0x1E = 0，所以进不了这个分支。
- **风格值本身。** 原生场景 21 在 `0x20167B30`、`0x20374920` 给出 style 1。模块在 `0x20199D58` 把 style 1 映射为 ISP mode 0。
- **其余四个字节。**
  - +0x33 只在 style 6 分支用到。
  - +0x34..0x36 经 `0x20199760` 映射成有界的数值，非法值回落到 5。
- 这只是静态可接受，不证明观感和原生场景 21 一样。

## 独立审查（Opus，只读，跨模型）

审查者在只读条件下工作。它定点反汇编了 `jlaunch3`、`ilaunch3` 和 2j 的 payload。它把 2j 源码复制到 /tmp，加上自己写的 S1–S5 场景编成宿主程序，原有 256 项仍然全部通过。

**三种用法的结论**

| 用法 | 结论 | 说明 |
|---|---|---|
| (a) 刷 2j，表文件不带新位（含不放表） | **可以** | 与 2i 等价，没有卡死或行为改变的路径。<br>唯一差别：开机后第一次 T 读取失败的话，之后每次在 04 下开菜单会再读一次，直到读到有效值。 |
| (b) grain-test | 静态上可以 | F1、F2 实现正确。<br>剩余风险：运行期未验证，另见下面的发现 2 和 5。 |

**发现**

1. **【中，2i 起就有】T 步骤失败，界面却显示成功。**
   - 原因：`platform.c:129-130` 对 `RV1_CONFLICT` 且 `uncertain==0` 的情况，照样发布 S 并返回 OK。主代理已对照源码确认。这是有意的设计：任何 W 之前就失败的切换，跳过 ISP 行，但仍套用配方的普通设置。
   - 审查者复现了三个场景：
     - S5：07 生效时选 04，恢复步骤的回包丢了一次。菜单显示 04，T=0 却仍然生效。
     - S2：进入 07 时被前置检查拒绝，界面同样显示成功。
     - S3：T 被外部改回 2 后，07 退不出来，直到断电。
   - 唯一能看出来的地方：重开菜单时，光标停在实际生效的槽。
   - 修法：
     - 流程上（0 B）：每次选配方后关掉菜单再打开，确认光标在刚选的槽。不对就重选，再不对就断电。这条对普通配方同样有用，因为非 T 切换在任何 W 之前失败时也是同样的表现。
     - 代码上：T 步骤失败时返回一个不会被吞掉的状态码，约 +8 B，放晚段。
2. **【低】颗粒误开。**
   - 场景：03 生效后，选一个 base_mode 同为 3 的卡上配方，而切换在任何 W 之前失败。这时颗粒会继续出。
   - 此时 03 的深层行本来就还在生效，所以颗粒与实际 ISP 状态一致，只是与用户的选择不一致。
   - 修法要占早段 12–16 B，而早段只剩 8 B，所以只写进文档。
3. **【低，2i 起就有】T 读取的「有效」判据偏宽。**
   - `deep_isp.c:215` 接受任意 u16，但回调的负数可能在 `0x2005AD6C` 被截成 u16，见 `research/body_rpc8_probe/REPORT.md` §3.1。主代理已核对两处。
   - 后果：一次失败的读取可能被当成异常值。界面会误报 `!4`，并在 RAM 写回 0x0002，这正是原厂值。也可能导致本次开机 sticky。两种都是失败关闭方向。
   - 修法：把 ≥0x8000 当作无效，约 +4–8 B，放晚段。
4. **【提示】`t_bit` 没加 `RFW_LATE`。** 它被编进了早段（`0x2005366C`，20 B）。不是缺陷。
5. **【提示】F2 的证据是静态的，而且只追了 2F02 一条 parser。**
   - P/A/S/M 下，`0x2019A260` 覆盖分支的「类别 4」条件是满足的，所以安全完全依赖 unit+0x0D ∉ {7, 8}。
   - 别的命令的 parser 也写同类字段，没有追：`0x20199288`、`0x20198514`、`0x20198A40`。
