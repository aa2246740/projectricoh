## 时间分布与 C 化估算

独立剖析执行 200,000 步，不计入上面的吞吐中位数。剖析后的状态哈希与相同步数的基准一致。

| 计时分类 | fast | debug |
| --- | ---: | ---: |
| 普通映射内存的 Python 回调体 | 11.49% | 10.89% |
| MMIO 回调体 | 0.12% | 0.15% |
| Python 循环及设备推进 | 52.29% | 55.42% |
| 原生 API 包络，含 GNU 核、缓存清理和调用边界 | 36.10% | 33.54% |

计时运行 fast 为 5.207 秒、debug 为 5.614 秒，比无剖析运行多约 20%–23%；上述比例只适用于该计时运行。纯 ctypes 边界不能从 GNU 执行包络单独准确拆出。独立空函数校准得到一次标量调用约 0.23–0.32 微秒，额外一次 C→Python 回调约 0.26 微秒；这是校准值，不是机身指令速度。

按实际 API/回调次数加权，标量调用边界下限约占未剖析耗时的 4.4%，RAM 回调边界约 1.5%。合并 RAM 回调体后，RAM C 化可移走的时间估计约 16%，完全消除该项的理想收益约 1.19 倍；实际暂估 1.1–1.2 倍。

另一段 cProfile 把必须保留的逐步设备/面板推进定位为约 35%，剩余可迁移的 Python 控制部分约 17%。若 RAM 项省去 80%、该控制部分省去 50%–100%，并省去标量调用边界，RAM 与循环一起迁入 C 的估算约为 1.3–1.6 倍。设备时钟、中断边界、RTE 栈组和缓存一致性都需保留。该估算没有 C 化实现或 C 化后的等价证据。

详细计时、调用次数、额外 cProfile 和校准数据见 `local/no-card-profile-*.json`、`local/no-card-*.pstats`、[空调用校准](local/ffi-calibration.json)及[计算公式](local/summary.json)。
