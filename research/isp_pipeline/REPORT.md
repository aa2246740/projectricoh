# GXR A12 50mm 1.51：ISP 管线、颜色能力与尚未确定的上限

2026-10-16。对象为 GR LENS A12 50mm camera unit，M32R，大端。

## 1. 可用于决策的结论

**静态确认**：这颗 ISP 的可编程入口多于现有 13 个 Image Settings 控件。除 type 26 的主曲线与 type 28 的 24 个颜色系数，还找到 type 23 的三组独立输出 LUT、type 26 的两张全零辅助表、type 28 的九系数矩阵、type 14 的四组空间增益表，以及额外的 LUT/滤波寄存器。把“五色色相、五色鲜艳度、对比度”当成硬件上限，会漏掉这些入口。

**推断**：最有价值的新增颜色能力是三通道曲线和通用矩阵。它们支持研究明暗分色、暖高光、冷暗部及更细的颜色校正。这里的“支持研究”不代表已确定通道顺序、启用位、数值裁切或相机效果。

**未知**：目前仍不能给出经过芯片规范或真机确认的完整硬件上限。尤其没有闭合 type 23/26 的通道语义、type 28 分区坐标及尾部增益表的自变量，也没有独立定位 demosaic、黑电平和传感器 RGB→工作 RGB 校准矩阵。没有足够证据把任意一个品牌 look 判为整颗 ISP 上绝对不可能。

**静态确认**：39 个 type 的写入入口、描述表、寄存器写入形状已逐项列出。它们不是 39 个依次串联的像素阶段，包含空描述项、控制块、表 RAM 和辅助处理器。软件写寄存器的顺序，也不等于像素经过硬件的顺序。

**未知**：Ricoh Positive/Negative、Leica、Fujifilm、Pentax、Olympus、Lumix 的精确外观匹配均未验证。本报告给的是可表达的变换类别与证据边界，不提供品牌配方，不生成固件。

## 3. 39 个 type：修正枚举与阶段清单

### 3.1 描述表的真实结构

**静态确认**：`0x20255618 / file 0x20A818` 比较 `type < 39`；有效编号确为 0..38。`0x202556B0..CC` 分别读取函数表 `0x2029C194[type]` 和描述指针表 `0x2029DA8C[type]`，再调用 writer。见 [hardware-dispatch.txt](evidence/hardware-dispatch.txt)。

**静态确认**：描述表不是统一的 `(address,0)` 对。通用 writer `0x20256988` 每次把描述指针和数据指针各推进 4 字节，遇地址 0 停止。专用 writer 先写一个零结尾地址列表，再把后续描述字当连续寄存器窗口的基址。见 [generic-writer.txt](evidence/generic-writer.txt)。

**静态确认**：例如 type 0 只写 `F0300004, F030000C, F0300020, F0300024, F0300028`，不会因表相邻就顺带写 type 1 的 `F0314xxx`。type 26 只覆盖 `F0349000..F03490AC`，不会延伸到 type 27。types `2,3,4,19,20,22,31` 的描述首字就是 0；该通用配置入口对它们不写任何 payload 寄存器，不能称为七个“尚未解析的阶段”。外围的公共状态操作仍存在。

**静态确认**：下表的寄存器地址、u32 数量和 wrapper 地址来自原始描述与 writer 循环。数量只计算 payload，未计临时门控/状态操作。完整非连续布局、每个 payload word 对应的寄存器、writer 地址及循环证据在 [register_layouts.json](register_layouts.json)、[register_payloads.csv](register_payloads.csv)。JSON另列type8/13/14/16/17/29/38的额外门控写，包括字宽和值序列。

## 4. 从 RAW 到 JPEG：能恢复的顺序

### 4.1 配置顺序与像素顺序分开

**静态确认**：`0x2010C248` 按请求位依次可调用 `18 → 21 → 23 → 24 → 25 → 26 → 27 → 28 → 32 → 14` 的配置入口。其中 type 14 放在配置序列末尾，正说明不能把软件写入顺序当成像素处理顺序。见 [apply-order.txt](evidence/apply-order.txt) 和 [pointer-init.txt](evidence/pointer-init.txt)。

**推断**：用于后续研究的逻辑流程如下，问号表示尚未闭合的硬件顺序，而非缺少这种常见处理就可默认补上。

```text
sensor / RAW buffer
  → 黑电平、缺陷校正、RAW NR ?       [type 1/6/7/8/9/10/11/12/13 等待绑定]
  → 四面空间 gain / shading         [type 14；相对其他 RAW 块的次序未知]
  → demosaic、camera RGB CCM ?      [没有独立确认的 type]
  → 多表块、三通道 LUT、gain ?       [type 21/23/24/25；真实顺序待证]
  → 对比度/编码曲线与滤波 ?           [type 26/27]
  → 可选择的 3×3 + CMAT 颜色处理     [type 28；内部 matrix/sector 次序未知]
  → edge / 其他滤波 / resize ?       [type 32 与其余未命名块]
  → still YCC RAM buffer
      → 场景后处理、noise / GCAL、额外曲线或缩放
  → JPEG encode / 保存
```

**未知**：这不是已证明的单一物理连线图。firmware 允许多次处理、旁路、RAW 专用处理和辅助引擎调用。JPEG encode 的专用寄存器和缓存协议未恢复，不能把 type 38 的三个 bank 因为邻近 JPEG 地址区就叫 JPEG encoder。

**静态确认**：三张DNG的BlackLevel=0、WhiteLevel=4095。**未知**：这不能证明前端没有黑电平校正；DNG可能已经扣除偏置，具体执行位置没有闭合。

### 4.2 空间增益的出口与精度已补齐

**静态确认**：`0x201080B8` 通过 `0x2010BBC0(15)` 取得 `0x2013E6D0+44` 起的 type 14 镜像。它遍历27行、32列，从三个 u16 输入面读取增益，乘 u8 mask、除100，再把第二个输入面写到两张输出面。输出面相对镜像的偏移为 `44,1988,3932,5876`，面间距1944字节，行间距72字节。每面可容纳972个u16，即36×27；实际遍历和边界补点不能简写成四张32×27紧密表。见 [lens-shading-packer.txt](evidence/lens-shading-packer.txt)。

**静态确认**：`0x201084B0 / file 0xBD6B0` 把百分数增益 p 转成 `floor(p*1024/100) & 0x1FFF`，再存入 u16 槽。代码提供10个小数位、13个有效打包位，unity=1024；它使用掩码截断，不是饱和钳位。高值不能不经验证就扩大。见 [shading-value-format.txt](evidence/shading-value-format.txt)。

**推断**：四面对应 R/B/G/G，其中中间输入复制到两个绿色位置。这可用于镜头阴影、WB 空间修正和暗角，不是由像素亮度或语义区域驱动的“局部颜色 LUT”。

## 6. 曲线：明确区分寄存器容量、软件限制和通道语义

### 6.1 type 26 不止第一组33字节

**静态确认**：`0x20118468` 生成176字节镜像，布局如下。此前的 A/B 两组表提取与本轮原始字节完全一致；所有节点见 [decoded_tables.json](decoded_tables.json)。

| 镜像偏移 / 对应寄存器 | 数据 |
| --- | --- |
| `+00 / F0349000` | 静态确认控制word。 |
| `+04..40 / F0349004..9040` | 静态确认31个u16数据；首项放低16位，随后15word各装两项。 |
| `+44..64 / F0349044..9064` | 静态确认33×u8主输出表；末word只有最高byte使用。 |
| `+68..88 / F0349068..9088` | 静态确认33×u8辅助表C。 |
| `+8C..AC / F034908C..90AC` | 静态确认33×u8辅助表D。 |

**静态确认**：主输入 `0x2012F40C` 有22×31个u16；主输出 `0x2012FF78` 有22×33个u8。C/D分别在 `0x2013024E/0x2013026F`，各33个u8，原始66个byte全部为0，不能称为直通曲线。普通配置把C/D表号都设1。选择字来自T+`0x2410..2420`，本轮解码脚本默认值再次确认九档选择1..9行。

**推断**：31个内部输入节点、两个隐含端点、33个输出值，是很强的分段曲线解释。输入表都在0..4095，输出是明确8-bit容器。硬件是否线性插值、端点位置和rounding仍未知。不能把22行ROM数量说成硬件只容许22条曲线，直接生成镜像可避开表号限制。

**未知**：目前没有证明type 26只作用Y，也没有证明三个bank就是R/G/B。尤其两张辅助表全零，不能把它们直接解释成完整G/B输出曲线。共享主曲线加差分/偏移、Y及色度修正、模式相关复用都未排除；辅助byte的有符号解释也未知。

**推断**：若C/D按主输入寻址并作为两路色度偏移，它们会成为直接的split-toning入口；若是通道差分或其他模式数据，表达能力又不同。这是值得优先确认的假设，现有零值本身不能证明其中任何一种。

### 6.2 type 23 有真正独立的数据 bank

**静态确认**：type 23 的68word镜像是 `1控制 + 16输入word + 3×17输出word`，总272字节。输入31×u16，输出每组33×u16。三个输出区分别是 `F0342044..2084`、`F0342088..20C8`、`F03420CC..210C`；每组第33项占末word高16位。见 [type23-packers-full.txt](evidence/type23-packers-full.txt)。

**静态确认**：零起算的六行输入在 `0x20130290`，步长62；三个输出bank在 `0x20130404/0x20130590/0x2013071C`，步长66。第3/4/5行不是复制同一条数据。举第5行的第32节点，三组分别为3900、3900、2277；第3行第三组首节点还为24。完整逐节点CSV见 [channel_curves.csv](channel_curves.csv)。

**静态确认**：packer有共享表与独立表分支。`0x20119D24..D6C` 会在控制条件满足时复制首bank到另两bank，否则分别装载；额外运行时入口 `0x201195A4` 也能分别构造三组，并在部分生成路径将结果裁到4095。`0x2011AC50` 在 `0x201A8F4C/0x201A9EA4` 等又被调用，因此只看最初Q packer不足以确定最后一次写入值。

**静态确认**：处理效果23的分支在 `0x2010E9A8` 读取 Q+`0xC5`，经 `0x2010EC98` 将值1/2/3映射到表行3/4/5，写入上述配置。场景28→处理效果23也已按跳表重验。场景产品名与数值仍沿用已有研究的证据边界，不以本轮未读取的机身资源重作命名证明。

**推断**：这组三通道12-bit非线性表是RGB颜色曲线的强候选。若通道确为RGB，就能分别弯曲中性轴的三个分量，让暗部与高光有不同色偏；这比全局WB或一组色相系数更接近split toning。

**未知**：本轮未把三个bank分别闭合到R/G/B输入，也未确定所有控制位、上电默认值和运行时覆盖。不能标成“已确认可用的RGB split-toning控件”。u16传输槽也不证明有效输出有16-bit，现有表与生成器支持12-bit工作范围，硅片保留位未知。

**静态确认**：底层writer按固定word数写镜像，不检查ROM行号，因此可写的数据不限于出厂六行或二十二行。type23和26当前驱动接口分别给31项输入数据及三组33项数据留出固定位置。**未知**：其他硬件模式能否改变节点数、输入/输出有效位或插值规则；这个接口容量不能冒充silicon的全部模式规格。

### 6.3 type 25、27及额外 LUT

**静态确认**：type 25只有5word，后四项初值512；已找到的packer只改首项。type 27是25word控制/阈值布局，包含两组各8个halfword形状数据，没有type 23/26那种31+33节点结构。见 [type25-small.txt](evidence/type25-small.txt)、[type27-packer-full.txt](evidence/type27-packer-full.txt)。

**推断**：type 25更像四路gain；type 27更像滤波/阈值块。不能因它们夹在曲线寄存器附近，就补出三条gamma曲线或认定它们没有任何颜色作用。

**静态确认**：type 34另有64个u16和65个u16的请求数据；type 38有3×256字节表RAM。这些是额外可编程表的证据，见 [glut-front.txt](evidence/glut-front.txt)、[aux-gcal-glut-writers.txt](evidence/aux-gcal-glut-writers.txt)。

**未知**：type 34的坐标轴/插值与type 38的通道、生产路径尚未确认。前者可在已知still RAW处理支路被调用，后者未绑定到用户图像请求。它们不能直接当成三个可用RGB曲线通道，更不是3D LUT证据。

## 7. type 28：24分区色表到底知道多少

### 7.1 54word的完整结构

**静态确认**：type 28不只是96字节系数表。下列五部分都由 `0x20257550` 写入。初始镜像与每个payload寄存器一一对应，前后紧邻的其他块未被混入。

| `F034C040..C06C` | `+8..+0x37` | 静态确认24×u16，软件以12word复制；ROM26行，基址 `0x2012C0F4`，或T+`0x141C`。 |

### 7.2 24×u32的实际编码

**静态确认**：`0x2011396C` 对每个命中分区，把四byte的word按两项系数解读、修正，再写成 `[A,B,B xor 0x80,A]`。byte负数是符号-幅值：`00..7F→0..127`，`80..FF→0..-127`，不是二补码。修正后的高位只保留低byte，存在16位截断和有符号除法，不是浮点模型。

**静态确认**：普通五色鲜艳度档位1..9给系数乘数80/85/90/95/100/105/110/115/120%。色相另加d0/d1。等价计算顺序如下，`trunc16`为有符号16位截断，除法向零截断：

```text
A' = d0 + trunc16(trunc16(decode(A) * k) / 100)
B' = trunc16(trunc16((decode(B) + d1) * k) / 100)
word' = [encode(A'), encode(B'), encode(B') xor 0x80, encode(A')]
encode(v) = (v < 0 ? (-v)|0x80 : v) & 0xFF
```

**静态确认**：普通路径d0经helper `0x201159D8` 选ROM数据，已定位的四组24×s8源为 `0x2012D362/0x2012D302/0x2012D28A/0x2012D22A`。d1来自T+`0xF60/0xF78/0xF90/0xFA8`，k基表来自T+`0xF00/0xF18/0xF30/0xF48`；中间档由相邻值作整数平均。这里的s8源增量与待修改系数的符号-幅值编码是两种格式。见 [sector_sources.json](sector_sources.json)、[sector-adjuster.txt](evidence/sector-adjuster.txt)、[hue-delta-table-selector.txt](evidence/hue-delta-table-selector.txt)。

**静态确认**：五组mask从T+`0x129C..12AC`读取；脚本默认与旧研究再次相符。

| 组 | mask | 命中分区，零起算 |
| --- | --- | --- |
| orange | 静态确认 `0x780` | `7,8,9,10` |
| green | 静态确认 `0x1F000` | `12,13,14,15,16` |
| blue | 静态确认 `0x7C0000` | `18,19,20,21,22` |
| red | 静态确认 `0x60` | `5,6` |
| magenta | 静态确认 `0x1E` | `1,2,3,4` |

**推断**：四byte形成 `[a,b;-b,a]` 的二维旋转/缩放矩阵，初始对角32意味着候选步长1/32，作用空间最可能是围绕中性色的两路色度。将其叫HSV、Lab，或指定每区15°，都超出现有证据。24个编码槽不等于已确认24个等角、硬切换的扇区。

**静态确认**：writer没有80..120%的限制，它只写24个u32。80..120%是当前软件对编码系数的乘数范围，不是硬件饱和度范围。字段能存7-bit幅值和一位符号；现有encode超出幅值127会与符号位混淆，不能靠扩大k绕过。

**推断**：若1/32尺度成立，系数幅值127对应约3.96875；这不是已验证的最终饱和度倍率，更不是可安全设到397%的结论。允许的旋转角、寄存器保留位、溢出、插值与clip未知。

**静态确认**：五色调整器本身只依据分区编号和参数数组，不依据每像素Y值；它在编程时产生24组常数。**未知**：硬件如何结合前表、矩阵和尾表使用这些常数，因此整个type 28是否有亮度依赖仍不能下否定结论。

## 8. 3D LUT、亮度相关色度与“做不到”的范围

**静态确认**：本轮对39个type的全部描述和writer形状做了枚举；type 23/26/34是节点表结构，type 38是三个独立256字节窗口，type 28是上述有限几个bank，没有发现一块具有明确R×G×B三轴寻址、三输出体素布局及装载者的3D LUT。

**未知**：这只支持“尚未找到原生3D LUT”，不能支持“芯片绝无3D LUT”。未命名的type 21、DMA/间接地址、其他工作模式及未绑定的库入口仍是覆盖缺口。单靠表的总字节数也不能排除很小或压缩编码的LUT。

**未知**：没有确认任意 `hue × luminance` 表，也没有确认可独立改变高光/阴影色度的硬件控制。但type 23三路曲线是split toning候选，type 28尾表是额外色度依赖候选，故不能把这两项判成硬件不可能。

**推断**：在已解码子集中，一个全局WB或常数3×3不能单独表达任意按亮度分段的偏色；一个固定二维色度线性变换也不能单独为每个亮度选不同旋转。若三路LUT是RGB，则中性轴 `t→(fR(t),fG(t),fB(t))` 可以随明暗改变颜色，却仍不等价于任意三维颜色函数。这些是变换形式的限制，不是对全部未知硬件的排除证明。

**推断**：已经裁剪、丢失的信息不能靠后级tone curve恢复；提高饱和度或锐度也不能补回目标相机不同光谱响应、纹理或动态范围。能写出相似参数结构，不证明品牌look跨场景一致。

## 9. 软件变换与 still YCC 缓冲

### 9.1 颗粒处理点的图像在哪里

**静态确认**：`C.scene=21 → 0x201961EC → 0x20195764 → 0x20195340(C,C+0x168)` 的噪声分支已重验。噪声缓冲由CPU填充；T+`0x2424`的0/1/2对应3/4/5bit随机值，其他值清零。默认脚本该byte为2。后续行复用随机对齐片段，不是每像素独立调用RNG。

**静态确认**：图像与噪声不是同一指针。`0x20195884` 读 `C+0x158` 作图像源，`0x201958A4` 用同址作目标；噪声来自C+`0x168`。宽/高/步长来自 `C+0x162/+0x164/+0x160`，部分模式改用尺寸getter。每1344像素的横向分块偏移为2688字节。两个pass调用 `0x20125060`，格式/操作字段分别为3和4；最终又经request101及 `0x2011C63C` 处理。见 [grain-block-buffers.txt](evidence/grain-block-buffers.txt)、[grain-final-request.txt](evidence/grain-final-request.txt)。

**推断**：这是JPEG编码前可由内存地址描述的全尺寸YCC图像，强烈支持2字节/像素的打包/共享色度布局，而不是只有小预览可修改。`0x201A00D8` 将输出尺寸和两倍宽度步长写入C附近字段，另给640×480、160×120等小图安排不同描述。见 [still-buffer-allocation.txt](evidence/still-buffer-allocation.txt)。

**未知**：这里没有看到CPU对图像像素逐点读改写，只有CPU生成噪声、硬件源/目标地址和原地运算。因此“CPU可直接安全读写整个YCC缓冲”仍是推断。具体是YUYV/UYVY还是别的布局、色度取样相位、缓存flush/invalidate、别名、所有模式的内存寿命、JPEG启动前的同步点未确定。不能直接把 `C+0x158` 当可安装的软件LUT钩子。

**静态确认**：已有grain混合依赖 `MidExIsp_GCAL` 请求，不是用M32R循环逐点混合的证据。CPU写噪声缓冲快，不代表CPU执行12MP三线性LUT也快。

### 9.2 有条件的成本估算

**静态确认**：DNG记录RAW4304×2862，输出裁切4288×2848，即12,212,224像素。

**推断**：按2字节/像素布局估计的单帧为24,424,448字节，最少一次原地读写48,848,896字节；RGB u8临时帧为36,636,672字节。17³ RGB u8 LUT本身仅14,739字节，33³为107,811字节。数值和公式见 [software_cost_model.json](software_cost_model.json)。

**未知**：没有找到可证明M32R CPU实际主频的常量或时钟树。`0x20228BF8` 读运行时值 `0x204A3848` 并除1,000,000打印CLK，来源经 `0x200F28AC/0x200F2370`；尚未证明这是CPU时钟，也没有其当前值。显示CCIR-CLK的日志同样不能用来代替CPU时钟。见 [clock-diagnostic-source.txt](evidence/clock-diagnostic-source.txt)。

**推断**：最近邻小LUT只需少量随机查表；三线性RGB查表每像素至少涉及8角×3分量的值、索引、插值，以及YCC↔RGB及色度重采样。实际cycles/pixel受缓存、内存等待、乘除、打包布局及实现影响。下面是明确假设，不是跑分，也不是查到的机身主频。

| 假设 cycles/pixel | 假设100MHz | 假设200MHz | 假设300MHz |
| --- | --- | --- | --- |
| 推断100 | 12.21s | 6.11s | 4.07s |
| 推断300 | 36.64s | 18.32s | 12.21s |
| 推断1000 | 122.12s | 61.06s | 40.71s |

**推断**：估算公式为 `t=N*c/f`，还要加未被c覆盖的内存、调度和缓存维护成本。现阶段应按可能增加数秒到数十秒、较慢方案超过一分钟来评估still软件变换，不能承诺实时或固定拍摄延迟。具体c与f都需目标CPU实测，本轮没有执行benchmark。

### 9.3 live view 不会自动获得 still 软件效果

**静态确认**：同一套Q/P packer接受多个request。已保存的still调用有request32/34/35，monitor侧有request16，并有对type 23的额外重写。request编号与处理效果编号不同。见 [monitor-isp-caller.txt](evidence/monitor-isp-caller.txt)、[still-main-isp-caller.txt](evidence/still-main-isp-caller.txt)、[awb-gamma-caller.txt](evidence/awb-gamma-caller.txt)。

**推断**：修改共同硬件配置有机会同时覆盖预览和拍摄，但必须同时处理各请求的选表、旁路和后续覆盖。只插在场景21的still后处理处，普通live view不会因此执行同一CPU变换；需要另写预览路径，或接受预览与最终JPEG不一致。

**未知**：普通live view的全部像素阶段是否与still完全相同、原生颗粒是否有独立预览近似，以及各效果的最终重写顺序，尚未逐项闭合。

## 12. 最有价值的三个后续目标

1. **推断，首要目标**：闭合type23的三个通道与type26的全零辅助bank。沿 `0x20119BC8 → 0x201195A4 → 0x2011AC50` 及 `0x20118468`，分别使用单位/单通道常数/单节点差分作为后续受控测试设计，查清RGB/YCC顺序、12-bit有效范围、辅助表是否为色度偏移、preview/still一致性及覆盖。这直接决定独立RGB曲线与split toning是否可做。
2. **推断，第二目标**：恢复type28的坐标和内部顺序。优先追 `C040` 的24个u16与 `C120` 的7节点/9增益，而不是继续把C080称作已知HSV表；同时确定Q10矩阵的sign、offset、clip与位置。它决定24区颜色的真实精度，以及是否已有亮度或色度幅值相关的颜色能力。
3. **推断，第三目标**：闭合普通still的YCC缓冲到JPEG交接，以及CPU/cache/clock。把 `C+0x158` 的格式、所有权和同步点写成完整契约，再用目标CPU的一个小整数变换测cycles/pixel。只有这三项清楚，才能决定软件3D LUT值得做，还是应优先复用辅助LUT/硬件块。
