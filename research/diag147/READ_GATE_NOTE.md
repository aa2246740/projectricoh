# 读卡门：持有 47 时怎样判定"可以只读打开"（设计说明，本轮不实现）

2026-10-31。本文供 g140 第二层（按 OK 读效果文件 `GXRFX.BIN`）使用。g147 的按键读卡因为复审 R3-01 撤下，g147a 不碰卡。本文只整理已有证据，提出判定条件，并列出缺口。没有新写代码，也没有新跑重放。

## 1. 问题是什么

"只读打开一个已有文件"本身不写卡。但原生 lookup 在换入共享 FAT 缓存时，会先把**别的文件**留下的脏缓存提交到卡上：`0x200B86EC` 提交，经 `0x200BB5B8` 分派，到写回调 `0x200A3358`（复审 `review_diag147` 第 3 节）。因此，持有 47 时必须确认：**没有原生文件槽被占用，共享 FAT 缓存是干净的。**否则只能判 BUSY，不进入 parse/lookup/attach。也不能自己 flush 或清脏标志，那等于替别的文件写卡。

## 2. 已知的原生字段（官方 1.51 与 v3.8 的文件系统窗口逐字节相同）

## 3. 建议的判定（草案）

持有 47 时（只试一次、超时 0，不变），**全部满足**才允许进入 parse：

1. `0x204C8668 == 0`；
2. 对 i = 0、1：`F_i+4 == 0xFF` 并且 `F_i+6 == 0xFF`（两个原生槽都空闲）；
3. 对 i = 0、1：`F_i+700 == 0`（没有待写回的 FAT 缓存）；
4. （可选，作为一致性检查）16 个高层句柄项的 mode 都是 0。

任何一条不满足，就显示 BUSY，并记下是哪一条（相当于 g147 的 `B L47`/`B Fn`，扩展成 `B C`、`B S`、`B D` 之类），立即释放 47。只读，不改任何字段。

为什么第 1 条不够（R3-01）：关闭 API 在取 47 之前就把计数减到 0，此时槽仍是 `1,0`，`F+700` 可能还是 1。第 2、3 条正好覆盖这个中间状态。复审的两个"关闭交接"用例在这个状态下应当返回 BUSY。复审补全目录缓冲后跑的"完整关闭"用例，结束时计数 0、槽 FF/FF、`F+700 = 0`，应当放行。

读取这些字段本身是否安全：
- 它们都是机身 RAM 里的固定地址，读只是普通的字节或字载入，没有设备访问，也没有副作用。地址在 1.51 和 v3.8 上相同；以后机身换版本要重新核对。
- **一致性**取决于写这些字段的代码是不是都在持有 47 时执行。已知不是的有：打开计数的检查和减 1、句柄项的清零（第 2 节表）。所以这些字段只能当"拒绝的理由"，不能单独当"放行的证据"。第 2、3 条字段的写者目前按调用关系推断都在 47 内（第 4 节缺口 G1）。
- 读字段放在试锁成功之后、parse 之前，与 g147 的计数检查在同一个位置。ELF 证明可以照 `lock_proof147.py` 第 5 节，把"计数寄存器为 0"扩展成"四个条件都为真"的支配关系。

## 4. 证据覆盖到哪里，还缺什么

已有：
- **干净读句柄的关闭不回写**（`review_diag147` 第 3 节，原厂指令）：release 跳过 FAT、FSInfo、目录项收尾。只读本身的关闭是安全的。
- **别的文件开着（计数 ≥ 1）时 lookup 会写回**（`review_diag147`），g147 的计数门可以挡住（`native_replay147.py`、主机 `otherfile` 组）。
- **关闭中间状态（计数 0、槽占用、`F+700 = 1`）时 lookup 会写回**（`review_diag147_r3` 第 2 节，`elf_native_handoff.py` 两例）。
- **完整关闭之后再读，第一个请求是读**（`review_diag147_r3` 第 3 节，`close_window_review.py` 两例）。
- 关闭出错（设备返回 1、25）时，4 个观察都是计数 0、`F+700 = 0`、槽已释放（`close-error-observations.json`，只是观察）。
- 删除包装 `0x200A4910`、改名包装 `0x200A49D8` 在持有 47 时调用下层函数。删除会占用原生槽，但不加高层计数，所以第 2 条有必要。
- g146 在实机三个单元上，在 ig_init 和 H01 末尾用同样的读法读过卡上已有文件（读法本身已在机上证明，入口不同）。

缺口：
- **G1 写者普查：**文件系统窗口 `0x200A3000..0x200BC000` 中，所有写 `F_i+4`、`F_i+6`、`F_i+700`，以及其他可能的脏标志（目录扇区缓冲、FSInfo 待写）的指令，逐条列出，并判定执行时是否一定持有 47。目前只看了打开、关闭、删除、改名四个包装。
- **G2 还有没有别的脏状态：**lookup 换入时会不会提交第 3 条以外的东西，例如目录扇区缓冲的脏标志、卷上下文里的待写字段。要在原厂指令上，把 `0x200B86EC`、`0x200B82CC`、目录读写 `0x200B823C` 的所有写回分支走一遍。
- **G3 拍照存图的路径：**相机写 JPEG 用的是不是这些高层 API，计数、槽、脏标志在一次存图过程中依次怎样变化，有没有不经过 47 的下层调用。现有重放都是合成写方，不是真实的存图历史。
- **G4 其他目录操作：**格式化、建目录、删除、改名的错误收尾里，会不会留下"槽已空闲但缓存仍脏"的状态。
- **G5 FAT32 实卡：**所有重放用的都是合成卷，没有完整的 FAT32 挂载。
- **G6 调度：**持锁期间被抢占、看门狗余量、菜单关闭被推迟多久，都没有实测。

## 5. 建议的下一步（给 g140 第二层）

1. **先做零风险的采样探测**（可以单独出一个诊断 DAT，仍然不碰任何文件入口）：在 H07 按 OK 时只**读**第 3 节的四组字段，加上 47 的计数（`0x200D` 一带的信号量计数字，地址要先核实），显示在一页上。拍照后马上按，多按几次。这样不读卡，就能在真机上看到存图时这些字段的真实变化（回答 G3 的一部分）。静态检查要相应放宽：允许**读**这些 RAM 地址，仍然禁止一切文件和 47 的调用入口。
2. 补 G1、G2 的原厂指令普查，把复审的 `elf_native_handoff.py`、`close_window_review.py` 扩展成"四条判定"的对照：关闭交接两例必须 BUSY，完整关闭两例必须放行并且第一个请求是读。
3. 实现时保持 g147 已验证的形状：只试一次锁、唯一释放点、门在 parse 之前、ELF 支配证明加变异自检，以及原生重放里"不加门必写、加门不写"的成对用例。
4. 另一种思路可以并列评估：不在按键时读，改在 H01（打开菜单）末尾读（g146 已在机上用过这个入口），或者开机时把效果读进 RAM（设计 §3.4 因为 8 KB 常驻空间否掉过）。这两种同样要过第 3 节的判定，只是调用时机不同；拍照后立刻打开菜单时，存图可能还没写完。
