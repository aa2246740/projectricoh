# Stage 2k v2：卡上代码 overlay 评估

建议保留 overlay 方向，但目前不能批准为“284 B 常驻代码即可解决空间、删文件即可恢复”的方案。主堆的分配和所有权有肯定证据；主堆取指权限、完整缓存同步和 task 6 调用安全还没有闭合。复用 2j 的文件读取、CRC 和 ABI 桥后，完整 loader 的手算预算仍为 352–508 B，连同分发与原生入口适配为 664–1068 B。它们都不是编译结果，也不是理论最小值。

overlay 能把 a/b/c 的大部分逻辑移到已分配的 RAM，因此在条件成立后可以完全避开段 7/10/13。但不能把尚未证明的堆可执行性、284 B 装入和崩溃恢复，换成三个新的默认假设。

本轮只做设计和静态分析。没有构建代码、生成 overlay/升级包、访问相机或 SD、构造 U 型 RPC。原 [REPORT.md](REPORT.md) 和原有私有笔记保持原样；新增证据在 [local/overlay/](local/overlay/NOTES.md)。

## 1. 可以执行的 RAM 与缓存

### 1.1 主堆：分配已证，执行未证

静态确认：`0x2005BF00` 从 `0x200C0DC0/C4` 读取 `0x20704800` 和 `0x40000`，建立主堆；`0x2005BF5C` 分配、`0x2005C038` 释放，边界存放在 `0x200D3488/8C`。2j 的 `gxr_alloc` 就调用这个分配器。它返回的是普通数据指针，没有设置可执行权限的参数，也没有在所查函数中改页表或保护寄存器。

尚未找到“从该分配器取得地址，写入代码，再间接调用”的原生正例。body 在 `0x2004xxxx..0x2040xxxx` 执行 RAM 代码，不足以证明 `0x20704800..0x20744800` 具有相同的取指属性。

对官方 body 的 16 段和既有 Monitor 反汇编做了有边界的常量传播扫描。扫描没有识别出 Linux M32R 所用 MMU/TLB 寄存器范围的有效访问；这不是“没有 MMU/NX”的证明。扫描不能解析所有间接地址，原始反汇编也混有数据，另有更早的硬件启动状态没有闭合。`mvtc` 指令和 PSW 初始化本身也不能证明堆的页面或总线取指权限。

[Renesas M32R 软件手册](https://www.renesas.com/en/document/mah/m32r-family-software-manual) 描述的核心控制寄存器，不能替代本机具体 SoC 的保护与总线手册。[Linux 的 M32R MMU 定义](https://raw.githubusercontent.com/torvalds/linux/v4.16/arch/m32r/include/asm/m32r.h) 说明这个家族存在带 MMU 的实现。因此本报告不给出“所有 M32R 都没有 NX”的结论。

| 候选区 | 已知事实 | 能否作为本方案的代码区 |
| --- | --- | --- |
| 主堆 `[0x20704800,0x20744800)`。 | 2j 已使用；有明确分配/释放合同。 | 首选，但取指属性和缓存合同未证。 |
| IRAM `0x05000C00` 起的内核区域。 | 官方在此执行内核。 | 未找到供扩展取得独占、长寿命代码块的分配服务，不能借用。 |
| 普通任务栈池、系统栈、INT_USR_STACK。 | 已有各自所有者；任务 6 的已登记栈为 16 KiB。 | 不作为代码分配来源，也不在栈上执行下载代码。 |
| UI/image arena、高端保留区。 | 有原生像素、DMA 或启动用途。 | 没有本扩展的分配与执行合同。不能凭地址别名猜出一块 executable heap。 |
| 独立程序使用的低地址 RAM。 | 存在复制代码后跳转的原生路径，见下节。 | 该程序会重设机器环境，未找到日常扩展可调用的分配合同。 |

当前没有一个已闭合、可直接替代主堆的代码分配区。

### 1.2 原生缓存操作的确切范围

静态确认以下逻辑；这里只列地址和动作，不公开指令字节。

| 地址 | 动作 | 对 overlay 的含义 |
| --- | --- | --- |
| bootstrap `0x2004BACC..0x2004BADC`。 | 读 `0xFFFFFFFC`，检查 bit 0；置位时写 `0x101`。 | 是段加载器的内联尾部。 |
| main loader `0x20088578..0x20088588`。 | 同一条件和写值；后面立即接本函数的出栈返回。 | 不能跳进中段作为 flush 子程序，否则使用了不存在的栈帧。 |
| `0x200888F4..0x20088904`、`0x200890F8..0x20089108`。 | 同类内联序列。 | 不是独立 cache API。 |
| `0x20093114..0x20093128`、`0x200932CC..0x200932E0`。 | 条件仍检查 bit 0；以当前寄存器值 OR `0x101` 后写回。 | 比固定写值保留更多状态，但仍未证明是完整 D-cache clean 加 I-cache invalidate。 |

这些短序列里没有显式 D-cache 范围回写，也没有等待维护完成的循环。不同 M32R 芯片的同名控制位不同，[Linux 原生 cache 实现](https://raw.githubusercontent.com/torvalds/linux/v4.16/arch/m32r/mm/cache.c) 也按芯片分别处理。因此只把本机动作记为“条件写缓存控制寄存器”，不把 `0x101` 自动解释成完整的 I/D 同步。

另找到映像位置 `0x204026F8`、`0x2040270C`、`0x20402734`、`0x20402760` 的 cache 相关叶函数。后两者将范围按 16 B 扩展，设置 `0xFFFFFFC0/C4`，再对 `0xFFFFFFC8` 分别 OR `0x400`、`0x200` 并读回。`0x2040270C` 最后还把 `0xFFFFFFFC` 写成 0，不能作为保持原状态的通用 flush。

这里有一个关键的生命周期区别：`0x20401FE4` 起的启动代码，把源 `0x2040202C` 起的 `0x1D4C` B 复制到 `0x00010000` 后跳过去；随后的程序会设置 EVB、SPI/SPU 和 PSW。上述叶函数在这个被复制的程序内，运行地址应按复制关系换算，例如源位置 `0x20402734` 对应低地址 `0x00010708`。它们不是已经证明可从日常 body task 直接调用的 `0x2040xxxx` 服务。

所以本轮找到的是原生的操作序列及独立程序里的范围维护函数，尚未找到可交给 task 6 的完整、稳定 I/D cache API。不会调用整个段加载器来代替维护，也不会调用那个独立程序的启动入口。

### 1.3 task 6 的安全结论

已验证的 task-6 模式入口与 RPC 锁合同继续成立，见 [FOLLOWUP.md](../stage2k_design/FOLLOWUP.md)。它证明可以在相应边界调用已有同步服务，不证明某个 MMIO cache 序列对所有并发任务和 DMA 都安全。

本轮还确认 `0x20068818 -> 0x20088358` 的原生段加载链，及其若干调用者；没有据此声称菜单现场与这些调用现场等价。独立程序的 cache 叶函数没有 OS 调用，也不足以证明日常环境可以安全改变全局 cache 状态。

loader 的执行顺序必须是：完成读文件及其 DMA/CPU 可见性，校验最终 RAM 内容，完成所有代码/GOT 写入，完成必要的 D-cache clean，再完成 I-cache invalidate 和指令流同步，最后发布入口。真正采用的寄存器位、完成条件、临界区和调用上下文仍是发布前条件。不能在文件 IO、CRC 或 RPC 等待期间关中断。不能直接使用 GCC 默认的 `trap #12` 缓存接口；[GCC 文档](https://gcc.gnu.org/onlinedocs/gcc/M32R_002fD-Options.html) 的默认值不证明 Ricoh 注册了对应服务。

主堆执行与 cache/task-6 安全目前均为“未证”，不是“静态确认可用”。

## 2. 容量、碎片与寿命

### 2.1 分配器给出的肯定证据

`0x2005BF5C` 按 4 B 对齐，使用 12 B 块头，沿空闲链做 first fit；空间足够时拆块。释放器验证边界和块头，再按地址插回并合并相邻空闲块，没有移动已分配块的压缩步骤。

因此成功分配且尚未释放的代码块，不会因为后续正常分配而搬家或被再次分配。这解决了“原生代码是否仍把该块视为空闲”的正常分配器所有权问题。它不防越界写、错误 free、整个堆重建或硬件别名覆盖。

原生另有 `0x200BBE00/0x200BBF20` 的跟踪分配/释放包装和 `0x200BBDBC` 的批量释放链。2j 直接调用底层分配器，不加入这条跟踪链；overlay 沿用同一家族时，不会仅因该跟踪链被清空而释放。失败路径必须用匹配的底层 `0x2005C038` 释放原指针，不能把它交给 `0x200BBF20`。2j 目前没有导出 `gxr_free`，loader 要自行包含正确的 native ABI 调用适配。

所查分配/释放函数自身没有锁或关中断。2j 菜单的既有调用是使用先例，不能代替整个分配器的跨任务串行化证明。后续须确认调用环境或找到原生分配保护；不能拿 overlay 自己的 busy 位当原生堆锁。

### 2.2 能预算多少

256 KiB 是容量，不是已知剩余。没有本轮实机的 free/largest-free 数据，不能断言日常总有 8 KiB 连续空间。一个长寿命块分配一次以后不会自行碎裂，但反复加载/卸载会改变其余分配的布局。

读取既有 `firmware/stage2j/build/layout.o`，得到 32 位 `RfwCache` 大小 3548 B；另有 3604 B 的旧表缓冲。下表采用保守预算，保留旧缓冲，另开 overlay 状态区，不假定可以安全回收旧指针。

| 常驻项目 | 请求/内容 | 正常拆块时含底层块头的占用 |
| --- | ---: | ---: |
| 既有 2j UI cache。 | 3548 B。 | 3560 B。 |
| 既有 2j 表缓冲。 | 3604 B。 | 3616 B。 |
| overlay 文件，含头、imports 和 entry 表。 | 4096 或 8192 B；额外请求 15 B 用于把执行基址对齐到 16 B。 | 4124 或 8220 B。 |
| overlay 状态区。 | 初版固定 6144 B。 | 6156 B。 |
| 合计，不含其他原生分配。 | 4 KiB / 8 KiB 文件两档。 | 17456 / 21552 B，约占堆总量 6.66% / 8.22%。 |

6144 B 状态区容纳既定 v4 表缓冲 5156 B、engine 256 B、扩展 journal 96 B、probe 48 B 和 64 B ABI/context，合计 5620 B，余 524 B。表的临时流式检查窗口放在原设计的有界栈预算内，不再藏一份常驻 5 KiB 副本。原设计的额外栈上限 896 B 仍是预算，不是任务 6 的实测高水位。

表中数字是请求对应的正常块占用，不是对实际空闲链的测量。分配器遇到不足以再拆出小块的余量时会整块交出，每块还可能消耗不足 28 B 的尾部余量；长期原生分配造成的碎片另计。不能把合计简单从 256 KiB 扣掉，就当作相机可用余量。

本文 v1 loader 固定申请最大 8192 B 文件区，实际按 21552 B 一档规划。4096 B 一档仅用于比较较小 loader 配置，不是说 8 KiB 上限的 loader 读取小文件就自动少占 4 KiB。

8 KiB 代码块要求至少约 8220 B 的可分配连续空间，另要 6156 B 状态块。分配第二块失败时释放第一块，保持原 2j 路径。成功的两次分配也只证明当时能取得空间，不证明之后原生拍摄路径的内存峰值仍安全。只读空闲链快照可以评估连续空间；原生模式切换、JPEG/RAW、回放和录像的峰值需求还需既有证据或以后单独验收。

### 2.3 装载与退出时机

初版只在明确的菜单打开/操作事件加载，不在 boot、模式 dispatcher、grain hook 或 RPC worker 中加载。仅凭 `init_recipe_cache` 这个 hook 名字不够；resident 必须确认实际任务 6、已有 `rfw_ui_active()` 的全部 ADJ 条件，以及允许加载的菜单事件。开机初始化即使经过 `rfw_open`，也不能触发读代码和跳转。

| 事件 | 代码块与状态区 | unit/S 行为 |
| --- | --- | --- |
| 首次菜单事件，尚未接管深层状态。 | 分配、读取、完整验证、维护 cache；纯私有 RAM 初始化成功后发布。 | init 不发 RPC、不改 S、不注册 heap 回调。 |
| 菜单关闭、菜单 view 重建。 | 保留两个块和独立 root；不得随 ADJ binding 丢失。 | 沿用既定 engine 所有权和恢复合同，关闭 view 不等于销毁会话。 |
| 模式切换、直接回放。 | 保留代码，先调用现有设计的共同恢复入口。 | 全部已改行、T 控制及 S 所有权规则均须满足；失败不宣称 stock。 |
| 卡移除、换卡、文件被替换。 | 不热替换、不 free、不再次装载。已载代码不再依赖卡文件。 | 已保存的恢复材料继续可用；换表前先恢复。没有可信卡代次事件时禁止会话内自动重载。 |
| 休眠、唤醒。 | heap/代码保留和恢复时序尚未证。 | 在确认休眠前边界能恢复、唤醒能重验代次前，daily 不放行。不能在唤醒后盲跳旧 heap 指针。 |
| 正常关机。 | 在 `0x2005CF7C` 最前、`0x2006015C` 之前做恢复；不必为省几 KiB 在收尾中 free 代码。 | ready 被清掉后不能再补恢复。原 teardown 合同不变。 |
| 强制断电、异常、watchdog 重启。 | 没有保证执行的清理机会；body 与 unit 的重启代次可能不同。 | 不承诺 RAM/T/S 自动恢复，见第 6 节。 |

## 3. 文件格式、ABI 与完整性

以下为建议的 overlay v1 合同，不是已经可用的 BIN。文件仅为 `/ATA1/DEEPOVL0.BIN`，初版不做 0/1 双代码文件择优，以减少加载器和恢复分支。“两张卡”指轮换使用的两张 SD；只读当前挂载的 `/ATA1`，不寻找另一张卡上的代码。

全部整数大端。v1 是无运行时重定位的平坦 PIC 文件，大小至少 164 B、最多 8192 B，必须为 4 的倍数。前 160 B 固定，后面才是代码/只读数据。CRC 使用既有 `rv1_crc32`，即 CRC-32/ISO-HDLC，数值 0 合法。

### 3.1 64 B 头

| 偏移 | 大小 | 字段与校验 |
| --- | ---: | --- |
| 0 | 8 | magic 为 ASCII `GXROVL1` 加末尾 NUL。 |
| 8 | 2 | format=1。 |
| 10 | 2 | header_bytes=64。 |
| 12 | 4 | file_bytes，范围与实际读取长度完全一致。 |
| 16 | 4 | resident_abi_id，必须精确匹配已安装的 resident 版本。 |
| 20 | 4 | body_layout_id=1，绑定本项目 body 1.51 地址/调用合同。 |
| 24 | 4 | unit_layout_id=1，绑定 A12 50mm 1.51 行映射；不代替每次 RPC 前的实际 unit/link 核验。 |
| 28 | 4 | features，bit 0=core、bit 1=v4、bit 2=probe，其余位拒绝。 |
| 32 | 4 | code_offset=160。 |
| 36 | 4 | code_bytes，必须等于 file_bytes−160。 |
| 40 | 4 | state_bytes=6144。初版固定工作区，禁止额外未预算 BSS。 |
| 44 | 2 | entry_offset=128。 |
| 46 | 2 | entry_count=8。 |
| 48 | 2 | imports_offset=64。 |
| 50 | 2 | imports_count=16。 |
| 52 | 4 | payload_crc32，覆盖 `[64,file_bytes)`。 |

ABI ID 的具体常数必须在以后 resident 链接并冻结后，由服务表、签名、事件语义、结构尺寸和目标版本共同生成；当前不虚构一个已经安装的 ID。改变这些合同必须改 ID。仅在同一 ABI、资源上限和 hook 集合内改 a/b/c 功能，才可以只换卡文件。

### 3.2 64 B 服务表与 32 B 入口表

文件 `[64,128)` 是 16 个 u32 的服务地址表。resident 将它与自己编入的 64 B 白名单逐项比较，不接受文件请求任意 native 地址。下列地址来自本轮读取的既有 2j map；未来首次安装 resident 如重排 2j，必须重新冻结地址和 ABI ID。

| 槽位 | 服务 | 当前 2j 地址 |
| --- | --- | --- |
| 0 | `rfw_read_path`。 | `0x20052AD0`。 |
| 1 | `rv1_crc32`。 | `0x20053920`。 |
| 2 | `gxr_alloc`。 | `0x200527E8`。 |
| 3 | `rfw_ui_active`。 | `0x20052A44`。 |
| 4 | `gxr_thread_context`。 | `0x2005283C`。 |
| 5 | `gxr_unit_info`。 | `0x20052848`。 |
| 6 | `gxr_rpc_ready`。 | `0x20052824`。 |
| 7 | `gxr_rpc_limit`。 | `0x20052830`。 |
| 8 | `rfw_rpc8_call`。 | `0x20053728`。 |
| 9 | `gxr_preview`。 | `0x200527F4`。 |
| 10 | `gxr_ascii`。 | `0x20052800`。 |
| 11 | `gxr_language`。 | `0x2005280C`。 |
| 12 | `rv1_decode`。 | `0x200539FC`。 |
| 13 | `rv1_plan`。 | `0x20053CD8`。 |
| 14 | `rv1_apply`。 | `0x20053DA0`。 |
| 15 | `rfw_open`，原 2j 实现。 | `0x20052DD4`。 |

这些服务保留现有 GCC ABI，不是裸 Ricoh ABI。`abi.S` 的 native/GCC 桥必须继续保存其规定寄存器；native 调用者不能直接跳 GCC C 函数。服务表只是版本合同，不是安全沙箱，CPU 不会阻止 overlay 自己构造其他地址。`rfw_rpc8_call` 的既有前置检查也不代替新增的整个事务 owner/native gate。

`rfw_open` 在现有 2j 中不是纯绘制函数：它重载 bank、调用旧 `rfw_deep_refresh`，并依据旧 deep state 匹配槽位。槽位 15 只可用于明确的原 2j fallback，不能在 overlay 接管后无条件调用，否则会重新引入 F6/F7。首次 resident 要么拆出不触及 deep 的 view 服务并改 ABI ID，要么让 overlay 自带对应的 UI 协调实现；不能直接把“已有 open”计作免费复用。原 fallback 函数须有独立入口，不能让服务表指向新 dispatcher 而递归调用自己。

文件 `[128,160)` 是八个 u32 相对文件基址的入口偏移，依次为 `init`、`open`、`select_commit`、`grain`、`lifecycle`、`playback`、`teardown`、`native_gate`。八项均须位于 `[160,file_bytes)` 且按 4 B 对齐；未使用项指向明确的无副作用返回函数，不用 NULL。入口偏移在整个文件基址上相加，不在 `code_offset` 上再加一次。

入口统一使用不超过四个 scalar/pointer 参数，首参为有尺寸和 ABI ID 的 context；其他参数为事件、参数结构和结果结构。不得让 C struct 隐式按不同编译器布局传值。`grain` 和跨任务 `native_gate` 的合同明确禁止分配、文件 IO、等待和发起新的恢复事务。实际 `Rv1SettingsPort` 等旧结构也必须在 ABI 冻结中记录尺寸和字段偏移。

### 3.3 随机堆地址与 PIC

现有 2j 是固定 VMA，不能直接复制到随机堆地址。`-mmodel=medium` 不是位置无关编译。读取本机 GCC 13.4.0 的 M32R backend，确认有 PIC/GOT 支持、r12 PIC base 和 PC 获取序列；这只证明工具链存在相关机制，没有本轮生成的 overlay PIC 产物。

v1 要求所有内部符号隐藏或局部化，内部代码/数据引用为位置无关形式，原生服务一律从经过校验的 imports 取地址。静态地址初始化、绝对内部指针数组、绝对 GOT 项和未经处理的链接重定位一律禁止。可变指针在 `init` 中构造，常量表用偏移。以后交付工具必须对最终 ELF 的 relocation、GOT、全局指针和反汇编逐项审计，并验证至少两个不同运行基址；不能用一个 `-fPIC` 开关替代这些检查。

首版不加入运行时 relocator，也不让代码自搬家。若最终 GCC 输出不能满足此合同，应改布局或拒绝该产物；不能悄悄从未验证入口先运行“自修复”代码。

### 3.4 loader 的完整顺序

1. resident 确认菜单事件、任务和独立 root 有效，且没有已接管、未恢复的旧会话；原子标记 LOADING。旧 2j 已 active/uncertain 时不在原地升级，先用其已有恢复材料恢复并核验，或结束该会话。不能把空 cache 或 active=0 当作 unit stock 证据。所有非菜单入口只分发，绝不加载。
2. 用现有分配家族申请最大文件区加对齐余量，保留原始 free 指针。分配结果不只检查非 NULL，还核对原指针、对齐后基址和完整请求区间位于已知主堆内。用 `rfw_read_path` 完成有界读取、短读循环、超长探测和 close。读取失败、无卡、缺文件均不能进入代码。
3. 先核对实际长度与最小头范围，再核对固定 magic、版本、目标、全部固定偏移/计数、长度关系、feature 依赖、状态区大小；用减法和有界比较防止整数溢出。不能先用磁盘提供的偏移取指针。
4. 核对 header CRC、payload CRC、完整 imports 白名单和全部八项入口范围/对齐。未知版本、未知位、截断、尾随数据、错 ABI、错目标均拒绝。失败后关闭句柄、匹配释放，不登记任何 heap 回调。
5. 申请固定状态区，同样验证完整边界且与代码块不重叠，再显式清零。分配失败释放代码区；分配器元数据或返回区间异常时保留故障证据，不能对可疑指针盲目 free。准备 resident ABI/context。按已证明的最终 cache 合同同步代码；此合同目前尚缺，因此当前设计不允许实际执行。
6. 仅调用已验证的 `init`。它只能操作私有状态区。返回必须是约定的成功值，context 的尺寸、ABI ID 和能力回报也必须一致。失败按同一家族释放；不得把 init 放到 boot 重试循环。
7. 最后才原子发布 READY root，供现有 hook 使用。实际 unit 行、T 和 S 的首笔修改另经过原 2k ownership/reader gate，不能因文件 CRC 正确直接接管。

文件读入后不再重读、拼接另一代文件；CRC 检查的就是最终执行缓冲。IO 可见性必须先于 CRC。全部结构和完整性检查在第一条 overlay 指令之前完成；init 的返回检查则在发布前完成。

CRC32 检测损坏，不认证作者，也不证明代码正确。若以后要求抗篡改，应把公钥验证和可信 key 放在 resident，并另算空间；把 SHA-256 或签名验证器放进尚未认证的 overlay 没有解决引导信任问题。

## 4. hook 怎么分发，缺文件时怎样运行

外部 native hook 始终先到 resident，native 表里不保存 heap 函数指针。resident root 与 ADJ descriptor 分开，建议 16 B，记录已发布指针/一致性信息和状态；heap engine 保存详细会话代次、dirty、owner、inflight 与恢复材料。root 的具体打包和原子发布还需 ABI 审计，不能为了 16 B 省掉 F7 的独立所有权。

| 既有/新增边界 | resident 留下什么 | overlay 执行什么 |
| --- | --- | --- |
| `0x2028709C` 到 `ricoh_recipe_open`；当前 GCC `rfw_open=0x20052DD4`。 | 保留 native ABI 桥和原 2j fallback；在合格菜单事件尝试首次加载。 | READY 后接管新 open/view/engine 协调。 |
| live `0x202BB968`、确认 `0x202871D8`、Fn2 `0x202BE24C`。 | 保留寄存器/PSW 保存、原指令重放、continue/return 约定。 | select/commit、03→04 的 `S+0x645/646` 所有权恢复。 |
| grain `0x2017098C` 到固定 `0x20053FEC` stub。 | 保留已固定位置和 inline ABI；READY 才分发。 | 只读查询 engine 后决定 grain 参数，不能在拍摄路径装载或恢复。 |
| mode dispatcher `0x20069D4C` 最前。 | 新的 resident 入口/返回适配；缺 overlay 走原生。 | 共同 exit engine；不得把普通 status 当 mode 或负 callback 返回。 |
| 直接回放 wrapper `0x202FB9CC` 之前及四个已查 caller。 | 拒绝分支和调用合同必须常驻，不能只改被忽略返回值的 callback。 | 在第一笔回放副作用前恢复，并返回明确结果。 |
| teardown `0x2005CF7C` 最前。 | 提前分发，不能等 ready 清零。 | 有界的一次恢复尝试，复用原设计 exit_epoch。 |
| native RPC 前门、mutex 74 的两处失败点。 | 原生入口适配和失败早退必须常驻。 | owner/native-inflight 判定可在代码已发布时由 `native_gate` 处理；未发布时无 overlay 事务。 |
| sleep/wake、可信卡代次事件。 | 尚未定位全部 hook，需预留和核验。 | 复用 lifecycle，但不能只靠“有这个入口”假定事件一定送达。 |

不能只替换 open 和 select，就声称 findings 1/2/3、F6/F7/S3 全部得到补强。整个 RPC cursor 的原生竞争入口、模式/回放/teardown 的拒绝合同和 cache 丢失处理仍是 [原设计](REPORT.md) 的要求。

干净会话中，缺文件、无卡、版本不符、CRC 错误或内存不足，均走原 2j 实现。不会在 boot 反复读坏文件，也不从别的路径寻找同名代码。两张轮换卡只有一张带 BIN 时，另一张在新干净会话中运行 2j；换文件只在下一次干净会话生效。v4 表不能由原 2j reader 解释，缺 overlay 的卡若要完整使用 2j 深层配方，须保留 v3 表。

fallback 的正常 2j 行为保持一致；两处 native 锁失败仍按 resident 补丁早退，这是有意保留的补强。

一旦已经发布并接管状态，缺卡不能把 resident 直接切成 fallback。必须保留有效代码和 journal，先完成恢复和读回，再撤销所有权。普通菜单重开不热更新，避免同时存在旧回调和新 ABI 的两代代码。overlay 失联、root 损坏或代码完整性不可信时进入 UNKNOWN，不能把它当“从来没有 overlay”。

## 5. 哪些代码可以移走，剩多少常驻空间

### 5.1 a/b/c 的归属

| 层 | 可以放入 overlay | 必须常驻或仍待证的部分 |
| --- | --- | --- |
| a，core robustness。 | findings 1/2/3、F6/F7/S3 状态机、完整行预检/恢复/读回、S 的 03→04 恢复、owner 与退出决策主体。 | root、入口分发、native ABI/重放/返回适配、native 前门、锁失败早退、发布与失败状态。 |
| b，v4。 | 格式 reader、行校验、D8/T2 事务、restore/readback、表缓冲和 journal。 | 不新增独立常驻表 reader；仍使用上述 resident 入口。unit quiescence、T2 cache 来源/代次未证的问题不因 overlay 消失。 |
| c，probes。 | D8/T2 白名单、07/08 test slots、结果和恢复材料。 | 复用 resident 启动/分发；测试权限不放宽 unit 写入地址或控制合同。 |

请求开关独立保存为 core/v4/probe。v4 或 probe 需要的共同安全 engine 没有就拒绝该能力，不静默绕过 core。全部关闭时为 2j baseline。缺 overlay 时原 2j 的既有问题也仍在，不能将此状态标成“daily T1 已加固”。

两处 native mutex 获取失败检查，`0x200900B4`、`0x20090360`，仍应是 resident 小补丁，失败走已证明的不发送、不等待、不 unlock 早退族 `0x200900A4`、`0x20090350`。overlay 缺失时也不能跳进 heap 来处理锁失败。实际覆盖窗口、跳板和失败返回约定还须下一轮静态 ABI 审计。

### 5.2 字节预算

预算按已见 M32R 16/32 位指令、2j ABI 桥和服务复用手算。没有编译，也没有提交可执行 loader；下限只是该设计的乐观预算，不是最优汇编的数学下限。现有 `rfw_read_path`、`rv1_crc32` 和 native 桥的全部体积已经属于 2j，不重复收费。

| loader 项目 | 新常驻 B |
| --- | ---: |
| 分配、调用已有 read-path、检查 IO/长度、正确 free 的路径。 | 48–80。 |
| 头/目标/版本/长度规则及两次 CRC 校验。 | 88–136。 |
| imports 精确比较循环。 | 16–28。 |
| 固定 16 项服务地址。 | 64。 |
| 全部入口的范围/对齐检查循环。 | 28–44。 |
| cache adapter 预留；实现合同尚未证。 | 24–48。 |
| init、发布、失败状态。 | 48–72。 |
| 文件名，含对齐。 | 20。 |
| 独立 root。 | 16。 |
| loader 小计。 | 352–508。 |

另加事件分发/重入 64–112 B、模式/回放/teardown 适配 112–192 B、native RPC 前门适配 112–208 B、mutex 失败适配 24–48 B，合计为 664–1068 B。覆盖原生指令的 patch-site 字节和可能的额外分支/对齐要在最终 patch map 分开列清，不能藏在“原位置已有代码”里。

“理想 160 B”至多可作为只读文件、做少量检查、调用一个入口的精简启动器目标，不能据此给本题完整 loader 承诺 160 B。若把 ABI 表改成 resident 校验一个摘要可省常量，但要另订碰撞与认证合同；把校验移到 overlay 自己执行，或把所有失败清理省掉，都不满足本题的第一跳要求。即便小型启动器以后压到 160 B，其余 124 B 也不能未经证明就容纳全部 native 适配和退出合同。

overlay 内沿用原 a/b/c 代码预算：core 1180–1956 B、v4 448–720 B、probe 128–224 B，合计 1756–2900 B。另给 PIC/GOT、context/entry 适配、加载后协调预留 256–640 B，加固定头/表 160 B，得到 2172–3700 B 的主体预算。还须解决旧 UI/deep 的耦合：现有 `rfw_open` 单函数在 map 中占 1132 B，不能假定复制/拆分它没有代价。暂给 UI 协调和所需 helper 额外 512–2048 B，文件规划为 2684–5748 B。因此建议先以 8 KiB 文件上限设计；4 KiB 仅是需要后续尺寸证明的优化目标。

若选择 resident 拆分 UI 服务，新增常驻净字节也必须另记，不能算在 overlay 的这项余量里。若后续移动原 2j 实现，须单独核算 fallback，不能同时声称它已搬走且无卡时仍存在。以上数值都没有 PIC 编译产物支撑。

### 5.3 只使用已能解释的空间

已证明的 A 类仍是 8 B、20 B、256 B 三块，共 284 B，最大连续块 256 B，地址分别为 `[0x20053E64,0x20053E6C)`、`[0x200546EC,0x20054700)`、`[0x20054700,0x20054800)`。末块当前仍有 probe reserve 合同，必须由后续集成明确退役；本轮没有覆盖它。

现有 20 B 可规划 16 B root，8 B 可放固定标识或短跳板，尾部 256 B 留给 bootstrap。但这个分配不能容纳上述完整方案。当前没有一张“所有新常驻内容都落在已证空间内”的可批准 placement map，不能靠把尾部当成连续 284 B 来过关。

若坚持完全避开未知区，后续需要在同一批已归扩展所有的 8340 B payload 容量内，重构并静态证明至少约 380–784 B 的净回收，再补齐碎片化、跳板和对齐余量，保留完整 2j fallback；或者实证一个更小的 resident 设计。这里没有宣称已找到这些可回收字节。本轮不做构建，也不拿原生别处的长零串当免费空间。

结论分两层：overlay 在架构上消除了对段 7/10/13 存放 a/b/c 主体的需求；当前 284 B 约束下，尚未证明能实现整个 resident，因此还不能宣布空间阻塞已解除。该替代方案不申请这三个未知区，也不依赖以后把它们证明为空闲。

## 6. 故障和恢复边界

| 故障 | 已设计的行为 | 不能承诺的部分 |
| --- | --- | --- |
| 缺失、短读、超长、CRC/版本/ABI 不符。 | 不执行任何 overlay 指令，关闭文件、释放私有块，干净会话走 2j。 | 原生 IO 若自身永久阻塞，菜单任务何时被 watchdog 处理尚未证。 |
| 分配失败、init 正常返回失败。 | 不发布 root；init 合同禁止修改 unit/S，按同一家族释放。 | init 违反合同、写坏 resident 或不返回，不是普通错误返回。 |
| 运行中 RPC 错误、恢复读回不符。 | 原 2k UNKNOWN/dirty 与有界退出合同继续生效，保存全部恢复材料。 | overlay 不是额外的远端隔离层，不解决 ISP reader、迟到应答或 cursor 竞争的未知。 |
| overlay 代码异常或死循环。 | 首次加载发生在菜单事件之后，resident boot 路径没有装载/调用 overlay。 | 尚无异常隔离、任务 6 强制终止后安全回收或 watchdog 时限证明；不能承诺任意崩溃后仍可安全继续。 |
| 从卡上删除 BIN。 | 下次干净启动和菜单事件不再加载它，走 2j。已载会话中不 free 代码。 | 删除文件不恢复已写 unit RAM/T，也不撤销已保存的 S。 |
| body 暖重启，unit 未重启。 | 必须识别为代次不明，不能凭空 root 当作已恢复。 | 仅含旧 2j 的 fallback 不认识 D8/T2 journal，不能独自还原这些行。 |

“移除文件能恢复 2j 行为”只在未执行 overlay，或已完成全部恢复并读回的边界成立。对已经崩溃且丢失 journal 的会话，这个承诺不成立。要覆盖该情况，需要经过验证的完整 body+unit 冷启动重载，或一个能在 overlay 缺失时独立运行的 resident emergency restorer。后者还要保留可信 journal、会话代次和通信恢复合同，体积不在当前 664–1068 B 预算内，更不可能当作零字节附带功能。

本轮没有验证强制断电的真实复位范围。完整断电后让官方初始化重新建立 unit RAM，是后续恢复验收候选，不把它写成已上机证实的事实。CRC、版本检查、菜单才加载，可以排除很多坏文件进入代码；它们不能把同权限机器码变成可捕获、可回滚的沙箱。

## 7. 下一步的验证与推进顺序

先做不触机的静态闭合。确定 body 的具体 CPU/SoC 与早期保护设置，沿内核/启动路径核对页表、地址别名、总线取指限制；取得 cache 位定义及完成合同。核对主堆初始化和释放的完整交叉引用、分配串行化，及 sleep/wake 的 heap 代次。然后仅在已归扩展所有的 payload 内给出完整 resident placement、PIC/ABI/入口审计和 fallback 差异证据。

以后若单独获准只读上机，可以读取实际保护/映射和 cache 状态，并对主堆边界、空闲链总量与最大连续块做一致快照。当前未确认一个现成、稳定、只读的“堆剩余+执行权限”诊断 API，不能把未审计的 `cache` 命令当查询来运行。自由变化的链表需要一致性条件，静态一次相机 RAM 快照也不代表模式切换峰值。

只读读取本身不能证明真实取指成功，除非完整硬件权限模型已足以作出判断。若还需要“分配、写入最小函数、cache 同步、调用、校验返回”的实验，那已经是新固件执行探针，须另立任务，不能叫零风险只读验证。本轮没有做该实验。

host 计划沿用 `firmware/stage2j/tests/equiv_driver.c` 的用户入口转录，新增以下行为检查，正式代码以后才实现和运行。

- 无文件、无卡、坏 CRC/ABI、非法长度/入口、超长和短读、close 失败、两次分配任一次失败，都必须得到相同的 2j S/菜单/grain 转录，且没有 overlay 调用或多余 RPC。
- 用宿主函数替身代替机器码，记录 read、完整校验、cache、init、publish 的先后；故意让任一步失败，证明不会提前发布。假 cache 函数只能验证顺序，不能证明硬件同步。
- 在两个以上基址检验相对入口/GOT/内部数据引用，覆盖跨 64 KiB 边界；静态 relocation 审计是独立 gate，不让宿主 C 指针代替 M32R 证据。
- 覆盖菜单 view 丢失、重入、卡消失/更换、模式、四个直接回放 caller、teardown、sleep/wake 代次失效；active/unknown 时不能 free、热载或静默 fallback。
- 原 a/b/c 的失败注入、恢复读回、S+0x645/646、native 并发和 mutex-failure 检查继续执行。对进入 overlay 后不返回的情形，host 只能标记未覆盖，不能模拟一个假 watchdog 后宣布恢复通过。

建议分阶段推进，每阶段都保留恢复边界。

| 阶段 | 开放能力 | 进入下一阶段前的证据与恢复边界 |
| --- | --- | --- |
| 0，静态设计。 | 本报告与数据格式模型。 | 现在停在这里。主堆执行/cache、resident 空间、休眠和异常边界未闭合。 |
| 1，另行授权的 loader 空操作探针。 | 只验证 RAM 取指、cache、PIC 和缺文件 fallback，不改 unit/S。 | 完整性失败不执行；成功代码也不能写 unit。崩溃后的 boot/移除文件路径需要实测。 |
| 2，D8/T2 小幅 probe。 | 复用 beyond24 的 test slots、白名单、restore/readback；a 的共同安全机制必须存在。 | 每次保持完整恢复材料，退出与 04 读回均通过才算结束；失联停在 UNKNOWN。 |
| 3，core 与 daily T1。 | findings 1/2/3、F6/F7/S3、锁失败、全部生命周期恢复。 | 逐项通过实际菜单/模式/回放/关机，sleep/wake 和 watchdog 未解决时不称 daily ready。 |
| 4，daily v4 与后续卡文件更新。 | 已验收的 D8/T2 配方；同 ABI 下仅换 BIN。 | 仅在已恢复的干净会话更新；保留不带 BIN、带 v3 表的 2j 卡。其恢复效力不延伸到未恢复的 unit 暖会话。 |

overlay 加载增加菜单 IO、分配和 CRC 时间，本轮没有量测毫秒。加载后每个事件多一次 resident 间接分发，不需要因此增加 unit RPC；D8/T2 切换的 RPC 数仍按原 [REPORT.md](REPORT.md) 的事务计算。所有原来尚未证明的 unit reader gate、T2 选择缓存寿命、远端完成和 watchdog 截止条件仍保留。

## 8. 本轮交付与证据分层

静态确认的新增事实是主堆 first-fit/块头/合并与跟踪包装区别、原生内联 cache 序列、独立低地址程序中的 cache 函数所属环境、既有 2j layout/map，以及本机 GCC 的 PIC 支持机制。文件布局、ABI、RAM/代码预算、resident 分工和恢复策略是设计提案。主堆可执行、完整 I/D 同步、task-6 cache 安全、实机剩余内存、休眠保留、异常/watchdog 恢复和 284 B 装入均未验证。
