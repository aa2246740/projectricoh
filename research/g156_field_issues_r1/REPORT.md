### 接管链与 release/test 差异

代码路径为：原厂首次待机触发 H50，resident 初始化并锁存 BOOT pending；H51 消费它，先尝试装载 DAT，再调用 BOOT_RUN；首次 Image ADJ 的 H01 重新检查 resident、调用 DAT 菜单，最后确认已经发布自己的八个物理行。H02/H05/H06/H07/H08 只有在该列表归属成立时才续接 DAT。

装载先试卡上的 DAT，再按规则试两个 IROM 槽。它核对文件长度、完整读取与 EOF、SD 身份、body/resident/ABI 身份、CRC、区段与重定位；DAT 的纯初始化还核对单元身份、原厂 pin、数据语义及 UI。RPC 或单元未发布的早期情况可以暂不消费装载机会，但进入正式装载后，失败会走退役。不存在“换个文件时间即可通过身份门”的规则。

首次菜单发布还要求 Image ADJ 的状态、activity、菜单层、栈顶、原厂描述符和行数符合已知合同。期间的 RPC 可以让出执行；发布边界会再次检查。第一次遇到的真实菜单对象、MOUNT 能力状态或构造时序与模型不同，就可能让 DAT 放弃本次接管。某些 UI 拒绝仍保留 READY，退出重入可以重试；装载失败、会话/代码/单元检查失败或硬 BOOT 故障会退役，普通重入不能解除。

| 差异 | release | test |
| --- | --- | --- |
| resident 的首次装载机会 | H51，同一机身路径。 | H51，同一机身路径。 |
| BOOT_RUN | 返回正常 PASS / UNSUPPORTED，零颜色写。这个返回本身不会退役。 | 初始资格不符时正常跳过；有效记录可以进入完整恢复事务。 |
| 首次菜单的旧记忆路径 | 仍走旧预选，只支持内置条目，并受 Standard/WB/纯原厂状态门限制。 | BOOT 已处理时使用其结果；初始 BOOT 提前跳过时仍可能落回旧首次菜单路径。 |
| 数据布局 | 19 个全局 Look 描述符，每单元可见 10 个。 | 17 个全局 Look 描述符，每单元可见 10 个，另有三个用户条目。 |

两包使用同一代数和同一 body/resident/ABI 接受合同。release 更小，因此“test 能装，release 因容量更大装不下”不成立。两包的配方数据、flags 和全局索引确实不同，不能把它们当成只差一个 BOOT 开关的二进制。

### 完整 S 重放与新增现场主线

`local/persistence_chain.py` 从新 MAIN 运行实际 GPIO 选择和关闭，导出完整 4096 B S。原样组直接将该文件作为下一台新 Machine 的逻辑设置读取输入，不改记录、任何设置或整块校验。另建仅更新最后 4 B 原厂整块校验的对照，不能把它标为原样重放。源会话分别来自 test 和 release，覆盖 HC BW、能保存的 Portra、不能保存的 LowSat，以及 OK 和 ADJ 关闭，共 12 条。每条又分别进入 test 和 release 的两种输入组，共 48 次新 MAIN。

严格快模型的 48 次全部完成，原样 24 次、仅更新整块校验 24 次，首次菜单均为 DAT 八行、resident READY，没有复现掉表。全部原样源块的整块校验都已过时，原厂启动拒绝后尾部变为零；校验对照的 40 B 全部保留。匹配 test 身份的六条对照还分别验证了完整 552 B BOOT 目标，其余输入按 release 关闭策略或身份不匹配跳过。LowSat 源会话保留的是先前可保存的 Look，并没有因此变成 LowSat 的记忆。独立回执为 `local/persistence-verification.json`。

| --- | --- | --- |
| test，HC BW，OK 与 ADJ | 4 次均接管；原记录被原厂校验拒绝。 | 4 次均接管；同包 test 恢复 HC BW，release 忽略不配对记录。 |
| release，HC BW，OK 与 ADJ | 4 次均接管；原记录被原厂校验拒绝。 | 4 次均接管；记录保留，test 身份不配对，release 原本不自动套用。 |

这反证“只要保存了这些会话的 S/记录，下一次必然掉表”，但没有否定朋友某个尚未取得的真实持久输入或单元状态。参考后端另完成有效完整 S 的 test 自动恢复、release 原样块拒绝、release 有效记录只预选三条复核。连同 activity 和模式早退，共五组快/参考对照，冷启动与首菜单的完整 4096 B S、完整 552 B 引擎状态均逐字节一致。test 有效输入还独立读回单元九行与 T，完整恢复 HC BW。见 `local/boot-observations.json`。

首组 HC BW + OK 的两份源会话中，原样 S 的记录 CRC 正确，整块原厂校验已过时。原厂冷启动会丢弃该块，新记录也不再出现；DAT 列表仍接管。只修整块校验后，记录保留，匹配的 test 确实恢复 HC BW，列表仍接管。这个对照限制了结论：原样坏校验块没有复现现场，不能用“读不到记录”假充“测试过有效恢复”。

BOOT pending/attempted/dirty/guard 是 resident 的 RAM 字段，不在这 4096 B S 或 40 B 记录中。新 MAIN 会重载它们的初始字节。当前代码没有把它们写入 NAND 的路径；若普通开关机实际保留部分 RAM，则需要另外验证，S 重放本身不覆盖该情况。单元九行和 T 同样不是 S 的那 40 B，协议模型默认从声明的原厂单元状态开始，未证明实机关机后的单元状态相同。

“release 开一次，再换回 test”有明确的代码效果：release 关闭 BOOT，两个包的 CRC 绑定不同，test 的记录在 release 下只会被忽略。普通开机没有删除或改写旧 40 B 记录的产品路径。因此仅换包本身不能被说成“清掉 NAND 记忆”；是否还改变了原厂设置、单元初始化、供电或存储时序，要靠完整链对照区分。

### FAT、时间戳与第一次开机

resident 不按根目录文件数量、FAT 簇连续性或时间戳决定 DAT 身份。严格快模型中，DAT 放到第 41 个根目录项、使用不连续簇和非默认时间戳，两包都接管；另以完整 29 个既有升级文件加 release DAT 的 FAT16 媒体普通开机，release 也接管。这没有执行升级，不能覆盖真实卡控制器、FAT32/exFAT、Mac 的全部文件或升级后的首次启动。原计划的参考媒体运行已为完整 S 主线让位，中止项不计通过。新现场说明卡未变也会第二次失败，所以媒体布局退为次要调查线。

H51 只消费一次首次待机机会。模型普通开机的首次 activity 是 0，实机未测；一个非零值本身只会让 test 不自动套用。装载发生在该资格检查之前，因此“首次待机不合格”与“当时根本不该进行一次不可重试的文件装载”要分别记录。后续 ADJ 退出的 state 32→5 不是新的开机。

边界挑战也已实测：在 H51 把 activity 声明为 6，test 跳过 BOOT，随后仍发布八行，单元 W 为零；在原厂 Image 构造边界把原始行数声明为 6，DAT 列表发布失败，但 resident 仍为 READY。缺 DAT 则进入本次禁用，后续菜单维持原厂列表。这些挑战证明可产生相似外观的不同分支，不能把声明值冒充机主的实际值。

另查出一个 host/target 不一致：装载前的两个 ready 原始值在目标代码用位与，`RV_HOST` 却分别按非零判断。独立参考 ISA 对当前机身真实 loader 的 7 组输入验证，两个非零但无共同置位的组合被目标拒绝、host 接受。当前整机正常模型的两个值均为 1；已知原生发布路径也写 1，尚未证明实机会出现那两个反例，因此这是必须修齐的合同差异，不是本案已定位原因。完整值、函数字节对应关系及回执在 `local/readiness-boundary.json`，公开报告不附固件地址或反汇编。

## Q2：Unsaved 的确切原因

代码根因已经锁定。`memory_build` 保存的是全局 Look 索引，保存服务 `owned_record` 却只认最早十个全局 Look。g156 把相同名字按单元拆成不同记录后，后面的有效 Look 超过了这条硬编码上限。op 5 在写 40 B 尾部之前就返回 `RV_ARGUMENT`，不是 NAND 空间不足，也不是颜色应用失败。

`apply_impl` 把这一返回记为 `memory_dirty=1`，但它不是未知尾部的 CONFLICT，所以没有永久阻止重试。后续边界仍可能重复尝试；列表的 `eng_memory_pending()` 因而显示 `>Unsaved`。颜色提交与保存意愿是两条独立路径。

这一 ARGUMENT 不会被当作颜色事务故障返回，也不会直接退役 resident。它解释 Unsaved 和旧记录残留，不能直接拿来解释 Q1 的列表消失。

| 包 | 不能写入新记忆记录的 Look | 单元 |
| --- | --- | --- |
| g156 test | HNCS LowSat、Vision3 500T、instax mini、Metropolis。 | 50mm、28mm、MOUNT 全部。 |
| g156 release | Kodachrome25，再加 test 上述四条。 | 50mm、28mm、MOUNT 全部。 |

其他六条 test / 五条 release 的记录索引通过这条分类器，不代表所有可能的 BUSY、epoch、未知尾部和真实关机路径都通过。

独立参考 ISA 实测：两包 × 三单元 × 十条，共 60 例，逐条执行最终 DAT 的 `memory_build` 和 `owned_record`。新记录均逐字节等于独立构造的完整 40 B，分类器 33 例接受、27 例拒绝，精确覆盖上表。见 `local/boundary.json`、`local/boundary.py`。这里实际执行了分类器；op 5 随后返回 ARGUMENT 的含义另由服务源码确定，没有伪造整机服务成功。

严格冷启动快模型观察了 MOUNT 十条、50mm 十条与 28mm 五条；MOUNT 整机参考后端也逐条观察了十条，四个 Unsaved Look 全部复现。test 的失败条目完整 552 B 颜色状态正确，dirty 为 1、blocked 为 0，旧记录仍是之前的 Kodachrome25。独立审计重放四组实际 RPC 日志，35 个观察点的九行和 T 均按选择顺序达到目标，行边界半字中范围外的相邻字节保持；完整记录也另行构造并逐字节核对。见 `local/audit-results.json`。

MOUNT 的原驱动在最终汇总遇到 JSON tuple-key 序列化错误，原始 result 仍显示 RUNNING，缺最后关闭及后端收尾回执；不能把该作业写成整流程 PASS。其十条已保存的样本、实际 RPC 与导出 S 已被独立审计，足以支持四条 Unsaved 的观察。28mm、50mm 修正后的快模型作业有完整结束回执。另一个可选 50mm 参考作业已为 Q1 持久链优先级终止，不计通过。边界与处置见 `local/run-disposition.json`。

关机含义必须分开：这些失败 Look 的新意愿连 RAM 尾部都没写入，所以当前代码不可能通过这条记录保存和恢复它。旧有效记录会留下；如果相机后来确实把该 S 保存到 NAND，下次 test 可能恢复旧 Look，而不是刚选的 Unsaved Look。若尾部原为空，则没有这条 Look 的恢复记录。release 即使成功保存某个 Look，当前 BOOT 关闭，旧首次菜单预选又只读内置项，不能据此期待 Look 自动恢复。真实 NAND flush 和掉电保存仍未测；导出 S 的新冷启动重放会单独标明。

## Q3：八个 Look 在哪里丢失，能否恢复

不是 g155c 或 g156 才删的。G154L 是 `engine_v65_g154_looks` 的独立 18 项包；g155 从原十项 `engine_v63_g154` 主线构建成 `engine_v64_g155`，g155b 再复制 v64，g155c 沿用它，g156 又明确只替换已有槽位。实际七份 DAT 的清单与此一致。g155 的 `looks_data.py` 仍读原十项输入，没有接入 G154L 的扩展选择。

丢失的八项为 Agfa LeBox、Y2K Plady、QianXi A、QianXi B、ARRI 709、Eterna BB、RED IPP2、Acros。没有找到复审淘汰或有意下架这八项的记录；可确认的是构建来源没有继承它们。g156 排除某些 flags 不兼容的新拟合候选，是另一个决定，不能拿来解释旧八项早已不存在。

容量也不是当时必须删除它们的理由。只恢复旧八项、保留原功能并按实际行去重时，g155b release/test 的主请求分别是 104,588 / 107,512 B，余 3,024 / 100 B；g155c 分别是 104,668 / 107,588 B，余 2,944 / 24 B。这是静态容量结论，test 的余量很小，不是重新构建或验收过这四个扩展包。

当前 g156 的恢复净增为 1,640 B，由八个描述符和新增共享行组成，不能按八份 552 B 简单相加。test 可以在内存整理后完整恢复。release 还存在 50mm Acros 的 flags 冲突：旧 Acros 依赖旧 HC BW 基底的 flags，g156 release 的 50mm HC BW 与 Tri-X 已成组换成另一种 flags。不能只改校验器放行，也不能只翻 Acros 的 flags。

可执行选择有两种：统一采用当前 test 的兼容数据布局，保留机主正在使用的 HC BW/Tri-X；或在 release 数据布局中把 50mm HC BW/Tri-X 成组退回旧兼容记录。若坚持保留 release 两条新拟合记录，就必须另做兼容 Acros 的完整重拟合与验收，本轮没有这份现成记录。

`local/plan_manifest.py` 另生成了可执行选项清单 `local/g157-selection-plan.json`：27 个全局描述符，每单元 18 个 Look、8 个内置、3 个用户项，共 30 个逻辑行，仍为八个物理行。清单逐项给出来源、完整记录 SHA、mask 与记忆全局索引，所有 flags 与基底相容。它只记录既有数据的选择方案，没有生成新 DAT。

## Q4：g157 的可执行设计

### 单一状态所有者与记录读取

保留 40 B v3 记录格式。由一个 `memory_codec` 定义分类范围、完整标志、单元和 CRC；不要让服务边界与引擎再各自维护“十个 Look”的常量。自有旧尾部的识别与当前 DAT 的语义解码分开，前者允许安全替换旧自有记录，后者必须再验证本 DAT 身份、实际全局索引、单元 mask 和合法档位。

把启动逻辑拆为三个结果对象，而不是一个 `restore_done`。

```c
SavedSelection memory_read(const SettingsLease *s, const ValidatedImage *image);
AutoDecision auto_decide(const SavedSelection *saved, const NativeSnapshot *now);
ApplyResult auto_apply(const AutoDecision *decision);
```

`memory_read` 只读并填缓存，能处理内置、Look 和用户条目。CRC、DAT 身份、单元或档位不合法时不加载；未知尾部不覆盖。当前 WB 不居中或图像设定不同，不再阻止读回已验证的保存值。`auto_decide` 另给出明确原因，不能把“已读回”画成“颜色已生效”。原厂状态与 DAT 没有建立有效颜色基线时，显示 Native / 未应用，不冒充纯 04。

自动套用继续要求已验证的启动来源、模式、对象/epoch、原厂锁，以及完整原厂行/T 的双读。WB 或原厂图像设定是用户后来改的，就保留用户选择；用户明确选择“应用保存值”才走正常完整事务。WB 归中不能触发无提示的自动重试，也不能被当作解除 resident 退役的办法。

### BOOT 与 resident

完整需求需要一个 DAT 加一个配套 resident 诊断版本。只换 DAT 可以修记录和数据布局，但 DAT 未装载或 resident 已退役时，它没有机会画拒收原因。因此“只允许现有 v3.10 机身、却要求任何 DAT 拒收都能拍到码”无法同时实现。

配套 resident 应分别记录首次 H50、H51、装载阶段和 H01 发布阶段；先保存第一个失败原因，再执行退役，不能让通用 STALE 覆盖具体原因。装载未开始前的单元/存储未就绪，使用独立的 WAIT 状态与一次有界重试机会；已发布、发生颜色写入、身份/CRC 不符或 DIRTY/GUARD 的会话继续保持现有退役保护，不热重用旧块。

BOOT 的自动套用仍只尝试一次完整事务。若装载晚到首次菜单，就读回并提示“启动时未就绪”，不要在菜单中补做一次隐式自动套用。真正硬故障仍保留 DIRTY/GUARD 与现有快门约束。Q1 现场码未定位前，不能扩大 activity、原生菜单对象或行数白名单来打开发布版 BOOT。

M 档必须成为 g157 的实际验收输入：先闭合其原厂选择、内部模式及子模式，再在 BOOT 入口和事务复核中共用同一规则。不能继续只用模型的唯一允许组合，便宣称已覆盖机主的 M 档；也不能为支持 M 直接改成“非 MY 都放行”。模式与 activity 同时不合格时，诊断保留两者，避免只看到第一处短路原因。

当前 resident 代码窗口本来只余很少空间，新增显示逻辑必须另做机身代码布局审查；本轮没有证明它能塞进现有窗口，也没有改信任身份。诊断页必须在 DAT 缺席或退役时仍可工作，且不依赖文件日志、DAT 堆块或修复一半的菜单对象。

既有严格链接的 resident 布局中，默认代码 7,968 B、只余 92 B；单内置副本布局余 272 B，卡上 DAT 单一来源布局余 608 B。可以把“仅卡 resident + 最小原因页”作为配套机身的容量退路，代价是放弃内置 DAT 回退；608 B 仍不是渲染器已经装得下的证据。优先把既有单项环形事件及计数区改成一次锁存的紧凑故障记录，完整细节留在已加载 DAT 的诊断区，避免扩大 root 或抢用未知原厂 RAM。默认布局若保不住，应先在独立机身设计中裁定这个取舍，不悄悄放大代码窗口。

### 可拍摄诊断码

成功接管时显示短码，例如 `G157 R03 WB`；拒收时由配套 resident 显示 `B311 L21`，下一行显示 `A08 V56 N06`。单行最多 13 个可见字符，使用独立详情页展示阶段、activity/state、原厂列表形状和退役原因。DAT 代数从已核对的头读取，并附 payload CRC 短码；未读到头时显示未知，不谎称正在运行 g157。不能为诊断增加第九个物理行或改变现有八行光标合同。

首次异常码锁存到本次断电前，后续退出菜单不覆盖它。已知待机上下文自动提示一次，并可用约定的 `MENU+DISP` 进入 resident 自己的详情页；这条入口必须在 DAT 缺席或退役时仍工作。未知菜单对象里只锁存原因，回到安全待机再画，不继续借用失败对象。机主拍屏即可，不要求记操作顺序。B311 是建议的新 body 标记，不表示本轮已经生成该机身版本。

| 码组 | 诊断含义 |
| --- | --- |
| L01/L02/L03 | 存储/单元未就绪；打开/完整读取失败；身份、CRC 或布局拒收。 |
| L10/L11 | 分配或 DAT 纯初始化失败；会话/代码/单元检查导致退役。 |
| L20/L21/L22 | 首次 Image 上下文、原厂描述符/行数、菜单栈/归属不符合。 |
| R00/R01 | 没有合法保存项；已读回并已自动套用。 |
| R02/R03/R04 | 原厂图像设定不同；WB 非中性；记录身份/CRC/单元不符。 |
| R05/R06/R07 | 模式或启动来源未确认；启动时未就绪/未在自动窗口完成；恢复事务失败。 |
| M01/M02/M03 | 原厂锁忙；未知尾部不能覆盖；记录索引/结构错误。 |

码是设计，不是现有 g156 已有的功能。记录错误显示具体 M 码并保留原记录；Busy 可以在下次用户边界重试，永久结构错误不无限重试。现有 `ERR` 文本只覆盖部分已进入 DAT 的不确定颜色故障，不能代替装载诊断。

针对机主这次“预选正常但未自动套用”，还必须在 `boot_run` 的现有提前返回之前记录独立的 B 码：B01 为未派发；B10 为首次 activity；B11 为模式/选择组合；B12 为 MY；B13 为模式切换 pending；B14 为 S 对象；B15 为非预期待机状态。进入恢复后，B20/B21/B22/B23 分别区分 S 资格、记录、完整行/T、原厂锁，B30/B31 区分事务失去上下文和写入/补偿错误。

一次锁存首个原因及全部不合格位，保留 H50、H51、DAT BOOT 入口、`eng_boot_run` 四个“到过”位和当时的模式、子模式、activity、state。不能等 H01 才重新读取并把菜单 activity 当作开机原因。干净跳过后的首次 ADJ 先显示完整八行诊断页，包含“记忆 03、当前 04”，OK 再进入原列表；每次开机只显示一次，之后可从状态入口再看。这样一张屏幕照片就包含原因，既不要求用户记操作，也不靠滚到隐藏的尾行。细分表和实现连接点见 `local/G157_DESIGN.md`。

### 配方与取舍

恢复八项使用 G154L 的完整旧行与元数据归属，不混入同名但 flags 不兼容的新照片拟合候选。推荐混合布局通过成组退回旧 50mm HC BW/Tri-X 解决 Acros 冲突；这两条与机主当前 test 相同，却会放弃 release 的这两条优化，不能隐瞒这个取舍。28mm 只换入报告已交接的 HNCS LowSat、01 GRPos、06 F-CN、08 L-Viv 四条，分别核对冻结的完整 552 B；不顺便加入其余未过兼容性门的候选。

28mm 这四条是更新既有条目：HNCS LowSat 换同名 Look，01/06/08 换现有内置配方，菜单不增加四个同名副本。恢复八项后每单元仍是 18 个 Look，容量表已经按这个清单计算。

保留 50mm Metropolis。新增同样本对照见 `local/metro-compare.json`：同一批 27 张 ISO200、2,592 个点，g156 比 g155c 高 0.0715 pp，4/27 张照片回退；266 张其他 ISO 组高 0.1161 pp，仅作迁移诊断。计算先逐值复现既有 g156 评分，再比较旧版，未重拟合、未选参数。旧报告中下降 2.642 pp 是不同照片集的变化，不能称作版本退化。删该单元项只省 128 B，推荐布局不需要这项损失。

若最终链接超限，按顺序处理：先删掉旧黑匣子死代码并合并重复记录解码；再考虑减少未使用的用户格式槽/缓存并同步所有解析合同；仍超限才减少发布配方。不要扩大 resident/文件/代码限额、弱化 flags 检查，或先删用户明确要求恢复的八项。完整 BOOT 的现场条件未闭合时，先交诊断与只读缓存候选，自动套用保持关闭。

### 交给实现者的验收顺序

1. 固定统一清单、三单元槽位/mask 和记录 SHA，先让生成器拒绝漏项、flags 不兼容、重复索引和越界；原厂 04 与未选记录维持原语义。g157 必须同步更新 `gate.c`、`eng_data_accept` 和 `uv_validate` 的三处代数门，不能只改 DAT 头；配套 resident 改动后也必须重新绑定实际 body/build/ABI 身份。
2. 改记录分类器和独立读取。用最高合法全局 Look、非法下标、未知尾部、坏 CRC、跨单元、旧 DAT 记录验证边界；逐条选择后检查完整 40 B，不能只看 dirty 消失。
