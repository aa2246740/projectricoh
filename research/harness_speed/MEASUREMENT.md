# 测量口径

要验证的判断是：同一 DAT、单元、CRC 模式和旧验收入口下，新后端减少执行成本，
验收 JSON 的值不变。完整组分别记录单次观察，不把它们称为稳定中位数。
合成热循环运行五组交替配对，分别检查映射缓存、寄存器解析缓存和统计开关。

所有 Python 使用 `/usr/bin/python3 -I -B`。调度只有一个测试 worker。
旧入口自身的串行 fork 和同步工具调用保留。JSON 结果、返回码和测试断言
用于判断有没有执行真实验收；没有验收结果的空跑不算通过。

完整组的总 CPU 为 worker 自身 CPU 加已回收子进程的用户态/内核态 CPU。
墙钟单独记录。fork 子用例在退出前保存自身的阶段记录，避免只统计父进程。
`boot` 包含装入、ADJ 父页和另一列表的构造；首次 `publish` 包含实际 loader
和首发。两者相加只用于报告前缀占比。后续 `publish` 作为重开单列。

解释器调用时间包含设备模型回调。设备回调又包含 RPC，故这些是嵌套口径，
不能直接相加。JSON 编码和 `Path.write_text` 计时单列。
合成热循环预先完成译码，计时区间内实际执行固定数量的 M32R 指令，并检查
停止原因、指令数和最终寄存器。进程启动由五次空 Python 子进程作独立控制。

cProfile 仅采集每个指定组开头最多 30 秒，主要定位装入与首次发布阶段。
这类运行不用于完整组的提速比值。首发之后的整组占比使用阶段计时，
不把 30 秒样本的函数比例扩展成整组比例。

`compare.py` 对验收 JSON 递归检查类型、键、顺序、长度和值，只移除代码中
明确列出的耗时字段。T、RPC、PC、代号、状态、返回值和错误记录都保留。
输入/源码身份文件单独保留，不拿新旧源码 SHA 必然不同当成产品结果变化。
接口观察文件中 Python 对象地址的差异单独报告，不改写成相同。

完整回归的节省时间只作推断。以用户给定的 34,000 CPU 秒乘以代表组实测
CPU 比值，另给三 worker 理想分摊的墙钟数；没有运行 81 组就不宣称实测整体用时。
