## 时间拆分

三个组都采集开头最多 30 秒的 cProfile 样本，完整阶段用 wall 和进程 CPU 计时。
总 CPU 包括已回收子进程。详细口径见 `MEASUREMENT.md`，数据见 `measurements.json`。
带 cProfile 的完整组耗时不用于提速比值。values 的剖析样本来自工具准备运行的首发
阶段，之后该准备运行在参考库编译时失败；完整成功基准是后续独立运行。

| 新版代表组 | 总 CPU 秒 | 解释器指令数 | 装入/准备/首发 CPU 秒 | 首发前缀占比 | 后续重开 CPU 秒 |
| --- | ---: | ---: | ---: | ---: | ---: |
| safety，50mm | 206.99 | 34,409,620 | 41.91 | 20.25% | 83.51 |
| values，50mm，all 原型 | 645.00 | 107,290,061 | 43.92 | 6.81% | 82.98 |
| view-reentry，50mm | 459.72 | 73,336,705 | 41.05 | 8.93% | 32.07 |

本轮具体调用路径已经在 wrapper 中复用公共首发态。三个组都只记录了 1 次 boot
和 1 次首次 publish，分别有 8、7、70 个串行 fork 子用例。后续子用例重复执行完整
首发前缀为 0 次；后续重开是验收本身的行为，单独列出。因而首发模板缓存没有取得
预期的重复命中收益，不能用背景中的原始重复成本直接宣称缓存提速。

三份首发样本接近一致。约 29.9 秒样本中，区域查询累计约 4.45–4.58 秒，寄存器
解析累计约 8.12–8.18 秒；两类调用树合计约 42%。指令语义函数自身仍占约 8.5 秒，
解释器循环自身约 4.3–4.5 秒。单步语义、逐次取字节和计数继续执行，限制了提速。

50mm safety 的设备回调 CPU 为 0.402 秒，其中 RPC 为 0.012 秒；JSON 编码为
0.016 秒，文件写入为 0.0048 秒。view-reentry 的对应值为 0.114、0.0155、0.236、
0.0279 秒。回调和 RPC 是嵌套口径。解释器调用计时也包含回调，部分重入调用使累计
值超过总 CPU，不能把这些累计值相加或据此声称 100% 精确占比。图形模型回调未逐个
包裹计时，其余开销仍归入解释器调用。

装入 16 段本身约 0.001 秒；包含文件校验、父页和其他列表构造的 boot 约 0.4 秒。
五次空 Python 启动控制的墙钟中位数为 0.0405 秒。JSON、日志和进程启动不是主要成本。

合成基准每项 5 次交替配对，每次实际运行 20,000 个 M32R 调用、40,000 步，失败数

## 切换与回退

1. 等 review-g129-r1、g131-merge-h07-r1、emulator-m2d-r1 全部结束，由任务负责人确认不再使用旧目录。本轮没有检查或改变这些任务。
2. 先补齐上表标记的完整配对，固定最终工具源码 SHA，保留同一 DAT、单元、CRC 参数和原入口。此项完成前不切换整个批组。
3. 新 wrapper 在首次导入前显式选择后端目录，每组启动全新进程；不能仅追加 sys.path 后继续使用旧模块。选择 region，保留覆盖、尾记录和写事件。每个 Python 子入口都经过同一版本绑定器。
4. 保留旧目录和旧 wrapper，后端选择做成显式参数。先启用已验证的直接入口，再扩大范围。

已具备可审阅的新入口示例，须用新的 name，避免覆盖记录：

```sh
sandbox-exec -f research/harness_speed/fence.sb \
  /usr/bin/python3 -I -B research/harness_speed/run_one.py \
  --side fast --mode region --name future_safety_50mm \
  research/g127_fix/run_existing.py --fast-crc \
  research/review_g126/safety_cases.py --unit 50mm
```

回退时把 side 改为 old，在新进程中运行同一命令和输入。无需恢复源码、删除缓存或
改动任何其他任务。当前已有 suite 和 wrapper 保持原样。

## 范围与过程记录

系统围栏在首次文件写入前建立，只允许两个交付目录。Ricoh 映像及译码页、二进制
中间文件只在被忽略的 local/ 中读取或保存。测试按单 worker 调度，保留旧入口自身
的串行 fork 和同步工具调用；不是严格只存在一个系统 PID。

准备阶段有 3 次自动 traceback 显示了旧脚本的栈帧行，初始化只读命令也曾短暂并行，
这两点没有满足原定输出与并发约束。之后入口只汇总名称、返回码和计数，错误不再
输出栈帧源码。旧脚本未手工打开或复制；原目录和其他任务的文件没有改动。

静态已证：缓存只改变查找/解析成本，逐次字节检查、指令语义和默认统计保留。
主机已证：上表明确列出的成功配对与局部检查。推断：完整回归约省一小时的理想
三 worker 墙钟。未知：修正后的完整 batch 配对、未标为完成的范围，以及任何相机、
存储卡、RTOS、像素或断电持久化行为。
