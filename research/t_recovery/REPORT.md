# T 参数块的官方恢复路径：完整更新每次都会重跑 ADJCOM

背景见 `research/t_persistence/REPORT.md`：T+0x2445 = 0 一旦被存下来，只刷 MAIN 救不回来。这次要回答的是，有没有官方、用户自己能跑的恢复路径。

## 主代理的定点核对

下列地址都用 `research/tooling_m32r/disasm` 的现成反汇编看过，与报告一致：
- **机身 `0x2036F244..5C`**：先调用 `0x2006015C`，再以 `r4 = 3`（机身 + 单元的更新掩码）调用 `0x2036D4E8`。
- **机身 `0x2035C970..A4`**：三处版本查询，只判断返回值是不是 -1（查询失败），不比较版本号。
- **单元 `0x2007C640..74`**：后缀 0..9 循环，只在该文件的标志字节为 0 时跳过，否则调用 `0x2007C000` 处理。
- **单元 `0x2007C120..28`**：头部类型等于 5 时跳到 `0x2007C2F0`。
- **单元 `0x2007C2F0..1C`**：打印诊断串后，直接调用文本解释器 `0x2007B9C0`；成功打印 `OK!`（`0x2007C340`），失败则 r8 = -1。中间没有版本比较。

## 结论

1. **完整官方更新每次都会执行 `jlaunch8`（ADJCOM），版本相同也不跳过。（已验证，静态）**
   - 机身和单元都已经是 1.51 时也照样执行。
   - 前提是单元更新阶段确实成功完成。卡上有这个文件，或者只完成了机身更新，都不算。
   - LCD 上没有 ADJCOM 专用的提示。
2. **ADJCOM 能修复 T+0x2445 = 0。（已验证，静态）** 执行顺序是：
   - `UEEF1`：从单元存储把整块 T 读进 RAM。它不会把 T 重置成内置默认块，因为不调用 `0x20065CA0`。
   - 5,047 条 W 写入固定常量，覆盖 10,090 B。其中 `jlaunch8` 文件偏移 `0x0C11B` 处是 `V2444`，`0x0C122` 处是 `W0002`，所以 T+0x2444 = 0、T+0x2445 = 2。
   - 重算 `0x3FFC..0x3FFF` 的校验值。
   - `UEE00` 提交（文件偏移 `0x1165E`）。
   - 存储里原有的另外 6,290 B 原样保留。固定区里如果有逐台的差异，会被常量替换。这是每次官方更新本来就会发生的事。
3. **我们的候选包也会触发 ADJCOM。（推断）** 候选包里带着官方的 `jlaunch8` 和其余单元文件，所以刷候选包也会执行它。之前每次单元更新成功完成的刷机，很可能都已经跑过 ADJCOM。具体是哪几次，无法从这里确认。
4. **可以无损快照 RAM 里的 T。**
   - 方法是 `X12C0`，然后对 `V0000..V3FFE` 逐个读取，共 8,192 次。（已验证）
   - 前提是四个记账计数 `0x2024615C..68` 都为 0。冷启动时它们是 0，只有 `UEE21/22/31/32` 会让它们递增，而我们从不发 U 命令。（推断）
   - 读到的是运行中的 RAM，不是存储镜像，也不是原子快照。2j 没有导出功能。
5. **恢复判定。**
   - 针对「只有 T+0x2445 = 0 被提交、单元仍能通信和更新」这种故障，恢复链在静态上已经闭合：刷完整包（官方恢复包或候选包都行），等单元更新完成，再冷启动。
   - 这条恢复链没有上机验证过。真要验证，就得先有一次 0 已经被存下来的状态，而故意制造这个状态正是要避免的危险操作。
   - 读一次 `V2444` 得到 0x0002，只能说明当前 RAM 正常。
