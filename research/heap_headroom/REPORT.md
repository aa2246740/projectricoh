分配器格式和检查点结果

静态已证：初始化入口为 0x2005BF00，申请为 0x2005BF5C，释放为 0x2005C038。申请入口在 0x200D3488 为零时才初始化。初始化只从 0x200C0DC0/0DC4 读取这一个池的基址和容量；0x200C0DC8/0DCC 描述的后续区间不能加进本池。证据见 [分配器窗口](local/windows/allocator.asm.txt)。

|---:|---|

| +8 | 大端 u32，包含原生块头的总跨度。 |

静态已证：请求必须为正且严格小于 262,144 B。底层需要 align4(request)+12 B，按地址顺序取第一个足够大的空闲块。尾部至少剩 28 B 时分裂，否则整块发出。释放先核对指针对齐、指针在堆内、跨度为正且小于容量、状态非零、next 为零，随后按地址插入并合并两侧相邻空闲块。无效 free 直接返回，没有错误消息接口。

静态已证：0x2040E088 指向一个位于 heap base 的零跨度哨兵，真正首个空闲块在 base+12。初始化却给该块登记完整配置容量。因此自由链管理区间的末端为 heap end+12；这 12 B 差异必须保留在账上。[rv_allocation()](../../firmware/resident_v36/resident/shared.c) 还要求整块落在配置边界内，并要求实际跨度严格小于容量。

[现有设计](../knobs_v2_engine_design/DESIGN.md)给出的预算为 DAT+BSS=100,620 B，加 sizeof(RvSession)=1,104 B、状态区 6,144 B 和 UI 状态容量 256 B，主请求共 108,124 B。固定 resident 的有效主请求上限为 122,192 B，预算还低 14,068 B。该上限是格式和布局限制，不代表实时分配一定成功。

[loader.c](../../firmware/resident_v36/resident/loader.c) 保留一块 608 B 工作区，随后申请主块；[ui_prepare()](../../firmware/engine_v48_own/candidate/engine_services/services.c) 按需保留并复用一块 1,968 B UI 快照。物理视图深度 1 或 2 不会各申请一块快照。菜单关闭或会话退役不能直接把已发布主块和快照加回空闲量。

因此，已算出的较紧并存模型仅剩 6,884 B，并能构造后续原生申请失败。它不是相机实测最坏峰值。由于触发关系、碎片、额外租约和 1,247 个未解析转移候选仍未闭合，全机无条件最坏余量未知，不能给出正数保证。

错误路径和连续块的两个具体模型

调整文本读取的 open 失败路径已逐指令核对：0x200793C0 申请，0x200793DC 调 open，0x200793E4 在成功时跳往正常处理；负值沿 0x200793E8 直接跳到 0x2007954C 的函数尾，正常 free 位于 0x20079530，未经过。该函数内漏掉 free 为静态已证；上层间接回收和重复可达性未知。

若三次这样的失败各保留 32,792 B，则 108,124 B 会话剩 53,032 B，77,312 B 原生请求失败。同样条件下，75,124 B 会话还剩 86,032 B，该请求成功。此处的顺序、无上层回收和最后的日志请求都是模型前提，没有假定它们已在相机发生。不能据正常 free 位置把错误分支也当成已释放。

另用已经识别出的原生大小构造分配/释放历史，保留两个事件对象、系统日志、CLIPINFO 和一个调整任务块。申请 loader 工作区后，总空闲仍有 194,192 B，最大连续块仅 76,716 B；75,124 B 主申请通过，108,124 B 主申请失败。这是独立主机反例，说明“75 KB 长期可用”和“空闲总量够”都不足以证明 108 KB 的连续块要求。该历史的相机可达性未知，具体顺序见 [budget-results.json](budget-results.json)。

分配失败时，配方 loader 的结果较明确。[loader.c:95–111](../../firmware/resident_v36/resident/loader.c#L95) 在工作区或主块分配/核头失败时转入退役；本次开机的尝试标记保留，普通重新进菜单不会重试。预期可见结果为配方菜单未出现或回到原厂项。原生代码在若干路径没有判空，失败可能影响整机响应，无法承诺它们都只丢一条日志或出现统一错误框。真实异常屏幕、是否冻结、是否自动重启仍须设备或后续 CPU/异常模型证据。

分类结论与最短只读核对方法

安全，有对应范围内的证据支持：

- 给定 M2b 静置检查点具有单一完整空闲块；108,124 B 主块、608 B 工作区和 1,968 B 快照同时符合原生头和 loader 边界合同。检查点读取与主机模型均已验证。
- 在这三块之外，12 个已识别原生申请分别单独发生时均能成功，最大请求后仍有 74,072 B 链表余量。此结论限定为没有其他原生持有块的连续堆布局。
- 正常分配不会再次发出仍被持有的块；原生 free 能合并相邻空闲块。已有头和区间检查支持这些局部合同，不能据此宣称跨堆重建仍保留会话。

未知，需要后续证据：

| 未知问题 | 最短只读核对方法及能证明的范围 |
|---|---|
| 真机静置、首次开配方菜单时到底持有哪些块 | 用已经存在的只读 RAM 通道读 0x200D3488/8C、0x2040E088，再按 next 读每个 12 B 头；同时按跨度枚举物理块。菜单前后各取一致快照，用本报告格式解析。只读工具不做试分配、free、改配置或文件操作。可证明当时布局与连续容量。 |
| 三份事件对象、系统日志、调整任务和 CLIPINFO 是否启用 | 在同一快照中读 0x2040F688/68C/690、0x20414BE8、0x204AB6A8、0x205E4484，并按双层头核对它们是否真是活动块。槽里非零旧指针本身不是持有证据。 |
| 菜单、回放、USB 的运行期峰值 | 用户原本要做这些操作时，在操作边界取上述快照；若已有硬件执行跟踪，可在 12 个调用返回处只读记录申请大小、结果和 free。边界照片或两次快照不能排除短暂峰值。没有现成跟踪能力时，交给后续模拟器 HID、回放、USB 里程碑。 |
| 真正拍摄、格式化是否造成更高峰值 | 严格只读上机只能看半按准备、格式化确认页后取消，不能代替写照片和真正格式化的峰值。完整流程交给后续捕获/存储模拟里程碑；本轮没有执行这些操作。 |
| 调整文本错误返回是否被上层回收、能否重复进入 | 在用户已有该操作需求时，用现成只读跟踪对比函数前后空闲链和跟踪链；不要为本研究创建缺文件、修改调整文件或反复触发错误。后续模拟器可在无设备写入的模型中走 open 失败分支并查清返回上层。 |
| 108 KB 会话之后的所有原生申请是否仍足够 | 从一致只读快照复制空闲链，在电脑中按新大小计算 first-fit 和头校验，并结合调用返回处的峰值记录。一个静置快照只能给瞬时结论。最终 DAT 还需以其真实主请求和额外租约替换预算。 |
| 堆重建、休眠/恢复及其他段重载是否影响长期块 | 对正常模式往返和已有休眠动作前后只读核对边界、根、活动头及 resident 会话状态；仅边界地址相同不足以证明未重建。完整 init/清零/段重载路径仍需后续跟踪。 |

本轮没有确认用户已有哪一种只读 RAM/硬件跟踪通道。若没有，以上上机方法还不能立即执行，需要先具备该观察能力。已有 v32_load_diag 会真实申请和释放探测块，不满足这里“不改变堆”的只读定义，不能直接拿来替代。此限制来自所需证据，不要求本轮刷固件或接设备。

不安全，有静态或主机反例支持的具体做法：

- 把整块 262,144 B 账面跨度直接当作任意可写用户空间。初始化多登记 12 B，接近整池的请求还可能无法通过核头或释放检查。
- 假定调整文本读取所有错误出口都释放 32 KiB。open 失败的本函数路径明确跳过 free。若连续保留三份，则存在 75 KB 会话能容纳、108 KB 会话无法容纳同一 77,312 B 后续请求的模型反例。
- 只用空闲总量或旧 75 KB 成功来批准 108 KB 连续申请。194,192 B 总空闲、76,716 B 最大连续块的模型反例已重现。
- 在条件并存预算只剩 6,884 B 时仍要求额外 32 KiB 原生请求成功。该预算明确不足；这些条件在普通相机使用中是否同现仍未知。

复算和交付

[checkpoint.py](checkpoint.py) 只读已有检查点；[static.py](static.py) 准备本地解码输入、扫描调用和查询窗口；[budget.py](budget.py) 复算申请模型；[evidence.py](evidence.py) 冻结输入、提取窗口、比对解码字节及生成清单。它们都不导入旧研究脚本。完整复算见 [run.sh](run.sh)，只用现有 objdump 和系统 Python，所有步骤串行。

```sh
sh research/heap_headroom/run.sh
/usr/bin/shasum -a 256 -c research/heap_headroom/SHA256SUMS
```

命令从仓库根执行。run.sh 会重算本目录证据和 SHA256SUMS；只想检查交付原状时执行第二条。清单以仓库根为基准，覆盖本目录全部交付文件和被忽略的本地证据，自身除外。结果核对见 [verification.json](verification.json)；PASS 仅表示本地输入、字节、链表及模型检查通过。
