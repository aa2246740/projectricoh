# 28mm 推 ADJ 显示原厂菜单（第四轮）：g144 现场结果、候选表、g145 卡上记录

2026-10-31。本轮没有写卡，没有碰 `/Volumes/RICOHDCX`，没有 git 写操作，没有开子代理，同时最多两个测试进程；临时文件在 `/Volumes/Workspace/Scratch/tmp/projectricoh/unit28-r4`，结束时清理。没有改 g138 的目录。上一轮报告存为 `REPORT-r3-g144.md`。

## 结论

- **g144 现场结果**（B 卡 `acb44ac0…`，机身 v3.8 `d4fa3b46…`，机身是装着 50mm 刷的）：
  - 50mm：发布 S 页（IMG_6111），读数和 g142 一致（堆 206 vs 210 KiB，DAT 变大导致）。
  - 28mm：推 ADJ 三次，三次都是原厂菜单，**没有 S 页，也没有 `DIAG 144` 读数页**。
- **能排除的**：卡上文件本身坏、机身/resident 身份不符、DAT 主块太大，这几样在 50mm 上已经走通，同一张卡同一个机身，可以排除。读数页“字形转换失败”（`ov_fail=1`）也可以基本排除：同一机身、同一语言，50mm 上转换正常；28mm 读数页上唯一和单元有关的文字是单元名，已过滤成可打印字符。
- **排除不了的**（第 1 节表格）：DAT 在 28mm 上没加载、加载后在 init 前或 init 后菜单前被退役、菜单入口失败、读数页挂不上（`ov_fail=2/3`）、改从 IROM 加载别的程序。屏幕上什么都没有，这几种看起来完全一样。
- **g145（新）把证据写到卡上**，不需要拍照：
  - 一个固定文件 `/ATA1/GXRTRACE.BIN`（4,096 B），由编排者在 Mac 上放到卡上；DAT 只打开已有文件、核对长度和文件头、原地覆盖，**不新建、不改名、不删除**。
  - 每个单元一格（50mm、28mm、MOUNT、其他）；记录单元名和版本、加载时的状态（就绪字、堆、resident 状态）、每次进入菜单时 owned() 的全部输入、两个掩码、读数页是否挂上及失败码。
  - init 结束时写一次（**这是 DAT 在“加载后、第一次菜单前就被退役”时最后能写的地方**），之后每次进入菜单写一次，每次开机最多 16 次。
  - 屏幕行为和 g144 相同（50mm 照样出 S 页）。
- **它能分开的**：28mm 那一格是空的 → DAT 没执行到 init（没加载，或 init 之前失败）；只有 init 记录、没有菜单记录 → 加载后、第一次菜单前被退役；有菜单记录 → 菜单入口跑了，记录里直接给出被拒的那一项或读数页失败码。
- **它分不开的**：“没加载”和“init 之前失败”。要分这两样，只能改 resident（第 4 节），本轮只给方案，不做机身。
- **刷机时装的是哪个单元**（第 3 节）：从 loader 和就绪判断的代码看，DAT 加载依赖的都是开机后单元链路写进 RAM 的值，没有读任何随刷机保存的东西；所以没有证据说“装 28mm 再刷一次”能解决问题，不建议刷。但有一个**完全混淆的变量**：28mm 至今所有上机失败，机身都是装着 50mm 刷的。
- 包：`firmware/package_v38_diag145/SD_ROOT/`
  - `GXRCE.DAT`：29,164 B，generation 145，SHA256 `222ccf4b4f7975bc758160e184742631d4f8bf05fed968ce72483071b1a06a2b`，连续两次构建逐字节相同；
  - `GXRTRACE.BIN`：4,096 B 空白记录文件（只有文件头 `GXRT145`），SHA256 `d207116ca69b55ecc91dd5be07ef5441009ee1758c29d953e4b2f333c37c9cae`；
  - 机身沿用 v3.8，不在包里。
- 主机验收 12 组全部通过（第 5 节），S 区零写入，文件写只落在这一个文件上，没有新建/改名/删除。
- 模拟器（真实原厂 FAT 代码，官方 1.51 机身，合成 50mm 单元）确认：flags 2 打开后是原地覆盖，只改该文件自己簇里的数据扇区，目录项和 FAT 不变，冷启动重启后读回一致（第 8 节）。

## 1. 候选表（加入 g144 现场结果）

| 候选 | 50mm 出页、28mm 无页之后 | 依据 |
|---|---|---|

| DAT 主块分配失败 | **很低**：g144 主块约 49.7 KB，50mm 上加载后还剩 206 KiB；28mm 的原生堆用量没测过，不能完全排除 | `loader.c:110-111` |

| R2b 加载中途失败（读卡、`unchanged()` 发现单元快照或堆边界变化、init 前的检查） | **保留** | `loader.c:7-14,104-122`；失败即退役，重启前不再加载 |

| R5 读数页挂不上：`ov_fail=2`（保护条件）或 `=3`（原生名表不在 RAM、未对齐，或行数不在 1..8） | **保留，但偏低**：照片显示 28mm 的图像设定是标准 7 行；`ov_fail=1` 基本排除（见结论） | `diag.c` `overlay_show` |

| 打开的不是图像设定、单元身份/版本、T 值、九行数据、临时未就绪 | **已排除**（第二、三轮） | — |

**对 MOUNT 的含义**：MOUNT 走的是同一条 loader 路径、同一个 resident、同一个 DAT（单元名 `l08firm`，数据组 2），差别只在单元链路（就绪时机、单元信息包）。R2/R3 都和单元链路有关，所以 28mm 的结果**不能**外推为 MOUNT 正常，也不能外推为 MOUNT 失败。MOUNT 在 v3.8 上从没上过机，g145 的步骤里一并测。

**第 3 节提到的混淆变量**：28mm 至今所有上机失败（10-26 gen 115 / v3.4c，10-30 g137 / v3.8，10-31 g142、g144 / v3.8），机身都是装着 50mm 刷的；从没有过“机身装 28mm 刷、再用 28mm 测列表”的记录。

## 2. g145：DAT 写卡上记录

### 2.1 可行性

- **调用路径**：g145 自带四个原生文件入口桥（`bridges.S`）：open `0x200A40B4`、缓冲 read `0x200A449C`、缓冲 write `0x200A45E8`、close `0x200A437C`。没有 create（`0x200A544C`/`0x200A41AC`）、rename、delete 的入口；静态检查确认引擎里不出现这两个 create 地址，引擎里唯一的路径字符串是 `/ATA1/GXRTRACE.BIN`（`static-diag145.json`）。
- **open 的两种用法**：`dg_file_open(path,0)` 只读打开已有文件；`dg_file_open(path,2)` 打开已有文件、可写。原生 open（`0x200A40B4`）只有在 flags 含 `0x200` 时才走新建分支（`0x200A40D4..E8` → `0x200A544C`）；不含时走按名查找已有文件（`0x200A4100` → `0x200A65F8`），文件不存在就返回 −1，不会新建。gen 115 现场分析（`research/gen115_field_r1/REPORT.md:152`）已核对：底层写权限检查允许 mode 低两位非零，open 分支设 mode=2，可从头覆盖。静态检查确认 DAT 里调用 open 的三处 flags 只有 0 和 2。
- **为什么不新建**：gen 115 现场已证明 create 会给同名文件再分配一条目录项（重复项）。g145 一律不新建，文件由编排者在 Mac 上放好；文件不存在、长度不是 4,096、文件头不是 `GXRT145` 时，DAT 什么都不写，屏幕照常。
- **任务上下文和卡锁**：读写都在 H01 里进行，和 resident loader 读 GXRCE.DAT 是同一个任务、同一时刻（菜单构造器内）。原生文件 API 自己取放文件信号量 47（M2c：`0x0500D4E4/0x0500D4FC`）；如果别的任务正占着卡（例如刚拍完照在写），这一次 H01 会等它放开，菜单会晚一点出来，不会并发写。gen 115 的黑盒在现场从引擎上下文成功写过卡上文件（create+write+close），所以“DAT 上下文写卡”本身有现场先例；**open-existing 覆盖写这一条路径没有现场先例**；除静态分析和主机模型外，已在模拟器的真实原厂 FAT 代码上确认是原地覆盖（第 8 节），但还没有在相机上跑过。
- **模拟器核对**：已在批准的目录 `research/emulator_m2d/local/unit28-g145/` 里跑完，用真实的原厂 FAT 代码确认“flags 2 打开后原地覆盖、不重新分配、目录项不变、重启后读回一致”，见第 8 节。（第一版脚本 `emu_trace_file.py` 当时因为镜像路径不在允许范围而没跑，已由 `emu_g145_trace.py` 取代。）

### 2.2 记录内容（`diag.c` `TraceSlot`，解码：`decode_trace.py`）

文件 4,096 B = 64 B 文件头 + 4 格 × 1,008 B（50mm、28mm、MOUNT、其他）。每次开机只覆盖自己单元那一格，其他格原样写回。

| 内容 | 来源 |
|---|---|
| 开机次数、本次写入次数、阶段位（init / 菜单 / 发布 / 被拒 / 入口失败） | DAT 自己计数 |
| 单元名和版本（两份：原生 `0x2040F81C/0x2040F848`，resident 会话里的副本） | 记录在哪个单元上跑的 |
| init 记录 | entry_serial、resident 状态和标志、check_failure、rpc_ready、link 字、槽数、`0x200D7FD8` 原值、堆最大空闲/总空闲、主块地址和大小、generation、当时的名表/行数/kind/activity |
| 每次菜单记录（前 8 次，外加最近一次） | 进入计数、结果字母、入口是否成功、读数页是否挂上和 `ov_fail`、body/DAT 掩码、被拒次数、上一次写入的读回结果、activity、原生状态、part、count、栈顶 tag/state、kind、原生名表和行数、seed 表、resident 状态/标志/check_failure、就绪字、T、九行比对、最大空闲、视图数组、ui_restore、`0x2037F3BC`、底层 tag、屏幕上实际的名表和行数 |

每次写完会重新读出 4,096 B 逐字节比对，结果写在下一次记录里（最后一次的结果只在 RAM 里）。

## 3. 刷机时装的单元会不会影响加载（静态）

- **loader 和就绪判断读的值全部在 RAM，由开机后单元链路写入**：
  - `0x200D7FD8`（rpc_ready）：只由 `0x200935B4` 写入（`0x200935DC` `st r4`）。调用者是 HSP 链路处理：`0x2009394C`、`0x20093998`、`0x20093A30` 置 1，`0x20093B00`、`0x20094860` 置 0。
  - `0x2040F804`（link）：只由单元信息接收函数 `0x200637E0` 在 2,044 B 加和校验通过后写 1（`0x2006387C`）；校验失败时把 `0x2040F818` 起 2,048 B 填 FF、不置位（`0x2006384C..74`）。
  - 单元快照：`0x2040F818` 起的名称和版本（`resident.c:11-15`），同样来自这次开机的单元信息包。
  - 堆边界 `0x200D3488/8C`、卡上文件；没有一处读取随刷机保存的数据。
- **刷机流程写了什么**：机身确认 `0x2036D4E8` 之后按更新掩码走单元、机身或两者（`research/unit_recovery/REPORT.md:90`）；单元文件传送循环 `0x2010D4B4` 用单元信息 `+4` 的名字拼文件名（jlaunch*/qlaunch*/l08firm*），只给**当时装着的单元**写它自己的文件。机身映像 ilaunch3 无论装哪个单元都是同一份。
- **结论**：从 loader 和就绪判断的代码里，找不到“刷机时装的单元”能影响 28mm/MOUNT 加载 DAT 的路径；**不建议**为此重刷。
- **但不能说完全无关**：10-26 的 50mm 开机挂死就和“刷机时装的单元”相关（`unit-boot-hang-recovery`、`research/boot_hang_v35/REPORT.md`），那次的持久字段至今没找到。加上第 1 节的混淆变量，它是一个合理的分叉实验——**只在 g145 显示“28mm 那一格是空的”之后**才值得考虑，而且要先确认用 A 卡加 50mm 走“+ & playback”能恢复（50mm 挂死时的已知恢复办法）。

## 4. 如果 g145 显示“没执行到 init”：最小的 resident 诊断改动（只报告，不做）

- **问题**：resident 记录在 RAM 里，DAT 没加载就没人能把它写出来或显示出来。所以光“多记几个值”不够，必须让 resident 在之后某个时刻还能把 DAT 加载起来。
- **最小改动**：
  1. root 里现有的保留字（`diag_early` 4 B、`grain_bytes/grain_value` 8 B）记录：H01 调用次数、就绪字为 0 而返回的次数、最后一次 `rv_load` 的返回码和失败阶段、最后一次 check_failure（约 40 B 代码）；
  2. 第一次 H01 因“未就绪”返回后，在之后的 H09（拍摄模式初始化）或 H05（列表绘制）里，一旦两个就绪字都为 1，就补一次 `rv_load`（约 30–50 B）。这其实就是机身更新清单里的“28mm first-open fix”。
  3. 补加载成功后，g145 的 init 记录会把第 1 步的计数写到卡上。
- **大小**：约 70–90 B，v3.8 resident 余量 176 B（`research/emptystack_v38/REPORT.md`），装得下，未链接验证。
- **局限**：如果就绪字始终不为 1、加载始终失败，补加载也不会成功，这些计数还是出不来；那时只能靠机身侧显示（成本远高于上面）。
- **恢复**：刷新机身前必须确认 A 卡（Stage2l-50mm 恢复包）在手；出问题时装 50mm，开机按“+ & playback”用 A 卡刷回。

## 6. 用户步骤（不用拍照）

**准备（编排者）**：把包里的两个文件 `GXRCE.DAT`、`GXRTRACE.BIN` 放到 B 卡根目录（替换 g144 的 GXRCE.DAT），挂载后核对两个 SHA256，然后卸载。机身不刷。先告诉用户：这张卡没有配方。

1. 关机，装 **28mm**，开机，等 5 秒。推一下 ADJ，再按 ADJ 或 OK 关掉。这样做三次。关机。
2. 装 **MOUNT**，开机，等 5 秒。同样推 ADJ、按 ADJ 或 OK 关掉，三次。关机。
3. 装 **50mm**，开机，推一下 ADJ：应该看到一页英文字母和数字（第一行像 `S0001 RF`）。按 ADJ 或 OK 关掉。关机。
4. 把卡交回。

注意：

- 全程不要按左右键和上下键。
- 菜单可能比平时晚一点点出来（相机在写卡上那个小文件），是正常的。
- 不用拍屏幕，也不用拍照片。
- 如果某个单元上出现了一页字母和数字，也只要按 ADJ 或 OK 关掉，不用管。

**之后（编排者）**：从卡上拷出 `GXRTRACE.BIN`（留一份副本），用 `decode_trace.py` 解码，按第 2.3 节判读；把 g137 换回卡上之前不要删这个文件。

## 7. 要合进正式 DAT（g139）的内容

- **必须带上的规则**
  - 任何不能正常发布的显示都必须是 8 行，并且只在 `RF_PUBLISHED` 已置、READY 时才挂上，才受 resident 的 H06/H07/H08 保护（g144 的结论；7 行会让上下键直接写 `S+0x36E`）。
  - 左右键会改 `S+0x39F`（ADJ 位置，随 S 保存），这是原生导航，已接受，正式版不再试图拦截。
  - 写卡只用“打开已有文件 + 原地覆盖”，绝不对可能已存在的文件做 create（gen 115 的重复目录项）。
  - 直接调用原生字形转换只用于读数页；init 阶段不挂任何东西（那时还没有保护）。
- **28mm 修复本身**：等 g145 的卡上记录出来再定。按记录结果：
  - 只有 DAT 掩码非零：在 g139 的发布检查（`services.c` ui_list op1 / `native_seed.c`）里按具体那一位修改；
  - body 掩码非零：需要连同 resident 一起改（刷机）；
  - 只有 init 或什么都没有：需要 resident 改动（第 4 节）。
- **复审提过、正式版要处理的**
  - g137 在 T≠2 时第一次打开悄悄退回原厂，第二次打开自动全行恢复并把 T 写回 2（254 次 W）——正式版应先发布列表并显示 `!4`，由用户决定（第一轮报告）。
  - 第 8 行详情：不归属的 8 行列表上，原生 H05 读的第 8 项是相邻 kind 9 详情表的首项（当前全零），正式版发布自己的 8 行时走的是归属路径，不受影响；但不归属时依赖相邻零记录，不能当作普遍安全。
  - 堆：g137 主块 108,136 B；诊断读到 50mm 上加载后最大空闲 206 KiB。28mm/MOUNT 的值等 g145 记录（init 记录里的最大空闲）。
- **不要带进正式版的**：诊断页面、读数页、卡上记录（除非你决定正式版也要保留一个现场记录）。

### 8.2 过程和结果

### 8.3 第一次（run1）为什么没返回

- 不是哨兵问题，也不是死循环：是**模拟器默认的单次调用预算 2,000 万步**，加上**真实的原生行为**。
- 第一次的写 50mm 格之后，读回的第一次 256 B 读取在 2,000 万步时还没返回（同类读取通常 3.4 万–24 万步）。
- 第二次（run2）把单次预算放到 1.5 亿步，并每 500 万步采样一次：这次读取在第 33,839,199 步返回，结果 256 B 且内容正确。期间 Task 8 在文件信号量 47 上等待（`file-lock-wait` 于第 50,794,900 步，`signal` 于第 68,373,916 步），信号量计数为 0 约 1,760 万步；CPU 大部分时间在 Task 3（内核地址 `0x0500xxxx`），随后 Task 6 连续取放文件锁。同一时间窗里原厂建了 `CLIPINFO` 目录。也就是说，文件锁被原生的卡初始化活动占着，我们的读取在排队，最后正常完成。
- 两次运行到出事前都逐步一致（同样的步数和返回值），是确定性的。

**对相机的含义**：

- 如果原生正在用卡（例如首次建目录、刚拍完照在写），DAT 在 H01 里的文件调用会等它放开，菜单会晚出来；这和第 2.1 节说的一致。
- 卡 B 上 `DCIM`、`CLIPINFO` 早就存在，这次那种“首次建目录”的长时间占用不会再发生；但别的原生卡操作仍可能让菜单晚一点出来。

### 8.4 这次没有覆盖的

- DAT 本身在 H01 里的执行（只重放了它的调用序列）；
- v3.8 机身本身（文件路径代码与官方逐字节相同，见上表）；
- 真正的 28mm/MOUNT 单元（模拟器只有合成 jlaunch，且文件路径与单元无关）；
- 真实 SD 卡的电气、时序和断电行为。
