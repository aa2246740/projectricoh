# v3.5 机制门槛报告

结论：`STOP_AFTER_DESIGN`，不构建 v3.5。现场结果确认原生固件也会挂，resident/loader/engine 不是必要条件；但尚未锁定 50mm 冷启动到 H05 的调用，也未证明零详情表单独足以修复。因此不满足本任务“correct and sufficient boot fix”的构建门槛。

本轮只写 `research/boot_hang_v35/`，未构建、刷写、上卡、访问相机或相机USB、联网、提交或派生代理。`decisions.tsv` 未读取、未写入、未进入冻结摘要。实现条件和功能约束见 [DESIGN.md](DESIGN.md)。

## 已锁定的消费链及断点

以下地址均来自真正官方字节。段0/9及本链段8的文件映射为 VMA减`0x2004AE00`。脚本按完整段表核对映射，没有把其它段一概套用此差值。

| 位置 | 文件偏移 | 实际行为 |
|---|---|---|
| `0x201D82FC`，分支到`0x201D8352` | `0x18D4FC`、`0x18D552` | 图层路由在layer参数为2时调用`0x201FFD68`。 |
| `0x201FFD68..0x201FFDA8` | `0x1B4F68..0x1B4FA8` | 按view tag分派；`0x20224B38`的101项短偏移表中，只有tag33进入`0x201FFF2C`。 |

| `0x201FD402` | `0x1B2602` | 通用ADJ绘制器调用`0x201FDD10`。 |
| H05 `0x201FEBE4` | `0x1B3DE4` | 仅type5分支构造详情表`0x2023FD38`，在`0x201FEBEC`存到`sp+36`；type9另走`0x2023FD8C`。 |
| `0x201FED64..0x201FED78` | `0x1B3F64..0x1B3F78` | `index=(sp+52)+(sp+64)`，乘12，读record第0字段；非零才解引用其指向的RAM字。 |
| `0x201FEE00..0x201FEE28` | `0x1B4000..0x1B4028` | 读record第4字段，非零才读取其指向的一个字节，并进入后续UI处理。 |
| `0x201FEE98..0x201FEEA2` | `0x1B4098..0x1B40A2` | 第8字段非零才再次解引用；七个原生type5行的此字段均零。 |

原表7×12 B在VMA`0x2023FD38`/file`0x1F4F38`。0起算rows0–2全零，rows3–6各为`(0x205BEAD4,0x2023FFCA,0)`。`0x205BEAD4`是需再读一次的RAM字地址，不是函数入口；`0x2023FFCA`在映像中是字节`0B`。下游调用包括`0x201D74A8`、`0x201D709C`、`0x201D7170`、`0x201D79B0`、`0x201D7B88`。不能把这几个常量当成直接的镜头/RPC入口。

Stage2l的H05是`d2c0200582e23e6c`，直接装载`0x20053E6C`，file`0x906C`的192 B全零。三份映像中原始`0x2023FD38`的84 B完全相同；Stage2l改变的是使用的指针，并没有清掉原表。

用户已给定Stage2l在零表下保留八配方色彩。这支持详情抑制不会清掉配方look；本轮未拍摄或重新验色。不能把这个色彩结论扩大成原生28mm编辑入口、统一引擎或开机充分性均已验证。

新增 [23例指令重放](local/detail-replay.json) 强制从`0x201FED5C`进入：官方7行中，只有rows3–6读`0x205BEAD4`及`0x2023FFCA`，并各经过7次上述UI调用；Stage2l零表的16行均无这些嵌套读取和UI调用。执行的是映像匹配的指令；native UI callees为替身、RAM标签指针为合成值。它证明零表抑制的具体内容，不证明开机可达、实际绘制结果或真实挂死。

未闭合的两点不能省略：

1. 还没有50mm冷启动到layer2/tag33/type5绘制的完整调用链。原生view初始化`0x201C05A8`会清空view计数，之后push/redraw才经`0x201D82FC`进入绘制。旧开机模型只覆盖有限初态和替身callee，不能排除异步事件，也不能证明实际失败时已到H05。不能把“尚未找到”写成“绝不会开机执行”。
2. 没有失败时的row、`0x205BEAD4`内容、原生UI/任务状态或致挂持久字段。已识别消费段不读镜头身份；镜头区别若在上游能力/状态或原生调用中产生，尚未闭合到50mm。原生能力缓存和getter确实因单元输入分支，但不能把未命名的能力值直接标成50mm。持久状态是最强解释，具体字段及“由配方使用累积”的因果未在主机侧证实。

## 唯一下一个相机实验，尚未构建或执行

以真正官方`da1980…`为底，仅把type5七行详情区VMA`0x2023FD38..0x2023FD8C`、file`0x1F4F38..0x1F4F8C`的84 B置零，再按原规则重算头校验。实际有32个非零数据字节改变，邻接type9表不动。H05指令、描述符、FF窗口、全部原生代码及28个兄弟文件保持真正官方。完整before/after在 [next-experiment.json](local/next-experiment.json)。

校验字段file`0x16C`由`6acdb212`变为设计计算值`6acd597a`。公式是对file512以后的字节用权重2,3,4,5,6,7循环求和模2^32，BE32存储；无独立段校验。本轮只算替换差量，未生成候选映像或声称新映像校验已通过。

由用户在既有固定条件下挂28mm更新，确认启动后关机换50mm冷启动，只记是否进入正常LCD；不打开菜单来改变判定。成功说明这一84 B数据组在本次状态下单独足以翻转开机结果，仍不定位到某一字段；失败说明此七行组单独不够，不能据此交付H05单项v3.5。失败也不排除Stage2l更长零表、描述符变化或其它交互。最坏是原样绿灯闪/黑屏，需要既有卡A恢复。此次只提出一个实验，不补列第二个分支实验。

## 交付与恢复边界

本目录的[SHA256SUMS](SHA256SUMS)覆盖所有交付文件，排除摘要清单自身。新冻结清单含5,729个文件，覆盖官方、zip、v3.4c、Stage2l、round-1和译码输入；最终复核不得放行任何非预期变化。自写摘要打印器的一处TypeError已修复，记录于[dev-errors.log](local/dev-errors.log)，不作为停止原因。

重跑只读证据及交付校验：

```sh
/usr/bin/python3 -I -B research/boot_hang_v35/probe.py all
/usr/bin/python3 -I -B research/boot_hang_v35/probe.py delivery-verify
/usr/bin/python3 -I -B research/boot_hang_v34c/local/finalize.py verify
```

`all`会重写本目录派生证据；若要更新交付摘要，完成审阅后再运行`probe.py seal`。它不编译或封装固件，不写任何受保护输入。

恢复边界沿用已成功现场流程：卡A Stage2l、50mm保持安装、“+ & playback”。真正官方1.51恢复源是本轮核验的`artifacts/downloads/gxr-151.zip`；官方本身在当前50mm状态仍会挂，不能把“可回刷官方”称为“官方能正常使用50mm”。本轮没有操作或重测恢复。

机制/设计证据可交新一轮独立对抗审查；没有通过机制门槛的v3.5固件包可供发布/刷写审查。如果直接把本假说当修复，失败模式是仍然绿灯闪、LCD黑屏，或者冷门禁/暖路径改动导致八行、微调、高亮或grain回归；现有主机证据不能排除这些结果。
