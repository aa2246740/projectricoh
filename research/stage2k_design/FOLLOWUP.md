# Stage 2k 静态补查：空间归属、RPC 游标与模式退出

本轮结论：可以继续准备 2k 的错误传播与状态修复；还不能把段 7/10/13 的 3024 B 算作已证明可用的代码空间，也不能把自动模式退出恢复标为可交付。三个候选块都归为“运行期归属未知”，其中段 13 的证据最好。RPC 补查还发现了一个影响所有深层配方的原厂失败路径：同步包装器忽略 mutex 74 获取失败，随后仍会发包。

原 [REPORT.md](REPORT.md) 保留。本文件补充或收紧其中的空间和退出设计，不改变已接受的错误修复目标。证据级别仍分为“静态确认 / 推断 / 未知”；没有把静态检查称为相机验收。

### 2.2 DMA、别名与 cache 还能下什么结论

静态确认：主图/YUV 路径有独立图像布局和描述指针，不是“段尾没装载，所以暂借来放像素”。机身 `YuvTask`、`K+0x14C` 像素指针及步长/宽/高的证据仍见 [grain 可行性报告](../grain_raw_feasibility/REPORT.md) 的机身路径。以上已定位的 arena、栈和主堆都不覆盖三候选块。

静态确认：软件确实计算另一地址形式，例子是 `0x2006BE78..84` 的低 28 位掩码及 `0x20000000` 位。按同一算式，图像 arena 对应的另一地址范围从 `0x208BC000` 起，也不覆盖候选块。但这是软件取址事实，不能独立证明所有硬件别名或其 cache 属性。

未知：未取得该 SoC 的完整物理映射、MMU/保护配置和 DMA 地址转换契约。本轮没有找到足以给三块逐一标注“可执行、cacheable/uncached、与其他总线地址不别名”的权威表。段头只有 source/load/init/BSS，不能从中读出页面权限。loader 在成功后访问 `0xFFFFFFFC` 的维护动作只能证明其控制流，不能替代 cache 属性说明。

### 2.3 地址计算和逐块判定

本轮在旧的直接引用与 BE32 搜索之外，增加了保守的词法常量折叠：处理寄存器复制、位运算、加减、移位及有效地址，遇分支清状态，不把从可变内存读出的值当常量。它扫描了 1,464,962 个解码操作，没有得到落入三候选块的确定计算地址。[完整输出](local/followup/computed-address-candidates.json) 仍保留 2235 条“已知邻近基址加未知索引”的语法候选；这包含数据误解码和合法索引，不是 2238 个实际 owner，也不是完整 CFG/别名分析。

段 13 对应的 19 处已逐一核对。跳表读范围、跳转目标、十六进制字符表和两个字模 helper 均不命中 `0x203C7810..0x203C7C00`。尤其 `0x203B50D4/0x203B5564` 的字模公式虽然允许抽象整数算进候选块，但其 17 个固定 caller 都传 ASCII 常量或截为 u8；相应字体读区间止于 `0x203C6724`。`0x203C74F8` 数组的扫描上限为 16 项，比较表 `0x203C757C` 的上限为 10 项，都止于候选块之前。见 [逐项范围复核](local/followup/seg13-bounded-index-review.json)、[窗口](local/followup/seg13-index-windows.txt) 和 [字模 caller 参数](local/followup/i-calls-203b50d4-203b5564.json)。这关闭了这些具体计算，没有关闭从其他内存读入的通用指针。

| 候选块 | 已排除 / 仍保留的证据 | 运行期分类 |
|---|---|---|
| 段 13：`0x203C7810..0x203C7C00`，1008 B | 无现有 init/BSS 交叠；无精确 BE32 指针模式；上述 19 处计算已排除。缺完整 DMA/别名、由内存载入的指针来源和实际段装载生命周期证明。 | 未知；三块中优先级最高。没有发现肯定 owner。 |
| 段 10：`0x20380410..0x20380800`，1008 B | 无 init/BSS 交叠、无 BE32 模式。上一轮 `0x201042F4 -> 0x203806CC` 仍只是数据区域的线性解码匹配。邻近程序/状态基址的未知索引候选未全部闭合。 | 未知；不能分配给扩展。没有发现肯定 owner。 |
| 段 7：`0x201BD810..0x201BDC00`，1008 B | 无 init/BSS 交叠；8 个未对齐 BE32 模式不是已证指针；旧线性目标 `0x200C692C -> 0x201BD9BC` 同样未证可达。邻近 UI/图像布局的计算与别名未全闭合。 | 未知；暂排在后。没有发现肯定 owner。 |

[逐块清点](local/followup/block-ownership.json) 保存全部匹配及头部交叠检查。三块的“可证明无人拥有”合计是 **0 B**，“已证明被某 owner 占用”合计也是 **0 B**，“未知”合计 **3024 B**。原报告 B 类表示候选置信度，不能升级成这三块的运行期空闲证明。项目已有的 284 B 仍是另一类容量，其中 256 B 需要退役 probe。

关闭空间 gate 至少还需：补齐段 10/7 的有效索引与内存载入指针追踪；给出硬件或完整初始化代码支持的 CPU/DMA 别名及属性；证明段 13/10 在第一笔扩展调用前已加载、之后不会被别的装载或重置写覆盖。只有段表、checksum 和负引用扫描仍不够。

### 2.4 扩 init 长度对 loader 的影响

三块均可在文件不增长、后段 source/VA/BSS 字段不变的情况下，将 init 长度从 `0x10` 改到 `0x400`。对应长度字段为文件 `0xB4/0xF0/0x12C`。这个格式算术已确认，但不能表述为“loader 的其他行为完全不变”。

| loader | 长度分支 | 成功后的固定顺序 |
|---|---|---|
| body bootstrap `0x2004B89C` | `0x2004B92C..30` 检查 `len & 511`。 | 拷初始化数据；`0x2004BA4C..78` 按该段原 BSS 字段清零；置 loaded byte；可选返回入口；`0x2004BACC` 后执行维护动作。 |
| body main `0x20088358` | `0x200883E4..E8` 同样分流。 | 数据；`0x200884F8..0x20088524` 清该段 BSS；置 `0x200D7F74[index]`；可选入口；`0x20088578..88` 读控制寄存器，按原条件写 `0x101`。 |
| 官方 Monitor `0x27E36980` | `0x27E36A0C..10` 同样分流。 | 同构的 BSS、loaded、入口、维护顺序；[窗口](local/followup/monitor-27e36980-27e36bc0.txt)。 |

静态确认：`0x10` 原来走“整块数为 0，读一个尾块到 scratch，再复制 16 B”；`0x400` 改走“直接把两个 512 B 块读到段 VA”。body main 的块读链为 `0x20087F48 -> descriptor +44`，getter `0x20089F00` 对设备 2 填入 `0x20087D64`，再调用 `0x200A08CC` 的块读取路径。原来末块读写的是 scratch，扩展后目标直接是代码 VA。因此块读取次数、目标、传输大小和失败时已写范围都变了，底层 DMA/cache 行为需要接受检查。

静态确认：所查 loader 的 BSS 地址/长度来自同一记录的独立字段；它们不按 init 终点推算，也没有因为 init 变长而调换 BSS 清零顺序或换一套成功后维护条件。三段 BSS 各 4 B，分别是 `0x205A158C`、`0x205E5400`、`0x206080B8`。维护动作次数的成功路径不依赖 `len & 511`；这不等于证明新数据已满足所有 I/D cache 与 DMA 一致性要求。

静态确认：weighted checksum 覆盖文件 `0x200` 之后全部内容，包含这些间隙；只改头部长度字段不会改变这个和，写入间隙内容会改变。不能拿 checksum 正确来证明段头合法或运行期空闲。

实现约束：不能为“确保 helper 存在”而在每次开菜单时盲目重载段 13/10。原 loader 会再次清这 4 B BSS，并执行维护动作。必须证明正常装载时序，并在跳往新 helper 前检查相应 loaded 状态；状态不成立就拒绝功能，不能跳进未加载的 RAM。未找到该 loaded byte 可充当完整生命周期/代次证明的依据。`0x20068818` 的 part 装载器还含有按连接状态与角色把请求发往单元的分支，不能仅凭该服务返回成功，就认定 body 的对应段已经装入。

## 3. X/V/W 的原生使用者与任务交错

### 3.1 收口点和清点范围

静态确认：固定引用清点得到同步 scalar API `0x2009005C` 的 43 个 caller，其中 RPC ID=8 只有 `0x2006B9E0`；同步 string API `0x20090308` 有 7 个 caller；异步 scalar API `0x200901AC` 有 47 个 caller，ID 均可解析，没有 7/8/15–20；异步 string `0x20090474` 没有固定 caller。前三项参数清点见 [API 总表](local/followup/rpc-api-census.json)。对当前映像另查了 API 地址的 BE32 指针，没有发现四个 API 本身的精确函数指针对象；这不排除运行时拼出的函数地址。

`0x2006B84C` 是文本调整器。`0x2006B53C` 先把小写转大写，随后解析字母索引和数值。远端目标标志有效时，最终从 `0x2006B9E0` 发 RPC 8；否则 `0x2006B70C` 调机身本地 callback。该标志是 `*(u32 *)(0x204102B0+48)`，初始化于 `0x20066BA4..AC`；控制台目标切换在 `0x2006621C/0x200662B0` 修改它。不能把每个文本 X/V/W 都自动算成镜头 RPC，也不能因默认目标是本地就证明以后没有远端发送。

另有一个精确 `0x2006B84C` 数据指针位于 `0x200CA78C`。已追到相邻 magic 被内存测试读取，但没有证明此指针表在普通运行中被间接调用，也没有证明它永不可达。故 33 点是完整的“已识别固定 caller”清单，不是包括一切动态执行的封闭调用图。

2j 自己的 `rfw_rpc8_native` 是另一发送源，不能因原厂固定点只有一个就漏掉它。它在主菜单事务的任务 6 中，通过变参 ABI 直接调用 native scalar API；新的退出恢复也必须使用同一事务 owner。

### 3.3 其他 RAM 通道与真正共享的状态

单元的 X 基址为 `0x204A5AEC`，V/W 游标为 `0x20246158`。X 文本实现 `0x20243068` 写基址；V 文本实现 `0x20242B68` 组合基址和偶数 offset 并改游标；W 文本实现 `0x20242DEC` 经 getter `0x20242B0C` 取游标，写后经 `0x20242B18` 推进。它们属于整个单元，不按机身 task 或 recipe 分开。原生调整范围锁保护注册表，不是跨三个命令的游标锁。

RPC 15/17/19 的机身发送点分别为 `0x2007B244/0x2007B48C/0x2007B6D4`，配对的 string 16/18/20 为 `0x2007B2C8/0x2007B510/0x2007B758`。单元为它们分别保存 byte/halfword/word 地址，位置是 `0x2033B144/148/14C`。它们**不使用上述 X/V/W 游标**，因此不能把这六项当成直接改 X/V 的证据。但参数可指向同一 T 或表，仍可能造成内容竞争；这些诊断服务也应受深层事务门约束。body 的相应注册表还允许任务 39 执行本地 RAM 服务，不能混淆两颗 CPU 的同地址函数。

同步 string RPC 7 的发送点是 `0x20066754`，来自控制台未被本地处理的文本。RPC 7 能进入另一侧命令分派，不能仅检查 scalar ID=8 就宣布排他。需审查/限制这个通道在事务中的间接调整、脚本和 RAM 命令。单元另有本地调整代码读取 X 基址，如 `0x20240FCC`；只在机身前门加锁也不等于阻止单元内部 callback。[单元状态引用](local/followup/unit-cursor-refs.json) 保留这些入口。

### 3.4 并发结论和新增失败路径

静态确认：未发现普通 AE/AWB、快门和回放固定发送 X/V/W 的第二个专用路径；已解析的异步 scalar 固定 caller 也没有 RPC 8。但控制台任务 4、脚本任务 5 和 RPC 服务任务 39 都是独立执行上下文；现有 target 标志、`cache->busy` 与单次 RPC mutex 没有把它们合并为一个事务。任务 6 等同步应答时，其他任务仍可执行。控制台/脚本竞争需要相应触发，本轮没有观察到相机在无输入的正常使用中实际发生竞争。

因此，全系统“X/V/W 一定独占”不成立为现有实现的保证。普通无控制台、无脚本会话的排他仍是条件推断；还缺解释器启动条件、动态接口和单元本地使用者的完整可达性。不能关闭 [body_rpc8_probe §5.2](../body_rpc8_probe/REPORT.md#52-rfw_apply-前的时序)：该节剩余的核心问题是单元 AE/AWB/ISP reader 的停止或排空。即使机身游标前门完全收口，CPU 表读与 ISP 重建仍可在逐 halfword 更新时并发。

新增静态发现：`0x200900B4` 调 `0x2005E360(74,0x7A120)` 后，下一条直接读 argc；`0x20090360` 同样直接继续字符串打包。两处都丢弃获取 mutex 的失败返回。`0x2005E360` 确实把内核等待结果或上下文错误返回给 caller。故不能以“native API 有 mutex”保证失败时仍串行；失败后还会走含 unlock 的普通出口。

最小修复设计是在两处获得锁后先检查结果，失败跳到各自不发包、也不 unlock 的早退路径，即 scalar 的 `0x200900A4` 一族、string 的 `0x20090350` 一族。不能跳到会执行 unlock 的 `0x2009018C/0x2009044C`。这项必须覆盖每次 X/V/W，而不是只给 T1 打补丁。[mutex 包装器](local/followup/i-2005e31c-2005e3c8.txt)、[两条同步 API](local/followup/i-2009005c-20090480.txt)。

### 3.5 最简单的事务门设计

设计推断：保留 mutex 74 只保护单包；另建独立的游标 owner 和 native 活动计数。原厂 scalar 8、string 7、RAM 15–20 在入口先登记活动，完成后退出；深层事务原子地预留 owner，拒绝新的相关 native 操作，等已登记操作完全退出后再发第一条 X。只增加一个 busy flag、不排空此前已进入的 caller，仍有竞争。

```text
开始深层事务：
    在短临界区预留 owner；阻止新的相关 native 调整进入
    退出临界区；有界等待此前的同步调整完成
    尚有在途操作、上下文不合法或链接代次已变：拒绝此次切换
    独占 X/V/W，直到最后读回与状态发布完成后释放 owner

native 调整入口：
    事务已预留，且不是 owner 的受控发送：返回该 API 已有的失败值
    否则登记 native_inflight；执行；在所有出口撤销登记
```

不能屏蔽中断等待 RPC，不能持有 mutex 74 后再调用会取同锁的 API，也不能暂停发送/接收工作任务。异步相关请求即使 API 已返回，数据还可能在队列 18 中；不能用入口计数为零代替队列排空。当前固定异步 caller 没有这些 ID，可考虑在 2k 会话中始终拒绝异步 7/8/15–20；若需兼容，必须另证完成屏障。

这仍只解决机身提交者竞争。单元内部 cursor/记账状态和 §5.2 的 ISP reader gate 必须另有证据。预计入口适配、计数和 owner 需要约 176–320 B 代码、16–32 B 状态；两处锁返回检查另预留 8–16 B 逻辑及重定位空间。均为未编译预算，不包含新传输实现或 ISP 停止协议。

## 4. 模式退出的任务、阻塞与返回契约

### 4.1 `0x20069D4C`：任务 6 可到达的统一边界

静态确认：任务 6 的入口 `0x2005CC7C` 初始化并登记 mode 表，在 `0x2005CD7C` 调 `0x20069D4C`。P/A/S/M 的 callback 为 `0x202AEAF8`；配方菜单位于其调用链。因此普通菜单事务和这一统一 dispatcher 在同一任务，不需要在两者之间另开工作任务。

静态确认：dispatcher 的 registry 查找 `0x20069CC4` 获取 `0x20412AC8` 对应的锁，在 `0x20069D24` 或 `0x20069D3C` 释放，之后才在 `0x20069D80` 调 mode callback。主循环在此调用处没有持有 RPC mutex 74。最前面的 adapter 是普通 task context；原生 API 仍会检查 `0x2005F228()==0`、ready 和 RPC 上限。由此可以支持“在入口做同步 RPC 不违反已查明的线程/锁前置条件”，不能扩大为无 watchdog 或无死锁风险的整机证明。

原生主循环的整数契约需要分清两层：

1. mode callback 在 `0x20069D80` 的负返回值使 dispatcher 进入终止分支；非负值只表示该 callback 没报错，并不直接成为下一模式。
2. dispatcher 随后在 `0x20069DA4` 调全局模式选择 callback。普通启动在 `0x2005CEA4` 注册 `0x20068A84`，它读当前 mode cell。dispatcher 最终返回下一 mode，并写回 `0x20412AB8`。
3. `0x2005CD88` 只有看到 `0x80000000` 才离开循环，随后调用 `0x2005CF7C` 收尾。把 `Rv1Status` 返回给外层会把它当 mode；把负错误码塞给内层会触发终止。

不能简单“失败就返回旧 mode”来宣称取消切换：`0x20069424/0x200693FC` 已更新 mode cell 和 context；`0x200694A0` 的提交还有 context/history 字段，旧 P/A/S/M callback 退出前也做过收尾。重进旧 callback 不等于回到原现场。本轮没有证明完整回滚契约。

### 4.2 直接回放路径也在任务 6，但拒绝位置不同

四个固定调用点为 `0x20373E48/0x20373E88/0x20373FD4/0x20374030`。前三个在 `0x20373D20`，由 mode-2 callback `0x20374208` 调用；第四个在 `0x20374008`，由 `0x20374050` 的消息分支调用，后者也由 `0x20374208` 调用。mode 表 `0x200C166C` 指向该 callback，故这些已识别原生直接路径同属任务 6，而不是一个独立回放任务。

静态确认：`0x202FB9CC` 在真正调用 `0x20301114` 前已检查/设置 `0x2037FCF1`，初始化回放状态、清状态字段并改运行标志；重复进入标志命中时甚至有循环等待。`0x202FBAA4` 调回放 callback 后，立刻调用 `0x20303150(0)` 和 `0x2030B2F0`，没有检查该 callback 的返回值。四个外层 caller 也不检查 wrapper 返回值，而是继续设置状态 `0x205E5368=2` 等。

所以只把 `0x20301114` 包成“恢复失败返回 -1”不能阻止直接回放，也不能正确通知 caller。若要允许失败后取消，必须把 guard 前移到 wrapper 的第一笔副作用之前，并修改四处 caller 的成功/失败分支，或进一步前移到它们已改运行标志之前。单补 `0x202FBAA4` 不够。

已查明的外层没有把 registry mutex 或 RPC mutex 跨到这一调用点；但 wrapper 先前各子系统的运行标志不能当成锁释放证明。因此同步恢复优先放在 wrapper 最早入口，不放在里面的回放 callback 前几条指令。ready、任务上下文、owner、代次检查仍必需。

证据：[直接 wrapper](local/followup/i-202fb9cc-202fbaac.txt)、[忽略返回值及后续清理](local/followup/i-202fba90-202fbb50.txt)、[mode-2 循环](local/followup/i-20374208-20374370.txt)、[消息分支](local/followup/i-2037436c-20374410.txt)、[前两个 caller](local/followup/i-20373dc0-20373ee0.txt)、[后两个 caller](local/followup/i-20373f80-20374070.txt)。

### 4.3 超时、watchdog 与关机

静态确认：同步 RPC 的 mutex 等待参数与普通应答等待参数均为 `0x7A120`，发送参数为 5000；RPC 8 不走 ID 31 的较短应答分支。时间单位没有在本轮独立证实。发送、接收和服务工作者是另外的任务，任务 6 等待本身不会让这些任务一起停止。

未知：没有得到“任务 6 可在模式边界阻塞多久”的 watchdog/协调截止时间。callback 开头的 `0x2006A6FC` 会发 RPC 13 并更新本地协调状态，不能凭函数位置就称它为喂狗。原生也有长等待，但这不证明额外恢复的时间预算安全。

按现有序列，控制字从 0 恢复 2 最多用四次同步调用：X、V、W、V；若读到已经为 2 则不写。最多两轮的数量上限为八次。即使修好锁失败早退，其最坏等待上界也可接近 `8 × (500000 + 5000 + 500000)` 个原生超时单位，还没计全部表行恢复。因此“只重试一次”不是已证的短时限保证。

不能单独缩短这两个固定 timeout 后立即重发。应答超时后，W 可能已执行、游标已推进；迟到应答是否会被后续请求误收，还缺请求关联或排空证明。恢复值幂等，并不自动让共享游标和通信队列幂等。重试必须重新取得 owner、确认同一链接代次并重新绝对 X/V 定位；有超时且未证通道恢复时停止后续请求。

正常收尾仍应在 `0x2005CF7C` 最前、`0x2005CF9C -> 0x2006015C` 之前处理；后者已会访问原生服务，随后还有 finish 和 RPC ready 清零。两个固定 caller 都在任务 6 的主循环退出路径。恢复失败后不能无限拦住关机，不能在 ready 已清零后再补救。强制断电没有可承诺执行的 hook。

## 5. 建议的最小安全设计与实施结论

### 5.1 先保住原生整数契约

设计推断：恢复结果放在 engine 的独立字段，例如失败阶段、最后 verified slot、控制字验证状态与链接代次；它不借用 native mode 返回整数。成功时只调用一次原生 callback，并原样保留原生返回行为。engine 的告警状态交给已有配方 UI 展示；“即时弹原生 warning”的绘制入口仍需核实，不能拿未经验证的消息编号当警告 API。

可选出口必须明确区分：

| 设计 | 本轮能否支持 |
|---|---|
| 成功恢复后继续统一 dispatcher / 直接回放 | 入口和任务链已确认；仍须空间、游标、ISP、时限 gate。 |
| 失败后保留原模式，有界重试再警告 | 用户体验合适，但不能靠 `0x20069D4C` 的返回值单独实现。还需在模式提交前延后事件，以及原状态保全、重新投递和 warning 契约。当前未闭合。 |
| 统一 dispatcher 入口失败后进入原生终止/正常收尾 | `0x80000000` 外层契约已确认，是不冒充旧模式的最小退路。必须明确告警状态，禁止继续调用新模式；它是受控终止，不是“已恢复”，也不证明镜头 T 已回到 2。 |
| 直接回放失败只返回 -1 | 不可用；原 caller 忽略结果。需要四处 caller 识别 guard 结果，并撤销它们已经作出的状态改变，或保证 T 未恢复时根本进不了 mode 2。 |

最低可审查的统一入口伪代码如下；这里只表达设计，不代表这些 gate 已存在：

```text
guarded_dispatch(next_mode)：
    若无本会话深层改动：调用 native_dispatch(next_mode)
    若无需离开且代次一致：调用 native_dispatch(next_mode)
    立即关闭颗粒，标记 exit_pending
    按已验证时限取得唯一 owner
    先恢复并读回 T=2，再恢复仍被本会话改动的表行
    全部成功：发布 STOCK_VERIFIED；调用 native_dispatch(next_mode)
    失败：保留 UNKNOWN/原 verified 身份与告警，禁止调用新 mode callback
          只有提交前延后/回滚契约已证明，才走“留在旧模式”
          否则仅允许明确的原生终止出口；不得返回任意 Rv1Status

teardown_guard：
    在第一笔原生收尾 RPC 前处理
    与 dispatcher 共用一个退出代次及尝试预算
    已用尽预算或通道不明时不再重复 W，不无限等待
    保留失败状态，按原生收尾契约继续；不宣称已恢复
```

最简单的近期产品选择仍是：修复五项既有状态/错误问题，保留“先选 04 再改模式”的规则；T1 暂不转为日用。若选择自动恢复，建议先实现统一任务 6 前门、明确的受控终止出口和有界失败状态，再单独设计“失败留在拍摄界面”。不能把缺少 warning/取消契约的 adapter 包装成后者。

### 5.2 空间预算对机身颗粒方案的影响

[grain 可行性报告 option (d)](../grain_raw_feasibility/REPORT.md#d-优先候选机身端给独立-jpeg-输入加低内存颗粒) 的代码估算单位是 KiB，约 1536–3072 B。即使不计本轮新增事务门、锁返回检查、传输时限或警告代码，原 2k 核心 868–1364 B 与之相加也要 **2404–4436 B**。

原设计两候选块加既有容量为 2300 B，最低合计已超 104 B；把段 7 也纳入才有 3308 B，最高合计仍缺 1128 B。这些只是容量算术，三块都尚未通过归属 gate。不能同时把同一块 2016 B 许给 T1 鲁棒性和 3 KiB 颗粒。机身颗粒的 9 KiB 工作 RAM 与这里的可执行空间是另一笔预算。

本轮建议先补可用空间证据、删除或共享重复逻辑，再排共同布局。若目标同时覆盖 2k 鲁棒性与 option (d) 的上限，至少按原 4436 B 加本轮新增 RPC 代码继续找空间；当前没有这样的已证容量。

## 6. 宿主验证应补什么

本轮只跑了静态清点、范围算术、输入保全与哈希验证，没有编译或运行 C 等价驱动。后续实施时扩展 `firmware/stage2j/tests/equiv_driver.c`，保留原 S1–S5，再补以下可观察结果：

| 场景 | 必须断言的行为 |
|---|---|
| 任意两个 RPC 之间插入任务 4/5 的调整 | 在 owner 预留后，新 native 操作被拒绝；此前已进入的操作先完成，深层第一笔 X 才可发送；实际表和槽身份不混用。 |
| native caller 已过入口、正在等 mutex 时开始切换 | 不能只看 busy flag 放行；活动计数归零之前不开始深层事务。 |
| 锁等待失败 | scalar/string API 都不发包、不等待回复、不释放别人的锁；配方不发布成功。 |
| 小写诊断、RPC 7 间接脚本、异步已入队操作 | 不能绕过事务门；API 返回不等于单元命令已完成。 |
| W 已执行而 ACK 丢失、迟到 ACK、掉线重连 | 不从旧游标继续写；未证排空时不重试；重连后旧 owner/代次失效。 |
| 统一 dispatcher 的每种恢复失败 | 新 mode callback 调用次数为 0；外层值只取已证明合法的 mode/终止值；不会把 RV1 错误码当 mode。 |
| 直接回放的四个 caller | 失败不进入回放，不写“已完成”状态，不遗留 wrapper 的重入标志；单独测“只在 callee 返回 -1”应失败。 |
| 已退出 P/A/S/M 又收到直接回放 | engine 必须已经 STOCK_VERIFIED；不在 mode-2 中临时借菜单 cache 恢复未知 T。 |
| dispatcher 失败后又进 teardown | 共用一次退出预算；不加倍重试、不重复未知 W；不宣称 04/stock 已恢复。 |
| 新段尚未 loaded / 被重载 | 不跳到 helper；loaded byte 不能掩盖 engine 代次失效。 |
| 新旧段长度的 loader 模型 | init 写区止于段界；各段 4 B BSS、loaded 标记、入口返回和维护调用顺序不变；显式记录 scratch→直接块读取的差异及失败的部分写范围。 |

宿主模型可以证明状态机与这些调用契约的实现，不能证明真实 DMA 别名、相机 watchdog 截止时间或单元 ISP 已停止。后续验收必须保留这几个层次，尤其不能用等价转录通过来关闭 §5.2。

## 7. 本轮关闭与未关闭的问题

| 问题 | 结论 |
|---|---|
| 已知主堆、普通任务栈和 UI/image arena 是否覆盖三块 | 已排除所列分配区和已查明取址形式的覆盖。 |
| 三块是否可证明运行期无人拥有 | 未关闭；全部 UNKNOWN。段 13 的 19 处具体索引已排除，仍缺全局指针、DMA/属性和装载生命周期。 |
| 扩 init 是否改变 BSS 顺序 / 成功后维护条件 | 所查三套 loader 的这些顺序和条件不变；块读取路径、目标和部分失败范围确实改变。 |
| 所有原生固定 RPC 8 数值发送点 | 已收口至 `0x2006B9E0`，并清点 33 个文本 caller；动态接口、通道 7 和单元内部行为仍不能据此清零。 |
| 正常操作中是否已观察到竞争 | 本轮没有运行相机；只证明独立上下文和缺少事务联锁，未声称观察到实际竞争。 |
