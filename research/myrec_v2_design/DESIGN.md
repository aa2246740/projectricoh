# MyRec v2（GXUI v2）设计 r1：把带全部新旋钮的配方从电脑写回相机

本文只是设计。没有写代码、没有生成 DAT、没有碰相机、存储卡或网络，也没有启动子代理。读过的源文件和数字出处都标在文中（`文件:行`）。每个数字都标明来源：**已证**（读代码或跑了只读脚本）、**估计**（没有构建，没有测量）、**未知**（只能上机或构建后才知道）。

"可以实现"的前提有两条，放在第 8 节：新引擎构建后主请求必须不超过 108,124 B（现有余量 364 B，R1）；这条线一旦被突破，按第 3.3 节的顺序省空间，而不是放宽上限。需要你拍板的 4 件事在第 9 节。

## 0. 结论一页

| 问题 | 结论 |
|---|---|
| 条目格式 | 新块 **GXUI v2**，放在原 GXUI 的位置，总长仍是 1,984 B。每条 **24 B**（和 v1 同大小）：底子、镜头掩码、8 B 相机短名、10 个档位、4 B 电脑端长名哈希。 |
| 档位存成什么 | 线上存 1 字节一个：Amount 存无符号百分数（0..150），其余 9 个存有符号字节（−9..+9）。引擎读出后放进现有的 `int16_t v[10]`（`UvLevels`，20 B）。理由：全表最大 \|level\|=9，Amount 最大 150，一个字节够用；这样记录不会变大。头里有 `value_format` 字段，将来要加宽可以升版。 |
| 和 v1 的兼容 | 新引擎只认 v2，旧引擎只认 v1；不做双解析。引擎和数据在同一个 `GXRCE.DAT` 里一起交付，不存在"新引擎读到旧数据"的正常场景。魔数和版本都不同，混装一定被拒绝。电脑端读两种，写按 generation 分派。 |
| 容量 | 格式里留 **80 条**（正好填满 1,984 B）。第一版引擎只收 **≤32 条**（BSS 不变）；第二版去掉每条一份的 RAM 副本（`saved[32]`，640 B）后收 80 条。 |
| 对尺寸的影响 | 第一版：DAT 数据段、BSS 都不变；引擎代码增减**未测量**（估计在 −0.5 KB 到 +0.3 KB 之间）。第二版 BSS −640 B。 |
| Amt 的谜 | **已解**，不用再核实：v1 条目里 `Amt`（−10..+5）从来不可能非零（第 4 节）。v2 直接存百分数，不涉及它。 |
| 写回 | 路径 A：只替换第七段里的用户条目区，其余逐字节不变；备份在先，写前用户确认，写后读回比对。 |
| 一个必须知道的限制 | **一条配方不一定在三个镜头上都合法**：Amount 的步长（10/20/25%）和 High/Satu 的到顶档位随单元不同。所以每条记录带"镜头掩码"，菜单只显示当前镜头可用的条目。 |

## 1. 现状核对（出处）

### 1.1 v1 到底长什么样（已证）

- 区域：`GXUI124`，总长 1,984 B = 64 B 头 + 24×48 B 配置表（1,152 B）+ 32×24 B 条目（768 B）。`firmware/engine_v53_g135/candidate/ui_data.py:8-12`；C 侧 `ui_v2_data.h:4-5`（`UV_EXT_BYTES=1984`）。
- 条目 24 B：`[0]=底子 1..8`，`[2..9]=名字`，`[10..20]=11 个 int8`，`[22..23]=序号`。名字**不是自由文本**：`ui_v2_data.c:73-74` 强制它等于"分组名 3 字符 + 标记('*'/'-') + 三位序号"，如 `GRP*001`。所以今天相机里根本没有"自定义名字"，这是 v2 新增的能力，不是照搬。
- 11 个字段里只有前 4 个可以非零：`ui_v2_data.c:55,69`（`k>=4&&value` → 整个 DAT 被拒）；Python 写入器也拒（第 4 节我跑了一遍）。
- 校验单位：`ig_init` 对每条记录做 `kv_ui_legacy_record` + `kv_data_request`，**任何一条失败，整个引擎初始化返回 `ENG_REJECTED`**（`adapter.c:454-457`）。
- 会话内每条记录有一份 RAM 副本：`UvLevels saved[UV_USERS]`，32×20 = **640 B BSS**（`adapter.c:14`）。微调会改写这份副本（`uv_store`，`adapter.c:222-225`），重开机恢复。**Default 会把它覆盖成表默认值**（`uv_disp` → `uv_preview(...,&levels,applied_user)` → `uv_store`），这是现在的行为。
- `uv_config()`（读 24×48 配置表）**在整个候选里没有调用者**，只有定义和声明（`ui_v2_data.c:20`、`ui_v2_data.h:10`）。配置表现在只被 `uv_validate` 自己检查，运行时是死数据。**已证**（grep 全部非 local 源文件）。

### 1.2 knobs v2 表（已证，`research/knobs_v2_r2/tables/final.json`，我只读了它）

- 201 项、3,430 点；183 个非 Amount 项的 level 全是连续整数；全表 \|level\| ≤ 9；Amount 最大 150。
- **三个单元的表不同**。逐底子比较（"="表示三单元该项的档位集合相同）：

| 底子 | 三单元不同的项 |
|---|---|
| 02、06 | 无，三单元完全相同 |
| 01 | Amount（7/7/9 档，三单元交集只有 3 档）、Satu（−9..+6 / +6 / +8） |
| 03 | High（18/18/19 档） |
| 04 | Satu（15/16/16 档） |
| 05、07 | Amount（9/9/16 档，交集 9 档） |
| 08 | Amount（7/7/16 档，交集 4 档）、Satu（18/18/19 档） |

结果：同一个 Amount=75 在 jlaunch/qlaunch 的 01 合法、在 l08firm 的 01（20% 步长）非法。**"一条配方写一次，三个镜头通用"不成立**，设计必须处理（第 2.3、3.1 节）。

### 1.3 尺寸现状（已证，`research/g135_v37/REPORT.md`；链接图用 `nm -S` 读过 `local/full-r13/engine.elf`）

| 项 | 值 | 上限 |
|---|---|---|
| DAT | 89,572 B | 98,304 B（余 8,732） |
| 引擎段 | 60,652 B | 65,536 B（余 4,884） |
| BSS | 10,684 B | — |
| DAT+BSS | 100,256 B | 114,688 B（余 14,432） |
| 主请求 | 107,760 B | 装载器硬上限 122,192 B；**本项目自设预算 108,124 B（余 364 B）** |

364 B 是自设的线，不是装载器的线：它存在的原因是原生小堆的真实最大空闲块不知道（`native-heap-headroom`：约 75 KB 已在相机上跑通，108 KB 未确定）。你说开机和拍照后堆里只有我们自己的会话块，这只说明没有别的占用，仍不能说明最大连续空闲块够多。所以我的规则是：**这一版的净增量必须 ≤ 0，不去吃那 364 B**，除非有一次堆探针给出答案。

函数尺寸（已证，M32R LTO 后）：`ig_init` 0x2960 = 10,592 B（`uv_validate` 被内联进去，单独拆不出来）；`kv_data_open` 1,820 B；`uv_sync` 352 B；`uv_group_entry` 140 B；`uv_count_group` 112 B。

## 2. 条目格式：GXUI v2

### 2.1 区域布局（大端，总长不变 = 1,984 B）

位置、总长不变，因此 **`eng_data.c:21`（第七段总长 20,776）和 `eng_data.c:76`（kv2 块偏移 3,392）两处写死的常量一字不改**，外层闸门、GXTM、GXKV2R2 都不动。

```
偏移   长度  内容
0      8     魔数 "GXUI2\0\0\0"
8      2     版本 = 2
10     2     头长 = 64
12     4     区域总长 = 1984
16     4     CRC32（整个区域，本字段按 4 个零字节计算；与 v1 同一算法 gxr2_crc_zeroed）
20     2     记录长 = 24
22     2     条目数 count
24     2     容量 capacity = 80
26     2     value_format = 1   （1 = Amount 为 u8 百分数 + 9 个 s8）
28     4     记录区偏移 = 64
32     12    三个配方库的 CRC32（与 v1 偏移 40..51 的绑定同义）
44     4     kv2 表绑定：GXKV2R2 块头里的 CRC32（现为 c8fb1b5b）
48     16    保留，必须为 0
64     24×80 记录区；count 之后的记录必须全零
```

**为什么绑 kv2 表的 CRC**：条目里每个档位是否合法取决于那张表。把表的 CRC 写进条目区，换了表而没有重新验证过条目就会被拒。引擎只需比较两个 u32（`kv_data_open` 本来就在验 kv 块自身 CRC）。

### 2.2 记录 24 B

```
0   u8   底子槽位 1..8          （与 v1 相同，也是相机里的分组）
1   u8   镜头掩码               bit0=jlaunch(50mm) bit1=qlaunch(28mm) bit2=l08firm(MOUNT)；
                                 取值 1..7；bit3..7 必须为 0
2   8B   相机短名，ASCII        1..7 个可见字符（0x20..0x7E，首尾不得是空格），其后补 NUL；
                                 第 9 个字节（偏移 9）必须为 0
10  u8   Amount 百分数 (control 0)，0..150
11  s8×9 control 1..9 的档位：Cont High Shad Fade Satu Warm Tint Splt Filt
20  u32  电脑端长名哈希         0 = 没有
```

- control 编号、顺序与 `kv_data` 的 `UvLevels.v[0..9]` 完全一致，解码就是逐字节搬进 `int16_t v[10]`，**无换算**。
- 03 的隐藏 Amount、04 的隐藏 Amount 仍存 100，隐藏的 control（03 没有 Satu/Warm 等）存 0；这是 `kv_data_request` 已有的规则（隐藏项必须保持默认），编码器输出的就是这个规范形式，不是另一套。
- **名字 7 个字符而不是 8 个**：相机一行最多 8 个字符，第 0 列要给标记（`>` 等，第 3.4 节），所以可见名字只有 7 个。字段留 8 B 是为了保证 NUL 终止。
- **长名哈希**：电脑端长名（可以是中文）UTF-8 NFC 后取 SHA-256，取最前面第一个非零的 4 字节窗口，大端。相机**不解释它**，只让它被 CRC 覆盖。用途只有一个：电脑读卡时把卡上的条目对回自己库里的配方（长名、备注、来源）。取 4 B 的理由：每张卡 ≤80 条，碰撞概率可忽略，并且 Studio 对回时还会再比较名字和档位。
- 没有序号字段、没有校验和字段：整个区域有 CRC32，整个 DAT 还有两层 CRC（`datcodec` 已验）；逐条 CRC 只增加字节，不增加防护。
- 分组沿用 v1：按底子分 8 组（`GRP GRN HCB STD FCC FCN LCH LVI`，`adapter.c:175`），组内顺序 = 数组顺序，由电脑决定。

### 2.3 引擎侧校验（`uv2_validate`，替换 `uv_validate`）

按以下顺序，任何一条不过就整体拒绝（沿用 v1 的"整体拒绝"，不引入"跳过坏条目"的新状态）：

1. `build_number == 136`，第七段长度 20,776（在 `eng_data.c` 的现有检查里改版本号）。
2. 头部各字段如 2.1，保留字节为零，CRC32 对。
3. 三个配方库 CRC 与实际 bank 一致；`kv2 CRC` 与 kv 块一致；`kv_data_open` 通过。
4. 逐条：底子 1..8、掩码 1..7、名字字符和 NUL、Amount ≤150、哈希不检查；**对掩码里的每个单元**调用 `kv_data_request(view, unit, slot, &levels, &request)`，必须成功（档位逐点精确匹配，不接受邻档，Amount 不接受表外百分数）。
5. count 以后的字节全零。

第 4 条意味着：**一条 DAT 要么对它声明的每个镜头都合法，要么整体被拒**，不会出现"换个镜头才发现某条不合法"。代价：开机验证最多 3×80 = 240 次 `kv_data_request`。每次是对最多 10 个项目各做一次线性点查找，量级是几万次整数操作；**ig_init 的时间影响未测量**，归第 7 节的 M4 在模拟器里量，并和现有 32×1 次相比；超出预算时的退路是只验证当前镜头（Studio 仍对三个镜头全验）。

### 2.4 为什么不是别的形状（几条被否决的方案）

| 方案 | 否决理由 |
|---|---|
| 档位存 int16 | 记录 36 B：80 条要 2,880 B，超出 1,984 B；同样 1,984 B 只放得下 53 条，而且会增加 DAT 和主请求。保留为"升版选项"：头里 `value_format=2` 即可，成本是 +12 B/条。 |
| 每条配方给 3 个单元各存一套档位 | 3 倍字节；多数配方在两个单元上是同一组数。用掩码 + 必要时写成多条更省。 |
| 另开一个卡上文件存用户配方 | 需要引擎或装载器读第二个文件。固定机身不变、"文件操作计数必须为零"（见 knobs v2 设计第 8.1 节）。越出范围。 |
| 把用户条目放到 kv2 块里 | 那块有 `pack(parse(b))==b` 的 SHA 登记（`datcodec.py:47`）和 13M 例差分验证，改动面大；而 GXUI 这块本来就是用户可替换区。 |
| 同时支持 v1 和 v2 | 多 0.8–1.5 KB 代码（**估计**，按 `uv_validate` 的复杂度，没测量）却没有任何实际场景需要。电脑端负责 v1→v2 转换。 |

### 2.5 一条配方怎样变成条目（电脑端，写回设计的一部分）

一条电脑端配方是 `{底子, 10 个档位, 长名}`。写成条目时：

1. 对三个单元分别用 `final.json` 判断该向量是否合法（Studio 已有 `menu.request`）。
2. 合法的单元组成掩码。三个都合法 → 一条，掩码 7。
3. 部分合法 → 默认只写合法的那些单元（一条或两条，每条用对应单元合法的向量，**同名**）。用户可以在预览里选"调整到三镜头都合法"，界面逐项列出被改的档位（例如 Amount 75→80，Satu +8→+6），**绝不静默改**（沿用 DECISIONS #1）。
4. 一条电脑端配方最多占 3 条相机记录（同名、不同掩码）。相机按当前镜头过滤，因此用户在相机上看到的还是一个名字。

这一点直接影响容量：10 条配方在最坏情况下占 30 条。

## 3. 容量与尺寸

### 3.1 32 条够不够

- 够做第一批测试（8 个底子平均 4 条）。
- 不够长期用：按 2.5 节，每条电脑端配方最坏占 3 条；相机里每个镜头看到的是自己的那部分，但容量按物理条数算。
- 所以格式预留 80 条（和现在的 1,984 B 正好一样大）；引擎分两步放开：

| 版本 | 引擎接受条数 | 为什么 |
|---|---|---|
| A（先做） | ≤32，超过则整体拒绝 | 保持 `saved[32]`、会话状态机、Default 行为与 v1 一致；改动只在数据层和显示层；BSS 不变。 |
| B（紧接着） | ≤80 | 去掉 `saved[]`（−640 B BSS）；微调只保存在当前向量里。见 3.3 与 3.5。 |

两版线上格式相同，Studio 的编码器不用改，只在"代数注册表"里登记每一代的最大条数。

### 3.2 对 DAT、BSS、主请求的影响（第一版 A）

| 项 | 变化 | 依据 |
|---|---|---|
| 第七段 | 0 B（1,408 + 1,984 + 17,384 = 20,776 不变） | 区域位置、大小不变 |
| BSS | 0 B | `UvState` 的 `saved[UV_USERS]`（UV_USERS 仍为 32）不变；不新增静态变量；名字、掩码都直接从 DAT 读 |
| 引擎代码 | **未测量**。去掉：v1 `uv_validate` 的配置表部分、`kv_ui_legacy_record/levels/entry`。加入：`uv2_validate`、`uv2_decode`、镜头过滤（`uv_count_group`/`uv_group_entry` 各一个条件）、名字行格式化。估计净变化 −0.5…+0.3 KB | 没有构建；`uv_validate` 已内联进 `ig_init`，现有链接图拆不出它的大小 |
| 主请求 | 107,760 + 引擎代码增减 | 必须 ≤ 108,124 |

### 3.3 如果放不下：省空间的办法（已量化，按推荐顺序）

| # | 办法 | 省多少 | 依据 | 风险 / 代价 |
|---|---|---|---|---|
| 1 | 去掉每条一份的 RAM 副本 `saved[32]` | **BSS −640 B**（32×20，精确） | `adapter.c:14` | 要改 `uv_sync`/`uv_store`/确认回退里依赖 `saved` 的逻辑；行为变化见 3.5。放在 B 版。 |
| 2 | 用 v1 代码路径的整体删除 | 估计 0.8–1.5 KB 代码 | 估计，未测量 | 已包含在 A 版设计里，不是额外动作。 |
| 3 | kv2 表的重复点序列共用 | **DAT −5,244 B**（精确：201 项里只有 117 个互不相同的点序列，重复点 1,311 个 × 4 B） | 我对 `final.json` 的只读统计 | 条目里本来就有每项的 `points_offset`，格式不用改；要把 `kv_data_open` 里"点区互不重叠、连续覆盖到块尾"的验证放宽成"可以共用"；块 SHA 登记要换；要重跑 13,172,736 次差分。 |
| 4 | 在 3 的基础上再去掉非 Amount 点的 level（level 就是连续整数，由 min_level+序号算出） | 合计 13,720 → 约 4,302 B，**约 −9.4 KB** | 同上，183/183 项是连续整数 | `kv_data_point` 要重写，是已验证模块的核心路径；只在 1–3 都不够时才碰。 |
| 5 | 缩小 GXUI 区域：配置表 1,152 B 是死数据，v2 不再带 | 区域 = 64 + 24×容量。容量 32 → 832 B（**−1,152 B**）；容量 64 → 1,600 B（−384 B）；容量 80 → 不省 | 1.1 节的"无调用者" | 第七段总长和 kv2 偏移不再写死，要改 `eng_data.c:21,76`（外层闸门常量，但不是归属判断）。只有在"想要更多空间而不是更多条数"时才用。 |
| 6 | 去掉 GXTM 旧范围表（1,408 B） | −1,408 B | — | **不建议**：`gate.c:8,110`、`semantic.c:127-161`、`gxts.c:11-14`、`panel_gxts_bind.c:14-18`、`eng_data.c:56-59` 都读它。动的是归属/面板绑定那一整串已复审的代码。 |

顺序：先 2（本来就做）→ 1（B 版）→ 3 → 5；4 和 6 不动。

## 4. Amt 编码核实（第 4 项）

**结论：不需要再核实。v1 的 `Amt` 字段在任何有效 DAT 里都是 0，因此"−10..+5 怎么对应 10/20/25% 步长"这个问题不存在。** v2 直接存百分数。

证据（均可复跑）：

1. **Python 写入器**（`firmware/engine_v53_g135/candidate/ui_data.py:75`）：`if not lo <= value <= hi or (k+1 not in visible and value != default): raise`。`visible = c[4:4+c[2]]`，对每个底子都只是 `{1,2,3,4}` 或 `{1,2,3}`（`ui_data.py:36-38`），也就是第 0..3 个字段。第 4 个起（含 `Amt`，序号 10）的值必须等于默认值 0。
   我用真实的 `config()`/`extension()` 对 11 个字段分别写 +1 做了只读实验（`python3 -I -B`，没有写文件）：`Cont/High/Shad/Satu` 接受；`Fade/Warm/Tint/Splt/Filt/Tone/Amt` **全部被拒绝**。
2. **C 校验器**（`ui_v2_data.c:55,69`）：`k>=4` 的字段范围必须是 `−9..9`（`Amt` 是 `−10..+5`，只是占位的范围常量），而记录里的值只要 `k>=4&&value` 就整个拒绝。
3. **转换函数**（`kv_ui.c:414-424`）：`kv_ui_legacy_levels` 对 `old[4..10]` 任何非零都返回 −1。
4. **已有测试**：`research/kv2_data_ui/REPORT.md` 记录"旧条目 6,674 例，覆盖四位置的全部字节值、预留字段"，其中"七个旧预留数值非零均拒绝"。

所以 ARCHITECTURE §7.2 / U16 里"`amount != 100` 的配方在 Amount 编码核实前禁止写"的前提作废：不是"没核实"，而是"v1 里根本写不进去"。需要更新的结论：

- **目标是 gen ≤135（v1）**：只能写 Cont/High/Shad/Satu 四项，Amount 固定 100，其它项必须为默认；有别的项非零就**拒绝写回并告诉用户原因**（这是真实限制，不是未核实）。
- **目标是 gen 136+（v2）**：直接存百分数；合法性由 `final.json` 的逐点精确匹配决定。

剩下的验收只有一项（放进 M1 的向量里）：v1 记录里 `Amt` 位置写 ±1，Python 写入器和 C 校验器都拒绝；这项已经被上面 1、4 覆盖，M1 只需要把它固化成可重放的向量。

## 5. 相机端 UI

### 5.1 视图（沿用现有 8 行窗口，每行 ≤8 字符）

| 视图 | 逻辑行 | 变化 |
|---|---|---|
| L1 | 8 个配方 + ` MyRec` 入口 | 无 |
| 分组页 | `< Back` + 8 组 = 9 行 | 组里的数字是**当前镜头可见**的条数（不是总条数） |
| 条目页 | `< Back` + 当前镜头可见的该组条目；没有则 ` None` | 行内容见 5.2；A 版最多 1+32 行，B 版最多 1+80 行 |
| 进入条目后的配方卡、逐项列表、数值页 | 与 g135 完全相同 | 档位全部来自该条目的向量 |

窗口函数 `uv_window` 对 count 本身无上限（`out->top/cursor` 是 uint8）。**但是它的穷举测试只覆盖 count=1…33**（`research/kv2_data_ui/REPORT.md` 窗口行）。B 版 count 最大 81，必须把穷举扩到 1…81（含所有 previous 值），否则不能上。

### 5.2 条目行

```
第 0 列   标记：'>' = 正在使用且未被微调；'*' = 正在使用且已临时微调；' ' = 其它
第 1–7 列 相机短名（最多 7 个字符，右侧补空格不显示）
```

- 这和 v1 不同：v1 把"*/-"塞在名字中间（`GRP*001` 的第 4 个字符，`adapter.c:233`），自定义名字无法这么做。
- 微调只可能发生在**当前使用的那一条**，所以第 0 列一个字符就能同时表达"使用中"和"已微调"，名字不用让位。
- 判断"已微调"：当前向量与 DAT 里该条目解码出的向量逐项比较（20 B）。

### 5.3 要不要显示"来自电脑"的标记

**不显示。** 理由：相机里的所有条目（v1 的，v2 的）都只能由电脑写入，标记对每一行都成立，等于没有信息，还占一列。需要区分时用别的办法：

- 分组页和条目页的位置本身就是"来自电脑的 MyRec"，L1 里也是单独的 ` MyRec` 入口；
- 电脑端靠长名哈希把卡上的条目对回库里的配方，那里显示"来自 Studio 的 <长名>"。

如果你以后想在相机上区分"出厂示例条目"和"你写的条目"，建议用掩码字节的 bit3 做"出厂"标记，再决定在哪里显示；现在先不占用。

### 5.4 只读条目临时微调后的行为

| | A 版（保持 v1 的行为） | B 版（建议） |
|---|---|---|
| 微调存在哪 | RAM 里 `saved[n]`（每条一份）| 只存在当前向量里 |
| 切到别的条目再回来 | 保留这条上次的微调 | 回到 DAT 里存的值 |
| Default（两次 DISP）| 把这条覆盖成**配方表默认值**（该条目在本次开机内失去原值，这是现有行为） | 恢复成**该条目存的值**；要回到纯底子配方，到 L1 选那个配方 |
| 断电后 | 全部丢失，回到 DAT 里的值 | 同 A |
| 能保存吗 | 不能（相机端无存储） | 同 A |

B 版的 Default 语义是一个**需要你决定的行为变化**，我的建议是 B：用户对"只读条目"的直觉是"Default = 回到这条本来的样子"，而现在 A 的行为会让条目悄悄变成另一个配方。这是 UX 问题，不影响数据格式，所以放在 B 版而不是 A 版，不增加 A 的风险。

## 6. 写回流程（电脑端，路径 A）

### 6.1 生成新 DAT：只改允许改的字节

Studio 的 `datcodec` 登记表为每个 generation 增加一条 profile（现在是 `Profile(generation, max_file, kv2_block)`，`datcodec.py:58-70`），新增字段：`gxui_version`（1 或 2）、`max_users`（127/129/131/135 → 32；136 → 32；B 版 → 80）、`template_digest`、`ilaunch3_sha256`（已有常量）、`resident_id`、`abi_id`。

规则：**可变字节集合 V 之外的每个字节，新旧 DAT 必须逐字节相等**。V 只有：

- DAT 头 `[20:28]`（头 CRC 与载荷 CRC）；
- GXUI 区域头 `[16:20]`（区域 CRC）和 `[22:24]`（count）；
- GXUI 记录区 `[64:1984]`。

文件长度、七个区段表、引擎、重定位、GXTM、GXKV2R2 全在 V 之外。实现为一个函数 `assert_only_user_region_changed(old, new)`，写盘前必须通过；这也是 `pack(parse(b)) == b` 的自然推论（`parse` 取出用户条目，`pack` 只重新生成 GXUI 区域和两个 CRC）。

### 6.2 绑定机身身份与 generation

DAT 自己带这些身份字段（`datcodec.py` 的 `Dat`）：`ilaunch3` SHA-256（头 `[48:80]`）、resident 构建 id（`[80:112]`）、ABI id（`[212:228]`）、三个单元的钉子 CRC。Studio 写前的检查，**任何一条不过就拒绝写、只给只读诊断**：

1. `peek_generation` 在登记表里（未登记 = 只读，沿用现有规则，`UnsupportedGeneration`）。
2. `parse` 严格通过（包括最后一道 `pack(dat) == raw`）。
3. 头里的 `ilaunch3` SHA、resident id、abi id 与该代 profile 登记值**逐一相等**。
4. **模板摘要**：把 V 里的字节全部置零后，整个文件的 SHA-256 必须等于该代登记的 `template_digest`。这一条把"引擎 + 所有表"钉在已发布的那一版上；用户若换过卡上的 DAT，这一条会挡住。登记值只是摘要，不含理光字节，可以进仓库。
5. GXUI v2 头里的三个配方库 CRC 与 kv2 CRC 等于 DAT 里实际算出的值。
6. 目标条目全部通过 `final.json` 验证（每个掩码单元），且条数 ≤ profile 的 `max_users`。

**Studio 看不到机身。** 机身固件版本（v3.7，ilaunch3 `d0060740…`）不在卡上；它只能通过"该代 DAT 要求哪个 resident id"间接体现。预览页必须写出这句话："这个 DAT 要求机身是 vX（resident <id 前 8 位>），请确认你的相机已经是这个版本"，由用户确认，Studio 不假装能验证。

### 6.3 卡上原文件可回退

沿用 ARCHITECTURE §7.3，补充细节：

1. 选卷：只列含 `GXRCE.DAT` 的可移动卷，显示卷名、容量、卷 UUID。
2. 预览（不写）：读出卡上现有条目，列出新增 / 改动 / 删除 / 被丢弃或被调整的项，显示条数 / 容量、新旧 SHA-256；返回一个确认令牌，**绑定**旧 SHA、新 SHA、卷 UUID、条目差异的哈希和有效期。
3. **用户确认**。文案三句白话：这不是刷机；写完要关机再开才生效；相机里的实际观感还没验证过（标"电脑预测"）。没有令牌 → 写接口返回 403（有测试）。
4. **备份**：把卡根目录全部 `*.DAT`、一份 `manifest.json`（文件名、大小、SHA-256、卷 UUID、时间）复制进库里"相机备份/<时间>/"，复制后重新读取并核对 SHA-256。**备份失败 → 不写**。备份不自动删除。
5. 写 `GXRCE.TMP`（FAT 的 8.3 短名；不使用 `GXRCE.DAT.new` 这类长名）→ `fsync` → 回读核对 SHA-256 等于预期。
6. 用原子替换换成 `GXRCE.DAT`（macOS 上 `os.replace`）。FAT 上它不是真正原子，断电的窗口极小，由第 4 步的备份兜底。
7. 回读 `GXRCE.DAT`，`parse` 通过且 SHA-256 等于预期，条目与预览一致。任何一步失败 → 用备份恢复并再次核对，报告失败位置；卡上最后留下的要么是原文件要么是新文件，不留 `GXRCE.TMP`。
8. 写完不自动卸载（沿用现有习惯：卸载后卡留在读卡槽里）；提供"卸载"按钮，之后给出"关机再开"的步骤。

整个写入路径不联网（审计钩子拒绝 `socket.connect`，ARCHITECTURE §11）。

### 6.4 旧代数（v1）的处理

- gen 127..135 目标：Studio 继续只能写 v1 条目（四个旋钮、Amount 固定 100，名字由分组自动生成）。这条路**现在就能做**，不依赖新固件，可以作为 Studio 的第一版写回（M3a）。需要的改动：`datcodec` 里 v1 用户条目的字段按第 4 节改写文档和测试。
- 从 v1 卡升级到 v2：用户拿到 gen 136 的 DAT 包（出厂模板，条目为空或示例），Studio 提供"把卡上旧条目带过来"：每条按 `kv_ui_legacy_levels` 的规则转成新向量（位置 0..3 → control 1、2、3、5，Amount=100，其余 0），再用 2.5 节的方法算掩码；转换失败的逐条列出原因。

### 6.5 兼容矩阵

| 情形 | 结果 |
|---|---|
| gen 136 引擎 + v2 数据 | 正常 |
| gen 136 引擎读到 v1 区域（工具装配错误） | 魔数/版本不符 → `uv2_validate` 失败 → `ig_init` 返回 `ENG_REJECTED`（沿用 v1 校验失败的同一条路径）。**相机侧这时具体看到什么（回到原厂菜单还是别的）本任务没有证据**，由 M4 在模拟器里确认并记录。 |

| 新版 Studio 打开 gen 127..135 的 DAT | 正常，v1 编解码 |
