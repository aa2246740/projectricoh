有阻塞：g139 的用户条目存不了用户起的名字，只能存对比度、高光、阴影、饱和度四项且限 ±5。需要编排者决定：按这个限制先做（相机上显示自动编号，例如 `FCC*002`），还是等 g140 扩展条目格式

# 工作室「写入存储卡」设计

日期 2026-10-31。只做设计，没有写产品代码，没有跑测试进程，没有碰任何存储卡，没有联网，没有 git 写操作，没有开子代理。

下文的“已核实”都是读源码或读包内字节得出的（只读解析了两个 g139 包里的 DAT）。相机上的验证一项都没有做。

## 0. 结论

1. **能做，而且只改电脑端。**机身 v3.8 和 g139 DAT 都不用改。改了扩展区以后，只要重算 DAT 头里的两个 CRC，相机照样认。依据见 §1.2。
2. **但 g139 的用户条目比“我的配方”窄很多：**
   - **名字由相机规则生成，不能自定义。**格式是组名 3 字母 + `*`/`-` + 3 位序号，例如 `FCC*002`。工作室里的名字只能留在电脑上。
   - **只有 4 个旋钮：**对比度、高光、阴影、饱和度，每项 −5..+5。HC 黑白（内置配方 3）没有饱和度。褪色、色温、色调、分离色调、黑白滤镜必须是 0，强度必须是 100%。
   - 所以现在 LUT 拟合出来的配方，大多写不进去。工作室要么给拟合加一个“只用相机能存的旋钮”的选项，要么等 g140。
3. **g139 还没定稿。**`research/g139_fix/REPORT.md` 的 §4.3、§8、§9、§11 仍是占位符，发布 DAT `aab6c4f8…` 只是候选，还没上机。白名单（§2.1）必须等定稿以后再填。
4. **相机读到坏的卡上 DAT 不会出事：**它不认这个文件，改读内置存储的 DAT，或者按原厂相机运行。所以卡写坏了只是丢配方，可以用电脑上的备份恢复（§2.4）。

## 1. 已核实的事实

### 1.1 用户条目里存了什么

位置：DAT 第 7 区段起点 + 1,408 B，是 1,984 B 的 GXUI v1 扩展区。用户条目从扩展区 +1,216 开始，每条 24 B，最多 32 条（`UV_USERS=32`，`ui_v2_data.h:4-5`）。DAT 长度不变。

| 偏移 | 内容 | 相机怎么检查（`firmware/engine_v56_g139/candidate/containers/product/ui_v2_data.c`） |
| --- | --- | --- |
| 0 | 基于哪个内置配方：1..8 | `:62` |
| 1、9、21 | 必须是 0 | `:62` |
| 2..9 | 名字，8 B ASCII，以 0 结尾 | `:73-74`：必须**正好等于**`组名 + ('*' 如果有任何非零档位, 否则 '-') + 3 位序号`。组名按内置配方固定为 `GRP GRN HCB STD FCC FCN LCH LVI` |
| 10..20 | 11 个 int8 档位，顺序是 Cont、High、Shad、Satu、Fade、Warm、Tint、Splt、Filt、Tone、Amt | `:66-71`：前 4 项必须在该内置配方的范围内，**三个单元都要满足**；第 5 项起必须是 0（`k>=4&&value` 就拒绝） |
| 22..23 | 序号（大端），是这个内置配方组里的第几条 | `:62`：必须等于按存储顺序在本组里的累计数 |
| 条目数之后 | 剩下的位置全部是 0 | `:76` |

另外，扩展区头里的条目数要 ≤ 32，扩展区有自己的 CRC（`+16`），还存了三个配方库的 CRC（`+40`），见 `ui_v2_data.c:31-39`。

**档位范围。**我读了发布 DAT `aab6c4f8…` 的扩展区：三个单元、8 个配方的前 4 项都是 −5..+5。只有配方 3（HC 黑白）的 Satu 是 0..0，而且不显示。

**相机端怎么用这些档位。**`kv_ui_legacy_record`、`kv_ui_legacy_levels`（`kv2/kv_ui.c:417-450`）把 Cont/High/Shad/Satu 映射到 UvLevels 的第 1、2、3、5 项，强度固定 100。之后 `adapter.c:486-487` 再用 `kv_data_request` 核对：这个档位必须在当前单元的旋钮表里。

**工作室的旋钮名**（`engine/data/final.json` 的 `controls`）对应关系：
- contrast→Cont，highlight→High，shadow→Shad，saturation→Satu；
- amount 必须是 100；
- fade、warmth、tint、split、filter 必须是 0。

**相机上显示在哪里。**ADJ 菜单第一层最后一行是 `MyRec`（`kv_ui.c:225`），这是 g139 当前的相机字样。按 DISP 进入后：
- 第一层是 8 个组：`GRP`…`LVI`，每组右边显示条目数；
- 按 DISP 进入一个组，列出它的条目：`FCC*002`、`FCC-001`……

组内显示顺序是**存储顺序倒过来**：后写入的排在上面（`adapter.c:192` 的 `uv_group_entry` 从末尾往前数）。选中的条目在卡片和逐项页的标题里显示为 `<FCC*002`。名字第 4 个字符会被换成“当前值是否改过”的 `*`/`-`（`uv_name`、`uv_text`）。

**写入格式的工具。**
- `firmware/engine_v56_g139/candidate/user_entries.py`（存在，115 行）：
  - 检查信封：代数 ≥ 137，第 7 区段长 20,776 B；
  - 用冻结的 `firmware/engine_v46_ui/candidate/ui_data.py` 的 `extension()` 重新编码；
  - 断言“除了扩展区和头部两个 CRC 字以外，没有字节变化”；
  - 最后重新解析一遍。
- 工作室的 `camdata/datcodec.py:403` 有一份等价的 `_extension()`，`replace_users()` 在 `:551`。但 `PROFILES` 只登记到 138，没有 139。

**实物对照。**
- g139 测试 DAT `40bdfe76…` 里有 3 条：`FCC-001`（全 0）、`FCC*002`（Cont +1）、`GRP-001`（全 0）。
- 它与发布 DAT 一共相差 40 个字节。前 3 个落在头部 CRC 字（偏移 20..27），其余都在扩展区里。

### 1.2 机身 resident 的校验覆盖扩展区吗

**覆盖，但只通过整文件 CRC，没有单独固定扩展区的内容。**所以改了条目、重算 CRC 以后，相机照样认这个 DAT。

| 层 | 检查什么 | 出处 | 对扩展区的影响 |
| --- | --- | --- | --- |
| resident `rv_header` | 魔数、长度；头 CRC（偏移 20）；机身 ID（48..79）、构建 ID（80..111）、ABI ID（212..227）要等于机身里存的值 | `firmware/resident_v38/resident/validate_envelope.inc.c:12-30` | 不看扩展区。条目改动不碰这三个 ID |
| resident `rv_validate` | 256 B 以后整文件的 CRC（偏移 24）；区段表；重定位 | 同文件 `:32-55` | **覆盖。**改了条目必须重算偏移 24，再重算偏移 20 |
| 引擎 `gate_validate` | 头 CRC；模块 ID；固定的“原厂 04”（map + stock 行，`stock_crc32`） | `…/card_container_v2/gate.c:105-130` | 不看扩展区 |
| 引擎 `uv_validate` | `build_number==139`；扩展区自己的 CRC 和结构；配方库 CRC；每个条目（§1.1）；kv2 块 | `ui_v2_data.c:25-78` | 逐条检查。不合格时整个 DAT 被拒（`adapter.c:478`，`ig_init` 返回 REJECTED） |

**卡上 DAT 不合格时，相机怎么做**（`resident_v38/resident/loader.c:96-124`）：
- 先读 `/ATA1/GXRCE.DAT`。不合格就标记 `RF_QUARANTINE`，改读 `/IROM/GXRCE0.DAT` / `GXRCE1.DAT`；
- 都不行就不加载，相机按原厂运行。

引擎在 `ig_init` 被拒，属于 resident 的 `rv_engine` 失败路径（`loader.c:142-149` → `fail` → `rv_retire`），本次开机也不再有配方。**不会写单元，也不会刷机。**这一点是读源码得出的，没有在相机上故意放坏 DAT 试过。

`research/user_storage_r1..r3` 研究的是“相机自己在卡上保存”。结论是原厂存储排他门禁没闭合，相机内保存保持关闭；g139 的 S-1 也把 DAT 里的文件服务整个删掉了。**本功能是电脑写卡，相机只读，与那条结论不冲突。**

### 1.3 限制汇总

| 项 | 限制 | 来源 |
| --- | --- | --- |
| 条目数 | 0..32 | `UV_USERS` |
| 名字 | 不能自定义，由内置配方和序号生成，7 个可见字符 | `ui_v2_data.c:73-74` |
| 旋钮 | Cont/High/Shad/Satu，−5..+5，三个单元取交集；配方 3 的 Satu=0；其余旋钮 0，强度 100% | `ui_v2_data.c:66-71` + 发布 DAT 的配置 |
| 单元 | 条目不分单元，同一组档位在 50mm/28mm/MOUNT 上各自换算 | `adapter.c:486-487` |
| 代数 | 引擎只认 139（`ui_v2_data.c:29`），工作室也只能接受 139 | — |
| 对相机字形的要求 | g139 的名字只用 `A-Z`、`0-9`、`*`、`-`，这些在现有菜单里都显示过 | g139 REPORT §4.2 |

## 2. 设计

### 2.1 数据流

```
我的配方（电脑，my_recipes/<id>.json，含名字）
  │ ① 能不能写：基于哪个内置配方、档位是否在相机可存范围（§1.3）
  ▼
条目 {base: 1..8, levels: [Cont, High, Shad, Satu, 0×7]}
  │ ② 读卡上的 GXRCE.DAT，验明身份（白名单）
  │ ③ 新条目列表 = 卡上现有条目 + 本次新增 − 本次删除
  │ ④ 编码：datcodec.replace_users → pack；与 user_entries.py 的规则逐字节一致
  ▼
新 DAT 字节（只有扩展区和头部两个 CRC 字变化）
  │ ⑤ 备份旧 DAT 到电脑 → 写临时文件 → 读回 → 替换 → 再读回
  ▼
卡根目录 GXRCE.DAT
  │ 用户把卡插回相机，开机
  ▼
相机：ADJ → MyRec → FCC → FCC*002
```

**名字的对应关系。**工作室在“我的配方”上记录“相机中的名字”，以每次写入后读回的结果为准。现有的 `camera_short_name`（`lut/service.py:528`，格式 `U01-5ABC`）是凭空生成的，相机上不存在，要删掉，或改成写入后的真实名字。

**白名单。**只接受工作室认识的卡上 DAT：
- 代数是 139；
- 能用 `datcodec.parse` 严格解析，而且 `pack(parse(b)) == b`；
- 把用户条目清空、重新封装以后，SHA-256 在 `KNOWN_BASE[139]` 里；
- 定稿前，这一项暂时是候选值 `aab6c4f8d525dfda94fd33861c0a632b16f4d0df5481c7d9423e2bf820399e21`，**等 g139 定稿后再换成最终值**。

这样“只差用户条目”的 DAT 都能识别，测试包 `40bdfe76…` 也在内；引擎、机身 ID 或配方被改过一个字节，都会被拒绝。

### 2.2 写入前的检查（按顺序，任何一项不过就不写）

1. **选卡。**
   - 只按 `card_id` 选，不接受路径，沿用 `cards/discovery`。
   - 插着几张带 `GXRCE.DAT` 的卡时，必须由用户选，返回 409 `multiple_cards`，和 `import-card` 一致。
   - 没有 DAT 的卡不列为候选。
2. **记下卡的身份：**卷标、`os.stat(root).st_dev`、`statfs` 的 `f_fsid`、DAT 的 SHA-256 和长度。写之前每一步都重新核对；任何一项变了（换了卡、重新挂载、DAT 被别人改过）就中止。
3. **卷可写：**
   - `statvfs(root).f_flag & ST_RDONLY` 必须为 0；
   - 文件系统必须是 msdos 或 exfat（`statfs` 的 `f_fstypename`）；
   - 可用空间 ≥ DAT 长度 + 64 KiB。
4. **DAT 本身：**
   - 必须是普通文件，不是符号链接，`lstat`；
   - 长度 ≤ 98,304；
   - 一次读完，在白名单内（§2.1）。
5. **卡根目录不能已有 `GXRCE.TMP`。**如果有，而且电脑上的写入日志（§2.4）证明是工作室上一次留下的，就先按 §2.4 处理；否则拒绝，不删别人的文件。
6. **算新字节并核对：**
   - 新 DAT 与旧 DAT 只能在 `[20,28)` 和扩展区里不同（与 `user_entries.py:85-87` 同一条断言）；
   - 用 `parse` 重新解析成功，并独立重新检查每个条目（照 `ui_v2_data.c:59-76` 的规则用 Python 再写一份，不复用编码器）；
   - 新字节等于旧字节时，直接返回“没有变化”，不写卡。

### 2.3 写入

**只碰两个路径：**`<卡根>/GXRCE.TMP`（8.3 短名，不产生长文件名目录项）和 `<卡根>/GXRCE.DAT`。

1. **备份。**
   - 把旧 DAT 的字节写到 `~/Library/Application Support/GXR Studio/card_backups/<时间>-<卷标哈希>-<旧sha8>.DAT`，并写一份 `.json`：卷标、旧 SHA、新 SHA、条目清单；
   - 备份读回 SHA 一致才继续；
   - 备份全部保留，每份约 88 KB；界面只列最近 20 份。
2. **写日志。**`card_writes/<job>.json`，状态依次为 `prepared` → `tmp_written` → `replaced` → `verified`。每次改状态都先写临时文件再 `os.replace`，和 `lut/service.py:_write_json` 的写法一样。
3. **写临时文件：**
   - `os.open(TMP, O_WRONLY|O_CREAT|O_EXCL, 0o644)`，写全部字节；
   - `fcntl(F_FULLFSYNC)`，然后关闭。
   - 用普通 `open`/`write`，**不用 `shutil.copy2` 或复制扩展属性**，以免 macOS 在 FAT 卡上生成 `._GXRCE.TMP`。
4. **读回临时文件。**另开 fd，设 `fcntl(F_NOCACHE, 1)`，读全部，SHA 必须等于新字节。不一致时删掉 TMP，报“读回不一致”，旧 DAT 保持不动。
5. **替换。**
   - `os.rename(TMP, DAT)`，然后对卡根目录 `F_FULLFSYNC`。
   - FAT 上的 rename 不是断电原子的：先删目标的目录项，再改源的目录项。这一步被打断，可能只剩 TMP，或者两个都没了。由备份和日志兜底（§2.4）。
6. **读回 DAT。**用 `F_NOCACHE` 读，SHA 必须等于新字节，并且重新过一遍白名单和条目检查。日志置为 `verified`。
7. **核对卡上其他文件：**写前、写后各列一次卡根目录和 `DCIM` 的 `(名字, 大小, mtime)`，除 `GXRCE.DAT` 以外必须完全相同。这一项作为保护断言，在产品代码里也执行。

**审计钩子。**`audit.protect()` 现在拒绝一切对卡根的写入，需要加一个窄口子：`audit.allow_once(root, {"GXRCE.TMP", "GXRCE.DAT"}, job_id)`。只放行这两个文件名的 `open(写)`、`rename`、`remove`，作业结束立即撤销。其他写入照旧拒绝并记录。

**同一时刻**只允许一个写卡作业。同一张卡正在导入照片时，拒绝写卡（409 `card_busy`），反过来也一样。

**推出。**写完不自动推出。
- 状态行显示“存储卡：可以推出”，并给一个 [推出] 按钮，调用 `diskutil eject <挂载点>`（只传 `card_id` 解析出的挂载点）。用户也可以在访达里推出。
- `F_FULLFSYNC` 加读回之后，直接拔卡通常也安全；但卷没卸载，系统可能还在写自己的文件（例如 `.fseventsd`），所以仍然提示推出。
- 是否做 [推出] 按钮请编排者定。不做的话，就只显示状态行。

### 2.4 失败与恢复

| 中断发生在 | 卡上的状态 | 工作室怎么做 | 相机会怎样 |
| --- | --- | --- | --- |
| §2.2 任何检查 | 没动 | 报错，不写 | 不受影响 |
| 写 TMP 时出错或拔卡 | 旧 DAT 完好，可能残留半个 TMP | 日志停在 `prepared`。下次插卡时：TMP 长度和 SHA 都不等于预期新字节，而且日志里记着是本作业创建的，就删掉它 | 只读 `GXRCE.DAT`，不受影响 |
| TMP 读回不一致 | 旧 DAT 完好 | 删掉 TMP，提示失败 | 不受影响 |
| rename 时拔卡 | 三种可能：旧 DAT 在；新 DAT 在；只剩 TMP | 下次插卡对照日志：DAT 等于新 SHA，补做读回，置 `verified`；DAT 等于旧 SHA，删 TMP，按失败处理；DAT 没了而 TMP 等于新 SHA，再 rename 一次；都不符，进入“恢复” | 没有 DAT 或 DAT 坏：改读内置存储里的 DAT，或者按原厂运行（§1.2）。不会刷机 |
| 替换后读回不一致 | 卡上是坏 DAT | 自动用内存里的新字节再写一遍（整个 §2.3 只重试一次）；还不一致，就提示失败，并提供 [恢复] | 同上 |
| 工作室在中途崩溃 | 同上 | 启动时扫描 `card_writes/` 里没完成的日志，等对应的卡插入后，按上面几行处理 | — |

**恢复**的意思是：把某个备份按 §2.2、§2.3 原样写回。备份同样要过白名单，同样要读回核对。

写日志里没有 `verified` 的作业，界面要一直显示，直到处理完。

### 2.5 条目管理

**谁说了算。**卡上 DAT 里的条目列表就是相机里的列表。工作室每次写入都是“读卡 → 整表替换 → 写回”，不在电脑上另存一份当准。

**卡上已有的条目。**条目里没有 ID，按 `(base, levels)` 和“我的配方”配对：
- 配上的显示电脑上的名字；
- 配不上的（别处写的、测试包带的）显示相机名和档位，**默认保留**。

| 操作 | g139 的做法 |
| --- | --- |
| 新增 | 追加到列表末尾，序号取本组下一个号。在相机的组里排第一位 |
| 改名 | 只改电脑上的名字。相机名不能改，界面上不提供“改相机名” |
| 删除 | 从列表里去掉。**同组后面的条目会改号**，例如删掉 `FCC*002`，原来的 `FCC-003` 变成 `FCC-002`。确认框里要列出“改号前 → 改号后” |
| 调整顺序 | 第一版不做。跨组排序在相机上看不出来（按组分开显示）；组内调顺序会让编号变化，容易混淆 |
| 满 32 个 | [写入] 不可用，提示配方已满，请先删除不用的配方 |
| 同名 | 相机名按规则生成，不会重名。电脑上重名照常允许，不拦 |
| 完全相同的条目（同一内置配方、同一组档位） | 拒绝：“存储卡上已有相同的配方（FCC*002）” |
| 全零条目（`FCC-001`，等于内置配方本身） | 允许，不提示 |

**相机上正在用的条目被删掉以后，相机安全吗？安全。**
- 选用户条目时，写进 S 尾部的“记住”记录是 40 个 0（`eng_core.c:287` 的 `if(user)return;`）。用户条目从来不会被记住，也没有任何地方按序号持久引用条目。
- 换卡要关机。下次开机时，`ig_init` 按新 DAT 重建 `n.ui.saved[]`（`adapter.c:485-488`），旧序号已经不存在。
- 如果关机前单元里还是那个条目的效果：开机检查时九行不等于 stock，g139 不预选、不显示 `>`、不写入；用户第一次选择时，按 P1-01 完整重写九行并读回（g139 DESIGN §1 P1-01、P1-03）。

### 2.6 和“相机记住上次配方”的关系（g139 方案 B）

记录的数据标识是 DAT 头偏移 20..27 的两个 CRC（`eng_core.c:290`）。条目一变，这两个 CRC 就会变。所以：

- **不会指错。**写入后第一次开机，旧记录对不上 → 不预选，菜单停在 `>4 Std`，纯 04（g139 `bad-dataid` 用例同路径）。
- **代价：**每写一次卡，相机就忘掉一次“上次的内置配方”，要重新选一次。没法绕开，除非改 DAT。
- 条目没变时（§2.2 第 6 步）不写卡，这次就不会忘。

### 2.7 界面草案（文案由编排者定稿）

### 2.8 接口草案

| 方法 路径 | 作用 |
| --- | --- |
| `GET /api/card-recipes?card_id=` | 读卡上的条目：`{generation, dat_sha256, known: bool, reason, entries:[{index, camera_name, base, levels, recipe_id?}], capacity: 32, writable: bool}` |
