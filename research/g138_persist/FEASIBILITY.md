## 1. 108,124 B 上限从哪里来

**结论：这个上限是 DAT 和构建侧的预算，不在机身 v3.8 里。**

| 位置 | 内容 |
| --- | --- |
| `firmware/engine_v53_g135/candidate/build135.py:62-63`（g137 的构建经 `research/emptystack_v38/build_tools.py` 重定位后沿用） | `request=7504+((len(blob)+bss+3)&~3)`，`assert request<=108124` |
| `research/emptystack_v38/artifact_check.py:44-45` | 同一公式，验收断言 `request<=108124` |
| `research/knobs_v2_engine_design/DESIGN.md`、`research/heap_headroom/REPORT.md` | 来源是设计预算：DAT+BSS=100,620，加上会话 1,104、状态区 6,144 和 UI 256，合计 108,124。`heap_headroom` 明确写到：它是“所给设计预算”，用于控制原生小堆里的连续块风险，不是格式限制。 |
| 机身 `firmware/resident_v38/resident/resident.h:39,89-93` | 机身真正的限制是 `RV_MAX_IMAGE=114,688`，`RV_BLOCK_OVERHEAD=sizeof(RvSession)+6144+256=7,504`，主块上限 `RV_MAX_BLOCK_BYTES=122,192`（另有 `RV_MAX_FILE=98,304`、`RV_MAX_CODE=65,536`）。机身里搜不到 108,124。 |

其中 7,504 B 的开销由机身决定（`sizeof(RvSession)` 是 1,104 B）。108,124 这个数字只出现在构建脚本和验收脚本里。按任务规则，不属于“上限在机身里”的情况，可以继续实现。上限不放宽，最终仍按 `≤108,124 B` 验收。

## 6. 如果要放宽 108,124 B：依据和风险（等编排者决定，本轮不放宽）

**依据**
- 机身的硬上限是 `RV_MAX_BLOCK_BYTES = 7,504 + 114,688 = 122,192 B`（`resident_v38/resident/resident.h:89-93`）。放宽只需要改 DAT 构建和验收脚本里的 108,124，机身不用改。
- g137 复审（`research/review_v38_g137/REVIEW.md:107`）记录：现场三次诊断时的连续空闲都是 204,280 B。按条件推算，换成当前 108,136 B 的主块、再加 1,980 B UI 快照后约余 151,408 B。**这是推算，不是本版本在真机上的测量。**

**风险**
- 主块是一次性的连续申请。`heap_headroom` 的主机反例里，总空闲 194,192 B，但最大连续块只有 76,716 B，这时 108,124 B 的申请就会失败（相机上能否走到这一步未知）。主块越大，越容易撞上碎片化。
- g129/P2-01 仍然开着：调整文本打开失败时，每次漏掉一个 32 KiB 块。连续三次后，在 108,124 B 会话下约余 53,032 B，原生 77,336 B 的申请会失败。主块再加大，这个余量还会更小。
- 申请失败时，loader 会退役，本次开机不再加载配方，菜单退回原厂项（`loader.c` 的失败路径）。原生代码里还有若干处申请后不判空，失败后果不能保证只是“没有配方菜单”。
- 现场 204,280 B 只是 v3.7 诊断程序在三个时刻的读数，没有覆盖 MY、回放、长时间拍摄后的堆状态。

**建议**：本版已经装进 108,124 B，不需要放宽。以后要增长，先用诊断 DAT 在 v3.8 真机上实测主块申请前的最大连续空闲，再决定新预算。
