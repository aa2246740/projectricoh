仅改配方包，不能让 A12 28mm 在冷开后首次 H01 尚未就绪时，于同一次打开中自动显示 8 行配方。gen 121 在本题约束下无法交付这个行为。推荐保留 v3.6 已有的退路：未就绪时显示原生 7 行，不消耗尝试标记；链路就绪后的下一次打开，在首次绘制前发布 8 行。这个退路不需要改产品代码。

根因是执行顺序。resident 在读取任何配方文件之前检查就绪状态；检查失败后，配方包既没有被加载，也没有执行入口。H05、H09 和其余后续 hook 都不能代替 H01 启动加载。把等待、重画或提示逻辑放进新配方包，无法改变尚未读取该包时的行为。

本轮只做静态研究和原生指令模拟，8 个场景全部通过。未构建产品 DAT，未改机身或配方包，未访问相机、存储卡或网络。研究结论与实机显示、启动耗时的证据边界分别列在下文。

## 加载为什么停在第一次打开

[loader.c](../../firmware/resident_v36/resident/loader.c) 第 66 至 90 行先检查 `0x200D7FD8` 和 `0x2040F804`。任一为 0，就返回 `RV_STALE`；写入 `RF_ATTEMPTED | RF_BUSY`、分配工作区、打开 GXRCE 文件都在此后。

这也由冻结 ELF 的实际指令确认：

| 位置 | 实际行为 |
| --- | --- |
| `0x200534EC` 至 `0x20053504` | 读取两个就绪字，结果为 0 时转向返回分支。 |
| `0x20053AE8` | 设置返回值 `-5`，即 `RV_STALE`。 |
| `0x20053508` 至 `0x20053514` | 就绪检查通过后，才设置尝试标记和加载状态。 |
| `0x20053524` | 随后才第一次调用文件打开服务。 |

见 [resident 指令](static/resident.txt) 和 [静态约束检查](static-contract.json)。所有未就绪原生场景均实际观察到 `state=0`、`block=0`、`flags=2`、文件调用 0 次、配方入口 0 次。`RF_ATTEMPTED=32` 始终未置位。

因此，在这次检查失败的路径上，把 gen 117 文件换成任何 gen 121 文件，都不会改变当前列表。机身尚未读取两者的任何字节。这是执行入口的限制，不是配方包容量不足。

resident 的实际代码末端为 `0x20054638`，距离根区 `0x20054700` 正好 200 B。在保留 200 B 的条件下，可增加的空间是 0 B。本轮没有提出修改 resident 的实施方案。

## 各 hook 和后续事件能做什么

[hooks.c](../../firmware/resident_v36/resident/hooks.c) 与上述 ELF 一致。

| 入口 | 已有职责 | 冷开首次未就绪后，能否启动配方 |
| --- | --- | --- |
| H01 `0x2028709C` | 图像列表构造时加载配方，再调用 `menu_open`。 | 只有它能加载；本次检查失败即返回。 |
| H02 `0x202870A8` | 已发布配方列表的光标衔接。 | 不能。`owned` 不成立，直接返回；不重查就绪状态。 |
| H05 `0x201FEBE4` | 逐行绘制时，为已发布列表提供详情指针。 | 不能。没有 `rv_load` 或配方函数调用，共享绘制路径也不会创建会话。 |
| H06 `0x202BE24C` | 已发布配方列表的 Fn2 入口。 | 不能。原生 7 行时沿用原生 Fn2。 |
| H07 `0x202871D8` | 已发布配方视图的确认、退出和关闭。 | 不能。未拥有配方视图时执行原生关闭流程。 |
| H08 `0x202BB968` | 已发布列表的选择变化。 | 不能。原生 7 行时执行原生选择逻辑。 |
| H09 `0x2017098C` | 在已有颗粒快照条件下处理报文参数。 | 不能。它既不加载配方，也不调用配方代码；未 READY 时直接返回。 |

H06/H07/H08 的配方回调都要求 `owned` 成立，包括 READY 状态、已保存的 UI 记录、8 行、活动项 8、state 56、part 2，以及正确的视图栈。首次未加载的原生 7 行页不满足这些条件。

原生构造器地址 `0x20287080` 的相邻地址合成，在官方 16 段的扫描中只找到 `0x202BA764` 一处，随后由 `0x202BA76C` 调用。它对应 22 项原生分发表中的第 8 项。直接 BL24 候选和对齐指针字均未找到该目标。扫描只覆盖这些具体编码，不宣称穷尽任意寄存器计算目标。[调用与事件表](static-paths.json)、[原生入口](static/image-entry-dispatch.txt) 和 [v3.6 构造器](static/patched-image-constructor.txt) 保留了原始字节与解码。

配方服务中的 `RV_EVENTS` 只读取事件记录或追加一条记录，没有注册回调、定时重试或后台任务的操作。即使某个机身事件自然再次进入 H01，现有 v3.6 也会重试加载；更换配方包不能创造这次事件。本轮没有模拟完整 RTOS 启动与所有通知时序。

## 原生路径验证

执行输入是冻结的 v3.6 `ilaunch3` 和已审 gen 117 DAT/ELF，没有使用 gen 120 诊断代码。`0x20271FEC` 的固定返回替身已移除，`0x2009359C` 也执行真实读取函数。

正常菜单、光标、活动项、视图栈及 resident 状态均由原生指令生成。就绪字通过真实入口 `0x200935B4` 写入，记录到的写入 PC 为 `0x200935DE`。link 通过真实函数 `0x200637E0` 接收模型单元报文、校验并发布，写入 PC 为 `0x2006387C`。没有直接预设这两个就绪字。

| 场景 | 首次绘制 | 后续结果 | 证据 |
| --- | ---: | --- | --- |
| 打开前两项均已就绪。 | 8 行 | 再次原生重画仍为 8 行。 | [记录](native/ready-at-entry.json) |
| 就绪事件在 H01 前的 `0x20287098` 发生。 | 8 行 | 这次构造直接加载并发布。 | [记录](native/ready-before-H01.json) |
| H01 返回后，在 `0x202870A4` 就绪，此时尚未到 H02。 | 7 行 | H02 和首次绘制均未重新加载，配方入口 0 次。 | [记录](native/ready-after-H01.json) |
| 首次打开后 rpc_ready 从 0 变 1。 | 7 行 | 原生重画、上下键及 H09 后仍为 7 行；关闭重开才为 8 行。 | [记录](native/ready-after-open.json) |
| 首次打开后 link 从 0 变 1。 | 7 行 | 同上，停留期间没有第二次加载。 | [记录](native/link-after-open.json) |
| 两项均在首次打开后就绪。 | 7 行 | 同上，下一次 H01 才加载。 | [记录](native/both-after-open.json) |
| 离开前一直未就绪，第二次打开也未就绪。 | 7 行 | 两次均不锁死；离开后就绪，旁边的原生列表仍保持原生行为，第三次打开图像设置才为 8 行。 | [记录](native/not-ready-before-exit.json) |
| 首次失败后就绪，再按原生 Fn2。 | 7 行 | 命中 H06，仍没有文件读取或配方入口。 | [记录](native/late-ready-Fn2.json) |

“H01 前后”的两例只切换模拟 CPU 上下文来执行真实就绪 setter，再恢复被暂停的寄存器；没有改菜单或 resident 字段。H09 例从真实报文格式函数入口执行，不能据此推断相机会在菜单停留时自然调用它。

重画实际执行 `0x201FD360`，并断言新增 H05 调用。7 行页上的上下键实际进入 H08 和原生模式 getter；ADJ 退出按真实 state-56 事件表依次执行 `0x202C2ABC` 和 `0x202B76EC`，Fn2 从表中列出的原生入口执行。已就绪后重开时，第一批 H05 调用即看到 8 行，没有先绘制 7 行再修正的模拟轨迹。

[汇总](acceptance.json) 覆盖全部七个 hook。8 例的 create、write、rename、delete、写模式 open 计数均为 0。这里的文件系统是内存边界，零计数说明这些执行路径没有请求写文件，不代表真实介质验收。

## 方案取舍与 gen 121 改动量

| 方案 | 只改配方包是否可做 | 风险或限制 | 建议 |
| --- | --- | --- | --- |
| 在 H05/H09 或首次列表的后续按键中，等就绪后改成 8 行。 | 不能。包未加载，这些 hook 没有加载入口。 | 改配方函数收不到这次调用。若另改共享原生路径，还必须限定菜单归属，且已超出本题范围。 | 不列入 gen 121。 |
| 在配方 `init` 或 `menu_open` 内等待就绪。 | 不能解决本问题。 | 就绪检查先于这两个函数；首次失败时它们根本不执行。等待循环还会阻塞菜单任务。 | 不采用。 |
| 用 `RV_UI_LIST op 3` 直接把原生 7 行换为 8 行。 | 当前冷开路径不能。 | 它需要有效会话、READY、CAP_UI 和有效 UI 数据。v42 源码还要求当前视图已归该列表所有；它不是冷加载入口。 | 只用于已发布列表的重画。 |
| 原生 7 行上加一行“配方加载中，请重开”。 | 不能。 | 同样没有配方执行机会。新增可选行还需定义其确认、Fn2、上下键和退出行为，不能只改行数。现有 `RV_UI_TEXT` 只接受可打印 ASCII，中文也不能直接传入该接口。 | 不承诺菜单内提示。 |
| 保持原生 7 行，等就绪后的下一次 H01 直接发布配方。 | 可以，v3.6 已有。 | 下一次仍未就绪时继续显示 7 行；这是保留重试机会，不是后台预加载。 | 推荐。产品改动 0 行、resident 改动 0 B。 |
| 在使用说明中提示 28mm 冷开后稍候再打开；看到原生页时返回重开。 | 可以。 | 实机就绪时间未测量，不应规定固定等待秒数。 | 若 gen 121 需要说明，可增加约 1 段、5 至 10 行文档；本轮未改已有文档。 |

v42 的 `RV_UI_LIST op 3` 在写入边界重新检查视图归属，`list_bind(3)` 也先检查。相关条件包括活动项、state、part、原生表指针与行数、视图栈、session 和 lease。它们用于防止已经运行的配方代码改到别的菜单，不能帮助尚未加载的包获得执行机会。gen 117 服务没有 v42 新增的这项 op 3 检查，本轮没有把它当作可安全更新任意原生列表的接口。

“gen 121 首次自动出现配方”没有可交付的包内改动估算，因为缺少允许修改的执行入口。推荐退路本身已存在，无需增加定时器、后台任务或配方状态。未来若允许改变机身入口，需要另行研究，不能计入本次包内改动。

`firmware/engine_v42_ux/STATUS.txt` 当前明确记载 gen 120 尚未验收。本轮对 v42 只做源码检查，不把本项研究当作 gen 120 的完整回归，也不据此放行 gen 121 产品包。

## 需要保留的验收条件

在本次固定 resident 范围内，任何后续 gen 121 都应至少复跑上述 8 例，要求未就绪分支保持 `state=0`、`RF_ATTEMPTED=0`、无配方文件打开、无 RPC；就绪后的下一次 H01 在首次绘制前发布 8 行。还应核对原生上下键、Fn2、确认和退出，并在切到其他菜单后确认没有配方 UI 写入。

若以后另行允许研究同次打开更新，需要新增更严格的检查：就绪事件恰好发生在 H01 前后、构造尚未结束、用户已关闭或换菜单、Fn2 数值页正打开、链路再次失效，以及更新时的嵌套绘制。必须在写入当刻重新核对视图归属，并验证失败后的原生表、行数和光标恢复。只验证最终行数不足以放行。

本轮未运行完整相机启动、完整主 MENU 路径、50mm/MOUNT 回归或实机显示测试。后续如有实际产品改动，还需相应回归及另行获准的相机验收。8 个当前场景证明固定代码的分支行为，不证明相机就绪延迟、显示刷新耗时或拍摄效果。
