# M/S 首次 ADJ 的 slot 31

M/S 首次 ADJ 保留为模型边界。六组只读冷启动对照已通过断言：g157 拒绝 BOOT、g158 release 关闭 BOOT、g158 test 已套用完整颜色之后，同档位都发出相同参数的 slot31 请求，严格模型均停止，未给出设备回执。这些是边界定位结果，六组都不算首次 ADJ 成功。

静态分析已把请求追到原厂快门/光圈曝光参数路径。单元端会接收参数、更新曝光状态并计算返回值；机身把返回值按有符号 16 位数转换后继续换算。完整地址、原厂调试字符串、调用片段和输入都保存在被忽略的 `local/accept-r2/slot31/`，公开文件不复制固件字节和派生表。

这不是已经证明恒为零的应答。单元当前模式、曝光状态和校准设置会参与分支；现有功能单元模型只声明了有限的信息交换和颜色表访问，尚未重建这些曝光状态。给所有请求填零会制造一个未经证明的曝光结果。本轮尚未增加这样的设备行为，也未修改产品。

## BOOT 与手动路径

BOOT 和手动都通过既有颜色原语写回、读回完整颜色，两套补偿编排分别验收。它们的 S 写计划共用生成函数，修改颜色参数、图像设定和 WB，不包含原厂这段曝光计算读取的快门/光圈设置。菜单显示使用的原厂曝光调用和机身字节均保持不变。

BOOT 在第一次原厂 ADJ 菜单建立之前写颜色。手动套用先打开原厂菜单，随后才写颜色；再次打开 ADJ 时，单元已经走过一次菜单初始化。因此，两者进入同一个曝光请求路径，并不证明单元私有曝光状态和初始化先后完全相同。

现有模拟器从它已声明的 AUTO 输入冷启动，在 BOOT 派发边界声明实测 M/U/N。它覆盖模式门和后续原厂调用，但没有重建单元在实机 M/S 冷启动时的全部曝光初态；不能把这组 RAM 入口声明当成完整的物理拨盘和单元启动模型。

机主补充的 g157 test 现场事实是：M、S 冷启动后的第一次 ADJ 都正常，B11 诊断之后能回到列表；M 档整天手动套用后再开 ADJ 也正常。这证明原厂实机能完成这些正常路径，支持把当前严格模拟器的缺项与产品故障分开。g158 的 BOOT 已先写颜色，仍需由它自己的首次 ADJ 现场结果确认。

## 对照与结论门槛

新增六个只读冷启动探针，比较 g157 test 的 BOOT 模式拒绝、g158 release 的策略关闭，以及 g158 test 的 BOOT 已套用，分别覆盖 M/S。输入的原厂设置部分相同，只替换对应包的记忆记录和完整 S 校验。观察器只读取原厂函数入口的参数、返回地址、模式和设置，不修改寄存器，不添加设备回执。

首轮六个观察器在进入 MAIN 前被 strict_r4 的回调注册门拒绝，原错误均保留。重跑改用已有的 `native_controls.stop_at`，暂停后由主机只读寄存器和设置，再移除停止点，继续执行原指令；没有增加任意回调或设备行为。新标签为 `r2b-slot31-*`。

六组重跑均已触达实际请求。首次调用来自比候选菜单元数据函数更早的原厂 ADJ 曝光显示路径；它同样把设置器保存的返回量换算成显示值。实际返回地址、设置器与 wrapper 的顺序、HSP 三个参数已纳入验证，不能把未执行的候选函数当作运行时证据。

探针实际结果及判定已写入 `local/accept-r2/slot31/verification.json`，状态为 `MODEL_BOUNDARY`。同 SHA 的独立参考 M 档也已在完整 BOOT 颜色读回之后停于相同 slot31 请求，原失败保存在 `local/runs/reference-field-M/result.json`。目前无法从现有功能 peer 可靠重建单元曝光初态、实时曝光量和校准相关状态，严格模型继续拒绝该请求。

现场按 [OWNER_STEPS.md](OWNER_STEPS.md)分别冷启动验证“首次 ADJ 在先”和“首拍在先”。拍照会经过另一段原厂曝光流程；手动重开、先拍照后首次开菜单、其他档位的成功，都不能代替不按快门的首次 ADJ。
