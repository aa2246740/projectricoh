# GXR 1.51 菜单任务栈余量与私有栈研究

已核实：主应用任务 6 的栈是 16 KiB。普通菜单与普通拍摄 sender H09 都能沿任务 6 的模式循环到达。在本轮核对的调用路径中，扣掉原生帧、76 B 任务上下文和 v3.1 的增量后，仍剩 15,096～15,788 B。现有证据支持先记录实际 SP，不建议仅因 v3.1 超过 Stage2l 的增量就增加私有栈。

这不是全局安全证明。任务 6 的绝对栈基址来自启动时的顺序分配，本轮没有闭合所有启动分支，未得到唯一绝对地址；扩展调用的原生文件、UI、RPC 深层开销，以及共享 H05/H09 的全部动态调用上下文，也没有闭合。因此下面的余量和安全系数都带有明确的路径条件，不能直接据此关闭刷机前的栈验证要求。

日期为 2026-10-24。本轮只读静态研究，只写 `research/stack_headroom/`。没有构建固件、运行相机代码、访问相机或存储卡、安装包、启动子代理、sleep、轮询、commit 或 push。官方文件、既有研究和其它工作目录均未改写。私有栈和水位记录均为设计，未编入任何候选固件。

## 2. 任务和栈地址

### 2.1 创建参数与实际地址的区别

`0x2005CEE8..0x2005CF00` 的参数为 ID=6、入口 `0x2005CC7C`、priority=50、stack bytes=16384。`0x2005D924` 先调用 `0x2006DC04(id, bytes)`，再把以下字段交给内核创建服务 `0x0500C4CC`：属性 2、入口、优先级、大小、基址。后者通过 `trap #7` 的分发表进入 `0x05003D04`。

原生分配器从固定栈池顺序分配。每次分配将游标增加请求大小，并在该块最低 word 写哨兵 `0x8C938D4F`。任务 ID 用来选记录，不能用 ID 乘固定栈大小计算基址。

| 对象 | 已核实的地址或规则 |
|---|---|
| 普通任务栈池 | `[0x2042C200, 0x204A9200)`，`0x7D000` B。 |
| 44 项原生栈记录 | 基址 `0x2042BFE4`，每项 12 B，分别为在用标志、基址、字节数。 |
| 任务 6 的记录 | `0x2042C02C`。在用标志在该地址，基址 word 在 `0x2042C030`，大小 word 在 `0x2042C034`。 |
| 任务 6 的精确区间表达式 | 令 `B6 = *(u32 *)0x2042C030`，则为 `[B6, B6+0x4000)`。低端 4 B 是哨兵。 |
| 任务 6 的内核保存 SP 槽 | `0x200D2174 + 4×(6−1) = 0x200D2188`。此值在当前任务运行时可为旧保存值，不能替代当前 r15。 |
| 内核原始栈顶槽 | `0x200D0B4C + 4×(6−1) = 0x200D0B60`。创建服务由基址加按 4 B 对齐的大小形成它。 |
| 当前 task ID | 内核在 `0x200D1838` 使用的 halfword。探针应与 SP、SM 一起记录。 |
| SPI 系统栈配置 | `[0x05016000, 0x05018000)`，8192 B；启动把 SPI/SPU 暂设到 `0x05017FFC`。任务开始后 SPU 按派发器切换。 |
| 另一配置区 | `INT_USR_STACK` 为 `[0x206FF800, 0x20704800)`，20 KiB。没有证据将它当作任务 6 的 16 KiB 栈。 |

未知：本轮没有核定此前所有条件初始化和任务创建的分配总量，因此没有给 B6 填一个猜测的绝对数值。它须在同一次开机中读原生记录得到。在池内且大小为 `0x4000` 时，B6 的静态范围是 `0x2042C200..0x204A5200`。这一地址未知不影响容量为 16 KiB 的结论。

内核创建路径对调用者提供的栈基址设置属性位，然后保存 base、size、top。初次激活会在 top 下方构造 76 B 初始上下文，派发时将它完整弹出，因此任务入口的正常 SP 是 top。不能把这份已经弹出的初始上下文再次计入持续原生深度。

证据为 [创建包装器](local/body-2005d924-2005da20.asm.txt)、[任务 6 创建点](local/body-2005ce08-2005cf48.asm.txt)、[栈池、分配和哨兵](local/body-2006db40-2006ddd0.asm.txt)、[内核创建](local/body-05003d04-05003ee8.asm.txt)、[初始上下文](local/body-0500239c-050024cc.asm.txt) 和 [常量](local/words-200c0d20-200c0d38.json)。

## 3. SPU、SPI、中断与任务切换

### 3.1 普通任务使用 SPU

PSW 的 mask `0x80` 是 SM，SM=1 时 r15 对应 SPU，SM=0 时对应 SPI。BSM 的 mask 是 `0x8000`。Renesas 的 [M32R Family Software Manual，§1.3 和 TRAP/RTE 指令](https://www.renesas.com/en/document/mah/m32r-family-software-manual) 给出银行选择、trap 保持 SM 和 RTE 恢复 BSM 的规则。

本机内核也直接支持这一判断：`0x05002488..0x05002498` 给初始任务上下文设置 SM、BSM；`0x0500C928..0x0500C938` 从选中 task 的保存槽加载 SPU，再切 SM=1；随后弹出上下文并 RTE。保存槽保存的是实际 r15，不会每次按原始 top 重新推算。

### 3.2 外部中断先用 SPI，但任务栈仍须留 76 B

M32R 外部中断将 SM 清零。Renesas [32182 User’s Manual，§4.9.3](https://www.renesas.com/en/document/mah/32182-group-users-manual) 说明该核心行为。这里只用它核对 M32R 的银行语义，没有把 32182 的外设地址或具体向量地址套到 Ricoh SoC。

本机中断入口 `0x05000EDC → 0x0500221C` 保存 15 个普通寄存器及 accumulator 两 word、BPC、PSW，共 19 word，即 76 B。中断准备 helper `0x05000EE4` 还使用 24 B，其后才调用具体 handler。handler 及嵌套中断的最深 SPI 开销未知，不能用 76+24 B 代替整个 ISR 的最坏值。

关键代码在中断返回处：

1. `0x050022A4` 检查被打断上下文的 BSM。
2. 来自普通任务时，`0x050022AC` 取 SPU，先减 80；随后第一次预增 store 写在原 SPU−76。
3. `0x050022B8..0x05002324` 共复制 19 word，将该任务保存 SP 和 SPU 指向原 SPU−76。
4. `0x0500233C` 跳入派发器，后者恢复被选任务的 SPU 和上下文。

这个复制分支看 BSM，不以“最后有没有选另一个任务”为条件。即使 handler 在 SPI 上执行，来自任务的普通中断在返回路径仍会使用该任务栈下方的 76 B。嵌套中断若打断 SM=0 的 handler，则继续使用 SPI，不把每层 ISR 的全部帧重复扣到任务 6。

### 3.3 同步系统调用也会触及当前任务栈

`trap #7` 保持 SM，`0x050021D4` 先在当前 SPU 保存同样的 19 word。创建、等待等内核服务随后在入口检查 BSM，将实际 SP 存入 `0x200D2174+4×(id−1)`，清 SM 后用 SPI。普通返回从保存的 SPU 恢复。

例如 `0x05003D2C..0x05003D38` 和 `0x050023F0..0x050023FC` 明确执行“保存实际 SP，再清 SM”。这也解释了为什么只改当前 SPU，内核仍有能力阻塞并恢复该任务。同步调用自身的 C 函数帧属于原生 API 开销；下面另外预留的 76 B 是上下文，不能替代这些 C 帧。

证据为 [完整 IRAM 内核](local/body-05000c00-0500f8fc.asm.txt)、[trap 与中断窗口](local/body-050021d4-0500239c.asm.txt)、[派发恢复窗口](local/body-0500c784-0500c98c.asm.txt)。`analyze.py` 对 19 次 push 和 19 次复制 store 分别计数，并对关键 SP 保存、SPU 恢复指令校验原始字节。

## 4. 原生调用深度和余量

### 4.1 逐帧计算

以下帧包括序言的 push 和负向 SP 预留，不计已经返回的子函数。选定调用点前的临时参数 push 另外核对。`analyze.py` 检查序言、相关调用点前的 SP 算术及直接调用目标，保存全部 SP 操作供复查。它不声称完成全程序 CFG、跳表和递归证明。

普通路径的共同深度为 `12+16+16+168 = 212 B`。因此：

- H01/H02 为 `212+4+8 = 224 B`。
- H06 为 `212+20 = 232 B`。
- 已核对的 ADJ H07 路径取较大者，为 `212+12+16 = 240 B`。H07 是函数入口，此时它自己的原厂 push LR 尚未执行。
- H08 为 `212+12+8+28 = 260 B`。
- H09 的普通拍摄较大路径为 `212+4+164 = 380 B`。H09 同样位于 sender 入口，不提前计入它尚未执行的 push LR。
- H05 的同步建项绘制路径为 `224+4+28+20+20+60+296 = 652 B`，其中额外 4 B 是 `0x2028718C` 为 UI 建项压入的栈参数。绘制器中另一处临时 8 B 参数已在到达 H05 前回收。

还存在不能漏掉的外层：mode 2 callback `0x20374208` 在 `0x20374390` 调 `0x20373D20`，后者在 `0x20373F24` 调普通拍摄 callback `0x202AEAF8`。这两层共增加 112 B。下面统一计入它，作为所列两类入口路径的保守模型值。没有把未核实的其它模式组合当作已经实际到达过。

### 4.2 余量与安全系数

定义 D 为表中的原生路径深度，I 为任务上下文 76 B，栈底哨兵另留 4 B。E 为题给 v3.1 的扩展增量。

```text
R = 16384 − D − 76 − 4
模型剩余 = R − E
条件安全系数 = R / E
```

| Hook | 普通原生 D B | 加 mode 2 外层后的 D B | 扩展前 R B | v3.1 E B | Stage2l E B | 扣 v3.1 后 B | 条件安全系数 |
|---|---:|---:|---:|---:|---:|---:|---:|
| H01 | 224 | 336 | 15,968 | 872 | 292 | 15,096 | 18.31 |
| H02 | 224 | 336 | 15,968 | 180 | 0 | 15,788 | 88.71 |
| H05 | 652 | 764 | 15,540 | 104 | 0 | 15,436 | 149.42 |
| H06 | 232 | 344 | 15,960 | 820 | 68 | 15,140 | 19.46 |
| H07 | 240 | 352 | 15,952 | 840 | 288 | 15,112 | 18.99 |
| H08 | 260 | 372 | 15,932 | 812 | 312 | 15,120 | 19.62 |
| H09 | 380 | 492 | 15,812 | 104 | 72 | 15,708 | 152.04 |

已核实的是容量、所列帧和算术。推断是这些路径的容量足够容纳题给 E。表中系数只对所列调用链、单次 hook 以及给定扩展模型成立，不是整机安全系数，也不是允许同一扩展递归 18 次的依据。

未知的两个加数必须明确保留。令 U 为扩展调用原生 API 时尚未纳入的深度，Q 为这类调用触发其它 hook 或动态回调的重叠开销，完整条件是：

```text
D + E + U + Q + 76 + 4 < 16384
```

已有 v3.1 模型明确排除原生固件 callee。例如本轮只看序言，就得到 native open 12 B、read 44 B、close 24 B、同步 scalar RPC `0x2009005C` 180 B；这些仍不是完整 API 峰值。文件接口还间接调用具体设备方法，不能把 wrapper 的几十字节当成 VFS 全链上界。

UI 有可量化的重入例子。引擎服务 `rv_native_draw` 指向 `0x201FD360`，会继续进入 `0x201FDD10`，两帧合计 356 B；若走到 H05，还会再使用它的 104 B。H05 的特殊分支在 `inflight` 检查之前执行，因此引擎运行期间的这份开销确实不能漏掉。若用 H01 的 336 B 外层、其整体 E=872 B 再保守相加这一分支，扣除上下文和哨兵后仍剩 `16384−336−872−356−104−76−4 = 14636 B`。这是这一已识别 UI 叠加的预算，仍未代替文件、RPC 或其它 UI 路径的 U。

Stage2l 的日常使用按任务给定事实视为已实证安全。它证明此前实用路径及其增量能够工作，没有给出最小 SP，所以不能反推出精确绝对余量；“v3.1 比 Stage2l 多”本身也不能推出 16 KiB 栈不安全。

结论：已核对路径在数值上容得下 v3.1 增量，未发现接近任务栈边界的证据。全局最坏 D、U、Q 未闭合，静态研究不能给无条件安全结论。

## 5. 私有 4 KiB 栈方案

### 5.1 中断会不会落到私有栈

推断：在 SM=1 时将 r15 换成私有栈顶，只会改变当前 SPU。硬件中断的 handler 仍使用 SPI；但 §3 的返回流程会把 76 B 上下文写到当前私有 SPU 下方。因此答案是“ISR 主体使用 SPI，任务上下文会落到私有栈”。私有栈必须预留它，不能以独立中断栈为由按零计算。

切换必须由独立汇编 wrapper 完整负责，先保存旧 SP 和 LR，再换 SP，返回时换回后再弹出旧栈上的保存值。不能在普通 C 函数中插一行改 SP，然后继续让编译器访问先前的局部变量。保持 SM=1 和原来的中断允许状态，不把 SPI 当扩展栈，也不能为整个文件或 RPC 调用长时间关中断。

只要旧 SP 保存在遵守 ABI 的 callee-saved 寄存器或有效会话状态中，单条 SP 赋值前后的中断都能由现有上下文保存机制处理。私有栈必须在换入前已经对齐、初始化并归属于当前会话；切回前不得释放。

### 5.2 调原生 API 和任务切换

已核实的内核创建、trap 保存、等待入口及派发恢复路径，没有把“当前 SP 在原始任务 base/top 内”作为保存和恢复的前提。它们保存实际 SP，恢复时写入 SPU。因此从这些路径看，任务在堆内私有栈上阻塞、让出 CPU、再继续执行，在机制上可行，task ID 和优先级仍是原任务的。

这不能扩大成“内核和所有 API 均无任何边界检查”。本轮没有证明所有错误、诊断、task exception、退出和重启路径都容忍替代栈。内核保留的原始 base/size/top 仍指向原栈；现有栈底哨兵检查也只检查原生记录中的基址，不会保护新私有栈。不要修改这些原始栈记录或 TCB 以伪装私有栈。

文件、UI、RPC API 的任务上下文和参数 ABI 不因 RAM 地址改变而自动失效；同步阻塞恢复也有上述内核证据。但仍须满足原 API 的锁、指针生命周期、可访问缓冲区和任务上下文要求。将栈移到堆里不会修复 RPC 游标互斥、超时或原厂忽略锁失败的问题，也不会证明异步消费者在返回后不再使用某个局部指针。

建议将私有栈作为引擎自身 BSS 或明确持有的私有 lease 的一部分，按会话与 heap 代次持有。不要占用“看起来是 FF”的固定地址；不要让 retire、关页、热插拔或另一任务在原任务等待时回收它。该设计还需证实休眠和 heap 生命周期，沿用 `research/engine_lifecycle/REPORT.md` 的未知项。

4 KiB 不是已证足够的大小。当前 product 引擎入口子树的模型最大值是 692 B。只举一个已识别 UI 叠加的预算，私有块内留 64 B guard、再扣 692+356+104+76 B 后，剩 2804 B。文件、RPC 和其它原生分支的完整上界仍未知，不能拿这个例子批准 4 KiB。相较原任务约 15 KiB 的模型余量，4 KiB 反而缩小了引擎可用空间。

### 5.3 只有菜单任务进入引擎时的互斥

一个共享私有栈至少要求以下条件同时成立：

1. H01、H06、H07、H08 的引擎入口只由 task 6、SM=1 进入，并记录意外 task ID。H02、H05、H09 在 v3.1 中不调用引擎。
2. 同一会话同时只能有一个引擎 entry。现有 `rv_engine` 在短关中断区设置 `r->inflight`，loader 用 `RF_BUSY`；普通引擎 hook 遇到它们会返回。须保留这些门，特别是首次 bootstrap/init 的加载路径。
3. 原生 API 回调不得绕开这些门重新换入同一个栈顶。H05 会在引擎期间执行 observer，但不换栈、不再调用引擎；它仍消耗当前私有栈。
4. 引擎等待 RPC 时其它任务可以运行，但不得取得同一私有栈，也不得撤销它的分配。引擎返回、切回旧 SP 后才结束 owner。

现有 guard 支持已查菜单路径的单入口设计，不等于全系统任务独占已经闭合。未来让 H09、后台工作者或 native RPC callback 调引擎时，必须重新设计 owner 或给每个并发执行者独立栈。

### 5.4 常驻代码预算

已核实：现有 resident payload 7772 B、root 256 B，总计 8028 B，余量 312 B。链接要求至少保留 300 B，实际可净增加的只有 12 B。现有 `rv_invoke` 在 `0x20053FF8..0x20054010` 长 24 B，本轮直接从已存在的 ELF 再解码并校验了这 24 B，见 [窗口](local/v31-rv-invoke.asm.txt)。

| 方案 | 未编译的指令预算与影响 |
|---|---|
| 极限替换 `rv_invoke` | 理想地把入口参数重排、旧 SP/LR 保存、换栈与返回都紧凑配对，约 36 B，较现有净加 12 B。它假设栈顶参数已免费送到 wrapper，没有加入 owner、SM、有效性或调用点成本，不能作为可交付估算。 |
| 常驻层提供可用的换栈 wrapper | wrapper 约 40～64 B，替换原有 24 B；另计栈顶传递、调用点和资格检查约 12～32 B。净增约 28～72 B，需要先从其它位置至少省 16～60 B 才能保留 300 B。此数为手工指令预算，未汇编、未链接。 |
| 引擎侧入口 trampoline | 常驻层净增可以为 0 B。各引擎入口先通过有效 context 找到自有 BSS 栈，再进入内部实现。代码和栈都由引擎承担，仍须验证同一套调度、重入和生命周期条件。 |

引擎侧切栈只能迁走引擎进入后的工作。初次读文件、验证和加载引擎之前的 resident loader、常驻 hook 保存区及调用前缀还留在原栈；H02/H05/H09 的普通入口也不会因此自动迁走。后续若实测确有压力，优先评估引擎侧 trampoline，避免为它先挤压仅有的 12 B 常驻净预算。

## 6. 不改常驻层的栈水位记录设计

### 6.1 记录哪些入口

在引擎自身的入口 wrapper 捕获当前 r15 和 PSW，位置在 C 序言或任何 helper 调用之前。随后以尾跳转进入原实现，保持参数、LR 和原先的 callee-saved 寄存器。记录器不调用文件、UI、分配器或 RPC，也不改 PSW.SM。不要用普通 C 的局部变量地址代替入站 SP。

由入口符号确定 hook，不只看 `q->args[8]`，因为 H08 的行号可能与 H07 的数字 7 重叠。

| 引擎符号 | hook 和 phase |
|---|---|
| `ig_bootstrap`、`ig_init`、`ig_menu` | H01，分别记录 bootstrap、init、menu phase。 |
| `ig_panel_open` | H06。 |
| `ig_event` | H07。 |
| `ig_apply` | H08。 |

H02、H05、H09 没有引擎入口，因此这个“只改引擎”的方案不能直接记录它们的 SP。探针必须显示“无采样入口”，不能填零或复制另一个 hook 的值。若将来要求它们的直接水位，须另行授权修改对应常驻入口或使用独立运行期观察机制。

### 6.2 状态与更新

在产品引擎 BSS 留 128 B 诊断记录，地址作为该引擎构建的固定相对偏移写进主机 manifest。记录由当前 image 地址加该偏移定位，不新增 resident root 字段或服务 ABI。首次进入时，按当前 lease 初始化一次；后续 `ig_init` 不再擦掉已收集值。

建议字段为 magic、schema、lease/会话身份、seq、task ID、base、end、最小 SP、对应 hook/phase 和 PSW，以及四个可采 hook 的 hits、最小 SP、最近 SP。计数饱和即可，避免回绕。将未写入的最小 SP 初始化为 `0xFFFFFFFF`。先检查 task 6 记录在用、size=`0x4000`、base 和 end 在池内、SM=1；不满足时只记录异常身份和原始值，不继续计算假的余量。

一个入口的逻辑如下，属于设计伪代码，不是可编译固件：

```text
entry wrapper 先捕获 sp_before_prologue、psw、hook、phase
从当前有效 context 定位本引擎的诊断区
seq 变奇数
记录 task ID、base、end、原始 SP 与异常标志
该 SP 更小时，更新全局及本 hook 最小值
增加本 hook 次数
seq 变偶数
保持原 ABI，尾跳转到原引擎实现
```

使用同任务单 writer 和既有 entry 互斥；若未来多任务也可进入，须重新约束 writer，不能把普通 32 位 store 当成整个记录的原子提交。实际汇编必须维持编译器要求的内存顺序，并核对新 wrapper 自己不先压栈。记录器所需代码放引擎，resident 增量为 0；本轮没有给未经编译的诊断代码宣称精确字节数。

### 6.3 只读探针如何显示

探针按当前 product build ID、image 地址、BSS 大小、诊断偏移、schema、lease 核对记录。它一次读取 seq、复制记录、再读 seq；奇数或变化就显示“记录更新中”，本次退出，不轮询。不要通过换装另一个引擎后去读旧引擎的已失效 BSS；可让现有产品内的只读诊断视图或经批准的只读 RAM 通道读取当前仍存活的记录。

显示内容至少包括 task、SM、真实 `[base,end)`、各入口样本数、最小入站 SP、对应 hook/phase、最小入口可用字节数，以及“其它三个 hook 无直接样本”。显示值按下式计算：

```text
已观察入口深度 = end − min_entry_sp
已观察入口可用 = min_entry_sp − (base+4) − 76
```

这里减掉的 76 B 是未来上下文预留，不是假称探针当时已经看到这份帧。若最小 SP 越界或算术不成立，显示原始值和异常，不做无符号下溢。

这只能实测入口水位。入口之后才发生的引擎局部帧、原生 API 峰值以及短暂 H05 重入，可能更深；因此“最小入口可用”是完整最坏余量的上界，不能当作已测得的完整安全下界。若用现有编译帧推回原 hook SP，必须同时钉住 build 和 phase，当前模型的 live prefix 在 H01 bootstrap/init 为 240 B，menu 及 H06/H07/H08 为 148 B，不能统一加一个常量。

需要得到完整运行峰值时，可继续只在引擎内部增加少量明确的深层采样点，并在调用 native API 前记录 SP；native 内部的瞬时峰值仍需相应原生上界或另获授权的观察手段。不要填涂正在使用的原生任务栈来伪造 canary 水位。

本轮没有上机。后续经授权测量时，覆盖首次加载与再次开页、Fn2、上下移动、OK/MENU 关闭、回放后再进拍摄和普通拍摄；保留当前构建身份、task、base/end、SP 和 phase 原始值。H05/H09 的直接样本缺口仍须在验收记录中保留。

尚未关闭的结论边界如下：

- 任务 6 的绝对 base/top 需读同次开机的原生记录。没有用 task ID 算出一个虚假的固定区间。
- 表中 D 是指定路径的帧模型，没有穷尽模式嵌套、所有动态 callback 和递归。H05/H09 的其它 task ID 没有全闭合。
- v3.1 的 E 没有覆盖原生 API 完整子树。本轮补出了 RPC 的 180 B 本体和 UI 的一条叠加，未穷尽 U、Q。
- 没有测 SPI 或任务栈水位，也没有验证私有栈的阻塞、休眠、重入、退出和生命周期。因此私有 4 KiB 栈不属于已验收方案。
- 引擎入口记录能直接回答实际入口 SP 和原生区间；它无法独自证明所有 hook 的完整最深水位。
