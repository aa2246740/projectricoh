## 1. 第 1 步：入口相关的未知项

本节第 1 版的结论除下面标"修正"的地方外不变。

### 1.1 按键事件码（H10 `0x202B120C` 看到的 r11）

**已证（静态）**：
- 按键消息（类型 `0x700B`）由 `0x202AFE98` 换成 UI 事件，换算表是 `0x20375F14`，每项为（原始键码 u16，基值 u16）。
- 事件值：按下 = 基值+29，松开 = 基值+58，长按 = 基值+87（其中 105 改成 47，106 改成 48）。
- 字节 `0x205D9B70`==1 时换用 `0x20375F88`，这张表只放行半按、全按和原始键 32。

**已证（模拟器）**：[observe_keys.py](tools/observe_keys.py) 从官方 MAIN 冷启动 5,500 万步后逐键按下 40 万步、松开 70 万步，用时 105.9 秒。全部命中在任务 6、状态 2、层 1。

| 原始键码 | 名称（来源） | 按下 / 松开 | 模拟器 |
|---:|---|---|---|
| 24 | OK（现场证实 0x23） | `0x23` / `0x40` | 一致 |
| 23 | ADJ 推入 | `0x2B` / `0x48` | 一致 |
| 21 | DISP（现场证实 → H06） | `0x25` / `0x42` | 一致 |
| 15 / 18 / 17 / 16 | "上/下/左/右"（m2d 推断）；18 被 g121 推断为 Fn2 | `0x1F/0x3C`、`0x22/0x3F`、`0x21/0x3E`、`0x20/0x3D` | 一致 |
| 19 / 20 / 22 | 未命名（与 DISP 同一矩阵行） | `0x27/0x44`、`0x28/0x45`、`0x26/0x43` | 一致 |
| 26 / 27 | 未命名（与 ADJ 推入同一行） | `0x30/0x4D`、`0x2F/0x4C` | 一致 |
| 13 | 半按 | `0x29` / `0x46` | 一致 |
| 14 | 全按 | `0x2A` / `0x47` | 静态；模拟器在 H10 之前停在单元报文上 |

- **全按**：按键消息进入 `0x202AFE98` 约 3.3 万步后，模型停在 `0x20074028` 的单元报文发送上，没有到达 H10。所以过片锁超出 H10 合同。
- **H10 之前的两个调用**，已证（静态）：`0x2026A310` 只存状态字节到 `0x205D9A83`，`0x2026A328` 只存事件码到 `0x205D9A84`，没有其他副作用。
- **Fn1/Fn2 的物理键**：刷机后由配套 DAT 记录最近 8 个 H10 事件码并显示在只读页上，拍 1 张屏幕即可确认。不影响机身。

### 1.2 "状态 5 = 拍摄待机"，以及它是否早于首张准入

**已证（静态）**：
- 状态写函数 `0x202B0A74` 在状态变化时，先把 `0x205D9C04..` 的 10 字历史整体后移一格，再写 `0x205D9C00`。
- 调用点共 310 个：直接写 5 的 9 处，值由运行时算出的 216 处。

**已证（模拟器）**：模型开机从状态 0 到 2，之后一直停在 2，等单元结果（事件 131）。H09 在状态 2 命中 1 次（任务 6，LR `0x202D6B6C`）。

**结论：未知**，自动恢复保持关闭。

**最小上机探测**（只读，用 v3.8，2–3 张照片）：在诊断 DAT 页上显示 `0x205D9C00..0x205D9C2B` 和 `0x205D9A83/84`。拍三次屏幕：开机后第一次开 ADJ、拍 1 张后再开 ADJ、可选的从回放开机后。

### 1.3 升级流程会不会经过 UI 事件入口

**静态和模拟器结论不变**：
- 升级代码在 `0x2036C000..0x20370000`，模式 1 的 init 是 `0x2036E9AC`，每次开机都先于第一次 UI 事件执行；
- `0x202B1100` 只有一个调用点，在 `0x202AEAF8` 里；
- 真正执行升级时，确认画面经不经过 `0x202B1100`，路径级仍未闭合。

**resident 侧已证**：H10 不初始化 root，也不装载。只有状态 5/56、会话 READY、发布了 CAP_BODY 三者同时成立，H10 才会调 DAT；而 READY 只能由本次开机里的 H01 产生。r7 的机器码用例 `ui_hooks/enabled_state2` 已经核对：状态 2 下 H10 不调 DAT，事件码不变。

### 1.4 H40 的前置问题（修正）

1. **外层返回地址**：已证（静态，复审独立复核）。`0x2015F854` 压 7 个寄存器，到 `0x2015F9D8` 之前 sp 不再变化。原厂 SP = `f+68`，外层返回地址在 `f+72`，也就是原厂 SP+4。
   - **修正**：第 1 版说"DAT 读 `*(args[10]+4)`"是错的。`rv_engine` 会把 `args[10..11]` 覆盖成私有上下文地址和 120（复审 P1-02）。
   - r7 改为 `args[12]`=原厂 SP，DAT 读 `*(args[12]+4)`。
2. **编码描述符**：已证（静态）。包装器读 K 的 +5、+6、+8、+0x6D、+0xB1、+0x14C、+0x154、+0x190、+0x194、+0x198，并把 K+0x1C4 交给下层编码函数。
   - **r7 采用复审推荐的做法**：resident 保存和恢复 K+0x14C..0x15B 与 K+0x190..0x19B，同时保留"先标记再改"的合同（§4 P2-04）。
3. **错误传播**：两个检查返回值的调用者出错时只是把 −1 返回上一层，再往上没有追完。写像素保持关闭。
4. **主图缓存一致性**：未知，沿用方案的分级实拍。

### 1.5 栈（修正）

- **修正 1**：第 1 版说"模型里开机时清零"，证据不足（复审 P2-02）。第 2 版重新冷启动 4,000 万步（[stack_fill.py](tools/stack_fill.py)，69.8 秒），结果见 `local/emulator/stack-fill-r2.json`：
  - 任务 6 栈 `[0x20442200,0x20446200)` 和任务 26 栈 `[0x20461A00,0x20465A00)` 的最低一个字都是 `0x8C938D4F`，其上为 0。
  - 往上第一个非零字：任务 6 在 `0x20444EC4`（模型 4,000 万步时约用了 4.9 KB），任务 26 在 `0x20465980`（空闲等待，用了 128 B）。
- **已证（静态）**：`0x8C938D4F` 是 RTOS 的栈底哨兵，不是栈使用痕迹。
  - 分配栈时，`0x2006DC70` 一带把它写到栈记录的基址上；
  - `0x2006DBB8` 起的循环逐项检查栈记录表 `0x2042BFE4` 里每个栈底是不是这个值，不是就在 `0x2042C1F4` 置位并返回 −5。
  - 同一张表的第 0 项是 `0x05016000` 起的 8 KiB 栈（由 `0x2006DC9C` 一带初始化）。它是不是 IRQ 栈属推断。
- **未知**：RAM 里栈区的 0 来自固件清零，还是模型的初始内存。所以上机探测必须先拍一张基线。
- **探测方法修正**：从栈底往上扫描时跳过最低一个字（哨兵），找第一个非零字。
  1. 开机后看一次，作为基线；
  2. 拍 1 张 JPEG、1 张 RAW+JPEG，再看一次。

  值本身为 0 的写入会让结果偏浅，预算要留余量。

  这个探测只覆盖任务栈；IRQ 栈的界限和嵌套深度仍未知。
- **修正 2**：resident 的栈账见 §4 P2-02。`rv_hook_observe` 的 44 B 帧来自 vS1（vH 是 36 B），不是 C4 造成的。r7 在 H40 和 H10 上到 DAT 入口都是 156 B，由机器码实测。

## 3. 第 2 版的尺寸（严格链接，真实 root `0x20054700`，24 B 门槛只在 `resident.ld` 定义一次）

- `discard_main` 内联后 −40 B，`rv_load` 的帧仍是 88 B，原来 16 B 的 `discard_main` 帧消失；

- **H40**：`args[8]=40`，`args[9]=K`，`args[12]=0x20465800`（原厂 SP），`args[13]=0x2016583C`，`args[10]` 是上下文地址，`args[11]=120`，`args[2..7]=0x1000,0x1111,0x1222,0x1333,0x1666,0x1777`（即 `epoch[0,1,2,3,6,7]`）。
- **H41**：`args[13]=0x87654321`，就是包装器替身写入 `0x201BC3AC` 的值；包装器自己返回 0。
- **5 个外层返回地址**：`0x201558A8`、`0x2015EAA4` 放行（DAT 回 DONE，随后有 H41）；`0x20155428`、`0x20155478`、`0x2015E9B0` 拒绝（DAT 回 PASS，没有 H41）。五种情况都正常调用包装器 1 次，最后 r0=0，SP 复原。
- **恢复和锁存**：
  - 没先标记就修改两段 K、然后出故障：包装器看到的是原始 K；
  - 先标记再修改、DAT 回 PASS：跳过编码，r0=−1，锁存 `0x100`；下一张照片不再调 DAT，按原厂编码。
- **H10**：状态 56 和 5、发布了 CAP_BODY 时，r11 由 `0x23` 改成 `0x25`；状态 2 或没发布 CAP_BODY 时不调 DAT，r11 不变。
- **H09**：4 条在范围内的编辑生效，偏移 144 的编辑被忽略；没发布 CAP_BODY 时参数块一个字节不变。
- **栈**：H40 和 H10 进 DAT 时，在原厂 SP 之下用了 156 B（机器码实测）。

**P2-03 的完成语义（r7）**：
- 第一次调用 DAT 之前，resident 已经完成长度、头部、CRC、机身/build/ABI 身份、section、重定位和 `entry_offset` 的校验；这一次调用之前设好 `RV_READ_CAPS` 和 bindings。
- 这一次调用必须同时满足以下条件，才会发布 READY：
  - 返回 `RV_PASS` 或 `RV_CONSUMED`；
  - `reply.status==RV_OK`，`reply.actual==40`；
  - **`reply.detail==RV_INIT_DONE`（0x49）**，DAT 只能在纯初始化全部成功之后才回这个值；
  - `r->state` 仍是 VALIDATED；
  - 入口表 `version==1`、`bytes==40`，9 个入口都 4 B 对齐，并且落在代码区以内；
  - 代次和会话复查都通过。
- **只登记入口表、回旧式回复（detail=0）的 DAT 会被拒绝**（主机用例 `legacy_registration_only`）。
- 失败时的状态：
  - `r->state=RV_DISABLED_UNTIL_REBOOT`，`RF_STOP|RF_ATTEMPTED` 置位；
  - `RF_BUSY`、`RF_PUBLISHED`、block、lease、inflight 都撤销；
  - 打开的文件已经关闭；原生列表保持 7 行；
  - 本次开机内不再尝试装载（再调 `rv_load` 返回 `RV_FAULTED`）。
  - 这**不是**回到 `RV_FACTORY`，主块和装载工作区沿用现有的"不释放"策略。
  - 主机覆盖了 53 种失败（9 个入口槽各 3 种错法，以及 version、bytes、actual、旧式回复、status、CLOSE_AND_PASS、FAULT、负返回值、回复的 version/bytes、state 被改、STOP、12 个代次、堆头、代码被改）。
- VALIDATED 阶段的 DAT 已经拥有读能力，这是相对 v3.8 的行为变化。用例 `rpc_write_in_validated` 证明这个阶段 RPC 写返回 `RV_CAPABILITY`，原厂写 0 次。纯初始化仍须关闭自己打开的文件、归还自己认领的资源。
- 旧 DAT 由新的 build/ABI 身份在第一次执行前就被拒绝；完成标记再防住同一身份下只登记、不初始化的错误构建。
