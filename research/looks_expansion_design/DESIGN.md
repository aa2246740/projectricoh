### 1.2 为什么这一阶段不做任何放宽试验

- 复审用原生分配器指令做出了反例：
  - 相同的申请和释放会把内存逐字节写回原样，所以哈希、CRC、逐字节比较都会漏掉完整的临时分配（P1-01）；
  - 主请求加到 122,192 B，会让原本能成功的 12,368 B 原生申请失败，随后 `0x200DA69C` 不判空就去清零地址 0（P1-02）。
- 只读快照补不出没有观察到的历史。所以在分配器上真正记账之前（§6.5），任何超过 108,124 B 的主请求都没有运行证据。
- 本阶段的容量全部靠**在 108,124 B 以内腾空间**取得（§2）。

### 2.3 kv2 压缩的规格（给实现者）

- **格式**：魔数改成 `GXKV2R3`；头部"点长"字段（+32）从 4 改成 2；点区里只存 s16 剂量。
- **点数和长度**：
  - 点区长度 = 2 × 不同剂量点数，按实测是 2,119 × 2 = 4,238 B；
  - 块长 = 64 + 384 + 3,216 + 4,238 = 7,902 B，对齐后 **7,904 B**；
  - `KV_DATA_BYTES`、`KV_DATA_POINTS` 按生成器的结果填。
- **`validate_item`**：
  - offset 要求 2 B 对齐、≥ 点区起点、`count×2` 不越界；
  - 每个点的档位按规则计算，不再从数据里读；
  - 剂量的单调性、上下限、默认点的规则全部保留；
  - 用"最大尾"代替"累计等于"，最后要求最大尾 = 块长；另加"每串都至少被一个条目引用"。原型 `prototype/kv3/kv_data.c` 没有这一条，估计 +60 B。
- **`kv_data_point`**：档位按同一规则计算，剂量从 2 B 读取。
- **其他**：`kv_data_request`、`kv_data_find`、`kv_ui` 和所有上层调用都不变。
- **段长**：第 7 段从 20,776 B 变成 11,296 B（1,408 + 1,984 + 7,904）。`gate.c` 的 `gxr2_tweak_layout` 里写死的 `build_number==150 && s->length==20776` 特例，以及 `eng_data.c` 的长度检查，都要同步改成新长度和新代数。
- **等价性门槛**（必须在主机上穷举，这是本项唯一的放行条件）：
  - 对 3 个单元 × 8 个配方 × 每个控制 × 每个合法档位，旧 DAT 和新 DAT 的 `kv_data_request` 结果逐字节相同；
  - 所有控制都取默认值时也相同；
  - 再抽查组合：极端值两两组合，C 和 Python 的结果对照；
  - `kv_ui` 显示的每一档文字相同；
  - 任何一处不同就不能交复审。
- **生成器**：kv2 块由现有的 knobs 构建脚本生成，具体是哪个由实现者确认。电脑端 `studio/src/gxr_studio/engine/knobs.py` 用的是剂量（`Request`），不读 DAT 的点表格式。所以电脑端只要把生成器和 DAT 白名单的模板摘要更新为新代数即可。

  - v3.8 中档：前 2 个（徕卡 M9 STD、哈苏 HNCS 高反差，每个 217 B，区头 32 B，剩余空间 492 B）；
  - v3.8 低档：前 5 个（再加 Tri-X 400、Portra 400、Velvia 50，剩余空间 1,064 B）；
  - v3.9：0 个。

  把 §2.2 第 4、6、7 项都做了，也只能再多装 3–4 个，所以第一批放不全。**结论：kv2 压缩是这一版必须做的一项。**

### 2.5 模板建议：K = 32

| 机身 | 代码估计 | 主请求 | 离 108,124 的余量 | DAT | 离 98,304 的余量 |
|---|---|---:|---:|---:|---:|
| v3.8 | 中 / 高 | 105,628 / 106,204 | 2,496 / 1,920 | 88,862 / 89,438 | 9,442 / 8,866 |
| v3.9 | 中 / 高 | 106,904 / 107,480 | 1,220 / **644** | 89,986 / 90,562 | 8,318 / 7,742 |

- 在所有组合下，两项余量都 ≥ 512 B；v3.9 高档代码最紧，主请求只剩 644 B。
- **最终 K 的规则**：完整链接以后，取 `K = min(32, 满足两项 ≥ 512 B 的最大 K)`。如果 v3.9 实际代码超出高档估计，K 会降到 30 左右，第一批 10 个仍然放得下。
- 各种类行的容量：C0 = ⌈K/4⌉ = 8，C1 = K + ⌈K/2⌉ = 48，C2 = C3 = K = 32。区长 8,000 B。
- 第一批 10 个装入后，占用如下：
  - 表项 10/32；
  - 1 类行 10/48（每个 B5 一条）；
  - 2 类行 9/32（Tri-X 用 03 的颜色行）；
  - 3 类行 9–10/32；
  - 0 类行 0/8。

## 3. 方案 P 的细节（第 1 版 §2 修订后）

### 3.1 范围

- 本版只做：kv2 压缩（§2.3）+ 效果区 + Looks 页 + 第一批效果数据。
- **不改 GXUI v1**（P2-08），不做第 1 层（名字 v2、我的配方平铺、效果绑定）。GXUI v1 的条目照旧只能引用内置配方。

### 3.2 格式

**GXDP v2**：第 6 段头从 64 B 加到 80 B，多出的 16 B 是：

```
64  u32  效果区相对第 6 段的偏移（4 个行池之后，4 字节对齐）
68  u32  效果区总长
72  8B   0
```

效果区接在最后，效果区尾 = 段尾。效果区的位置和长度都固定，由模板身份约束，包括总长、K、各种类容量，以及不许改的段头。填入效果不改变 DAT 长度，BSS 不平移（复审已确认）。

**`GXFX` 效果区**（大端）：

```
0   "GXFX"
4   u16 版本 = 1
6   u16 头长 = 32
8   u16 容量 K ≤ 48
10  u16 效果数 n ≤ K
12  u16 表项长 = 32
14  u16 0
16  u8×4 各种类容量 C0..C3 ≤ 127
20  u8×4 各种类已用数 N0..N3（N ≤ C）
24  u32 CRC32（从偏移 32 到区尾）
28  u32 CRC32（头的前 28 B）
32  K×32 表项；n 之后全 0
…   行区：C0×62、C1×33、C2×96、C3×56，各自 4 字节对齐；已用数之后全 0
```

**表项**（32 B）：

```
0      基底槽位 ∈ {1,2,3,5,6,7,8}
1      标志：必须等于掩码里每个单元上基底描述符的 [1]
2..3   T = (标志&4)?0:2
4..7   内容 CRC（电脑端算，用作身份）
8..17  10 个行索引，次序同描述符（A5 B5 C080 C100 A20 B20 C D A14 B14）；bit7=1 指效果区本种类第 (i&0x7F) 行
18     单元掩码 1..7：bit0 = 50mm，bit1 = 28mm，bit2 = MOUNT
19     0（第二阶段可能使用，本版必须为 0）
20..31 名字：定长 12 B，1..12 个字符，不足补 0
```

**容量**（P2-07）：
- C1 = K + ⌈K/2⌉：每个效果占一条 B5，另外只多 K/2 条，所以只够约 K/4 个 T1 效果（每个 T1 再要 C、D 两条）。
- T1 版（50mm+28mm）和 MOUNT 的 safe 版分开存时是两个表项，可能还多一套拟合行。
- K 计的是全局表项数，不是每个镜头看到的名字数。

### 3.3 校验顺序（相机侧，`ig_init` 里，任何能力发布和第一次原生配方写入之前）

1. **`fx_area`**（P2-05）：
   - GXDP 头长 80 B、版本 2；
   - 偏移 4 字节对齐、≥ 80、在段内；
   - 长度 ≥ 32，并且等于段尾减偏移；
   - 保留字为 0；
   - K ≤ 48，C ≤ 127；
   - `32 + 32K + Σalign4(Ck·len_k)` = 实际长度。
2. **头**：魔数、版本、头长、表项长、保留字、n ≤ K、N ≤ C；头 CRC 和区 CRC；n 之后的表项全 0。
3. **每个表项**：
   - 基底；掩码；[19] = 0；T；
   - 掩码里每个单元上，基底描述符存在并且标志相等（重点是 MOUNT 的 06）；
   - 名字 1..12 个字符，都在 0x20..0x7E，不含 `\`，第一个 0 之后全 0。
4. **每条行**：
   - 索引在界内（内置池 < 行数，效果池 < N）；
   - 按种类套用内置行的同一套规则：0 类 `a_valid`（第 0、8 行上限 4094，第 4 行 4095）；1 类不减；3 类 `matrix_valid`；标志含 2 时第 6、7 行的 [32] ≥ 128。
5. **原有的行池、描述符、pin 和逐行规则全部保留。**

任何一项不过，`ig_init` 就返回 `ENG_REJECTED`。电脑侧的严格检查（内容 CRC 重算、行去重、每行都被引用、全点扫描）见 §4。

### 3.4 失败时的行为

| 情形 | 结果 |
|---|---|
| 效果区不合法 | 整个 DAT 被拒，在第一次原生配方写入和能力发布之前就拒收，**沿用原厂启动状态**，单元和 S 零写入。只有当该启动状态已经确认是 Standard，并且九行和 T 都是原厂时，才称为"纯 04"（复审） |
| 调节量运算返回 −2 | W 之前拒绝，零写入 |
| 原厂参数锁忙 | 与 g150 相同（§3.5） |
| W 之后失败 | 恢复到确认态：确认态是效果时，按效果身份从 DAT 重新展开；还不行就回到纯 04 |
| 断电 | 效果行丢失，S 选择是 1 → 下次开机纯 04 |
| 记住 | 选中效果时写 40 个零，开机不预选 |

### 3.5 与锁忙修法的关系（P2-09）

- 效果走 g150 的同一套事务：
  1. 切换并且计划非空时，先用 op 6 查锁（`eng_core.c:376`）；
  2. 写九行、T，并读回；
  3. op 2 写 S，这时才遇到忙，就用 `g.live` 全量写回此前的状态（`:341`、`:442`）。
- **效果身份**：`EngRecipeRef`（`eng_core.h:6`，现在是 unit、slot、identity[49]）加效果序号和内容 CRC。当前态、确认态、切换比较、补偿和重算都要用完整身份，不能只按基底槽位区分。
- **"计划为空"以真实比较为准**：模式、色彩、WB 等全部计划字节都相同才算空。现有内置配方和效果的计划字节都相同（实测：模式 1，色彩和 WB 全 0），但实现里照样按比较结果判断，不预设。
- **锁忙回归**：把 g150 的 `held-busy-ok/half/menu`、`race-at-s-ok/half/menu`、`transient-busy-fixed`、`offer-busy` 扩展成四种切换：
  - 内置→效果；
  - 效果→同基底的另一效果；
  - 效果→不同基底的效果；
  - 效果→内置。

  每种都核对九行、T、S、确认态和重开以后的状态。

### 3.6 名字与文本（P2-02、P2-03、P2-04）

### 5.2 拟合和编码的验收要点（来自复审，全部是放行条件）

1. **黑白**：
   - 用基底 3，C080 用内置索引 3 那一行。独立解码证实三个单元的这一行都是 96 B 全零。
   - 不许用 `fit.py:255` 的 bw 分支返回的 04 颜色行。
   - 验证"还是黑白"时，要从**最终编码行**计算结果。`fit.py:103` 的模型把 y 直接复制成三个通道，不能拿它来证明。
2. **矩阵**：用量化后的 row 与 row2（两行合计 56 B）。Tri-X 能不能共用 03 的矩阵，要比较最终字节，不能为了省空间无条件换回去。黑白基底沿用 03 的控制表：Filt 可见，Satu 隐藏，隐藏项保持默认值。
3. **14 = 5**：新效果的 A14 = A5（内置 A 索引 0），B14 = B5（量化 q 的索引）。不许把原厂 04 自己的 A14/B14 带进来（04 的第 14 行与第 5 行不同）。
4. **MOUNT**：用 50mm 的拟合行，保留 MOUNT 自己的原厂 04 和 pin，不重用旧 MOUNT 那批有曝光偏差的拟合。T1 的控制字、C/D 行和掩码一起编码；MOUNT 不能选用另外两个单元的 T1 表项。50mm 的模型不能当作 28mm 和 MOUNT 的独立标定。
5. **整数结果**：`ceiling.safe_fit` 现在只返回预测函数（`ceiling.py:149`）。实现时要把 `Problem.quantize` 的整数结果保留下来，用于编码，不许从浮点预测倒推行。预测和 CRC 都按最终编码行重算，不沿用旧分数。
6. **fotufilm**：用 `_srgb.cube`，不用 `_p3out.cube`。after04 和 scene 两种解释分别拟合，在同一留出集上比较，取余差小的那个。
7. **控制表**：基底 5 的控制表确实有 Satu、Warm、Tint、Splt（`kv_data.c:25`）。每个单元按点表逐点检查，再补极端组合，C 和 Python 的结果对照。相机端保留"W 之前返回 −2 就零写入"的路径。

## 6. 第二阶段：30 个以上，效果库放进 v4 的图像区

### 6.1 为什么要换地方

本阶段的上限约 32–42 个（§2.4）。到这个量，主块里几乎每个字节都用上了。再往上，不管是 DAT 文件上限还是小堆，都没有余地。图像大区很大：`0x808BC000` 起 124,518,400 B（`0x200C0DD0/D4`，`research/inbody_xpan_halfframe/REPORT.md` §3.1）。只需要从里面让出很小一块，并且它不在 256 KiB 小堆里，不会和原生分配争。

### 6.2 一次机身改动同时满足半格和效果库

| 项 | 规格 |
|---|---|
| 长度字 | `0x200C0DD4`：`0x076C0000` → **`0x06A80000`**（减 12 MiB + 256 KiB）。半格方案原来是减 12 MiB（`0x06AC0000`），这里在同一个数据字上多减 256 KiB，不占 resident 字节 |
| 保留区布局（从新的大区末尾起） | `[0, 12 MiB)` 给半格的帧缓冲；`[12 MiB, 12 MiB + 256 KiB)` 给效果库。两者不重叠，各自独立 |
| 备选：共用 12 MiB | 半格只要一帧 YUV422（12,212,224 B），12 MiB 尾部还剩 370,688 B，放得下 256 KiB 的效果库。好处是长度字仍是 `0x06AC0000`，不多占输出槽。前提是半格的最终缓冲 ≤ 12,320,768 B，要等半格设计定稿才能确认。建议默认用独立布局 |
| 读入 | v4 的 resident 在读完 `GXRCE.DAT` 之后，**用同一条调用路径、在同一个时机**读入 `/ATA1/GXRFX.BIN`（≤ 256 KiB），核对长度和 CRC，并核对 DAT 头里登记的 GXRFX 身份；通过后把地址和长度发布到 root 的新字段。这条路径每次开机都在用。**按键时、滚动时都不读卡**，不涉及 g147 的读卡门问题。具体的 API 和锁的合同要在 v4 复审里逐条列出 |
| 失败 | GXRFX 缺失或不合法 → 效果库判为空，内置配方照常可用，Looks 页只显示 DAT 里自带的效果，或者显示 `None`。不会出现半套效果 |
| DAT 侧 | 效果区格式沿用 `GXFX`，只是地址改由 root 发布。表项改成 v2：行索引用 u16，表项 44 B，所以每个效果约 260 B，256 KiB 约能放 1,000 个。DAT 里的效果区可以缩小或去掉，主块再腾出约 8 KB。效果数到几十个以上时，Looks 页要分组（例如黑白、反转片、负片、电影卷、拍立得、品牌），仍然按 8 行虚拟滚动 |
| 代价：连拍排队 | 输出槽池在单 YCC 时从 58.0 MB 降到约 45.2 MB（−22%）；在双 YCC 时从 33.5 MB 降到约 20.7 MB（−38%）。其中效果库那 256 KiB 只占 −0.45% / −0.78%，连一个槽都不到；大头是半格的 12 MiB。少几张要看 SLOT 页的槽大小（§6.3） |
| 代价：resident | 第二个文件的读入、校验和发布，约 120–200 B（估计），放进 archB 扩展（常驻 RAM），不占窗口（memory：body-update-bundle） |

### 6.3 v4 之前要上机确认的（只读，不加大主请求）

用一张观察 DAT，与半格研究 §5 的 IMG、SLOT、MEM 页合成一张：
- 主请求 ≤ 107,612 B（预计约 60 KB）；
- 不调用任何文件接口，不碰 47，不调用分配或释放；
- 遵守 P2-10、P2-11。

| 页 | 内容 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| IMG | 运行时的 `[0x200C0DD0]`、`[0x200C0DD4]`、P 的布局字段（+0xEC/F0/F4/F8）、单还是双 YCC | 大区起点、长度、各分区的实际位置 | — |
| SLOT | 各尺寸类别的槽基址、个数、间距 | 减 12.25 MiB 以后连拍少几张（换算） | — |
| MEM | 大区最上面 12.25 MiB 分块的校验值变化 | 拍照或回放以后**有变化** = 这块被原生用过，印证"输出槽一直用到顶" | **没变化 ≠ 没用过**（P1-01 的教训）。最终证明靠 v4 的哨兵测试：v4 让出以后，这块归我们，写入图样，连拍、回放、视频、USB 以后再核对 |
| BW | 在大区窗口里读 64 KiB 测带宽（只读） | 这个窗口有没有缓存；效果库在开机时校验 256 KiB 要多久 | — |

**观察版的边界**（P2-10、P2-11）：
- 读之前验证 root、堆边界和归属；不把 base 到主块尾一律当成自有；
- 遍历失败、布局变化或出现新 UI 块，就判这次读数无效；
- 会话最大值单独累积，不随显示历史丢失；
- 用复审的方法测整个回调的指令数（≤ 2.0 M）、IRQ 状态和菜单任务的栈。

### 6.4 v4 验收（刷机以后）

- **哨兵测试**：开机后在 256 KiB 效果库区和 12 MiB 半格区写入图样；连拍到槽满、回放并放大、录视频、USB 连接、格式化取消以后，图样必须完全不变。
- **效果库读入**：三种情况——文件缺失、损坏、长度超限——都要判为空库，内置配方照常可用。

### 6.5 真正的分配观测（可选，建议一起放进 v4）

要想以后有运行证据来放宽小堆的主请求上限，必须在分配器上记账。

| 项 | 规格 |
|---|---|
| 钩子位置 | 低层申请 `0x2005BF5C` 的入口（记录 r4 = 请求长度、调用者 LR）和返回（r0 = 结果）；低层释放 `0x2005C038`（读块头跨度）。这两处覆盖所有调用者，包括跟踪包装 `0x200BBE00/0x200BBF20` 和我们的 resident |
| 记什么 | 当前已用跨度、会话峰值、最大一次请求、失败次数、最后一次失败的长度和调用者；另有一个 32 条事件的环（每条 16 B）。只有这些计数器才能真正回答"峰值是多少、有没有失败"（P1-01） |
| 并发 | 低层分配器本身不屏蔽中断（`0x2005BF5C` 起的指令里没有 PSW 操作）。所以记账时自己用 `rv_irq_save/restore` 保护，只记账，**不改变分配结果** |
| 字节 | 2 个跳板，各约 16–24 B，放在窗口里；记账代码约 140–200 B，放在 archB 扩展；RAM 计数器 32 B，加事件环 512 B（估计） |
| 能不能放进 v4 | 能，但它在所有原生申请的必经之路上，出错会影响整机。所以要单独一个开关位，默认关，由诊断 DAT 在一次会话里打开，并且有自己的复审项（跳板正确性、替换掉的原指令、栈、IRQ） |

### 6.6 第二阶段的版本

1. 观察 DAT（§6.3），与半格研究共用，约 1 轮。
2. v4 机身：保留区、GXRFX 读入、可选的分配观测，加上半格和 XPan 的入口，一次刷机。
3. v4 配套 DAT：效果库地址、表项 v2、Looks 分组。
4. 电脑端的 GXRFX 写入。

另一条路——卡上分库文件，按键时读——不再推荐：它要先关闭读卡门的 G1–G6，而 v4 方案根本不需要按键时读卡。

## 给用户的大白话

- **现在能放几个**：第一批 10 个（M9、两个哈苏、Tri-X、Portra、Velvia、Kodachrome、Vision3、instax、Metropolis）**全部放得下**，而且相机用的内存不比你现在日常用的 g137 多。办法是把调节量的数据表"压一压"：原来每个点都存了两个数，其中一个可以算出来，三个镜头之间还有很多重复，压完省下约 9.5 KB，正好够放下效果。按现在的估计，最多能放 30 多个；第一版先留 32 个位置，以后加效果只是电脑重写配方文件，不用出新版本。
- **要不要再上机测**：不用专门测内存了，上次那种"加大内存的测试"已经取消。正式版做好以后，B 卡上试一次，大约 5 分钟、拍 3–4 张就行。
- **要 30 个以上，等什么**：等下一次机身更新（v4）。那次刷机会从相机拍照用的大缓存里让出一小块（256 KB，约能放上千个效果），和半格要用的那 12 MB 一起让出来，只刷一次机。代价主要来自半格那 12 MB：连拍时能排队等写卡的张数会少两成左右；效果库那一小块本身几乎没有影响。刷 v4 之前，要先拍几张只读的诊断屏幕照片，确认这块缓存的情况。
