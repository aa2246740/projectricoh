# GXR 1.51 引擎生命周期静态研究

建议采用“第一次打开配方菜单时从 `/IROM/` 加载、代码块持有、链路变化只作废单元绑定”的结构。已找到堆初始化、SD ID、单元信息更新及链路通知的具体入口；跨休眠的 RAM 保持和完整插拔通知覆盖仍未关闭，不能把“持有到关机”标为已通过。

本轮只做静态逆向，没有构建、生成卡文件、操作相机或存储卡、安装包、提交或推送。产出只写本目录；官方固件与其它 worker 目录只读。固件摘录、原始窗口和派生表全部在经 `.gitignore` 忽略的 `local/`。

“已核实”指本轮 GNU M32R 指令/字节核对，或明确注明的任务给定历史证据；“推断”包括建议设计；“未知”不以静态负搜索代替实机结果。

## 1. 结论与剩余阻断项

| 问题 | 状态与答案 |
|---|---|
| 谁初始化主堆？ | 已核实：分配器 `0x2005BF5C` 读取 `0x200D3488`；为零时在 `0x2005BF78` 调 `0x2005BF00`。既有固定引用清单中只识别到这一处建堆 caller；它是惰性初始化，不能说“开机直接初始化一次”。 |
| 回放、模式切换、USB 是否显式重建堆？ | 已识别固定 caller 中没有独立的这些重建入口。推断：正常路径中 allocator 不会每次重建。未知：间接调用、整段覆盖及实际电源恢复路径是否绕过这份清单；没有据此关闭 USB/休眠 gate。 |
| 能否识别破坏性重置？ | 已核实：建堆会重写空闲链；启动可清掉堆管理指针；段 1 重载会恢复堆边界的文件初值。常驻层可在这些已定位边界维护自己的代次。尚无“所有破坏性重置都已覆盖”的证明。 |
| 睡眠是否保 RAM？ | 未知。找到原生 sleep 组件及向电源接口交接的路径，没有得到 SDRAM 自刷新、供电保持或恢复后堆归属的闭合证据。 |
| 唤醒是否重新复制段 0？ | 未知。已核实 body bootstrap 自身请求段 1、15；通用段装载器支持覆盖段 0。没有闭合实际唤醒到哪种启动/Monitor 路径。 |
| 卡换过能否便宜地判断？ | 部分关闭。原生 `0x200A3240(dst)` 提供 16 B SD ID 缓存，原厂 GSID 使用它；`0x200A3568` 是缓存重建入口。未找到可直接采用的单调挂载代次，也未证明全部物理插拔都经过该入口。 |
| 单元缓存何时更新？ | 已核实：组件 init 填 `0xFF` 并登记块传输 13；接收 callback `0x200637E0` 安排 2048 B 接收，校验后置有效标志。getter 本身不更新。 |
| 单元会话如何作废？ | 设计可明确落点：ready setter `0x200935B4`、信息接收入口/出口、原生 unit 组件电源处理入口 `0x200630F4`。物理装卸到这些入口的完整覆盖仍需观察。 |

本轮没有重新调查已定位的四处直接回放 caller、RPC 8 表写入或三模块地址表；沿用任务给定事实与 `stage2k_design/FOLLOWUP.md`。历史 P0 成功只覆盖加载、分配、同步和短时执行，未覆盖长期持有。

## 2. 主堆的寿命与重置

### 2.1 惰性初始化的真实条件

已核实：`0x2005BF68` 读堆基址；非零就跳过初始化。`0x2005BF00` 从既有常量建立 `[0x20704800,0x20744800)`，写入边界 `0x200D3488/8C`，并通过 `0x2040E088` 建立分配器管理链。这会把原有分配全部从新建空闲链的意义上作废。

官方文件中 `0x200D3488/8C` 的初值都是零。固定引用和精确 BE32 查询没有发现另一处直接初始化调用或显式清零 store；这个结论只覆盖既有静态引用索引及这些精确常量。运行时拼接指针、批量 memset、DMA 和装载器写入不受此否定结论约束。

分配器返回 `header+12`，把头的 next 清零、`header+4` 的分配标志写 1。释放器在 `0x2005C03C` 回到 `p-12`，检查对齐、边界、长度、标志和 next，再修改空闲链。它不认识扩展的会话代次。因此“地址在主堆内、magic 还在”不等于可以调用或释放。

证据 E1：`local/body-2005bf00-2005c038.asm.txt`、`local/body-2005c038-2005c180.asm.txt`、`local/refs-2005bf00-200d3488-200d348c-2040e088-2040f818.txt`、`local/words-200d3470-200d34b0.txt`。

### 2.2 已识别的重置/覆盖边界

| 边界 | 已核实的行为 | 对引擎的影响 |
|---|---|---|
| `0x2005BF00` 建堆。 | 重建边界和空闲链。 | 先作废 heap lease；不得再 free 或恢复使用旧块。 |
| `0x20055048` 后的启动大清零。 | 调 `0x2005BE50`，返回零时清 `[0x2040AF84,0x20616B5C)`；非零跳过。这一范围包含 `0x2040E088`，不包含主堆内容区。 | 即使旧代码、magic、canary 留在堆 RAM，管理指针也可能已失效。 |
| 启动的另一段清零。 | `[0x200D1838,0x200D3480)`；末端在堆边界变量之前。 | 不能说这一循环把 `0x200D3488` 清零；它没有。 |
| 原生段 1 重载。 | 段 1 初始化范围包含 `0x200D3488/8C` 的零初值；该段 BSS 从 `0x2040E088` 开始。 | 既可能恢复边界初值，也会清掉管理指针，旧分配不能复用。 |
| 段 0 重载。 | 当前补丁窗口和建议 root 均在该段初始化范围内。 | root 可被覆盖，不能用 root 自己的 magic 或 loaded byte 证明它跨重载存活。 |

`0x2005BE50` 会按启动记录调用数个恢复 helper 并返回条件值。本轮读到了其分支，未把“返回非零”擅自命名为睡眠恢复，也没有证明它恢复了主堆。正常开机、暖重入和真正睡眠必须分开观察。

证据 E2：`local/body-20055000-20055110.asm.txt`、`local/body-2005be50-2005bf00.asm.txt`、`local/body-2005bd20-2005be50.asm.txt` 与 `local/inventory.json`。

### 2.3 对普通菜单、回放和 USB 的结论

推断：在同一 allocator 生命周期内，菜单关闭不应释放常驻引擎，回放和模式事件也不应因视图关闭而释放代码。任务给定的 Stage2l 行为支持每次重新取 S，不能把 S 当根状态。

未知：没有把全部 USB 入口和全部电源分支的间接调用图闭合，也没有运行这些动作。这里能支持“把独立 engine owner 放在常驻层”，不能支持“回放/USB/睡眠后旧指针必定可执行”。

## 3. 电源管理与段 0

### 3.1 读到的省电路径

已核实：组件表在 `0x200C1380/84` 登记 sleep init/finish `0x2006020C/0x200602FC`。初始化配置 22 个状态位，以参数 100 登记周期服务，并登记 scalar RPC 41/42；时间单位未证。`0x20060300` 按状态表调用寄存器 helper `0x2005FDB8`、`0x2005FCB0`、`0x2005FC08`，没有在这段代码里调用主堆初始化或段装载器。可直接读到的写入包括 `0xFF000074` 及该组件基址 `0xFF700000` 的偏移字段，未给它们补未经证实的 SDRAM 寄存器名称。

已核实：unit 组件任务入口 `0x20062F18` 使用原生 event flag 等待，处理后可转 `0x200630F4`。后者经设备 37 的 ioctl `0x2510`，成功后在 `0x2006316C` 停在原生等待循环。该 ioctl 经 `0x20070970 -> 0x200702F0`，继续使用原生电源传输接口。没有读到它保存整个主堆或发布“SDRAM 已保持”的状态。

推断：这些配置用于时钟/省电管理，是状态变化与电源交接的观察候选。未知：哪个状态对应用户菜单的睡眠、显示关闭、自动关机，以及外部控制器在交接后怎样处理 SDRAM 供电。不能用组件名 sleep 或函数能返回替代 RAM 保持证据。

证据 E3：`local/words-200c1200-200c1400.txt`、`local/body-2005fc00-20060320.asm.txt`、`local/body-20060300-20060600.asm.txt`、`local/body-20062d30-20063100.asm.txt`、`local/body-200630f4-200636c0.asm.txt`、`local/body-20070644-20070a28.asm.txt`、`local/body-200702a0-20070368.asm.txt`。

### 3.2 段装载的肯定证据与盲区

已核实：body 段 0 入口 `0x2004B000` 经 `0x2004B03C` 运行 bootstrap，后者在 `0x2004B0F0` 请求段 1、在 `0x2004B120` 请求段 15，然后进入段 1。这里没有再次请求段 0；段 0 的更早加载不在这两条调用内。

已核实：主装载器 `0x20088358` 接受 0..15，并不自行用 loaded byte 阻止重复装载。复制成功后清该段 BSS，在 `0x20088534` 写 `0x200D7F74[index]=1`。`0x20068818` 的普通本地分支会先查 loaded，但另一条路径 `0x20089158 -> 0x20088358` 直接调用装载器；其另一分支还可进入替代装载器 `0x20088E5C`。

因此 loaded 是布尔状态，没有记录重载次数。只在 `0x20088358` 挂通知也会漏掉替代装载器和更早的 bootstrap/Monitor 路径。`0x20068818` 还有单元转发分支，不能把它的返回值当成 body 段装入凭证。

未知：本轮未闭合真实唤醒到 Monitor、bootstrap 或持续执行的选择条件；不能回答“唤醒一定不重拷段 0”。已有 Monitor 装载器证据沿用 FOLLOWUP §2.4，本轮未重新反汇编 Monitor。

证据 E4：`local/body-2004b000-2004b0a0.asm.txt`、`local/body-2004b0a0-2004b130.asm.txt`、`local/body-2004b89c-2004badc.asm.txt`、`local/body-20088300-20088610.asm.txt`、`local/body-20089158-200891e0.asm.txt`、`local/body-20088e5c-20088fc8.asm.txt`、`local/body-20089060-200891b4.asm.txt`。

## 4. 卡身份、初始化与 `/IROM/`

### 4.1 可以复用的 16 B SD ID

已核实：`0x200A3240(dst)` 在媒体状态允许时，把 `0x204C6640` 起的 16 B 复制到 caller 的缓冲；失败返回 -1。原厂 `0x20383600` 调它并使用 GSID 的 SD ID 格式串输出。这是可用的原生身份指纹，不需要为观察再次打开卡文件。

已核实：`0x200A3568` 初始化过程中，`0x200A379C -> 0x200563A4` 取原生 SD 驱动缓存；失败分支在 `0x200A37AC..BC` 清零 16 B，成功分支在 `0x200A37E0..0x200A3818` 按 word 重排后写入 `0x204C6640..4F`。上层 `0x20114548` 的参数 1 路径也会调用这一初始化函数。原生 I/O 错误恢复 `0x200A39F0` 同样会再调用它。

这证明了缓存来源与更新点，没有证明标准 CID 的各 bit 含义、不可克隆身份，或每次热插拔立即刷新。`0x200A3240` 只是缓存读取，同卡重插仍会得到同样的值。

证据 E5：`local/body-200a31d0-200a32c0.asm.txt`、`local/body-200a36bc-200a3900.asm.txt`、`local/body-200560d0-20056460.asm.txt`、`local/body-203835ec-203836ec.asm.txt`、`local/body-20114380-20114650.asm.txt`、`local/body-200a39f0-200a408c.asm.txt`。

### 4.2 代次与通知的设计结论

推断：在 `0x200A3568` 入口递增自有 `sd_epoch`，完成前把自有 `sd_valid` 置假；完成后才接受新的非零 16 B 指纹。加载 SD 来源文件时，读取前后都核对 epoch 和指纹，任何变化都丢弃候选。重试导致的额外 epoch 是保守失效，可以接受。

未知：未找到已证明单调的 native 挂载序号；物理插拔、同卡重插和全部原生 mount/unmount 到这个初始化入口的覆盖未闭合。也不能把 `0x200A39C0` 当插拔通知：它是初始化时注册的 completion callback，参数为零时只置状态字节。

`0x200D8080` 仍只是初始化/媒体状态。另查到 `0x200A3550` 写 `0x200D808C`，它也是状态值，不是代次。

对本任务的新架构，卡只送货，加载源是 `/IROM/`。运行中的引擎、单元恢复记录和菜单标签不应再依赖 SD，也不应因换卡直接释放。SD epoch 作废的是运输/导入事务；只有容器所属 `/IROM/` 生命周期变化、heap/root 变化或明确更新容器，才作废加载对象。原生媒体动作是否连带重建共同 VFS 仍未知。

现有 `firmware/stage2l_switch/platform.c` 的 `rfw_read_path` 无条件先检查 `0x200D8080`。将其直接复用给 `/IROM/` 会继承 SD 前置条件；常驻 loader 应按源文件系统分别处理。`/IROM/` 的安装/原子更新由并行 irom_storage/card_container 任务负责，本轮不修改它们。

## 5. 单元装卸、缓存与会话作废

### 5.1 缓存初始化和交换

已核实：`gxr_unit_info(1)` 的 getter `0x20063F64` 只返回 `0x2040F818`。名称 `+4`、版本 `+0x30/+0x32` 沿用 multi_module 已核实布局；getter 不发起刷新，也不检查新鲜度。

已核实：hid 组件初始化 `0x20063A28` 清其 24 B 状态，把 body 信息尾部 `0x200D3720` 起的 1492 B 和 unit 缓存 `0x2040F818` 起的 2048 B 填 `0xFF`。它通过 `0x200902CC` 登记块传输 ID 13，发送 callback 为 `0x20063774`，接收 callback 为 `0x200637E0`；另登记 scalar 58/59 的 callback。这和协调状态使用的 scalar RPC 13 是不同的登记通道。

已核实：接收 callback 经 `0x2006C65C(cache,2048)` 设置原生接收描述，随后把前 2044 B 的 byte 和与末尾 word 比较。失败把 2048 B 填 `0xFF`，返回 -5；成功在 `0x2006387C` 置 `0x2040F804=1`。接收入口没有先清掉以前的该标志，因此不能仅凭标志为 1 接受正在重填或失败后的缓存。

启动的 `0x2005C2CC -> 0x20063894` 建本地 info、等待远端有效，再发送 2048 B 信息并置 `0x2040F808`。这一函数见到先前的 `+8` 标志会直接返回。该标志同样不能替代重连代次。

证据 E6：`local/body-200637b0-200638c0.asm.txt`、`local/body-20063894-20063928.asm.txt`、`local/body-20063a08-20063ae0.asm.txt`、`local/body-20063f24-20063f90.asm.txt`、`local/body-2006c5d0-2006c7b0.asm.txt`、`local/body-200902cc-20090308.asm.txt`。

### 5.2 通知方式与可用边界

已核实：`0x200935B4` 在短关中断区内向 `0x200D7FD8` 存 ready；已查到五处固定 caller，既有置 1，也有置 0。`0x20094860` 只经此 setter 清零。单次读取 ready 无法发现已经发生过的 1→0→1。

已核实：原生 unit 组件创建任务 3，入口 `0x20062F18`，通过 event flag 3 处理原生事件。它可交接给 `0x200630F4` 的电源路径。这不是一个已经证明可以安全挂入同步恢复 RPC 的菜单上下文，也未证明支持透明带电装卸。

推断：在 ready 的实际 store 附近记录自有 `link_epoch`，在信息接收开始前记录 `unit_epoch` 并使绑定失效，成功校验结束后才发布可重绑状态。即使名称和版本相同，每次 handshake/接收都形成新会话。`0x200630F4` 入口可作更早的保守停止点。

通知桩只置代次、关闭入口和颗粒、记录原因。任务 6 在下一次安全边界处理恢复或重新绑定；不得从异步 callback 读文件、free 引擎或发成串恢复 RPC。旧单元的 stock、邻接快照、T 检查、RPC owner 和 active 均不能用于新单元。失去链接以后不向新连接的单元“补写旧恢复”，也不能仅因 active 清零就显示“04 已恢复”；未完成恢复仍是 UNKNOWN。

未知：电气断连、故障掉线以及全部物理装卸是否必然触发这些已识别点。此处给出了可观测且便宜的通知来源，尚未声称物理事件覆盖通过。

证据 E7：`local/body-200935a0-20093650.asm.txt`、`local/body-20093920-20093b18.asm.txt`、`local/body-20094860-200948e8.asm.txt`、`local/body-20062d30-20063100.asm.txt`。

## 6. 加载、作废和最小 hook 建议

### 6.1 对象寿命应拆成三层

| 对象 | 所有者与保留规则 |
|---|---|
| 常驻 root、原厂分派与通知桩。 | 在段 0 既有窗口内明确布局与初始化。root 不放进 S 或菜单 cache。启动/段重载有独立处理。 |
| 引擎代码、容器数据和可信恢复记录。 | 常驻层通过主堆拥有；菜单关闭、普通视图重建、单元换绑、SD 运输事务变化不 free。释放只在引用排空且 heap lease 仍可信时做。 |
| 单元会话、S 与当前视图。 | 绑定 unit/link epoch；MY 后重取 S；每次重开重取 UI。链路变化只作废这层，保留代码分配。 |

最佳加载点仍是已有 `0x2028709C` 菜单初始化入口，在 native 数量、名称、枚举、details 被扩展发布前完成 `/IROM/` 加载与身份校验。只由任务 6 创建/修改引擎，第一次失败维持完整原厂菜单。拍摄 sender 保持常驻，只读已发布的小快照，不跳进需等待的 loader。

一次任务开始和每个会阻塞/让出调度的原生调用返回后都重新比较 heap/link/unit/source epoch。装载中发生通知就撤销候选，不能把返回成功当成旧会话仍有效。实际执行期间若原生能重建堆，事后比较已经太迟；必须先证明破坏性路径与 `inflight` 排空，或在该生命周期停用堆执行。

### 6.2 常驻层应一次预留的边界

下表是语义入口与适配职责，不是可直接刷写的 patch 字节；没有链接、ABI 桩尺寸或时序验收。

| Hook 家族 | 地址/边界 | 最小职责 |
|---|---|---|
| 原有 UI/颗粒条件分派。 | card_engine §1 的九处，包括 `0x2028709C`、`0x202870A8`、标签/数量/details、Fn2、确认、实时提交、sender。 | 默认原厂；只有当前页和代次有效才发布扩展，作废时收回全部 UI 引用。 |
| 启动处理。 | `0x20055074`，两段启动清零之间的首个安全锚点之一；入口适配仍需定稿。 | 不调用 allocator/RPC，只撤销旧发布状态并记录启动；不能把所有重入当冷启动。 |
| 主堆新建。 | `0x2005BF00` 之前。 | 更新 heap epoch，停止旧分配的使用和释放；保持原生初始化语义。这个通知本身不能解决执行中被覆盖。 |
| 段复制。 | `0x20088358`、`0x20088E5C`；bootstrap `0x2004B89C` 及更早 Monitor 为另一类启动边界。 | 复制段 0/1 前撤销扩展发布；维护独立见证。不能只挂 `0x20068818` 或读 loaded byte。 |
| 链路 ready。 | `0x200935DC` 的实际 store 附近，位于 `0x200935B4` 的短临界区。 | 记录 link epoch 并作废绑定，重放原并行/顺序指令语义。只采样 bool 不够。 |
| 单元信息交换。 | `0x200637E0` 入口和完整返回出口。 | 重填前作废、序号变更；仅本次校验成功后允许重新绑定。 |
| 单元电源交接。 | `0x200630F4` 入口。 | 立即关闭新扩展调用并记录原因；不在这里临时恢复 T。 |
| SD 重初始化。 | `0x200A3568` 入口/返回。 | 更新运输会话 epoch，成功前不采用缓存身份。不因它释放 `/IROM/` 的已加载代码。 |
| 模式、直接回放、正常收尾。 | 已有 `0x20069D4C`、`0x202FB9CC` 最早副作用前、`0x2005CF7C` 最前。 | 在有效链接和任务 6 中有界恢复，再调用 native；沿用既有四处 caller 的失败处理要求。 |
| 省电状态观察。 | `0x20060300`，以及 `0x200600D0/0x2006015C`。 | 先用于探针确认真实动作映射；未验证前不把低时钟状态统一当成睡眠。 |

要支持的日常事件尚未证明全部经过同一通知点，因此现在不能承诺固定最少 patch 数。首版若只做 `/IROM/` 的内存保留，SD hook 可以仅管理运输事务；启动、heap、unit 和原厂回退仍是常驻 ABI 的必备边界。约 3.75–5.5 KiB 仍是原设计预算，本轮没有重新测量容量。

模式/回放的恢复失败问题不因找到生命周期通知而消失。任务给定四处 caller 有忽略返回值行为；不能让 `0x20301114` 返回 -1 后就宣称已经拦住回放，也不能把生命周期错误码当原生下一 mode 返回。

## 7. 静态关不掉的最小探针

完整设计见 [PROBES.md](PROBES.md)，四项可共用一个只读 P 机制与菜单输出。

| 探针 | 要回答的问题 | 明确的失败/恢复边界 |
|---|---|---|
| P1，一次分配保留。 | 菜单、回放、模式、MY、真正睡眠、USB 后，同一地址、allocator 代次、数据/代码和执行结果是否仍有效。 | 任一代次或 CRC 失配立即停用，不读/执行/free 旧块；不反复分配。 |
| P2，启动与段重载见证。 | 操作后是否经过启动清零、主/替代装载器，段 0 root 是否被恢复。 | root 和见证同时丢失报未观测；不主动调用 loader 或 trap。 |
| P3，SD 通知与指纹。 | 不同卡、同卡重插及 I/O 恢复是否都改变自有通知计数，缓存何时刷新。 | 只读 RAM 指纹，不写文件、不主动重置 SD；缺事件即覆盖未通过。 |
| P4，单元通知。 | 同名同版本重新连接是否仍产生 ready/info/power 计数变化。 | 只观察，不发单元写入或电源命令；原生关机且没读回结果时报未观测。 |

这些都是未来验收设计，本轮没有制造或执行探针。不能靠旧 P0 的一次 AB 结果、没卡死或菜单标签未变来替代这些检查。

## 8. 文件、复核命令与边界

| 产出 | 用途 |
|---|---|
| `REPORT.md`。 | 本报告，静态结论、未知项、最小 hook。 |
| `PROBES.md`。 | 四项只读 P 探针、结果格式及恢复边界。 |
| `inspect.py`。 | 可复跑的只读窗口反汇编、既有引用查询、字符串与段映射工具。输出固定落 `local/`。 |
| `verify.py`。 | 对官方文件重验关键调用、段界、提取窗口及 GNU 反汇编结果，不执行相机代码。 |
| `.gitignore`。 | 仅忽略本任务的 `/local/`。 |
| `local/inventory.json`、`local/inputs.json`、`local/findings.json`。 | 官方/工具身份、读取输入哈希和结论索引。 |
| `local/body-*.bin`、`local/body-*.asm.txt`、`local/refs-*`、`local/words-*`、`local/strings-*`。 | 私有原始窗口和派生证据；这些 bin 仅供 objdump 输入，不是固件或可放卡文件。 |
| `local/verification.json`、`local/inspection-notes.txt`、`SHA256SUMS`。 | 复核结果、检查限制/失败记录和交付哈希。 |

在共享检出根目录执行：

```sh
cd /Volumes/Workspace/Projects/T3-Runtime/projects/projectricoh
git check-ignore -v research/engine_lifecycle/local/probe.txt
python3 -I -B research/engine_lifecycle/inspect.py inventory
python3 -I -B research/engine_lifecycle/inspect.py refs 2005bf00 200d3488 200d348c 2040e088 2040f818 --limit 30
python3 -I -B research/engine_lifecycle/inspect.py win 2005bf00 2005c038 --limit 30
python3 -I -B research/engine_lifecycle/inspect.py win 200637b0 200638c0 --limit 30
python3 -I -B research/engine_lifecycle/inspect.py win 200a36bc 200a3900 --limit 30
python3 -I -B research/engine_lifecycle/verify.py
cd research/engine_lifecycle
shasum -a 256 -c SHA256SUMS
```

本轮 `verify.py` 返回 `PASS_STATIC_EVIDENCE`，79 个提取窗口与官方字节及重新运行的 GNU 反汇编逐一吻合，9 个关键调用通过原字节检查。这不是相机生命周期验收。

复跑 inspect 会重写所选本任务 local 证据，现有清单的哈希应在复跑前校验。没有调用任何既有 build/package 脚本。官方 body `ilaunch3` SHA-256 是 `da1980e9d6f3996ede4953b8311cf0ce2abeb4bb300b6ee60a38f38e29a3cdf7`；GNU M32R objdump 为 Binutils 2.43，哈希是 `8d3712c11cac0ffc63b790148c49a916f25d96fceabbb3c1daa125cf4904368a`。

首次写入前和分析工具每次写入前均核对已挂载 APFS、可写、Volume UUID `14BE04EB-AF49-497E-B36A-B078B2F7C5E8`。没有访问 `/Volumes` 下的相机卡或其它卷；没有启动子代理、sleep 或轮询等待。共享检出的既有修改和未跟踪研究均未清理。
