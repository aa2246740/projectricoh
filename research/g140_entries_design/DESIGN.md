## 2. 第 1 层：条目 v2（名字 + 全部调节量）

### 2.1 区域格式 GXUI v2（大端，位置和总长 1,984 B 都不变）

位置和总长不变，所以第七段总长 20,776 和 kv2 偏移 3,392（`eng_data.c:21`、`:76`）都不用改，外层闸门也不用动。

```
偏移  长度  内容
0     8     魔数 "GXUI140\0"
8     2     版本 = 2
10    2     头长 = 64
12    4     区域总长 = 1984
16    4     区域 CRC32（本字段按 0 计算，gxr2_crc_zeroed，与 v1 同一算法）
20    2     记录长 = 32
22    2     条目数 count（g140 引擎要求 ≤ 32）
24    2     格式容量 = 60（64 + 60×32 = 1984）
26    2     value_format = 1（Amount 存 u8 百分数，另外 9 项存 s8）
28    4     记录区偏移 = 64
32    12    三个配方库的 CRC32（与 v1 的 +40 同义）
44    4     kv2 块头里的 CRC32（换了点表而条目没重新验证，就会被拒）
48    16    保留，必须为 0
64    32×60 记录区；count 之后必须全零
```

### 2.2 记录（32 B）

```
0      u8   类型和基底：bit0..3 = 基底槽位 1..8；bit7 = 新效果条目（第 2 层）；bit4..6 = 0
1      u8   单元掩码 1..7：bit0 = 50mm（jlaunch），bit1 = 28mm（qlaunch），bit2 = MOUNT（l08firm）
2..9   8B   名字：1..7 个字符，后面补 NUL。偏移 9 必须为 0（g140 的上限是 7，见 §2.4）
10     u8   Amount 百分数 0..150（control 0）
11..19 s8×9 control 1..9：Cont High Shad Fade Satu Warm Tint Splt Filt
20..23 u32  电脑端长名哈希。相机不解释它，只让 CRC 覆盖它，用来把卡上的条目对回电脑库里的配方
24     u8   效果 id 1..16。不是效果条目时为 0
25..27      0
28..31 u32  效果绑定 CRC32。不是效果条目时为 0
```

- 解码就是逐字节搬进 `int16_t v[10]`，不做换算。
- 隐藏项按 `kv_data_request` 现有的规则保持默认值，例如 03 没有 Satu。
- **为什么是 32 B 而不是 24 B**：第 2 层要给每条记录绑定效果（id 加 CRC，共 5 B）。给 24 B 的记录塞效果字段，要么挤掉长名哈希，要么另开一张表。32 B 时，容量仍有 60 条，比引擎上限 32 多。
- **为什么记录里不存序号**：名字由用户起，相机不再拿序号拼名字。组内顺序 = 存储顺序，由电脑决定。

### 2.3 引擎侧校验（`uv2_validate`，替换 `uv_validate`）

任何一项不通过，整个 DAT 被拒，沿用 v1 的 `ig_init → ENG_REJECTED`，不引入"跳过坏条目"这种新状态。

1. `build_number==140`，第七段长 20,776。改的是 `eng_data.c:21` 的版本号。
2. 头部各字段与 §2.1 一致，保留字节为 0，CRC 正确，count ≤ 32。
3. 三个配方库的 CRC 一致；kv2 的 CRC 一致。
4. 逐条检查：
   - 基底 1..8，bit4..6 为 0；
   - 掩码 1..7；
   - 名字 1..7 个字符，每个字符在 0x20..0x7E 之间，首字符不是空格，末字符也不是空格；之后全是 NUL；
   - 效果字段：bit7=0 时 id 和 CRC 都为 0；bit7=1 时 id 在 1..16，CRC ≠ 0；
   - **掩码里的每个单元**都要通过 `kv_data_request(单元, 基底, levels)`，档位逐点精确匹配。
5. count 之后全零。

第 4 条保证同一个 DAT 在三个单元上的结果一致：要么都接受，要么都拒绝。不会出现"换了镜头才发现 DAT 被拒"。开机时最多调用 96 次 `kv_data_request`，时间**未知**，由 M4 测量（`myrec_v2_design` R3）。

### 2.4 名字和字符集

- **最多 7 个可见字符。**相机一行 9 字节，也就是 8 列加 NUL（`KV_UI_TEXT=9`、`UvState.text[8][9]`）。第 0 列放标记（`>`、`*`、`<`），名字只剩 7 列。这满足"8 个字符以内"。
  - 格式本身给名字留了 8 B。如果 P1 探测（§5）证明 LCD 实际能显示第 9 列，以后只要放开偏移 9 的检查，格式不用变。
- **字符集分两级：**
  - 引擎只检查可打印 ASCII（0x20..0x7E），因为文本服务本来就只接受这个范围（`services.c:348`）。
  - 允许用哪些字符由电脑端的代数 profile 决定，可以更新，不用重建 DAT。
- **g140 的电脑端初始允许集**：现有界面字符串里已经出现过、发布版在用的字符：
  - `A–Z`、`0–9`、空格、`-`、`+`；
  - 小写字母：`a c d e f g h i k l m n o p r s t u v w y`，取自 `MyRec`、`Unsaved`、`Back`、`None`、`Error`、`Default`、`Sure?`、`Cont`、`High`、`Shad`、`Fade`、`Satu`、`Warm`、`Tint`、`Splt`、`Filt`、`Amt`、`DISP:Tw`。
  - `b j q x z` 和其余标点等 P1 照片确认后再加入。
  - `>` `<` `*` 不允许出现在名字里：它们是第 0 列的状态标记，放进名字会让人看不懂。
- 中文长名、带重音的字母：电脑端要求用户另起一个短名。默认建议取长名的 ASCII 转写前 7 个字符，用户可以改。长名本身只存在电脑上，卡上只放它的哈希。
- **相机设置成日文时**：`rv_native_ascii` 带 language 参数，ASCII 的字形是否随语言变化是**未知**。P1 要在用户当前的语言下拍；如果用户平时会换语言，就两种语言各拍一张。

### 2.5 相机上的 MyRec（8 行，每行 8 个字符）

| 视图 | 逻辑行 | 与 g139 的差别 |
|---|---|---|
| L1 | 8 个内置配方 + ` MyRec` | 不变 |
| ~~分组页~~ | — | **去掉**。名字由用户起以后，按基底分 GRP/FCC 等 8 组就没有信息量了，还多按一层 |
| 条目页 | ` < Back` + 当前单元可见的条目，按存储顺序；一条都没有时显示 ` None` | 平铺，最多 1+32 = 33 行，用 8 行窗口虚拟滚动（`uv_window` 已穷举到 33） |
| 卡片、逐项页、数值页 | 标题是 `<` + 名字的 7 个字符 | 标题以前是 `<FCC*002` |

条目行的格式：
```
第 0 列：'>' = 正在用，没微调；'*' = 正在用，已微调；' ' = 其他
第 1–7 列：名字
```
- "已微调"的判断：当前向量和 `saved[i]` 逐项比较，沿用 `uv_adjusted` 的写法，但比较对象换成该条目解码出来的值。
- 进入条目页时，光标停在当前正在用的那一条；不在用就停在第 1 条。
- 8 行保护不变：所有归我们的视图仍然是 8 行窗口（检查清单第 8 类）。去掉分组页以后，视图种类少了一种。

**备选**（§6 第 2 项）：保留 8 组分页，只改行文字。导航完全不变，风险更小，但名字前面多一层没有意义的组。

### 2.6 与 g139 的兼容和迁移

- g140 引擎只认 v2，g139 引擎只认 v1，不做双解析，因为 DAT 和引擎在同一个文件里交付。混装会被拒：v1/v2 魔数不同，`ig_init` 返回 REJECTED，resident 退出，相机这次开机按原厂运行，不会写单元。这一点是按 `studio_send_to_camera` §1.2 读源码得出的结论，没有上机试过。
- **迁移由电脑端做**，见 §4.3。v1 每条转成 v2：
  - 档位：v1 的位置 0..3 → control 1、2、3、5，Amount = 100，其余为 0。规则与 `kv_ui_legacy_levels` 相同；
  - 名字：原来的相机名把 `*` 换成 `-`，例如 `FCC*002` → `FCC-002`。用户可以再改；
  - 掩码：7。v1 的规则本来就要求三个单元都合法；
  - 长名哈希：配上了电脑库里的配方就用它的长名，配不上就填 0。
- "记住上次配方"不变：用户条目仍然写 40 个零（`memory_build` 的 `if(user)return;`），升级、写卡后照样忘一次。以后如果想让用户条目也能被记住，记录里有空位可以放条目序号，估计 +60…+100 B，**不在 g140 里做**（一个构建只带一个有风险的改动）。

### 2.10 复审方可先补的验收用例（第 1 层）

格式和编码（电脑端与固件共用一份向量）：
- `v2_roundtrip_all_positive`：每个正例 `encode(decode(x))==x`。
- `v2_header_each_field_rejected`：头部每个字段、每个保留字节逐一改错，`uv2_validate` 返回 0，Python 校验器也拒绝。
- `v2_count_33_rejected`：count=33 拒绝；count=32 接受；count 之后有非零字节就拒绝。
- `v2_name_bounds`：名字 1 和 7 个字符接受；0 和 8 个字符拒绝；首尾是空格拒绝；0x1F、0x7F 拒绝；NUL 之后还有非零字节拒绝。
- `v2_mask_bounds`：掩码 0 和 8 拒绝；1..7 接受。
- `v2_levels_each_unit`：对 24 个（单元，基底）组合的每一项、每个合法点接受；表外的每个字节值，只要掩码里有一个单元非法，就拒绝。
- `v2_amount_points`：Amount 只接受该单元点表里的百分数；50mm 的 01 上 75 合法、MOUNT 的 01 上 75 非法，这一对要按掩码得到相应结果。
- `v2_kv_binding`：kv2 的 CRC 改 1 位 → 拒绝。
- `v2_effect_fields_zero`：bit7=0 但 id≠0 或 CRC≠0 → 拒绝；bit7=1 但 id=0、id=17 或 CRC=0 → 拒绝。
- `v2_v1_region_rejected`：g140 引擎读到 v1 区域 → `ig_init` 返回 REJECTED，单元零写入，S 零写入。

相机端（主机模型，三个单元都跑）：
- `myrec_flat_list_8rows`：条目数 0、1、7、8、9、32 时，每一帧都是 8 行，光标和缓存一致，`uv_window` 与穷举结果相同。
- `myrec_mask_filter`：一条只对 28mm 有效的条目，在 50mm 上不显示，在 28mm 上显示，计数正确。
- `myrec_row_marker`：选中后行显示 `>名字`；微调一档后显示 `*名字`；回到原值后又显示 `>`。
- `myrec_title`：卡片和逐项页的标题是 `<` 加名字。
- `myrec_all_controls_apply`：10 个调节量都不为默认值的条目（含 Amount 150、Splt、Filt），选中后九行、T、S 和"在 L1 选同一基底再手调到同一组值"逐字节相同（沿用 `restore_compare` 的比较方法）。
- `myrec_user_not_remembered`：选中条目以后，S 尾部记录是 40 个零；下次开机不预选。
- `myrec_back_exit`：条目页按 Back 回到 L1 的 MyRec 行；按 MENU 退出、半按以后，状态都只能是完整配方或纯 04。
- 回归：81 组完整回归，组页相关的旧用例换成现行版本；测试包至少带 3 条条目，其中 1 条 7 个字符、1 条 10 项全非默认、1 条只对 28mm 有效。
- 尺寸：主请求 ≤ 106,124 B，并且不大于 g139 的 104,756 B（第 1 层应当是减少）。

## 3. 第 2 层：自带效果的配方（"新效果"）

### 3.1 效果是什么

一个效果 = 每个单元一套**替换 base 的深层行**，其余全部借用条目的基底：
- 调节量的点表（`kv_data_request(单元, 基底)`）；
- S 的写入计划，即模式、色彩、白平衡（`make_plan(基底)`）；
- 描述符标志。

计算时，`project_compute` 不再展开内置配方的 base，改为展开效果块。之后完全走现有路径：`kv_apply_work(stock, 效果base, request)` → `deep()` → S → 预览 → 提交。

所以：
- **S 不会出现新值。**基底的 S selector 是 1，断电后仍是纯 04（检查清单第 13 类）。
- **调节量照常可用。**Amount 在原厂 04 和效果之间插值，其余调节量作用在效果上。
- **安全规则：**效果在每个单元上的标志必须等于该单元基底描述符的标志。这样 T、各启用位、颗粒的发布与基底完全相同，变的只是行的内容。行内容再按内置行的同一套规则检查（§1 表格中"内置行的合法性规则"那一行）。

**能表达什么：**3 条 31 点的阶调曲线（0 类行），5 条 33 点的 1 类表，96 B 的 2 类行，以及色彩矩阵。漂白、褪色、交叉冲洗这类"阶调 + 饱和度 + 矩阵"的效果可以表达。

**不能直接表达的：**任意 3D LUT。要先拟合成行，和 01/02 当初的拟合一样（`gr4_nega_returns_r1`）。电脑端需要一个行级拟合器，这是研究工作，不在本设计里；见 §4.5。

### 3.2 效果块格式（两个方案共用）

每个单元一块，512 B：
```
0      u8   标志（必须等于该单元基底描述符的 [1]）
1      u8   0
2..3   u16  T（必须等于 (标志&4)?0:2）
4..506      10 条原始行，按描述符顺序，共 503 B
507..511    0
```

一个效果 = 16 B 头（id、掩码、保留）+ 512 B × 掩码里的单元数：
- 三个单元：**1,552 B**；
- 只有一个单元：528 B。

目录项 16 B：id、掩码、偏移、长度、整条效果的 CRC32。效果最多 16 个。
- 文件或区域头 64 B + 目录 256 B；
- 16 个三单元效果合计 64 + 256 + 16×1,552 = **25,152 B**。

**绑定方式：**条目的 [24]、[28..31] 记着效果 id 和整条效果的 CRC。相机加载时两者都必须相等，不相等就不应用。DAT 和效果文件只要有一个换了，相应的效果条目就会拒绝应用，其他条目不受影响。

### 3.3 方案 X：效果放在 DAT 里

- **位置：**第七段 kv2 块之后追加一个效果区，格式同 §3.2。第七段总长不再是常量，`eng_data.c:21` 的长度检查和 `uv2_validate` 的长度检查要改。
- **加载时机：**开机时 `ig_init` 一次性校验整个效果区，包括每块的行规则和标志规则。选中时只拿 DAT 里的指针，没有 I/O。
- **尺寸：**
  - 代码：公共部分 798 B（实测，[p_fx_common.c](prototype/p_fx_common.c)）+ X 专用 596 B（实测，[p_fx_x.c](prototype/p_fx_x.c)）+ 集成估计 200–400 B，约 **1.6–1.8 KB**；
  - 数据：区域头和目录 320 B，另加每个效果 1,568 B（三个单元）。
  - 合计：1 个效果约 +3.5 KB，4 个效果约 +8.2 KB。
- **对预算的影响：**做完第 1 层以后，到 106,124 B 只剩约 1.7–2.3 KB，**1 个三单元效果都放不下**。只放一个单元的 1 个效果（约 +2.5 KB）勉强贴线。超出部分要靠放宽预算，而放宽需要先有堆探测的结论（`heap_headroom/REPORT.md`：108,124 B 时已有 77,312 B 原生申请失败的反例，还没上机证实）。
- **读失败、锁忙：**不存在。DAT 被接受了，效果就一定可用。
- **断电：**效果行在单元 RAM 里，断电就丢；S selector 是 1 → 下次开机是纯 04。
- **记住：**效果条目写 40 个零，与普通用户条目相同。
- **优点：**没有新的 I/O 上下文，复审面最小。**缺点：**每多一个效果，主请求就涨 1.5 KB，而且每次改效果都要重写整个 DAT。

### 3.4 方案 Y：效果放在卡上单独的文件里，选中时读取（推荐）

- **文件：**`/ATA1/GXRFX.BIN`，8.3 短名，格式同 §3.2。由电脑写入。相机只读，不新建、不改名、不删除、不改长度。
- **加载时机：选中时。**
  - 用户在条目页对效果条目按 OK 或 DISP，才读文件。
  - 光标滚过效果条目**不预览**：行上只显示名字，生效标记 `>` 仍留在原来那一条上。
  - 开机时**不读**。开机全部读进来需要 16×512 B = 8 KB 常驻，比方案 X 还大。
- **读法，完全照 g146 已证明的形状**（原型 [p_fx_y.c](prototype/p_fx_y.c)）：
  1. 取锁只试一次：`0x2005E360(47,0)`。返回非 0 → `FX_BUSY`，不做任何文件调用。
  2. 新句柄：parse → lookup(mode 2) → attach。返回 −1 → `FX_OPEN`（这只表示"未知"，不等于"不存在"）。打开计数 ≥ 2 → 同样按 `FX_OPEN` 处理。
  3. 簇字节数和缓冲地址必须合理。置 mode 2，调用 `0x200AAD38(fd, 0, 簇)`。返回值必须大于 0 且**小于**簇（只有这样才能确认文件完整读进来了），否则为 `FX_READ`。
  4. 在句柄的缓冲里：
     - 核对文件头：魔数、长度字段 = 实际读到的字节数、头和目录的 CRC；
     - 按 id 找目录项：CRC 必须等于条目里的绑定值，掩码必须包含当前单元，长度必须与掩码一致；
     - 算整条效果的 CRC；
     - 当前单元那一块按行规则和标志规则检查；
     - 全部通过才把 512 B 复制到**暂存槽**。

     任何一项失败 → `FX_BAD` 或 `FX_GONE`，槽不变。
  5. 关闭（`0x200A6750`）。返回 −1 时，即使已经复制，也按 `FX_READ` 处理。最后释放一次 47。
  - 不 seek、不写、不在相机里读回；每次选中最多试 1 次，没有循环。
- **两个槽（BSS 2×512 B）：**
  - "当前"槽：`g.current` 是效果时，给 `settings_match`、`eng_check_settings` 重新计算用；
  - "确认"槽：`g.confirmed` 是效果时，给 `recover_confirmed` 用。
  - 新效果先读进不在使用的那个槽，应用成功后再改归属。应用失败时，原来的两个槽都不受影响。
  - 每个槽带标签 (id, CRC)，`project_compute` 核对标签，不符就返回 REJECTED。
- **读失败或锁忙时相机怎么表现：**
  - 这次选择**不应用**：单元零写入，S 零写入，仍保持选择前的完整配方或纯 04。
  - 该行临时显示 8 字以内的提示，文案见 §6 第 4 项：锁忙一种（"再按一次"的意思），读不到或数据不符一种。下一次移动光标就恢复成名字。
  - **不锁存**：下次按键再试，符合检查清单第 5、9、12 类。
- **读成功之后：**
  - 先重新核对归属：文件调用里原生代码会等 SD 驱动的信号量 24、25，可能让出 CPU（检查清单第 3 类）。
  - 再走普通的 `uv_preview` 或确认路径。W 以后的失败沿用现有补偿：恢复到确认态，确认态是效果就用确认槽；还不行就回到纯 04。所以不会出现半套。
- **断电：**同方案 X。效果行断电就丢，S selector 是 1，下次开机纯 04。
- **记住：**效果条目写 40 个零，开机不会预选效果。以后如果要做"开机停在上次的效果、按 OK 才读"，与 g139 方案 B 的语义一致，估计 +80 B，不在 g141 里做。
- **尺寸：**
  - 公共部分 798 B（实测）；
  - Y 专用 844 B（实测：`fx_load` 784 B + 字符串）；
  - 6 个原生桥加取锁，约 120 B（估计，参照 g146 每个桥 12 B）；
  - 引擎和 adapter 集成 300–500 B（估计）；
  - BSS 1,024 B（实测）。

  合计 **约 +3.1…+3.3 KB，与效果个数无关。**做完第 1 层以后，主请求约 107.0–107.7 KB：超过 106,124 B，不超过 108,124 B。
- **文件大小上限：**必须小于卡的一簇。16 KiB 簇（例如 64 MB 的 FAT16 卡）最多放 10 个三单元效果（15,840 B）；32 KiB 簇（常见的 SDHC FAT32）可以放 16 个。电脑端按卡的簇大小拒绝超长的文件。
- **未知（只能上机）：**
  - **U1：在按键入口（OK/DISP，Task 6 的 H07/H08）里读文件。**g146 只证明了 ig_init 和 H01 末尾。模拟器到不了 H07（M2d 结论），主机模型的卡是验收自带的模型，不是原厂代码。
  - **U2：**用户卡的文件系统和簇大小。FAT32 只有静态论证（`unit28_stock` §7）。读不涉及 FSInfo 回写，但 release 静态上能到达它。
  - **U3：**拍照后正在写 JPEG 时，信号量 47 被占的频率和时长，决定"锁忙"出现得多不多。
  - **U4：**一次读取的耗时，决定以后能不能"滚动时预览效果"。

### 3.5 推荐：方案 Y

| | X | Y |
|---|---|---|
| 1 个效果的主请求 | +3.5 KB | +3.2 KB |
| 16 个效果的主请求 | 约 +27 KB（超过硬上限的风险已经很大） | +3.2 KB |
| 改效果要不要重写 DAT | 要（"记住"也跟着丢） | 只写 `GXRFX.BIN`；DAT 只在条目绑定变化时才写 |
| 新的风险面 | 第七段变长 | 在按键入口做文件 I/O、锁忙、两个槽 |
| 上机前提 | 堆探测（预算） | P2 探测（U1–U4）+ 预算决定 |

选 Y 的理由：效果的数量和大小是用户想要的核心能力，X 的成本跟着效果数量线性增长，预算撑不住。Y 的新风险集中在一个已经有 g146 先例的读法上，可以先用只读探测把未知项关掉。

### 3.7 风险（第 2 层）

| 编号 | 风险 | 处理 |
|---|---|---|
| L2-R1 | 按键入口里的文件 I/O 会让出 CPU，返回时菜单可能已经不归我们 | 读完不碰任何原生 UI 字段，重新走归属检查；如果是半按或 MENU 退出，丢弃暂存槽。测试：读文件期间注入换视图、半按、MENU |
| L2-R2 | 原生 open 失败一律返回 −1 | 只判"未知"，不锁存、不新建，下次按键再试（检查清单第 9 类） |
| L2-R3 | 用户自制的行内容合法，但调节量数学会返回 −2（Y 行和非正） | 引擎里这属于 W 之前的拒绝，零写入；电脑端写卡前对每个效果、每个单元、该基底的全部合法点跑一遍 Python 版 `kv_apply_work`（`studio/engine/knobs.py`），有一个点返回非 0 就不让写 |
| L2-R4 | 画面效果出格（这是画质问题，不是安全问题） | 电脑端预览标"电脑预测"；第一次上机用一个保守的效果，只在 50mm 上试 |
| L2-R5 | 两个槽的状态机出错（确认态和当前态交叉） | 专门的用例（§3.8）；能证明的最低保证是：槽对不上时退回纯 04 |
| L2-R6 | 预算：Y 超过 106,124 B | 见 §6 第 3 项。不靠悄悄提高上限来解决 |
| L2-R7 | 28mm 和 MOUNT 没有校准样本，效果在这两个单元上的观感没有依据 | 电脑端默认只给 50mm 生成效果块（掩码 1），其他单元由用户明确勾选 |

### 3.8 复审方可先补的验收用例（第 2 层，方案 Y）

文件和块：
- `fx_block_rules`：每条行规则逐一违反（0 类行不递增、超过 4094/4095；1 类行下降；矩阵越界；T 与标志不符；标志 ≠ 基底标志；尾部不是 0）→ `fx_unit_valid` 返回 0，槽不变。
- `fx_expand_matches_builtin`：把内置配方 k 的 10 条行包成效果块，`fx_expand` 的 552 B 与 `gxr2_expand(k)` 除 [4..7] 以外逐字节相同。
- `fx_file_header`：魔数、长度、头 CRC、count>16、目录越界，每一种都返回 `FX_BAD`，槽不变。
- `fx_binding`：id 不存在 → `FX_GONE`；CRC 与条目不符 → `FX_BAD`；掩码不含当前单元 → `FX_BAD`。

读法（照 `lock_proof146.py` 的变异方法）：
- `fx_lock_busy`：47 被占 → 只有 1 次 poll，没有任何文件调用，没有释放，单元和 S 零写入，行显示锁忙提示；下一次按键再试，成功。
- `fx_open_minus1`、`fx_open_count2`：不新建、不锁存；释放 47 一次。
- `fx_short_read`、`fx_file_ge_cluster`、`fx_fill_minus1`：返回 `FX_READ`，槽不变。
- `fx_close_fail`：关闭返回 −1 → 不应用。
- `fx_lock_mutants`：busy 判断反转、去掉释放、两次释放、读之前没取锁，四个变异都要被查出来。
- `fx_static_calls`：ELF 里没有 flush、seek、create、rename、delete 的调用地址；唯一的路径字符串是 `/ATA1/GXRFX.BIN`；没有 47 的等待入口。

应用和状态（三个单元）：
- `fx_apply_complete`：OK 选效果 → 九行等于"`fx_expand` + `kv_apply_work`"的结果，T 和 S 与基底相同，读回一致，S selector 是 1。
- `fx_scroll_no_io`：光标滚过效果行，零文件调用，零单元写入。
- `fx_reentry_during_load`：读文件期间注入换视图、半按、MENU → 不应用，暂存槽作废，状态是完整配方或纯 04，所有视图都是 8 行。
- `fx_w_fail_recover`：W 中途失败 → 恢复到确认态（确认态是效果 A，就用确认槽）；把确认槽破坏后再做一次 → 回到纯 04。
- `fx_switch_A_to_B_fail_pre_w`：确认态是 A，加载 B 后在 W 之前失败 → 单元仍是 A，两个槽的标签与 A 一致，`eng_check_settings` 计算出来的仍是 A。
- `fx_knobs_on_effect`：效果条目上调 Amount 和 Cont，结果等于 Python 版 `kv_apply_work`；返回 −2 时零写入。
- `fx_memory_zero`：选中效果后 S 尾部是 40 个零；下次开机纯 04，不预选。
- `fx_power_cycle`：断电再开机 → 九行与原厂相同，S+0x36E 是 1。
- 尺寸：主请求的实测值与预算决定（§6 第 3 项）一致；BSS 增量正好 1,024 B。

## 4. 第 3 层：电脑端衔接（只写与 `studio_send_to_camera/DESIGN.md` 的差异）

### 4.1 白名单

- 登记表按代数分开：`PROFILES[140] = Profile(140, 98304, True, gxui=2, max_users=32, name_max=7, charset=…)`。
- `KNOWN_BASE[140]` 是**模板摘要**：可变区域置成"空区域"（count=0，记录区全零，区域 CRC 重新计算）后，整个文件的 SHA-256。第 1 层的可变区域是：
  - DAT 头的 [20,28)；
  - GXUI 区域里的 [16,20)、[22,24)、[64,1984)。
- 原设计 §2.2 第 6 步的断言"只有 `[20,28)` 和扩展区变了"仍然成立。扩展区的位置没变，变的只是内部格式。
- 方案 X 才需要把效果区加进可变区域；方案 Y 的效果在另一个文件里，DAT 的可变区域不变。

### 4.2 条目编码

- `datcodec`：新增 `gxui2` 的编码和解码，规则与 `uv2_validate` 一一对应；再写一份独立的 Python 校验器，不复用编码器。
- 名字：
  - 允许的字符取自 profile；
  - 长名到短名的建议规则：取 ASCII 转写的前 7 个字符；
  - 短名重名时只提示，不拦。
- 掩码（沿用 `myrec_v2_design` §2.5）：
  - 对三个单元分别检查调节量；
  - 默认只写合法的单元；
  - "调整到三个单元都合法"要逐项列出改动，不能悄悄改。
- 原设计里的限制提示"相机只能存储对比度、高光、阴影、饱和度（±5）"删掉，换成"这个调节量在 <单元> 上没有这一档"。
- §2.5 条目管理：
  - 删除不再导致改号，相机名就是用户起的名字；
  - "改名"从"只改电脑上的名字"变成"改相机名"，写卡后生效。
  - 去重规则：同一基底、同一组档位、同一效果绑定的条目只允许一条，名字不参与比较。

### 4.3 从 v1（g139）迁移

新流程"升级相机配方文件"：
1. 读卡上的 g139 DAT（白名单 139）；
2. 按 §2.6 把每条 v1 条目转成 v2；
3. 新 DAT = g140 模板 + 转换后的条目；
4. 断言新 DAT 等于"模板摘要 + 可变区域"；

### 4.4 效果文件 `GXRFX.BIN`（方案 Y）

- 写入路径照原设计 §2.3，新增两个名字：`GXRFX.TMP` 和 `GXRFX.BIN`。审计钩子的 `allow_once` 加入这两个名字。
- **顺序：**先写 `GXRFX.BIN`（TMP → 读回 → rename → 读回），再写 DAT。日志的一个作业里记两个文件的状态。
  - 中途断电时，最坏的结果是"DAT 是旧的，效果文件是新的"：绑定 CRC 对不上的效果条目在相机上拒绝应用，其他条目照常。下次插卡时，按日志补写 DAT。
  - 两个文件的备份都要先做。
- **文件内容规则：**
  - 效果 id 在文件内从 1 起连续编号；
  - 只放 DAT 里有条目引用的效果；
  - 没有效果时**删除** `GXRFX.BIN`（相机只读，删除对它无害）。

## 6. 需要决定的事项

   - (b) 上限提到约 109,500 B，前提是先做一次堆探测（`heap_headroom` 里的反例还没有上机证实）；
