# GXR 峰值对焦改色：静态研究与可加载模块设计

2026-10-21。对象为 GXR 机身 1.51 与 GR LENS A12 50mm 单元 1.51。只读官方固件与现有研究，未构建固件、发送 RPC、接触相机或存储卡。

结论：已有一条很小的 RAM 改色候选路径，MODE 2 值得优先验证，但目前不能承诺能把白色合焦边缘改红或改绿。最强编码假说是 `Y / ΔCb / ΔCr`，色度用符号幅值；硬件也可能把它当作背景底色。MODE 1 能否注入色度仍未知，若它只产生亮度过冲，改常量就无法给轮廓上色。

- 条件性颜色候选为红 `0x60A040`、绿 `0x60A0A0` 或较强的绿 `0x60C0C0`。这些值假设中、低字节分别为 Cb、Cr，且符号幅值成立，不是已经在相机上看到的颜色。
- 最小的广域写法是改 `T+0x2572/0x2573`，共两字节，但普通非辅助对焦配置也会读它们，不适合直接作为日常方案。较窄的 MODE 2 写法是把 `T+0x3B0D/0x3B0E` 改为 `21/10`，再写两个 D 表槽 `0x2012F00E/0x2012F014`，共四个有效字节。四组诊断另改 D 字节 `0x2012F009`，总共五个有效字节。
- D 表会在冷启动时从映像重载。T 写入只能在未来获准的探针中使用，退出先恢复 T 选择器，再恢复 D 表；绝不发送 U 命令。普通关机保存设置并不等于提交单元 T，但“任何路径都不会提交 T”没有证明。
- `0x2F02` 拍摄与 `0x2F03` 预览共用 parser；本轮还找到两者都经过 `r4=1` 的规范化调用。不能静态承诺照片完全不受影响。可加载模块必须在半按、拍摄和退出前恢复，失败时阻止继续使用脏配置。
- 一次上机依次观察 `0x400000`、`0x604000`、`0x600040`、`0x608180`。前一组辨明高字节作用位置，中间两组辨明色度轴，最后一组利用“负零与大负数”的差别区分符号幅值和二补码。完整序列见第 6 节。这次任务没有授权执行它。

交付状态为 `firmware_ready=false`、`camera_handoff_ready=false`、`device_tested=false`。结构化设计见 [probe_design.json](probe_design.json)。

## 1. 证据范围与复核方法

采用任务给出的 [Focus Assist 研究](../focus_assist/REPORT.md)，抽查并扩展了关键窗口。新增反汇编和固件派生数据全部位于被忽略的 [local/](local/)，没有改动原研究。所有地址均指 A12 50mm 1.51，T 始终是运行时 `*(u32*)0x200B2CF0`，不能把初值 `0x20022000` 当作相机当前指针实测。

[analyze.py](analyze.py) 解析官方段表和 `jlaunch8` 命令流，核对保留指令的机器码，再用有步数上限的标量算式解释器重建两个打包器。它只操作 Python 内存，不执行固件，不模拟 ISP 像素处理。任何未知读地址、未建模调用或指令都会报错，不用零值掩盖缺失。

## 2. 三字节编码：TE 是强先例，但没有闭合 type 32

### 2.1 原生 TE 的两路色量

【静态确认】TE 的原生值为 Sepia=6、Red=1、Green=2、Blue=3、Purple=4。机身 `0x202D41FC..0x202D423C` 把染色字段送入参数记录，单元规范化进入 `Q+0x0C`；快速路径 `0x2010C6C0..0x2010C6D4` 取该 word 的低 byte 交给 `0x2010D800`，转成颜色控制选择号。TE 的五种颜色最终选 `T+0x1230/+0x123A/+0x1244/+0x124E/+0x1258` 中的五个 16-bit 条目，按鲜艳度等级取用或插值。中间档 `r5=4` 读第一组，每色结果如下。选择号复算见 [local/te_selector_mapping.json](local/te_selector_mapping.json)。

| TE 色调 | 控制选择号 | 16-bit 颜色量 | 按符号幅值解释的高、低字节 |
| --- | ---: | --- | --- |
| 棕褐 | 0 | `0x8604` | −6，+4 |
| 红 | 1 | `0x8004` | −0，+4 |
| 绿 | 2 | `0x0084` | 0，−4 |
| 蓝 | 3 | `0x0582` | +5，−2 |
| 紫 | 4 | `0x0301` | +3，+1 |

【静态确认】`0x2011564C..0x201159D4` 的插值代码检查每个 byte 的 bit 7。两个负值插值时先减 `0x80`、处理幅值，最后重新 OR `0x80`。这证明这条 TE 控制路径把 bit 7 当符号，低七位当幅值，不是二补码，也不是以 128 为零的偏移二进制。`0x80` 是负零，`0x84` 是 −4，不能按二补码读成 −124。

【静态确认】结果进入颜色配置 `cfg+2`；`0x201152A0..0x201152AC` 放到 type 28 镜像 `0x20142AB4`，快速颜色路径也把该 halfword 写到 `0xF034C006`。它还使用 `0xF034C080..0xF034C0DC` 的 24 个颜色系数。TE 不是经 `0xF0353324`、type 32 写入。

【推断】棕褐的“第一路负、第二路正”、蓝的“第一路正、第二路负”、红的“第二路正”共同支持高 byte 是 ΔCb、低 byte 是 ΔCr。原生 TE 的灰度来源、系数尺度和合成次序没有完全恢复，不能把这里的“4”直接换算成最终画面四个色度码值。

证据为 [颜色控制打包器](local/evidence/color-pack-and-control.disasm.txt)、[选择器](local/evidence/color-builder.disasm.txt)、[TE 各档计算](local/te_control_words.json)。既有 type 28 的 24 区颜色字也使用符号幅值，见 [ISP 研究第 7 节](../isp_pipeline/REPORT.md)。该先例加强同一 ISP 的格式一致性推断，仍不等于 type 32 使用相同格式。

### 2.2 type 32 能确认到哪一层

【静态确认】三字段由 `ldub` 直接取出，以 `(high<<16)|(middle<<8)|low` 写入镜像 `0x20142D94`，随后写 `0xF0353324`。没有 CPU 侧的减 128、符号扩展、异或符号位或 RGB→YCC 转换。第二个消费者也同样搬运。因此仅靠这两段代码，不能判定硬件如何解释 byte。

【推断，首选】把高 byte 当 Y 或亮度底量，中、低 byte 当零中心色度，并优先试符号幅值，最符合 MODE 2 的 `0x600000`、TE 先例和“灰背景、白边缘”的已知产品行为。

| 编码假说 | 中性色度 | `0x81` | `0x80` | 当前判断 |
| --- | --- | ---: | ---: | --- |
| 符号幅值 | `00` 或 `80` | −1 | −0 | 最强先例来自 TE，但 type 32 未确认。 |
| 二补码 | `00` | −127 | −128 | CPU 搬运代码同样兼容，尚未排除。 |
| 偏移二进制 | `80` | +1 | 0 | 若这是直接生效的绝对 YCbCr 常量，默认 `60/00/00` 应强烈偏绿，与灰背景不符；若色度未使能或字段另有用途，仍不能仅凭默认值排除。 |

【未知】三字段还可能是滤波偏置、门限或与背景合成相关的量。没有芯片手册或上机结果，不能把“最像 YCbCr”写成“已确认 YCbCr”。

### 2.3 红、绿候选的算式

【推断，条件计算】先采用全范围 BT.601 形式作参考，零中心色度满足：

```text
R = Y + 1.402 Cr
G = Y - 0.344136 Cb - 0.714136 Cr
B = Y + 1.772 Cb
SM(x) = x              if x >= 0
        0x80 | abs(x)   if x < 0
```

这只是选数的数学模型，未证明 GXR type 32 的量程、增益、视频范围或色度次序。Y 是否直接作为输出亮度也未知。

| 目标 | Y、ΔCb、ΔCr | 符号幅值候选 | 模型裁剪后的 RGB |
| --- | --- | --- | --- |
| 易辨的红色 | 96，−32，+64 | `0x60A040` | 186，61，39 |
| 较温和的绿色 | 96，−32，−32 | `0x60A0A0` | 51，130，39 |
| 较强的绿色 | 96，−64，−64 | `0x60C0C0` | 6，164，0 |
| 接近纯红的数学参考 | 76，−43，+127 | `0x4CAB7F` | 254，0，0 |
| 接近纯绿的数学参考 | 150，−84，−107 | `0x96D4EB` | 0，255，1 |

若两路次序相反，交换低两个 byte。若二补码成立，−32 应为 `E0`、−43 为 `D5`、−84 为 `AC`、−107 为 `95`。注意 −64 在两种编码里恰好都是 `C0`，所以只试 `C0/C0` 不能辨别编码。若偏移二进制成立，中性色应为 `80/80`，所有候选要重算。完整六种编码/次序组合见 [local/color_models.json](local/color_models.json)。

【静态确认】`F0353054=000000FF`、`F0353040=00000001`、`F035311C=00FF00FF` 在两模式中相同。`B[1]` 虽由 `81` 变为 `82`，两行表恰好相同，不能把 `00FF00FF` 当成 MODE 2 独有的白色。其余十对 `F03530E8..F0353114` 系数也相同，只有表中两个 word 不同。

【静态确认】`F0353138..F0353150` 的差异来自 A[2] 低半字节经 `F+0xE/+0xF` 的另一组系数。原快速函数只重写 26 个寄存器，覆盖其中 13 个差异；它不重写这额外七个 word。因此“两个消费者都读同一常量”成立，但切换快路径和完整路径的全部响应字段不能混为一谈。完整列表、相同项及计算基线见 [local/register_reconstruction.json](local/register_reconstruction.json) 与 [差异清单](local/register_differences.json)。

【静态确认】MODE 2 在规范化时把 `Q+0x10` 覆盖为效果 7。短命令的 MODE 2 分支还调用 `0x20113FB4`，选第 28 张、96 字节全零的 type 28 颜色系数表。MODE 1 的开启分支直接选择其 A/B 记录，不走这次颜色表覆盖。关闭分支另按原图像效果和锐度重选普通记录并恢复颜色路径。

【推断】最贴合目前证据的硬件模型是“颜色阶段压掉场景色度，滤波阶段产生边缘响应，再与某个底量或常量合成”。零色度系数矩阵确实能压低色彩，TE 的符号幅值矩阵先例也支持这一解释。常量 `0x60` 很像灰背景底量，非线性响应表使强边缘变亮。它也可能是边缘输出常量或滤波偏置；CPU 代码没有暴露 mask 与常量之间的混合公式。

【未知】不能确认颜色阶段位于锐化之前还是之后，也不能确认 MODE 2 的去色会不会抹掉注入色度。MODE 1 没有已确认的独立 mask/色度注入开关；白边若只是 Y 的正过冲，常量改色可能只染背景、整幅偏色，或完全无效。把 MODE 2 的强滤波记录移给 MODE 1 会改变整个算法，不能当作“保留彩色背景的 MODE 1 改色”。

## 4. 最小写入集合、类别与生效时机

### 4.1 默认选择器决定哪些写入有用

【静态确认】原始配置如下，字节之间的空格不是地址跨度。

| 模式 | A[3] / A[4] | 高、中、低选择号 | 实际来源 |
| --- | --- | --- | --- |
| MODE 1 | `00 / 00` | 0，0，0 | `T+254B / T+2572 / T+2573` |
| MODE 2 | `20 / 00` | 2，0，0 | `D:2012F009 / T+2572 / T+2573` |

所以，在保持默认记录和消费者代码不变时，只写三张 D 源表不能让低两个 byte 非零。索引 0 明确走 T，不访问 D 表第一个条目。直接写展开区 F 或寄存器镜像是另一类运行时覆盖，下一次构造会被冲掉，不能算作“只改 D 源表”的解法。修改消费者指令或重定向 T 指针也不属于表字节方案，本设计不采用。

### 4.2 两条数据路径的代价

| 方案 | 有效写位置 | 逻辑改动量 | 影响与限制 |
| --- | --- | ---: | --- |
| 广域默认色度 | T 字节 `+2572/+2573` | 2 B；一个对齐 halfword | 两模式都立即有可重读的色度来源；普通锐化的索引 0 也读它们。只做最初的单轴红/粉色判断可仅改 `+2573` 一字节，但总线仍写两字节。 |
| MODE 2 专用选择器与 D 槽 | T 的 A[3] `+3B0D:20→21`、A[4] `+3B0E:00→10`；D 字节 `2012F00E/2012F014` | 4 B；四次 halfword 写，共 8 B | 两路改选槽 1，保留 Y 的槽 2；B 记录不改。红/粉色单轴试验可只改 A[4] 和低路 D 槽，共 2 个有效字节。 |
| MODE 1 也改选 D 槽 | 再加 T 的 A[3] `+3B03:00→01`、A[4] `+3B04:00→10` | 再加 2 B；两次 halfword 写，共 4 B | 保留 MODE 1 原来 Y 来源与全部滤波参数。是否会把边缘上色未知。 |
| 四组诊断的高字节 | D 字节 `2012F009` | 再加 1 B；一次 halfword 写，共 2 B | MODE 2 的高 byte 可由 `60` 改为 `40`；不改变 MODE 1 的索引 0。 |

T 中的 A/B 记录仍属于 T 类，不因它们是“查表记录”而变成 D 类。这里使用的 D 槽在映像中的文件偏移分别为 `0xE4209`、`0xE420E`、`0xE4214`，只用于定位和验证，不能据此修改官方文件。

【静态确认，有限范围】快速关闭分支用到的八条普通 A 记录 `T+0x1EC8..0x1EEB`，脚本默认的三选择号都是 0。它们不会读取新用的 D 色度槽 1。尚未穷尽所有特殊效果、请求及相机当前 T 内容，因此不能宣布两个 D 槽绝对归 Focus Assist 独占。

### 4.3 何时写、何时看到结果

【静态确认】完整 `2F03` parser 会重新规范化 Q，随后 ISP 配置申请可重建 F 和 type 32 镜像。`2F02` 也走这条 parser。短命令 `2F05` 的 handler 只在有效开关变化时调用 `2010C67C→2011659C→20115E80`，会重新读取当前 T 记录和 D 表。

【未知】不是已证明“每个预览帧都重算”；参数包、配置申请、视频帧是三个不同事件。完整 parser 每次构造 Q，也不等于每包必定完成整组 MMIO 重写，后续可能有请求选择或缓存。

【设计】每组先通过原生路径关闭辅助对焦，等待该请求完成；在串行、禁止拍摄的上下文中写表与选择器；再通过原生路径开启，等待确认后观察。不能保持 On 只写源 RAM 就期待下一帧一定更新，也不能先写镜像后任由下一包覆盖。首次启用和切换 MODE 时，应让原生完整预览配置走完，以建立完整路径才更新的额外系数。模块不按固定毫秒延时猜测完成时点。

## 5. 持久性、恢复与照片隔离

### 5.1 官方更新到底覆盖哪些 T 字节

| --- | --- | --- |
| `+254B` | `0xC84C`，游标 `254A`、`W3000` | `00`；同时 `+254A=30`。 |
| `+2572/+2573` | `0xC964`，`W0000` | `00 / 00`。 |
| `+3B00..+3B09`，MODE 1 A/B | `0x10865` 起的五次 W | 原 MODE 1 两条 5 B 记录。 |
| `+3B0A..+3B13`，MODE 2 A/B | `0x108AB` 起的五次 W | 原 MODE 2 两条 5 B 记录。 |
| `+3B03` | `0x10873`，`W2200` | `00`。 |
| `+3B04` | `0x10881`，`W00A0` | `00`。 |
| `+3B0D` | `0x108B9`，`W5520` | `20`。 |
| `+3B0E` | `0x108C7`，`W00BF` | `00`。 |

### 5.2 普通保存是否会提交 T

【静态确认，既有审计】X/V/W 的 RAM 写路径没有直接调用提交。T 提交函数 `0x20065DB0` 的两个固定调用者属于 UEE00 和 UEE53 导入；已有审计在普通菜单、拍摄、关机、睡眠等路径没有找到固定调用。工厂调整流程和官方更新会调用提交。见 [t_persistence](../t_persistence/REPORT.md) 及 [V/W/X 与记账代码](local/evidence/adjust-v-w-x.disasm.txt)。

【未知】动态分派未穷尽，`zero_persistence_proven=false`。V/W 还有调整记账副作用：四个计数 `0x2024615C..0x20246168` 非零时，读写会更新 `T+0x3F0C/+0x3F10`。冷启动后计数为零且没有调整操作，是本方案的前提。用 V 去“先检查计数”本身也经过该记账器，不能把它冒充无副作用检查。

【设计】日常用法应是每次启动在 RAM 中重设 D 表，T 选择器只在辅助对焦有效期间临时改动；半按、拍摄、回放、关机、模块卸载和错误退出都先恢复。保留实际读到的原值，不能拿脚本默认值覆盖相机中不匹配的数据。若不能获得这些生命周期入口和串行所有权，就暂不提供“全局常开”的日常模式。

D 类冷启动重载是项目已有事实；本轮未做冷启动相机测试。T 若从未提交，冷启动应从持久区重新装载旧值；若意外提交，单靠冷启动不会修复，应走成功完成单元阶段的完整官方更新。此次不制作更新包，也不尝试持久化来证明恢复。

### 5.3 “只影响取景”还不能静态签字

【静态确认】`2F02→201A9A38→20197F68` 与 `2F03→201AA9B4→20197F68` 共用输入；parser 在 `0x20198478..0x20198484` 一律以 `r4=1` 调 `201999C8`。Q 的开关、模式照常复制，MODE 2 的效果 7 覆盖条件也可能成立。仅把规范化入口的参数 1 叫作“预览标志”是不成立的。

【静态确认】有效开关关闭后，短路径会取普通 A/B 并恢复颜色路径；所查八个普通 A 默认均为三路索引 0，且没有改动的 D 槽 1 依赖。但“关闭”本身不恢复我们修改过的 T 默认色度，因此广域 `T+2572/+2573` 路径尤其不能靠关开关隔离。

【未知】没有证明这些硬件寄存器在 JPEG、RAW 处理、DNG 内嵌 JPEG 或缩略图生成期间不生效。RAW 像素可能走旁路，也不能据此承诺整份 DNG 无变化。

【设计】在允许拍摄前，必须恢复 T 和 D、走完原生 Off 的配置更新并验证状态。模块需要捕获拍摄入口，恢复失败则拒绝继续使用该探针状态；仅靠用户半按会取消辅助对焦的产品行为还不够。未来的照片验收应另拍相同曝光的 JPEG+DNG 对照，并区分 RAW 像素、预览/缩略图与 JPEG。此次静态任务无法替代这层验收。

## 6. 一次上机、四组观察的探针设计

下面只是可审阅的协议与状态设计，没有发包程序。这次任务未批准 T 写入，未来制作和执行仍须用户批准。

### 6.1 准备与快照

1. 使用已批准、具有可加载模块空间的机身扩展。校验单元身份为 `jlaunch`、固件 `0151`；RPC 8 已就绪、调用线程合法，其他深层配方/调整操作不活动。X/V/W 使用共享基址与游标，整个事务必须由同一个所有者串行执行。
2. 从冷启动开始，使用 P/A/S/M 的普通彩色设置，退出场景特效和其他深层配方。场景同时放置合焦细线、失焦平坦背景、真实白色物体和一块彩色物体。记录 Off、原 MODE 1、原 MODE 2，UI 作为独立参照。探针期间禁止拍摄、模式切换及电源退出穿过未恢复状态。
3. 原生 Off 并等待完成。用 `X2012` 读 `VF008/VF00E/VF014` 三个 halfword；原厂应分别为 `0060/0000/0000`。用 `X12C0` 读 MODE 2 的 `V3B0A/0C/0E/10/12` 五个 halfword，再读 `V254A/V2572`，共 20 B 的稳健快照。未知值或不匹配时停止，不据默认值盲写。加测 MODE 1 时快照改为完整 `3B00..3B13`，总 30 B。

当前 2j 的 `rfw_rpc8_call` 限制字母索引为 21..23，对应 V/W/X，满足不使用 U 的要求。新模块还需对白名单地址和事务长度设限，不能因为页 `2012` 已可达就开放整页任意写入。

### 6.2 选择器与每组三字节的 RPC 序列

RPC 8 的文本记法如下。每个 V 都检查返回的当前 u16，每个 W 都检查返回值，再用 V 独立读回；W 会把游标加 2，所以不能把一次旧 V 当成后续所有 W 的地址证明。

```text
MODE 2 选择器安装，Focus Assist 保持 Off：
X12C0
V3B0C -> expected 5520
W5521 -> expected 5521
V3B0C -> expected 5521
V3B0E -> expected 00BF
W10BF -> expected 10BF
V3B0E -> expected 10BF

每组 high=YY、middle=UU、low=VV 的 D 数据：
X2012
VF008 -> expected previous halfword
W00YY -> expected 00YY
VF008 -> expected 00YY
VF00E -> expected previous halfword
WUU00 -> expected UU00
VF00E -> expected UU00
VF014 -> expected previous halfword
WVV00 -> expected VV00
VF014 -> expected VV00
```

`00YY/UU00/VV00` 只在快照中的相邻 byte 确为零时使用；实现必须保留快照相邻 byte。T 的两个 W 同样保留 A[2]=55 和 B[0]=BF，没有改 B 记录。D 数据安装后，走完整原生 MODE 2 配置，再 Off→On，等待完成后观察。

| 顺序 | 三字节 word | 作用与预期判读 |
| --- | --- | --- |
| 原厂参照 | `0x600000` | 不额外写入。记住灰背景、白边与真实白物体的位置。 |
| P1 | `0x400000` | 高 byte 降低 32。若只灰背景变暗，支持背景底量；若只白边亮度变化，支持边缘电平。整幅变化或完全无变化分别记录。 |
| P2 | `0x604000` | 仅中 byte 正向。若顺序是 Cb/Cr，模型为蓝紫；若是 Cr/Cb，则偏红。记录颜色出现在边缘、背景还是整幅。 |
| P3 | `0x600040` | 仅低 byte 正向。应与 P2 交换红/蓝角色。两组都不变时，先检查配置是否消费，不判定“硬件不支持颜色”。 |
| P4 | `0x608180` | 符号幅值解释为 −1、负零，模型几乎中灰；二补码解释为 −127、−128，模型强烈偏绿。偏移二进制解释接近中灰，但它对原厂参照及 P2/P3 预测偏绿，应结合前三组判断。 |

以上 RGB/色名只用于区分假说，不是相机效果承诺。P4 近灰支持符号幅值，不足以单独排除偏移二进制；若字段是增益、被禁用、后级去色或发生剪裁，四组也可能不能唯一判定。届时保留未知，不能从“没变”反推格式。

每组可附四次 RAM halfword 读，检查选择器与结果：`X2038; V3F2E; V3F30` 对应 `F+26/+27/+28`，MODE 2 应选 `02/01/01`；`X2014; V2D94; V2D96` 检查镜像 word。镜像一致只能证明 CPU 打包，仍不能证明 MMIO 和像素效果；首轮不直接读写硬件 MMIO。

### 6.3 作用位置决定后续路线

| 看见的现象 | 支持的解释 | 下一步 |
| --- | --- | --- |
| P2/P3 只让合焦边缘变成互补的红/蓝，平坦背景仍灰 | 常量可参与边缘色度，主路线成立。 | 按通道顺序试红/绿候选，再验证照片隔离。 |
| 只有灰背景变色，白色合焦区域始终白 | 常量主要是背景底色，不能满足彩色峰值目标。 | 停止把它当作前景色；转查硬件 mask/软件叠加。 |
| 整幅连续偏色，包括真实白物体 | 常量是全局偏置，或颜色级没有局部 mask。 | 不作为峰值改色交付。 |
| UI 也变色、闪烁或状态不一致 | 影响越出了单元预览配置假设，或存在同步错误。 | 立即恢复并保留日志。 |
| RAM 镜像不随组值改变 | 选择器、重读、模式或配置申请未生效。 | 修正消费链证据后再解释画面。 |
| 镜像改变而画面不变 | 可能被后级去色、字段不是颜色，或未写入当前硬件实例。 | 结论仍未知。 |

MODE 1 加测只需另外安装两条 T 选择器：`V3B02/W2201/V3B02` 与 `V3B04/W10A0/V3B04`。保持高 byte 原索引 0，复用各组 D 色度，观察是否仍能只染边缘。P1 的 D 高 byte 对 MODE 1 不生效，这是设计预期。若为排除 Y=0 才加测高 byte，需把 `A[3]` 改成 `21` 选槽 2；这会同时改变亮度底量，应另记为不同条件，不能与“只改色度”的结果混用。

### 6.4 恢复顺序与失败处理

1. 保持拍摄阻断，走原生 Off 并等完成。
2. 先按快照恢复 T 选择器，MODE 2 为 `V3B0C/W5520/V3B0C`、`V3B0E/W00BF/V3B0E`；若加测 MODE 1，再恢复 `3B02/3B04` 对应原 halfword。实际恢复值始终来自快照。
3. 再恢复三条 D halfword，原厂是 `VF008/W0060/VF008`、`VF00E/W0000/VF00E`、`VF014/W0000/VF014`。
4. 再走一遍原生 Off 配置，让硬件和镜像脱离最后一次彩色状态；恢复用户原来的模式、开关，核对原生配置完成后才解除阻断和所有权。

先恢复 T，可避免辅助对焦在中途重入时继续读尚未恢复的 D 槽。任意 W/读回失败都记为“状态不确定”，不发布成功、不继续下一组；尽力恢复所有已触碰目标，保持拍摄阻断。D 的冷启动恢复和官方 T 恢复链是后备，不能把“以后可以重启”当作本次回滚成功。

| 项目 | MODE 2 | 同时加测 MODE 1 |
| --- | ---: | ---: |
| D 有效改动 | 3 B | 3 B |
| T 有效改动 | 2 B | 4 B |
| 全目标各写一次的对齐总线字节 | 10 B | 14 B |

每个目标 halfword 更新按 V/W/V 三调用计算；表中含 X 选页，不含身份/就绪检查、原生 UI/预览命令和异常重试。四组总 W 写入字节 MODE 2 为 `2×(2+12+2+3)=38 B`，同时加测 MODE 1 为 `46 B`。没有把 RPC 传输包头或实际机器码大小混进字节数。

【设计】可加载模块需要以下接口能力，当前没有实现或链接验证。

- `begin` 取得排他所有权、核验目标与生命周期状态、阻止拍摄，保存实际快照。
- `set_group` 在原生 Off 完成后只修改白名单 T/D halfword，核对 V/W/V，再请求原生完整配置与 On，按完成事件推进。
- `observe` 返回组号、F 选择器、镜像、RPC 状态和用户记录的颜色/位置，不输出“编码已确认”这种自动结论。
- `restore` 可重复调用；保存每个已改目标的进度，恢复 T、D、原生配置后才允许卸载。错误状态在成功恢复前保持锁定。
- 生命周期接口覆盖半按、拍摄开始、回放、关机、单元断开、模块卸载；RPC 8 只允许字母索引 21、22、23，与现有 `deep_isp.c` 共享串行所有者。

私有 RAM 设计上限可取 256 B，容纳 30 B 快照、12 B 组值、四组 8 B 的 RAM 观察和状态日志。模块代码、链接重定位、ABI、实际开销均未构建，代码字节数为未知；不能把这个状态预算称为模块总大小。

## 7. 常量失败后的机身软件描边方案

【推断】如果常量只染背景，机身软件重算边缘并在专用显示层着色仍可研究。优先找已有 ISP 边缘 mask 或独立 overlay；目前没有证据证明能读到它。没有 mask 时，不能简单把白像素改红，真实高光和 UI 也会被误改。

【静态确认，既有代码】机身显示代码含 320×240 与 640×480 两组尺寸。这不证明帧缓冲像素格式、stride、地址、缓存一致性、双缓冲所有权或帧率。CPU 主频等待正在开发的自检固件实测，本轮不运行该固件。

【推断，预算】按 50–200 MHz、全部 CPU 都可供循环使用计算，每像素上限如下；真实可用值还要扣除 UI、AE/AF、通信与调度。

| 假设处理尺寸/帧率 | 50 MHz cycles/px | 100 MHz | 200 MHz | 若耗 50–100 cycles/px，需 Mcycles/s | YUV422 全帧读写最低 MB/s |
| --- | ---: | ---: | ---: | ---: | ---: |
| 320×240 / 30 fps | 21.70 | 43.40 | 86.81 | 115.2–230.4 | 9.216 |
| 640×480 / 30 fps | 5.43 | 10.85 | 21.70 | 460.8–921.6 | 36.864 |
| 640×480 / 60 fps | 2.71 | 5.43 | 10.85 | 921.6–1843.2 | 73.728 |
| 320×240 / 15 fps | 43.40 | 86.81 | 173.61 | 57.6–115.2 | 4.608 |
| 160×120 / 15 fps | 173.61 | 347.22 | 694.44 | 14.4–28.8 | 1.152 |

算式是 `cycles/px=MHz×10^6/(W×H×fps)`、`MB/s=4×W×H×fps/10^6`。后者假定紧密 YUV422 全帧读一次写一次，不包含邻域重复读取、缓存回写、mask 和 overlay 流量；它不是实测带宽。50–100 cycles/px 沿用既有条件假设，不是已优化算法的性能保证。复算数据见 [local/cpu_budget.json](local/cpu_budget.json)。

【推断】在这档 CPU 上，640×480 全帧 30 fps 的新边缘检测不合适；320×240/30 fps 只有接近 200 MHz 且循环较省时才有空间。更现实的首个软件原型是 160×120、约 10–15 Hz 的亮度梯度和稳定门限，放大 mask 后在显示层画少量彩色轮廓；mask 放大与显示合成成本必须另外计算。低分辨率会损失精细合焦判断，不能承诺等价于原厂峰值。

320×240 的 8-bit mask 为 76,800 B，双缓冲 153,600 B；1-bit mask 为 9,600 B。640×480 的 8-bit 双缓冲为 614,400 B；160×120 的单个 8-bit mask 为 19,200 B。若直接修改 YUV422，色度由一对像素共享，还要处理染色扩散。

软件路线在开始实现前要补齐显示缓冲契约、可用 overlay 格式与调色板、帧完成事件、缓存/DMA 约束和可用 CPU 时间。只能写专用显示输出，不能碰仍供 JPEG/RAW 消费的共享缓冲。拥有专用显示层后才有可靠的照片隔离设计依据。
