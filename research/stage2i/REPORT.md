# Stage 2i：2h + 颗粒 / 逐通道 type-26 / scene-21 row 20，三项默认关闭（已构建、未上机）

2026-10-20。构建由 Opus worker 完成。它没有写 `.md` 的权限，本文由主代理根据它的报告删减落盘。没有刷机，也没有碰 SD 卡。独立代码审查另行进行，结果补在文末。

## 主代理的独立复核（全部通过）

- **ilaunch3 校验和**：自己重算，存储值与计算值一致，为 `0x6A790A5E`。
- **与 2h 相比只有三处不同**：
  - `0x16D..0x170` 的校验和；
  - payload 窗口内的字节；
  - 文件偏移 `0x125B8C` 处的 4 B 颗粒 hook：`2e7ff000`（`push lr; nop`）改成了 `fffb8d98`。解码后是 `bra 0x20053FEC`，正好跳到桩代码的起点。
- **其他位置不变**：
  - 2F02 发送函数本体 `0x125B90..` 与官方相同。
  - payload 窗口以外与官方的差异，只比 2h 多了这一个 hook，所以八个原有 hook 与 2h 逐字节相同。
  - 探针尾全为 `0xFF`；从 payload 结束到探针尾的字节与官方相同。
  - payload 的 SHA-256 与报告一致（`a3000093…`）。
- **包**：`shasum -c` 全部 OK，根目录 88 个、`local/` 8 个、`NOT-FOR-USE/` 3 个。2h 的包仍全部 OK。
- **等价性**：在 /tmp 用 2i 的 `tests/equiv_driver.c` 分别对 2h 和 2i 源码各编一次重跑：
  - 不带新位的表（equal-2h、matrix-test）：2i 的记录等于一次性 T 检查（`X12C0`、`V2444`）加上 2h 的原记录，逐字节相同。2h 一侧复现出 `8a4e8032…`。
  - 五份记录（含 grain-test、t-test）里只有 V/W/X 三种命令，没有任何 U 命令。

## 三项新能力（都由表文件 v3 的掩码打开）

| 位 | 能力 | 要点 |
|---|---|---|
| bit 3 | 颗粒 | 2F02 入口 hook 把包的场景字节改成 21。条件全部满足才改：配方带此位且状态不是「不确定」；类别为 0 或 4；B+1A、B+14、B+75、B+1E、B+26 都为 0（不存 RAW、单张、没有附带普通图）；尺寸码属于 {1,2,5,8,12,16}（原生场景 21 不允许尺寸 0）。B 是 r5，四个调用点都核对过。 |
| bit 1+2 | 逐通道 type-26 | 写 C/D（`0x2013024E`，66 B）和控制半字 T+0x2444。进入时先写 C/D，最后把控制改成 0；离开时先把控制恢复成 2，再写行。T 的每一步都是 `X12C0`、`V2444`（必须读到预期值）、`W`、`V2444`（必须读到新值）。不发任何 U 命令。C/D 有效必须同时带控制位；C/D 末值至少 128。 |
| bit 4 | A20/B20 | 场景 21 用的曲线行。B20 在奇地址：第一拍读到的 B19[32] 原样写回，B21 不碰。 |
| 无 | 开机自检 | 每次开机后第一次打开菜单时读 T+0x2444，与表文件无关。值是 0x0002 就不再做任何事；不是就只在 RAM 里写回 0x0002，菜单里的 04 显示成 `!4 Std`，直到关机。写回失败时，本次开机所有深槽失败关闭。 |

表文件 v3 是 3600 B，每个条目 448 B，前 272 B 与 v2 相同。条目 0 是 stock，payload 里编入了它的 CRC，覆盖 stock C/D（全零）、控制 0x0002 和 A20/B20，所以回到 04 永远不依赖卡。v1 和 v2 文件一律失败关闭。

## 上机顺序（要用户明确同意才刷）

刷 `candidate/SD_ROOT`，恢复用 `recovery-official-1.51/SD_ROOT`。

换表的步骤：选 04 → 关机 → 换 DEEPTBL0/1.DAT → 开机 → 开菜单。

1. **不放表文件**：八个名字都在，深槽表现和 04 一样，不卡死。04 不应显示成 `!4 Std`。
2. **equal-2h**：与 2h 相同。
3. **matrix-test**：与 2h 相同（01 是 T3b，03 是 T3a）。
4. **grain-test**：P 档选 03，只存 JPEG，单张，尺寸码不为 0，应当出现颗粒和原生高对比的观感。以下情况都不应出颗粒：RAW+JPEG、连拍、尺寸码 0、04 和其他槽。原生 SCENE 高对比黑白照常工作。
5. **t-test**（只有用户接受 T 写入风险才做）：M 档，固定日光白平衡，拍色卡，顺序是 04、07、04、08、04。08 应给灰阶带上色偏，回到 04 后在 ±2 码以内。然后选 04、关机、重开、开菜单，不应出现 `!4 Std`。

## 剩余风险

1. **T 持久化**：见 `research/t_persistence/REPORT.md`。只刷 MAIN 救不回来；自检只修 RAM，而且要等打开菜单才会执行。
2. **颗粒**：
   - 场景 21 加黑白 profile 时模块怎么表现，机身有没有超时，都没有上机验证过；
   - 拍摄任务的栈余量未知；
   - 出来的是原生场景 21 的观感，不是我们拟合的 GR IV 曲线；
   - A20/B20 生效期间，原生 SCENE 高对比黑白也会受影响。
3. **余量很紧**：payload 只剩 80 B，早段只剩 24 B。
4. **内存**：`gxr_alloc(3604)` 没在机身上跑过。失败时全部失败关闭，安全。
5. **推断**：C/D 的通道顺序和「控制 0」的含义都是推断。

## 独立代码审查（Opus，只读）

**结论：** 没有发现会让相机刷机后起不来、写坏持久存储，或者在失败时进入不安全状态的缺陷。所有新路径要么失败关闭，要么重选 04 或重启就能恢复。

几项关键事实：
- **桩代码透明（已验证）。** 桩保存 r0–r13、lr 和 PSW，C 位不变，栈的净变化是 −4 B，和原来的 `push lr` 一样。`0x2017098C` 只有那四个调用点。
- **没有跨任务竞态（推断，可信度高）。** 2F02 发送、配方切换和表刷新都在 task 6 的同一个 UI 事件循环 `0x202B1100` 里串行执行。
- **栈不是问题（推断）。** task 6 的栈是 16 KB（`0x2005CEE8`，栈大小 `0x4000`）。发送入口处最深约 372 B，加上桩和中断上下文约 524 B，比同一任务里的文件读取路径还浅。
- 门控字段、T 序列、B20 奇地址处理、v3 加载器和空间余量都与报告一致。审查者用自己写的脚本复核了 5 套表，全部通过。

**上机前应修：**
1. **【中】颗粒只认机身记录的「当前深槽配方」，不看当前设置。** 用配方菜单选过 03 之后，即使在普通菜单里改了图像设置，照片仍是高对比黑白加颗粒。修法：门控再要求 S+0x36E 等于该配方的 base_mode，约 16–20 B。
2. **【中】场景 21 的包不完全是原生的。** 原生场景 21 的 B+0x10 是 0，B+0x6F 取 S+0xC9D；2i 没有照做，模块在这种组合下怎么表现未知。修法：打开颗粒时一并写入这两个字节，约 12 B。B+0x0F 先不动。
3. **【低–中】T 检查不够健壮。** 第一次读取失败也会把 `t_checked` 置 1，之后不再重试。进入 T 配方前也没有先确认 T 是 0x0002，可能把各行写完后才 sticky 失败。修法：读到有效值后才置 1；进入 T 配方前，在写任何行之前先读一次，必须是 0x0002。约 12–16 B。

**其他：**
4. **【低】T 配方的作用范围不只是 SCENE 高对比黑白。** 07/08 生效期间，T 控制和 C/D 对所有模式都起作用。上机清单要写明「测完先选回 04 再切模式」。正式表应拒绝「有 bit 2 没有 bit 1」的条目。
5. 提示级：
   - 切换末尾两个写入的顺序被编译器对调了，同一任务里无害；
   - `!` 固定标在第 4 槽，不核对这一槽是不是 04；
   - RfwCache 丢失时，自检会重跑，可能误报 `!4`。

**结论的用法：** 用不带新位的表（equal-2h、matrix-test）时，2i 等于 2h 加一次 T 读取，可以安全使用。上面的问题只在打开颗粒位或 T 位时才有关系。修正版是 Stage 2j。
