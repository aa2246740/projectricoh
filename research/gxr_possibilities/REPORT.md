# 第一部分　结论（写给用户）

## 一句话

GXR 能做的比我们以前做的多。**最划算的入口在机身，不在单元。**机身在把照片压成 JPEG 之前，手里有整张未压缩图像，GR III/IV 社区的光晕、日期水印也正是在这个位置做的。机身刷机我们已经安全做过二十多次。在这里加一个"成片前处理"挂点，可以一次解锁机内裁切画幅（包括 XPan）、颗粒、暗角、配方名水印、边框，而且不用动单元。

单元固件也比以前想的更有底：单元的闪存分了区，启动程序和备用程序跟主程序分开放，官方升级包从不覆盖启动区。但"主程序装进去以后一开机就死机，还能不能救"仍然没有证据。所以改单元有一条明确的规矩：**改动只能在用户使用新功能时才生效，不能在开机时生效。**符合这条规矩的改动，坏了以后的恢复方法和今天一样，就是带着这个单元用官方包再刷一次。

## 1. 单元固件能不能恢复

### 今天"每个单元都点了 OK"，刷到单元了吗？

**几乎可以肯定刷到了，而且每次带着单元刷机都会刷。**

- 理光官方升级说明写明：按住"+"再按播放键，**只有一次"是/Yes"确认**，之后屏幕依次显示"传送固件 → 检查单元固件 → 检查机身固件 → **更新单元固件** → 更新机身固件 → 完成"。说明书还要求"有几个单元，就对每个单元做一遍"。没有单独的"要不要更新单元"提问，这和您记不起有单元提示正好对得上。来源：[官方升级说明 PDF，第 1、5–6 页](https://www.ricoh-imaging.co.jp/english/r_dc/download/firmware/docs/gxr_fwup_en.pdf)。
- 静态证据也一致：机身这条路径调用升级函数时，传入的掩码是"机身＋单元"两项（`t_recovery` 已核对）。
- 现场证据一致：10-26 发现，50mm 能否开机只取决于"上次刷机时装的是哪个镜头"；今天 28mm/MOUNT 的"只显示原厂菜单"问题，在带着它们刷了一遍同一个机身文件后消失了。
- 卡 B 上的单元文件是官方原件（28 个，与官方 ZIP 一致），所以写进单元的是官方 1.51 内容。

**不改任何东西就能确认的办法**

1. 下次本来就要刷机时，把屏幕录下来，看有没有"Updating camera unit firmware"那一行，并记下这一阶段用了多少秒。不增加任何写入。
2. 开机时按住"−"再按播放键，进入版本页，给每个单元各拍一张，保留为基线。这一页列出单元的 MAIN / BKUP / MONI / ADJD / EXTD / CPU1 版本，以及 SH、CV 两个数。版本相同时这一页分不出"重写过"和"没写"，但能证明单元有独立的启动程序（MONI）和备用程序（BKUP）。

### 新发现（静态，本轮）

- 50mm 和 28mm 单元的闪存是固定分区，块号如下。第 0 块：启动程序；第 1–32 块：坏块替换区；第 33–40 块：备用程序；第 41–42 块：校准数据；第 43–82 块：主程序；第 83–100 块：资源。MOUNT 的分区常量在另一个地址，本轮没有逐项解码。
- 单元写入代码按文件类型决定写哪一段：主程序文件只写主程序区，备用程序文件只写备用区；**只有"类型 1 / MONITOR"文件才会写第 0 块**。50mm、28mm、MOUNT 的官方包里都没有这种文件（只有 A16 的 `l06firm5` 是这一类）。所以官方升级包和我们以后做的同结构改包，都不会碰启动程序。
- 单元备用程序里有完整的诊断文字："主程序装载出错，所以用备用程序启动"、"按请求用备用程序重启"。说明启动程序发现主程序装不起来时，会改用备用程序。
- 备用程序自己就能和机身通信、接收文件、写入主程序；拿不到主程序版本时，报给机身 FFFF（已有研究已证）。
- 主程序里有一条维修命令"reboot -bkup"：先检查备用程序是否完好，再写一条重启请求并复位，下次用备用程序启动。本轮只找到维修命令行调用它，没找到机身能直接发的命令。

### 还不知道的

- 主程序装载检查通过、但运行后在开机初始化里死机：会不会自动切到备用程序？没有证据。程序异常时有"记录原因并复位"的代码，但复位后进哪个程序由启动程序决定，而启动程序不在升级包里，读不到。
- 刷写中途断电、坏块替换区出问题，是否可恢复，仍然未知。
- GXR 已停产，本轮没有查到理光是否还修单元的官方日期。按"修不了"来规划更稳妥（推断）。

### 结论：可以开始一次最小、可见、可恢复的单元演练

**演练内容：**把一个单元的 16:9 大尺寸 JPEG 高度从 2416 改成 2400。开机时这个数只被抄进一张参数表，真正用到是在拍 16:9 照片时（还需逐个使用位置核对）。

1. **零写入准备**
   - 拍版本页，作为基线。
   - 在主机上用原厂单元检查函数（文件头、长度、加权校验）重放候选文件，确认通过。
   - 确认这个数只用于拍照和取景的尺寸计算。
2. **第一次写入**
   - 包里放：机身 v3.8 不变、其余 28 个官方文件不变，只换这个单元的 `*3` 主程序。版本号、兼容号、文件头标志都不改，只重算校验。
   - 带着这个单元，用"+ 和播放键"刷机。
3. **验收**
   - 开机正常，3:2 照片正常。
   - 16:9 的 JPEG 变成 4288×2400。
4. **恢复**
   - 带着这个单元用官方包再刷一次。
   - 16:9 回到 4288×2416。

**这一轮能证明三件事**，都是以前没闭合的：

- 改过的主程序会被单元接受并写入；
- 同版本的官方包确实会重写主程序；
- 只在使用功能时出问题的改动，可以用官方包恢复。

**如果开机就出问题：**先带着它用官方包刷；如果版本页上单元 MAIN 显示"------"，说明在用备用程序，同样用官方包刷。两条都不行，这个单元可能要送修。所以请选一个您最舍得的单元。

### 半格双联的三条路

1. **拍完后在卡上拼，只换 DAT。**用两张已存的 JPEG 在熵编码层按 MCU 拼接，不解码像素。但查了您 80 张实拍：GXR 每张自己选量化表，80 张里有 25 套不同的表。连拍的相邻两张常常一样，但不保证。表不同时，要把第二张的系数换算成第一张的表，会有少量画质损失，但仍然不需要完整解码。另外 GXR 的 JPEG 没有重启标记，只能从头顺序解码；而 DAT 目前只证明能"从文件开头整写一个约 8.7 KB 的文件"。几 MB 的新文件能否写、要多长时间、会不会卡住菜单，都没证明。
2. **拍第二张时在机身拼。**需要在两张之间把第一张的一半图像（约 12 MB）留在内存里；机身空闲大内存未知。
3. **放在单元里。**单元管成像，但不管存卡，改动最大，不推荐。

**结论：**半格双联价值高，但工作量最大。在"成片前挂点"和"DAT 写大文件"两项都证明之前，不建议先做。过渡办法是先做"半格单张"：每张裁成 2144×2848 竖幅，然后在电脑工作室或 iPhone 上自动拼。半格单张需要竖裁（宽度变小），比 XPan 多一个编码步长问题，排在 XPan 之后。

### 为什么以前没做，现在变了什么

| 以前的阻力 | 现在 |

## B. 单元固件恢复

### B1. 官方升级流程（文档）

[官方升级说明](https://www.ricoh-imaging.co.jp/english/r_dc/download/firmware/docs/gxr_fwup_en.pdf)（本轮下载到 scratch，SHA-256 `1bd682db…68cc`，与 `unit_recovery` 记录一致）：

- 第 1 页：*"Firmware for both the GXR and a camera unit connected to it can be updated. If you have more than one camera unit, run firmware update for each of the camera units."*
- 第 1 页：版本页按"−"加播放键，列出 BODY 与 CAMERA UNIT 两栏，每栏有 MAIN / BKUP / MONI / ADJD / EXTD / CPU1，再加 ST/SH、CV。
- 第 5 页：按"+"加播放键 → 确认 → 用 Fn2 选 [Yes]，再按 MENU → 依次显示 *[Transferring firmware] [Checking camera unit firmware] [Checking body firmware] [Updating camera unit firmware] [Updating body firmware] [Firmware update complete]*，并注明 *"The order … may differ depending on the firmware version."*
- 第 6 页：*"If you have more than one camera unit, perform step 4 for all camera unit."*

**已证（文档＋静态）：**一次确认同时覆盖机身和所接单元。机身 `0x2036F244..5C` 以掩码 3 调用 `0x2036D4E8`（`t_recovery` 已核对）。

### B2. 文件角色

| 后缀 | 类型（头部 `+0x10`） | 作用 | 谁执行写入 |
|---|---|---|---|
| `0` | 8 BACKUP | 备用程序映像（含通信接收、版本信息、更新命令 10/3） | 单元当前运行的程序（MAIN 或 BACKUP）中的写入器；数据由机身传来 |
| `3` | 2 MAIN | 主程序（16 段） | 同上 |
| `4` | 6 EXTEND | 资源（含 640×480 JPEG）；四个单元族的 `*4` 加权和相同（`0x0AAA7C7F`），推断内容相同、只是头部不同 | 同上 |
| `5` | 1 MONITOR | **只有 A16 的 `l06firm5` 有**；我们的三个单元包里没有 | — |
| `8` | 5 ADJCOM | 文本命令脚本，逐行解释执行；每次完整更新都会执行（`t_recovery`） | 单元解释器 |

文件族对应：`j*` 是 A12 50mm，`q*` 是 A12 28mm，`l08firm*` 是 MOUNT A12（已有研究按型号头和实测确认）；`l06firm*` 是 A16，`i*` 是机身；`k*`、`n*` 推断对应 S10、P10，未逐个核对头部型号。

**已证（静态，已有研究）：**机身按单元回报的 2048 B 信息里的前缀选文件族；单元流程是命令 `9`（暂存）→ 传送 → `10`（检查头、长度、加权和）→ `3`（按后缀 0..9 写入）（`unit_recovery` §3–4）。

### B3. 单元闪存分区（本轮新证）

- **已证（静态）：**`jlaunch0` 的 ROM MAP 打印函数 `0x27E39684..`（file `0x39884..`）按块号打印各分区。块数取自初始化数据 `0x27E72780 / 0x27E72784 / 0x27E72788`，分别是 MAIN 40、BACKUP 8、EXTEND 18；`qlaunch0` 相同。
- **已证（静态）：**`jlaunch3` 的写入区间函数 `0x20077A84`（file `0x2CC84`）按文件类型查表 `0x200BF470`，用同样的常量 `0x200B2CA4 / A8 / AC` = 40 / 8 / 18；`qlaunch3` 相同。`l08firm` 的常量在别的地址，本轮没有解码。

| 块号（50mm、28mm） | 分区标签 | 写入区间函数中的类型（起始块） |
|---|---|---|
| 0 | Boot & Monitor | 类型 1：起始 0（`0x20077ABC`） |
| 1 | Replace table | — |
| 2–32 | Replace blk（31 块替换池） | — |
| 33–40 | Backup prog blk | 类型 8：起始 33，结束 N_b+32（`0x20077BB0`） |
| 41 | Adjust data blk | 类型 4：N_b+33（`0x20077B24`） |
| 42 | Adjust Kiz blk | 类型 11：N_b+34（`0x20077B38`） |
| 43–82 | Main prog blk | 类型 2：N_b+35 … N_b+35+N_m−1（`0x20077AF4`） |
| 83–100 | Extend data blk | 类型 6：从 N_b+N_m+35 起（`0x20077B4C`） |
| 之后 | BtApl/BtAdj 1–3、RESERVE、SYSLOG | 类型 12/13 另有签名判断 |

- **推断：**有 31 块替换池和替换表，说明是 NAND 类器件，带坏块重映射。MAIN 与 BACKUP 的**逻辑块区间不相交**；物理上通过替换池共用备用块，所以替换表是两者共同依赖的元数据（未知风险）。
- **已证（静态）：**只有类型 1 会映射到第 0 块，A12 三个单元的包里没有类型 1 文件，所以官方包或同结构改包不会写 Boot & Monitor。版本页单独列 MONI 版本，也与"启动程序独立"一致。
- **未知：**擦写顺序、掉电提交规则、替换表何时更新；写入器有没有别的入口会写第 0 块（本轮只读了按类型分派这一条）。

### B4. 启动选择与回退（本轮补充）

**已证（静态）：**`jlaunch0` 的启动原因打印在 `0x27E2C0F0..`，跳转表 `0x27E7C4E0` 共 21 项。其中有：

- "booted with Backup Prog, Because a MainLoad error occurred."
- "booted with Backup Prog by a demand (_LINE=%d)."
- "rebooted with Ramload Prog by a demand."
- "rebooted, because Reserved Instruction / Address Exception / Undef Irq / Undef Kernel call / System Break Interrupt was detected (0x%08X)."
- 另有 "MainLoad err(1)"、"MainLoad err(2)"、"Backup req"、"backup is Broken."。

原因记录来自 `0x27E2D65C()` 返回的结构 `{code, arg}`。**推断：**由启动程序在复位后写入。

**已证（静态）：**`jlaunch3` 的维修命令表里，"reboot [-bkup][-main(default)][raml]" 的处理函数在 `0x2006D434`：

- 选 `bkup` 或 `back` 时，先调 `0x20077174`（检查 BACKUP 是否完好）；完好就调 `0x2006C360`，否则打印 "backup is Broken."。
- `0x2006C360` 构造 256 B 重启请求，代码 2（`0x2006C398`），经 `0x2006DAEC` 写入后调用复位 `0x2004B5E4`。代码 1 是回到主程序（`0x2006C300`），代码 5 用于另一条装载路径（`0x2004B788`）。
- 在本轮搜索范围内（`seth/or3` 直接构址），`0x2006C360` 只有命令行一个调用者。

**已证（静态）：**`0x2006CFE4` 是异常后的处理：系统配置字节 `*(0x200B2CF0)+80 == 2` 且 BACKUP 完好时，写记录并复位；等于 1 时走另一路。**未知：**复位后启动程序选 MAIN 还是 BACKUP，有没有失败计数。

**已证（静态，已有研究）：**BACKUP 拿不到 MAIN 头时，仍报 `NL1/jlaunch`、MAIN 版本 FFFF，并注册命令 10/3（`blink_state_50mm` §3）。

**结论分级：**

| 故障 | 恢复判断 |
|---|---|
| 只在使用某功能时出错，开机正常 | **推断：可恢复**。和同版本官方重刷是同一条路，后者现场已多次成功（10-25、10-26、10-31） |
| MAIN 装载检查失败（头或校验坏） | **推断：大概率进入 BACKUP**，然后由机身走更新（有诊断文字和 BACKUP 更新代码支持，未在实机上见过） |
| MAIN 装载成功，但开机初始化里死机或异常 | **未知**。有异常复位代码，不知道会不会回退；可能反复重启 |
| 写入中断，或替换表、启动程序损坏 | **未知**，可能需要送修 |

### B5. 版本页上的 SH / CV

**已证（静态）：**

- 机身版本页函数 `0x201C27B0` 由 `0x20371C68` 调用。单元一栏：SH = 记录 `+124`，来自 `0x2036C5F8()` = 单元信息 `+0x1B0`，按 `%06d` 显示；CV = 记录 `+128`，来自 `0x2036C624(..,10)`，即单元信息 `+0x1B4`。
- 单元端 `0x20052ED0..DC` 把 MAIN 头 `+0x16`（兼容号，官方 `0x0035`）复制到 `+0x1B4`。所以 **CV = 兼容号，不是校验值**，版本相同时不会变。
- SH 的含义未知，是一个 6 位十进制数。
- 结论：版本页不能区分同版本的"重写"和"跳过"。

### B6. 今天的刷机判断

- **推断（高置信）：**每次带着单元、选 Yes 的"+ 和播放键"刷机，都会对该单元执行"检查 → 更新"。
- 依据：
  - B1 的官方流程；
  - 机身掩码 3；
  - 卡 B 上 28 个官方单元文件齐全（`decisions.tsv` 第 746 行）；
  - 单元写入器在已审的路径里没有同版本跳过（`unit_drill` §2.2，仍有替代分支这一缺口）；
  - ADJCOM 每次都执行（`t_recovery`）；
  - 现场现象（10-26 的"刷机时装的镜头"规律，10-31 的 28mm/MOUNT 菜单问题消失）。
- **未知：**严格的物理重写证据（写入次数、读回哈希），以及机身是否同时为所接单元保存了某些状态（这也能解释现场现象）。
- 零写入确认办法见第一部分 §1：录屏看阶段文字和时长，拍版本页留基线。

### B7. 最小演练的技术要点

- **目标数字：**`xpan_incamera` 已定位的 50mm L 尺寸 16:9 高 2416（指令立即数，由初始化代码 `0x201A2C68` 写入 RAM 参数组 `0x204392A0+0x28`，不是数据表）。该报告的分阶段计划第 3 步就是"可见的小演练 2416→2400"。另外两个单元的地址见同一报告 §3.1。
- **为什么选它：**
  - 结果可见（JPEG 尺寸），而且只有拍 16:9 时才用到；
  - 开机初始化只把它写进 RAM 参数组，不做 I/O，不影响启动分支。这一点要在候选审查中逐个使用位置确认（**未完成**）。
  - 2400 是 16 的倍数，满足 4:2:2 的 MCU 高度 8，JPEG 合法。
- **必须保持不变：**头部 `+0x12/+0x14` 版本、`+0x16` 兼容号、`+0x170..0x180` 五个标志、段表、长度、入口；其余 28 个文件逐字节官方。只重算 `+0x16C` 加权和：`C = Σ P[i]·((i % 6) + 2) mod 2³²`，相位 0。
- **主机准备：**在 `local/` 研究副本上，用原厂检查函数 `0x2007A6A8` 和加权和 `0x200759EC` 重放；在模拟器里跑一次官方机身的更新界面（模拟器已有合成 50mm 单元，能做到什么程度待评估）。
- **禁止：**改版本号、改兼容号、带类型 1 文件、改 `*0`/`*8`、在同一轮里改别的字节。
- **不能证明的：**"开机即死机"能否回退。这一项在演练之后仍是未知，所以下一条规矩继续有效：单元改动都要做成"使用时才生效"。

## C. 各候选功能的技术依据

### C1. 机身成片前挂点

**已证（静态，`body_lut_r2`）：**

- 挂点 `0x2015F9D8`（file `0x114BD8`，原 4 B：`mv r4,r8; jl r0`），调用主 JPEG 包装器 `0x2016583C`。
- `K+0x14C` = 主图指针，`K+0x154` = stride，`K+0x156/+0x158` = 宽、高；普通情况 stride = 2W。每 4 B 是 `[Y0,Y1,C,C]`。
- 原厂叠字链 `0x2015CFD8 → 0x201605D0` 由 CPU 直接写主图 Y。
- 这个位置之前，小 JPEG 和缩略图已经生成。

**推断（裁切）：**

- 16:9 主图为 4288×2416（现场 R8051500–1502 已证）。把指针下移 416 行、高度改成 1584，stride 不变，JPEG 输入 DMA（`0x203ED714`）就只编码中间这一段。416 和 1584 都是 8 的倍数。
- 宽度不变，所以 stride ≠ 2W 的问题只在竖裁时出现。原厂"特殊分支会改 stride"（`body_lut_r2` 表），说明 DMA 支持 stride ≠ 2W，但我们的组合没有闭合。
- EXIF 尺寸、缩略图、DNG 不跟着变（RAW 保持 16:9，用户已接受在电脑上处理）。
- 需要确认：编码重试 `0x20164E90` 会重读描述；写文件时用的尺寸来自哪里。

**社区对照（外部）：**GRMod 把日期水印和光晕放在 `JpegEncodeMacroProcess::Execute` 开头，由 CPU 处理主图、screennail、缩略图（[GRMod 仓库](https://github.com/Maxwooow/Ricoh-GRMod)）。GR III 运行 Linux 4.4 和定制 Poky（[gr3x-fw-hack](https://github.com/hhornbacher/gr3x-fw-hack)），资源与 GXR 不可同日而语。

**resident 预算：**

- `body_lut_r2` 估计透传桥 20 B、安全出口 8 B。
- 当前余量约 176 B（题设），必须保留的 200 B 区不能动用。
- 加上"DAT 是否已装载"的检查和一次性令牌，**推断**需要 40–60 B，**未链接验证**。
- 超出就用 archB（窗口 6,892 B，余量 736 B，已严格链接；永久 RAM 和早期装载屏障仍为 OPEN）。

**CPU：**

- `cpu_speed_r1`：tick 是 1 ms；有效 106–227 MHz。
- 推断：整帧 1,221 万像素，只改 Y 的颗粒或暗角每像素约 5–15 个周期，约 0.3–1.7 秒；光晕（缩小加多次盒式模糊）数秒。都是估算。

**恢复：**机身改动坏了，刷回官方 `ilaunch3`（`da1980e9`）即可，现场已验证多次。**未知：**机身在开机初期就崩溃时，"+ 和播放键"还能不能进入（`ilaunch0` 里有同样的分区标签，机身也有自己的 Monitor/BACKUP 结构）。所以机身挂点也要保持"开机不执行，用户触发才执行"。

### C2. 半格双联：JPEG 结构普查（本轮新证）

[jpeg_census.py](jpeg_census.py) 读取 80 张 `R80*.JPG`（captures 里用户的 GXR 实拍；结果在 `local/jpeg-census.json`）：

- 全部是基线 SOF0，4288×2848，Y 2×1、Cb 1×1、Cr 1×1（4:2:2，MCU = 16×8）；**没有 DRI**；APP1 约 30 KB（EXIF，含缩略图），APP2 128 B。
- 量化表：80 张里 **25 套不同组合**（相邻连拍常相同）。
- 推论：
  - **无损 MCU 拼接只在两张表相同时成立**；
  - 没有重启标记，必须顺序解 Huffman 才能定位 MCU；
  - 半宽 2144 = 134 个 MCU，对齐没有问题；
  - 表不同时要把系数重新量化（不需要 IDCT，有少量画质损失）。
- DAT 文件 I/O 的现状（`decisions.tsv` 第 729、736、738 行）：
  - 写：整个文件从偏移 0 写入，不能 seek（seek 返回 236）；
  - 读：从头整读；
  - 只证明过一个 8,704 B 的文件；更大文件的读取由 g147 测试中；
  - 创建、改名、删除都没用过。
- **结论：**卡上拼接需要先证明"预分配大文件，再整写"或"新建文件"，并且要在菜单任务里处理几 MB 数据而不触发看门狗；都是**未知**。

### C3. 开机 / 关机画面

**已证（静态）：**

- `ilaunch4` 和 `jlaunch4` 在相同的偏移（`0x204`、`0x6F458`、`0x78360`，以及 `0x81D7C`/`0x82238`）各有 4 张 JPEG：640×480 三张、320×240 一张。

- 字节没有放进本目录，scratch 副本已删除。

**推断：**RICOH 图可能是开机画面或升级画面的背景（下方的框像进度或消息区）；示例照片可能是演示用图。

**未知：**

- 解码这几张图的代码在哪里，开机时是否解码；
- 资源索引里有没有长度和校验；
- 换成不同大小的 JPEG 后，资源表怎样重排。

**风险：**开机路径。先在批量模拟器（官方机身冷启动约 75 秒）里追这张图的读取和解码，再考虑上机。

### C4. 颗粒、暗角、光晕

- **颗粒：**`grain_raw_feasibility` 和 `P1_P4.md` 已给出编码前只改 Y 的方案、2 行噪声约 8.6 KB、GR IV 颗粒统计（σ≈17.6 码，ρ1≈0.62）。缺的是挂点和计时。
- **暗角：**
  - 单元已有运行时 32×27 网格（`jlaunch3:0x201B2424`），只对效果 8/10（玩具相机、正片负冲）启用，普通配方走平坦分支（`hidden_processing` §6）。
  - 机身方案只需要一个径向系数表，不改单元。
  - MOUNT 原生有"周边光量 −3…+3"，负值就是暗角（[MOUNT A12 说明书](https://www.ricoh-imaging.co.jp/english/r_dc/support/manual/pdf/gxr/mount_a12_en.pdf)、[MOUNT 产品页](https://www.ricoh-imaging.co.jp/english/products/gxr/unit5.html)）。
- **光晕：**GRMod 的做法见 C1（[GRMod](https://github.com/Maxwooow/Ricoh-GRMod)）；GRLife 有 Soft Glow 和颗粒（[GRLife](https://grlife.app/)，另见 [Pentax Rumors 报道](https://pentaxrumors.com/2026/10/19/this-grlife-app-is-unofficial-browser-based-tool-designed-to-create-ricoh-gr-custom-firmware/)）。在 GXR 上要先测耗时。
