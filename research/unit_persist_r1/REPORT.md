根因：高度怀疑

已复现一个足以造成整表消失的 v3.10 装载缺陷：RPC 和单元已经发布，但卡文件或卡身份尚未可用时，H51 会消费本次开机的装载机会，随后退役；卡稍后恢复，首次 ADJ 也不再读 DAT。v3.9 等到首次 ADJ 才装载，同一时序输入可以成功。朋友是否命中这条路径，仍缺首次失败状态，不能把模型复现写成现场定责。

“根目录 29 文件必须长期保留”的假说尚未证实。resident/DAT 的身份检查不依赖这些根文件；本轮原厂更新器已把完整 v3.10 MAIN 写入模型 NAND，读回 SHA 与 r5 一致。升级收尾因主机桥接状态膨胀而中断，不计完整升级通过。普通开机的 ROM/MONITOR 选源仍未覆盖，MOUNT 现场 A/B 尚待结果，不能据此宣称实机一定从该内部 MAIN 启动。

原版三单元 MAIN 在早期文件打开不可用时都会退役；+88 B 候选在同一边界都能留到首次 ADJ 装载并发布 8 行。它修复这条掉表路径，但迟到的那次开机不保证首张自动套用。朋友实际是否命中仍需首错或版本证据。DAT 从首次加载就要求受支持的单元身份和运行时 1.51；没有“刷机首次开机放宽版本检查”的分支。

这是离线研究。没有接触相机、SD 卡或网络，没有安装依赖、commit、push，也没有修改既有包和源码。固件地址、反汇编、原厂表、派生映像、原始记录和重放脚本仅放在 [local/](local/)。未完成的矩阵和收尾单独列出，不计通过。

机主在 11 月 5 日的 MOUNT 数十次成功，包括已知的有监督 M/S 检查，继续作为现场成功事实保留。11 月 4 日那次掉表原因仍 OPEN。本轮的共同故障机制不能证明 28/50 必然比 MOUNT 更早就绪。

三单元健康 MAIN 模型中，用于消费 BOOT 的 H51 采样时，RPC 和单元发布字都为 1；只改变早期文件打开返回，三者都会掉表。现有模型没有给出“28/50 的 SD 必然更晚”或“单元必然更早”的结论，实机交错仍待首错记录。

## 3. 首次开机与后续开机

### 已装入 v3.10 MAIN 后的共同路径

1. MAIN 映像中的 root 初值是全 FF。H50 在原厂进入首次待机的局部点初始化合法冷 root，并置 BOOT pending。
2. 随后的 H51 先把 BOOT pending 消费成 attempted；若引擎未 READY，调用 `rv_load`。H51 在更早的循环中也可能被调用，但 root/pending 未成立就返回，不读 DAT。
3. `rv_load` 先检查 RPC 和单元发布字。早期未发布就返回，尚不置装载的 `RF_ATTEMPTED`，所以 H01 仍能重试。
4. 正式装载先置 `RF_ATTEMPTED` 和 busy。依次预开卡 DAT、IROM 槽 A、槽 B。没有一个能打开，就直接退役。
5. 找到来源后分配 loader workspace，采样单元、堆、epoch，先校验卡头，再按需要探测 IROM 两槽；有效卡始终优先。完整读取、EOF、CRC、body/build/ABI、重定位和纯初始化全部通过后，才发布 READY。
6. H51 再向 DAT 派发一次 BOOT_RUN。它不会发布 ADJ 列表。首次 H01 还要独立通过菜单、activity、栈、原厂描述符和行数等归属条件，才能发布扩展列表。

BOOT attempted 和装载 attempted 是两个不同的 RAM 标志。前者已经消费，并不说明 DAT 已读入；后者还没消费时，H01 仍可以装载。DIRTY/GUARD 保护的是颜色写入，不能拿它代替装载状态。

### 刷机后那次到底哪里不同

resident 没有“这是刷机后第一次”分支，也没有跨开机的首次成功标记。只要真正重新装入相同 MAIN、相同设置、相同单元和相同设备时序，扩展路径应相同。

但以下两件事尚不能混用。

- 升级收尾仍在原会话运行时，SD、文件系统和固件文件已经被升级程序访问过；下一次普通开机要重新建立这些条件。这是早期可用性差异的合理解释，尚不是朋友时序的实测。
- 若机主说的“第一次”已经是一次完整断电后的正常开机，不能再直接声称 SD 被上次刷机预热。应查内部程序实际版本、MAIN 前选源、原厂保存的设置/参数、单元状态及启动交错。

本轮没有完整复位 ROM、机身 MONITOR 或原厂关机模型。所有“新 MAIN”都明确指新建 Machine，没有恢复整机快照；不能把它们写成完整物理开关机或 ROM 选源验收。

## 4. 启动选源、刷写和单元版本

时间关联来自 `decisions.tsv`：11 月 4 日约 09:38 把 29 文件移到 `V310UPD/`；约 11:5x 列表消失，卡内容未变；12:09 复制 r4 后 29 文件重新回根目录，列表恢复。复制 r4 同时也恢复了 test DAT，之前还切换过 release，因此这一历史关联不是单变量 A/B。

### 身份检查不依赖根文件

当前 loader 只把卡 DAT 和两个 IROM DAT 当候选来源。body/build/ABI 比较使用 DAT 头和编译进 resident 的常量；DAT 的 gate 也用这些绑定和当前单元身份/原厂 pin，不打开根目录的 `ilaunch3` 或其他 28 个文件来计算身份。DAT 初始化另有可选 `GXRCE.CTL` 读取，与刷机文件无关。

因此“移走 ilaunch3 让 resident 身份校验读不到文件”已被静态控制流排除。

### 原厂程序确有多种装载来源，但普通开机选源仍待证明

原厂 BACKUP 包含 SD、IROM 和 NAND 的程序装载分支，也包含 body MAIN download boot 的状态文字。28/50 的 BACKUP 分别使用各自单元文件前缀；这些能力本身不证明普通拍摄开机会优先执行根文件。MAIN 的来源标记由 MONITOR 传入的启动对象复制而来，并不是 resident 通过根文件存在与否计算。当前官方包没有独立的机身 MONITOR，现有模拟器也从 MAIN 入口加载指定映像。此前 DAT-only 模型成功，不能反证更早的 SD 选源。

已完成 MOUNT、28mm 的根目录/子目录对照，50mm 的根目录组也完成。各组均在同一 MAIN 后达到 READY，并可进入扩展列表。子目录组保留原文件簇和 DAT 的目录位置，只移动 29 文件的目录项；不是重建卡布局后作比较。在已观察到的 native open 中，只有 DAT 和可选控制文件，没有 launch 文件。该停点观察要求 PSW 的系统位有效，不能当作所有早期文件访问的穷尽记录。50mm 子目录组尚未补齐。

“不是官方 1.51 构建”还要分两种：运行时报告旧版本时会被上述版本门拒绝；若仍报告 1.51、内部子版本为零且名称匹配，另一份构建并不因整体字节不同而必然被拒绝。现有 pins 不提供完整 ROM 身份保证，这类构建的后续 native 兼容性没有在本轮覆盖。

核对时还要记录单元全名，不只记“28mm”。本扩展只接受上述三个前缀，其他单元即使报告 1.51 也不因此受支持。判断主版本时看 MAIN，不要求 BKUP、MONI 每一栏都显示 1.51；这些栏先按原值记录，不据此自行判定需要重刷。

| 配方记忆和完整 S | 自有 40 B 在原厂设置块内，原厂保存链可能使其跨开机留存。 | 绑定不符或坏记录通常只跳过恢复；不等于停用整张列表。复制相同 DAT 不会清它。 |
| 单元九行、T、单元启动设置 | 与那 40 B 分开。实机关机后状态及原厂加载顺序未知。 | 重刷/断电/重连可能改变初始化，但本轮没有实测这些动作的效果。 |
| IROM 槽 A/B | 文件可长期存在。当前 g158 不安装自身到 IROM，storage service 对外关闭；旧 `mark.c` 虽仍在树中，不代表这条安装/改名路径可达。 | 单纯复制 DAT 不清槽；完整刷机也不应被当作可靠的删槽操作。原厂某些异常单元更新分支会格式化 IROM，不能把这个副作用当修复。 |
| 内部固件与原厂 T 参数区 | 更新程序有实际 NAND 写入，和 resident 的 RAM 退役不同。 | 只有执行完整更新链才能讨论写回，卡上文件相同本身不证明已写入。 |

有效卡 DAT 优先，旧 IROM 不能在它成功时抢先接管。卡尚不可用时，旧槽可以先被打开；身份不符会被拒绝。若没有任何可接受来源，当前代码仍会退役。兼容的旧 IROM DAT 若被接受，则该会话不会在卡稍后出现时自动热换，和跨开机“已装载标记”是两件事。两槽实机内容目前均未知。

原厂 MAIN 还有按启动参数决定是否保留部分 RAM 的分支。它不能证明 resident root 也会跨普通关机保留，但足以要求现场把普通重启和取电池后的冷启动分开记录。若 root 确实保留，已退役状态会继续挡住 H50/H51/H01；这可以解释“重刷才恢复”，无需假设 NAND 中有退役计数。该前提仍需实体或更早启动层证据。

## 7. 复现与其他候选

初始主机矩阵覆盖 50mm、28mm、MOUNT 的全就绪、SD open 迟到、CID 迟到、RPC 迟到、单元发布迟到、旧/有效 IROM、身份尚未发布。C 后端覆盖全部；独立 Python 后端复核 SD open、CID、单元迟到。v3.9 三单元在 SD 于 ADJ 前恢复时都能装载。

三单元 MAIN 对照在正常设备输入下都能发布列表；只在早期 resident 文件打开边界声明一次不可用，即可得到退役和原厂列表。保留的首次失败包括失败前的 root、原始返回、候选路径和后续 ADJ；没有用最后一次重试覆盖第一次失败。模型的底层行数字段原厂为 7、扩展为 8；这是内部物理行数，不是机主口述的可见配方总数。

其他候选按当前证据保留。

1. 根文件影响 MAIN 之前的程序选源，或现场更新没有把目标 MAIN 写入内部。历史关联强，但缺单变量现场结果及完整 MONITOR 路径。
2. 早期主块/工作区分配失败。主机注入会得到同样退役外观；真实空闲堆和最大连续块未知。DAT 允许的最大请求不是实机可用量证明。
3. 早期单元身份已非零但尚未稳定，或装载后身份变化。前者可在初始化失败，后者可被 `rv_check` 撤销；RPC ready 非零不保证全部单元业务已完成。
4. 有效保存记录让第二次启动首次进入 BOOT 颜色事务，某个单元应答、epoch 或资格复核失败后退役。已通过的 28/50 保存重放削弱“记录必然出错”，没有覆盖朋友真实保存块和单元状态。
5. DAT READY，但首次列表发布或原厂 UI 归属失败。这与“未装载”外观可以相同，有些分支允许退出重入，有些硬错误会退役。
6. 文件消失、被改名、格式化后没放回 DAT、媒体/目录差异或实际刷入版本不同。朋友还没给出关机后的文件清单，不能提前排除；现有 g158 代码不会正常把 DAT 自行改成 OK。

普通 WB/模式/外包记录拒绝本身正常返回，不能直接解释整表消失。没有把“未自动套用”当作“DAT 没装载”。

## 8. 修复方案与字节账

先关闭根文件 A/B。若证实实际问题是程序选源/未写入，修安装链并验证内部完整读回；以下方案只修已经复现的早期装载缺陷。

### 能否只换 DAT

可以在 DAT 内把不成熟的 BOOT 颜色事务延后，干净跳过尚未稳定的资格、保留首次失败、改善 READY 后的列表重入与诊断。这样适用于“引擎已 READY，之后 BOOT/UI 失败”。

卡 DAT 在被装载前不能执行代码。resident 已因读卡失败而退役时，换 DAT 无法让它重试；在 DAT 内写“等首次 ADJ 再装载自己”也没有执行机会。关闭 BOOT 的 release 同样要先经过 resident 装载。因此若现场确认的是本轮 SD 早期失败，完整修复必须改 resident。

### 实际严格链接的隔离候选

所有候选从实际 resident 源复制到本轮 `local/`，保留链接脚本、root/pins 布局、24 B 预留区、身份/CRC/epoch 检查。原始包和源码没有改。

| 候选 | resident 代码 | 相对当前 | 92 B 中剩余 | 作用与缺口 |
| --- | ---: | ---: | ---: | --- |
| 原版复编对照 | 7,968 B | 0 B | 92 B | resident 和整份 MAIN 都逐字节等于原包。 |
| H51 不再主动装载 | 7,812 B | -156 B | 248 B | 恢复首次 ADJ 装载；会失去正常开机自动套用，属于明确降级方案。 |
| 预开全部失败时不消费装载机会 | 7,988 B | +20 B | 72 B | 不分配 workspace 就返回 FACTORY，保留 H01；漏掉 CID 暂不可用和旧槽能打开但被拒绝的情况。 |
| 上项加 H51 的 CID 门 | 8,024 B | +56 B | 36 B | 能避开早期 CID 失败；仍不能完整处理“卡文件晚到、旧 IROM 可开”，且改变无卡 IROM 自动套用时机。 |
| 有界可用性后补 | 8,060 B | +92 B | 0 B | 额外 workspace 至多一份；保留卡/IROM 完整校验。 |
| 合并可用性返回的候选 | 8,056 B | +88 B | 4 B | 三单元实际 MAIN 早期 open 不可用→首次 ADJ 列表恢复通过；更广矩阵未补齐，尚非发布固件。 |

这里的 +88 B 是链接后代码长度的增量，不是只修改 88 个文件字节。按当前研究身份重组 MAIN 后，该候选实际改变 3,917 个字节：resident 区内 3,914 B，区外只有头部校验字段的 3 B；12 处外部 hook、段表、root 和 pins 均不变。LTO 重新布局会连带改变函数内部地址。完整账目见 `local/patch-byte-account.json`，baseline 的整份 MAIN 差异为零。

最后一个候选的逻辑差异只有 loader。

- 预开全部失败时，释放 busy，回 FACTORY，不分配、不消费装载机会；H51 本身仍只派发一次，后补由明确的 H01 触发，不增加后台循环。
- 卡头探测为不可用、没有可接受来源时，只允许一次后补。复用 root 中原本未使用的一个字节作本次 MAIN 的计数，新增一次 workspace 保留有明确上限。
- 卡头/CRC 错误仍按原规则校验并尝试可接受的 IROM；没有可接受来源时退役。内存分配失败、epoch/身份变化、已执行引擎后的硬错误也保持退役。不能把所有失败改成无限重试，也不能释放已发布或归属不明的内存。
- 卡恢复后的 H01 只恢复列表和正常手动操作，不偷偷补做已经错过的 BOOT 颜色事务。

候选为了重放原始 g158，暂保留原 trust 常量；这是研究条件。正式变更必须生成新的 resident 身份，并重封对应 DAT 的绑定，重新核对最终机身、DAT、工具和恢复包；不能把这些研究映像直接当朋友更新包。

建议准备 v3.10b 的装载修复候选，先做三单元和恢复验证，再决定现场试用；现在不建议立即发布，也不建议让机主尚在 v3.9 的 28/50 为复现而一齐升级。若根文件 A/B 指向另一层，v3.10b 的范围必须随之调整。

只采用 +88 B 候选时，早期 SD 迟到的那次开机只保证后续手动列表可以恢复，不能承诺首张自动套用。要在卡恢复后仍自动套用，必须另设计受首次成像边界约束的再派发，并重验 DIRTY/GUARD；不能简单把 H51 改成循环重试。正常卡已就绪的开机仍沿用原 BOOT_RUN，这与迟到后的功能保证要分开验收。

## 9. 机主的最小现场诊断

### 先补只读版本信息

1. 若还保留 g158 失败现场，先拍首个原厂 ADJ 画面，注明当前单元，不先回刷。
2. 正常关机，保持同卡同单元，用“−键＋播放键，超过 1 秒”读取完整版本页。先抄 BODY MAIN 和 CAMERA UNIT MAIN，再保留整屏；不要只报“都是 1.51”。
3. 退出并正常关机，另装另一支单元，单独读版本。读版本页不能替代正常开机的列表测试。
4. 若已回退 v3.9，标明这是回退后的读数，不为补历史版本页重新刷 g158。

### 先做 MOUNT 的根文件 A/B

一次只动一件事。由机主在正常关机后移动文件，本研究不操作卡。

1. A：保留当前根目录和当前 DAT，正常开机，第一次进入 Image ADJ，记录列表及完整 Status；不先拍照或改变配方。
2. 正常关机，只把那 29 个刷机文件移入目录。DAT 路径、名称和 SHA 不变，不格式化，不换单元，不换 DAT。
3. B：同一拨盘/设置正常开机，等待待机稳定，第一次进同一个 Image ADJ，记录结果。若原厂列表，先保留这一现场，不靠重新刷机恢复。
4. 正常关机，只把同一 29 文件放回根目录，再做 A。这个回合不重新刷机。

B 仍成功，可以排除 MOUNT 普通开关机必须保留根文件的强假说；B 失败而 A 恢复，说明文件放置影响行为，仍需区分程序选源和 SD 初始化时序。B 成功不等于已读回内部 MAIN；若要排除 RAM 复用，在正常关机完成后另做一次取电池冷启动，继续保持 B 的文件条件。若曾格式化，必须先确认 DAT 仍在根目录；把 DAT 一起删掉不是有效 B 组。

### 28mm、50mm 先留 v3.9 基线

1. 只装 28mm，在当前匹配的 v3.9/G154L 下记录一次列表和目标配方保存结果。
2. 正常关机再开，卡不动，待机稳定后第一次打开 Image ADJ，记录列表和记忆值。
3. 关闭并重开 ADJ 一次。随后正常关机，再换 50mm 单独重复前两步，不在一次开机里混换单元。

这组只能确认现有稳定组合及保存反馈，不等于已经在 v3.10 上定责。需要 v3.10 诊断时先选一支单元，由独立验收过的诊断方案采集首次失败；不要让多个动作同时改变现场。

### 三类状态必须由 resident 证据区分

| 要区分的情况 | 确切判据 | 普通屏幕能说明什么 |
| --- | --- | --- |
| 尚未成功装载、仍允许后补 | FACTORY，尚无装载 attempted/stop，未有 READY 会话。 | 后来首次 ADJ 成功可以支持“此前没装”，原厂列表本身不够。 |
| 已退役 | DISABLED_UNTIL_REBOOT/stop；再看是否曾发布 READY，区分装载前失败与执行后撤销。 | 同次退出重入仍是原厂列表，与没有触发装载仍可能同貌。 |
| DAT 已 READY、列表没发布 | 有 READY 会话，检查 UI 发布/恢复记录、H01 返回和归属拒绝。 | 能打开 g158 Status 可证明 DAT 运行；重入恢复支持临时发布问题。 |

当前 g158 的 Status 在 DAT 中；DAT 没装进来或已经退役时，它不能显示原因。没有找到已验证的机外只读 root 读取入口。因此现有包无法只靠一张原厂 ADJ 屏幕无歧义地区分上述三类，不能把“无 Status”直接写成“已退役”。后续诊断必须补一个不依赖 DAT 的 resident 状态出口，并在第一次失败时冻结装载阶段、原始返回、候选来源和是否曾 READY；本轮的离线分类按这些原值判定。

读取状态时，`RF_PUBLISHED` 只表示曾发布引擎 READY，不表示列表已经发布；退役后该位仍可能留下。`RF_SD` 也不是 SD 就绪信号。现有 `rv_retire` 会把多种装载错误统一记成 STALE，单看最终 fault 和零 check_failure 不能还原原始 open/CID 失败。诊断出口的空间和显示路径要单独链接、验证，不能假定 +88 B 候选剩下的 4 B 足够加入它。

诊断版还要先显示独立的机身/resident 身份标记，再读上述状态。若标记也没有出现，应另列为“启动了官方或旧 MAIN，或该诊断入口未执行”，不要套进三类 DAT 状态。出口应保留原 H51 时机，只在首次 ADJ 后读取已冻结的结果；不得为了显示方便而先清退役、先装 DAT 或改掉现场时序。

若只做现有包的最小观察：记录首个原厂列表，退出重入一次，再独立做一次取下电池后重启、仍保持同卡同单元。取电池后恢复只能支持 RAM/初始化差异，不能单独证明 NAND 被清除；不要连续改 WB、复制 DAT、格式化、重刷，把首个失败抹掉。

## 10. 给朋友的临时建议

继续使用此前看起来稳定的匹配 v3.9/G154L 组合，分别确认 28/50 的正常关机后列表和上次配方高亮是否保留。该旧包只预选上次配方，需要 ADJ 后按 OK 套用；Look 和自建条目的微调原本就不跨关机保留，不能拿它验收 g158 的完整记忆。暂不把 g158 当作这两支单元的稳定升级。

如果还保留着失败现场，先记录具体单元、第一次 ADJ 全屏、是否真实执行过升级、关机后 DAT 是否仍在及根文件是否被移动/格式化。只有这些材料留存后再按已知恢复方案处理。不要反复刷同一包来充当诊断，也不要删 IROM 或初始化内置存储。暂时保留根文件可以作为有记录的对照条件，不能宣称它们是正式运行依赖。

## 11. 验证边界与复跑材料

所有 Python 读固件/DAT 均用 `-I -B`，计算以 nice 15 启动，按 `tools/loadgate.py` 的 `workers()` 或 `cap(len(running))` 决定准入；0 就推迟。没有做主机墙钟性能结论，也没有使用 `quiet_for_timing()`。

最初 strict_r4 的 `panel.py` 和登记清单在本轮期间由外部工作发生变化。第一次拒绝的 `unregistered source file` 已保留；受影响运行不计通过，没有修改共享模拟器或跳过校验。随后模型分组需绑定新的独立输入清单；原来的三单元基线、指令主机后端和 legacy 参考结果分开记录，不能混写为一个不变的模型矩阵。固件/DAT 输入未见变化，漂移详情在 `local/boot-source/input-drift.json`。

保留的驱动失败还包括最初头偏移断言写错、冷 root 的 FF 指针观察错误、分配故障探针的寄存器别名错误，以及把 ADJ 构造夹具的 activity 误用于 BOOT。它们均与固件故障分开，原结果保留，修正后使用新运行名。PASM 首次菜单另遇未声明的单元消息，未伪造应答，后续 AUTO 对照不能追认该路径通过。

长时间更新重放已因主机资源问题停止，原始 `KeyboardInterrupt` 和完整中断快照保留。停止点是约 69.67 亿条模型指令，实际 NAND 已含完整目标 MAIN；不能把中断写成更新器自身报错或完整升级通过。宿主采样足迹为 9.8 GB，峰值 12.4 GB，主要栈在 native bridge 导入、解析状态；最终 native GC 记录约 328 万个 live objects。快照压缩后约 14 MB，没有发现重复保留大快照。实际快照中的 Monitor.calls 已积累 4,083,305 条；Observer 也有只追加的历史容器，桥接器会反复搬运这些历史。

有界版本和控制组均从同一保存点完成 500 万步，功能状态摘要、停止位置、步数与 NAND 摘要相同。Monitor 调用历史保留 512 条，新增 Observer 历史也设 512 条上限；恢复后的功能状态摘要与原快照相同，保留 RAM、寄存器、NAND、设备 pending 队列和计数。结果分别见 `local/boot-source/official-to-v310-cap-5M/result.json` 和 `official-to-v310-control-5M/result.json`。此段没有升级收尾事件，有界结果仍为 `OPEN`，不是完整更新通过。

这个短段中 Observer 历史没有增长，控制组也先裁掉了原快照的 Monitor 观察历史，避免再次搬运四百多万条记录。因此它只证明声明保存点之后这一短段的功能结果一致，不能代替历史增长场景或长时间内存稳定性验证。新作业均服从正常 VM 压力门，未获准入的部分继续延期，没有关闭或绕过该门。

复跑入口、输入身份、原始命令、首个失败、构建差异及逐项结果在 [local/REPRODUCE.md](local/REPRODUCE.md)。最终结果汇总核对了 69 份记录，其中 63 份行为检查通过，6 份保留为驱动错误，已执行的行为断言没有不符；仍有 48 项计划未完成。[local/validation.json](local/validation.json) 为 `OPEN`，不表示所有计划通过。普通 MAIN 的成功负例使用 `FACTORY_LIST` 状态，不属于驱动错误；汇总器最初误分这三份记录的问题已改正并重跑，原固件结果未改。

剩余工作包括 MAIN 前 ROM/MONITOR 选源、50mm 的根文件子目录对照、从本轮实际更新 NAND 启动的新 MAIN、单元版本负例的其余组合、有界续跑的历史增长与长尾，以及候选的重复 CID 不可用、旧 IROM 与晚到根文件等矩阵。保存 S 的重放也未替代实际关机提交。没有实体相机、SD 介质、ROM loader、真实 NAND/ECC、真实关机保存或朋友现场的验收声明。

所有队列已结束。最终汇总检查已执行；最终封存作业因负载门返回延期，未生成 `SEAL.json` 或最终 `SHA256SUMS`，不作完整封存声明。原始结果、首错、脚本和独立 NAND 读回均已留在本目录。
