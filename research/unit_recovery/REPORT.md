## 2. 四个文件的角色和头部

【静态确认】角色来自头部 `+0x10` 的类型值，以及 `jlaunch3` 中打印类型名的 switch。switch 在 VMA `0x200789D8`，跳转表在 VMA `0x200BF4C8`、file `0x746C8`。形式来自 `+0x11` 的 `BINARY`、`MOTHEX`、`TEXT` 分派。见 [类型反汇编](evidence/14-type-labels.txt)、[分派表解码](decoded-dispatch-tables.json)与 [头部摘要](a12-header-summary.json)。

## 3. 机身选择文件、传送和单元接收

### 3.1 机身端可定位的路径

【静态确认】机身确认函数在 `ilaunch3` VMA `0x2036D4E8`、file `0x3226E8`，调用 `0x2036CAD8`；后续根据返回值和更新掩码进入单元、机身或两者的分支。单元写入包装函数在 `0x2036FAC8`、file `0x324CC8`。见 [机身 UI 摘录](evidence/01-body-ui.txt)。

【静态确认】机身 `0x20063F64(1)` 返回单元信息缓冲区 `0x2040F818`。该缓冲区在 `0x200637E0` 路径中读入 2048 字节，并核对前 2044 字节的加和；文件传送循环使用该信息 `+4` 的字符串组成文件名。单元映像中有 `/ATA1/jlaunch`、`/IROM/jlaunch` 及 `NL1` 标识。见 [机身单元信息](evidence/12-body-model-info.txt)、[数据摘录](evidence/13-data-and-labels.txt)。

【推断】机身从已连接单元取得信息中的文件前缀，结合后缀选择对应族，而非把所有 `j/k/n/q/l*` 文件逐个灌给单元。该推断与官方对自动选文件的描述一致。

【未知】单元没有启动或无法返回上述信息时，机身还有哪些替代识别途径、是否能从更早启动层取得前缀，本次未闭合。正常单元能够提供文件名前缀，不等于损坏 MAIN 的单元仍然能提供。

【静态确认】机身 file `0xC26B4`、VMA `0x2010D4B4` 的循环枚举后缀 `0..8`，构造源与目标路径，先调用 `0x200924DC`，失败后走 `0x20091F88`。另一路 `0x2010D578` 使用常量后缀 `00 03 04 08 FF FF FF FF`，先发命令 `78`，再处理文件。见 [机身传送摘录](evidence/02-body-transfer.txt)。

【静态确认】`0x2036FE48`、`0x2036FBE4`、`0x2036FAC8` 的具体路径受 `0x20090AB8(6)` 影响。该函数比较参数与通信状态字节，并非一个已经证明的“Safe Boot 可救援”判定。传统命令路径中可见命令 `9`、文件传送、命令 `10` 检查以及命令 `3` 写入；还有 `0x20092AA8`、`0x20092B0C` 等替代分支。

【未知】上述替代分支的完整状态机及本机 A12 当前运行时所选分支尚未确定。因此这里给出可核对的局部调用关系，不把它们拼成没有条件的唯一更新时序。

### 3.2 双方可对上的命令封装

【静态确认】机身 `0x2009005C`、file `0x4525C` 构造以下大端字段，经 `0x20093D48` 发送，并等待返回；参数数目必须小于 `11`。单元 MAIN 接收任务用 32 字节步长收包，检查长度，并按 packet kind 分派。见 [机身传送](evidence/02-body-transfer.txt)与 [单元接收](evidence/03-unit-receiver.txt)。

```text
u16 +0   packet size = 12 + 4 * argc
u8  +2   packet kind = 0x0D
u32 +4   0
u16 +8   command id
u16 +10  argc
u32 +12  arguments...
```

【静态确认】单元 packet kind `0x0D` 经跳转表进入 `0x200802B4`；普通命令被送入 mailbox `19`，再由命令任务进入 `0x20080E44`。后者读取 command id、argc，从 `0x203400E4 + 8 * id` 的运行时表取得函数并调用。command `8` 另有分支。不能把“收到 0x0D 包”直接等同开始擦写。

【静态确认】命令注册和处理函数可以配对如下。`0x2007CBA8` 检查命令、参数和函数指针后注册。见 [注册与处理](evidence/04-unit-command-registration.txt)。

| 级别 | 命令 | MAIN 注册位置 | MAIN 处理函数 | 已读出的行为 |
|---|---:|---|---|---|
| 静态确认 | `9` | `0x2014BFE0..0x2014BFF4` | `0x2014B830`，file `0x100A30` | 等待同步，处理 `/IROM/DUMMY.BIN`，清理 `/IROM/jlaunch%d` 暂存文件。 |
| 静态确认 | `10` | `0x2005815C..0x2005816C` | `0x2007AD38`，file `0x2FF38` | 建立文件清单，调用逐文件检查，要求有可处理的程序类文件。 |
| 静态确认 | `3` | `0x20058170..0x20058184` | `0x2007AE3C`，file `0x3003C` | 调用 `0x2007C630`，遍历启用的文件并处理。 |
| 静态确认 | `78` | `0x2014C028..0x2014C03C` | `0x2014BCC4`，file `0x100EC4` | 文件准备路径中的辅助命令；完整语义未还原。 |

【未知】已读到的软件层协议没有给出物理总线的完整电气与重试语义。`/IROM` 是固件内部路径，不是 Mac 挂载路径；清理该路径不能直接证明 MAIN 物理分区已经擦除。

### 3.3 `SysUnit_FileVersionCheck` 与同版本问题

【静态确认】三个诊断字符串确实位于 `jlaunch3` file `0x136E44 / 0x136E69 / 0x136E8D`，对应 VMA `0x20181C44 / 0x20181C69 / 0x20181C8D`。邻近的后缀表由 `0x2014B95C` 使用，但该函数是逐文件存在性扫描，不能因此改名为完整的 `SysUnit_FileVersionCheck()`。见 [数据摘录](evidence/13-data-and-labels.txt)与 [暂存函数](evidence/11-unit-staging.txt)。

【未知】BE32 常量和 96 字节内 `seth` 配对搜索没有定位三个字符串的直接消费者。搜索不覆盖所有别名、间接引用和寄存器值流，因此不能据此宣称这些字符串无用。当前没有可靠的该函数入口、完整版本比较分支或同版本最终选择掩码。搜索范围和结果保存在 [bounded-xrefs.json](bounded-xrefs.json)。

【静态确认】已读到的 `0x2007A6A8` 检查路径会读取 512 字节头、核对类型、头部、payload 加权和与容量，再把识别的类型写入清单标记。`0x2007C630` 根据这些非零标记调用处理函数。这里没有独立证明“比较当前版本相等后跳过”的逻辑。见 [文件检查](evidence/05-unit-file-check.txt)。

【未知】“这个局部函数没有找到同版本跳过”不能推出“正常更新一定重刷同版本单元”。跳过也可能发生在文件传送前、不同协议分支或未定位的上层比较中。因此答案仍是未知。

## 4. 写入顺序、执行位置与 BACKUP

### 4.1 文件检查和处理顺序

【静态确认】`0x2007C630`、file `0x31830` 按后缀 `0..9` 升序扫描清单 `+12+index` 的非零标记，并调用 `0x2007C000(index,0)`。后者读取文件头，根据类型处理。对类型 `2 MAIN`、`8 BACKUP`、`6 EXTEND`，可进入通用写入函数 `0x2007BCB0`、file `0x30EB0`；类型 `5 ADJCOM` 直接进入解释器 `0x2007B9C0`。见 [写入摘录](evidence/06-unit-writer.txt)。

【推断】如果四个 A12 文件都已暂存且清单标记均启用，该循环的顺序是 `jlaunch0 → jlaunch3 → jlaunch4 → jlaunch8`。它是带前提的代码顺序，不能写成“每次正常更新都会依次重写这四个文件”。

【静态确认】通用写入函数按文件类型取得存储描述与回调表，检查容量和标志，再调用存储处理函数。其 MAIN 路径的回调包括 `0x20077540`（内容写入）和 `0x200778B4`（512 字节头部写入），检查回调为 `0x20077A1C`。通用函数先处理内容及校验，再在 `0x2007BFC4..0x2007BFD0` 调用 header 写入回调。存储分派和回调地址见 [存储分派](evidence/07-storage-dispatch.txt)及 [解码表](decoded-dispatch-tables.json)。

【静态确认】MAIN 的内容回调调用后端 `0x2008C27C`、`0x2008C55C`，并在启用 verify 时调用 `0x2008CA18`。BACKUP 与 MAIN 由不同类型构建存储范围。`0x2008C27C` 还包含块链和内部元数据处理，不能只按它的参数把 VMA 换算成物理擦除地址。

【未知】本次未完整还原后端的物理闪存页、擦除块、坏块映射和掉电提交规则，也未证明重写 MAIN 时任何物理别名都不会影响 BACKUP。头部后写是已读出的逻辑顺序，不是原子更新或断电恢复保证。

### 4.2 刷写时依靠哪些单元代码

【静态确认】MAIN 映像中的接收、检查、写入函数位于 `0x2007xxxx..0x2008xxxx`；BACKUP 映像另外包含对应接收任务和更新函数。BACKUP 的注册器位于 `0x27E3C390`，检查命令 `10` 注册到 `0x27E3A528`，写入命令 `3` 注册到 `0x27E3A62C`；后者调用 `0x27E3BE18` 的逐文件处理循环。对应文件偏移分别是 `0x3C590 / 0x3A728 / 0x3A82C / 0x3C018`。见 [BACKUP 摘录](evidence/09-backup-receiver.txt)。

【推断】如果 BACKUP 已被正确装载并初始化通信，它具备不调用 MAIN 地址的更新实现。这比只有“Backup prog blk”字符串更强，但还不是实机恢复成功的证明。

【未知】正常机身更新过程中，单元究竟保持 MAIN 运行、先切 BACKUP，还是由更早启动层协调，现有局部调用关系不足以判定。MAIN 段表和 BACKUP 装载地址也不能独自证明处理器当时执行哪份代码。

### 4.3 MAIN 崩溃后的入口仍缺什么

【静态确认】`jlaunch0` 入口 `0x27E00000` 设置栈、PSW，并执行 `trap #0x2`、`trap #0x0`，之后初始化程序。映像中有“MainLoad error”与“booted with Backup Prog”诊断文字，`0x27E2C1E4` 附近有打印启动原因的分支。文字和分支证明代码能表示这种启动原因，不能证明复位代码怎样产生该原因。见 [BACKUP 摘录](evidence/09-backup-receiver.txt)。

【静态确认】本目标的四个 `jlaunch*` 文件里没有类型 `1 MONITOR` 文件。包中其他单元的 `l06firm5` 虽然类型为 `1`，不能移用于 A12 50mm 的启动链分析。`Boot & Monitor`、`Backup prog blk`、`Main prog blk` 是分区诊断标签，不能把标签当作不可写保护或自动回退逻辑。

【未知】尚未取得并识别 A12 50mm 真正硬件复位层或 MONITOR 的完整映像，也未确定 `trap` 服务、启动选择、坏 MAIN 判定及从运行崩溃切换 BACKUP 的条件。机身 `Safe Boot` 相关字符串同样没有在本次追踪中闭合到可操作入口。

【推断】即使之后证明 MONITOR 在 MAIN 校验失败时启动 BACKUP，也仍要单独回答“校验通过但运行时崩溃”。修改后的程序若具有正确加权和，可能通过载入检查，随后在错误代码中停机；载入错误回退不能覆盖这个故障。

【未知】BACKUP 是否在每次 MAIN 写入时保持完全不变、是否具备写保护、更新中断后谁还能启动、机身能否主动请求 BACKUP，这四项都没有充分证据。不能用过去“28 个文件保持官方”来代替这些答案。

## 5. 完整性检查及修改文件的必要条件

### 5.1 已定位的校验

【静态确认】相同 36 字节加权和函数出现在 `jlaunch3` VMA `0x200759EC`、file `0x2ABEC` 和 `jlaunch0` VMA `0x27E3553C`、file `0x3573C`；机身两份程序也有相同函数。匹配记录见 [checksum-function-matches.json](checksum-function-matches.json)。函数及头部检查见 [校验摘录](evidence/08-checksum-header.txt)。

【静态确认】公式如下，`source` 来自头部 BE32 `+0x20`，`N` 来自 BE32 `+0x164`。覆盖的是 payload，结果按 32 bit 回卷；这不是数字签名。

```text
P = file[0x200 : 0x200 + N]
C = sum(P[i] * (((source + i) % 6) + 2) for i in range(N)) mod 2^32
stored C = BE32(file + 0x16C)
```

| 级别 | 文件 | 起始 phase = `source % 6` | 官方保存值与本次复算值 |
|---|---|---:|---|
| 静态确认 | `jlaunch0` | 2 | `0x102B95E6`，一致。 |
| 静态确认 | `jlaunch3` | 0 | `0x42F515C2`，一致。 |
| 静态确认 | `jlaunch4` | 0 | `0x0AAA7C7F`，一致。 |
| 静态确认 | `jlaunch8` | 0 | `0x00E43CF5`，一致。 |

【静态确认】`0x20075BA0` 在 `header+0x174 == 1` 时调用头部检查，在 `header+0x178 == 1` 时复算 payload 并与 `header+0x16C` 比较。头部检查包括标识、形式、总长度和类型对应的装载范围。文件检查路径 `0x2007A6A8` 还通过 `0x2007A47C` 分块计算同一加权和；因此它不只是一个脱离更新代码的通用函数。

【静态确认】通用处理路径受头部 flags 约束，并有写后 verify。对 MAIN，内容回调里的后端比较调用与头部单独写入可定位；对 ADJCOM，完整性检查后进入命令解释器，而非照搬 MAIN 的二进制写入步骤。

【未知】本次没有定位数字签名验证，但“没有定位”不足以排除所有启动层或协议层认证。也没有证明单元每次上电都使用同一套 payload 检查，或校验失败必定进入机身可用的恢复模式。

### 5.2 什么修改才有资格进入后续研究

【推断】同长度 payload 修改至少要满足正确 `NL1` 标识、类型、形式、文件与 payload 长度、段表与装载范围、兼容性及版本策略，并重算 `+0x16C`。还要通过实际采用协议分支的校验和 verify。当前只证明了其中部分检查，不能给出“只改加权和就一定接受”的结论。

【推断】首个演练应保留版本字段、兼容字段、flags、入口、段表和未修改文件。关闭检查或提高版本号都会改变恢复前提，不适合作为可逆性的起点。即便所有字节检查都通过，恢复入口仍须另有证据。

## 6. `jlaunch8` 为什么不能先当作更安全的变体

【静态确认】官方 payload 共 10,100 行：`V` 5,048 行、`W` 5,047 行、`X` 2 行、`U` 2 行、`#` 注释 1 行。命令字符是 ASCII，注释含 CP932 日文。开头为 `X12C0`、`X12C0`、`UEEF1`、`V0002`、`W0151`，末行为 `UEE00`。详见 [命令统计](jlaunch8-command-census.json)及 [原样 payload 摘录](jlaunch8-payload.txt)。

【静态确认】`0x2007B9C0` 读取命令行，跳过 `#` 或 `;` 开头的注释，对普通命令检查行长与空格后调用 `0x2005AE30`。后者解析命令与十六进制值，最终通过 `0x2005AD3C` 查表调用处理函数。见 [ADJCOM 解释器](evidence/10-adjcom-interpreter.txt)。

【未知】`UEEF1`、`UEE00` 以及全部 `V/W/X` 的持久化对象、提交规则和错误退出语义尚未还原；不能仅凭命令字母声称它写的是 EEPROM、色彩表或普通文件。`V0002; W0151` 是否就是版本页的 `ADJD` 字段，也未证明。

【推断】命令脚本可能改变程序文件之外的持久状态，且执行到一半可能已产生副作用。刷回 MAIN 不必然撤销这种状态；重新执行官方 ADJCOM 是否能恢复所有受影响字段，仍需逐命令证明。因此暂时没有依据判定修改 `jlaunch8` 比修改 MAIN 的显示字符串更安全。

## 7. 故障位置与可恢复边界

【推断】正常机身更新器至少需要机身 UI、单元识别、通信接收、文件检查、存储写入以及重新启动全部可用。UI 运行在机身只覆盖第一项。下表是依赖分析，不是相机故障注入结果。

| 级别 | 故障 | 正常更新器的可达性判断 |
|---|---|---|
| 推断 | 仅在按下快门后的特定处理代码中崩溃。 | 若更新启动路径从不执行该代码，且单元初始化、通信与写入路径正常，则有条件可达。需证明更新路径隔离。 |
| 推断 | 仅在 live view 中崩溃。 | 若更新启动可跳过 live view，且单元仍响应命令，则有条件可达。机身能显示更新页不等于单元尚未启动 live view。 |
| 未知 | MAIN 在初始化通信前崩溃。 | MAIN 中的接收器无法成为恢复依据；必须证明更早层或 BACKUP 可独立启动并响应。 |
| 未知 | MAIN 校验错误、头部坏或内容被截断。 | 缺少实际 MONITOR 的错误处理与回退链，不能保证机身仍能检测并更新。 |
| 未知 | MAIN 加权和正确，但入口或早期任务崩溃。 | 载入检查可能放行，尚无证据证明启动失败计数或机身强制 BACKUP 能救援。 |
| 未知 | ADJCOM 改坏单元启动依赖的持久状态。 | 即使程序与 BACKUP 完整，也可能影响硬件、通信或初始化。官方脚本是否覆盖所有改坏字段未证明。 |
| 未知 | 擦写 MAIN 时断电。 | 头部后写不足以证明掉电可恢复；物理擦除和提交规则未闭合。 |
| 未知 | BACKUP 或共同的启动、通信、闪存元数据损坏。 | 正常更新所需共同路径可能失效；本次没有已证明的外部救援途径。 |

【推断】可恢复与不可恢复的实际边界，是仍有一份可启动、可通信、可写回官方内容的单元执行环境，以及机身能把该环境带进更新模式。修改触及共同启动路径或持久依赖时，正常更新恢复的论证就失效。目前尚不能把这条功能边界换成一组已经证明安全的物理闪存地址。

## 8. 最小演练设计，均未达到可写入条件

### 8.1 MAIN：只改显示用文本，保留版本策略

【推断（设计）】首选是同长度、单字节、无格式占位符的显示文本替换，保持头部版本 `0x0151/0x0000` 及兼容字段不变，只重算 payload 加权和。不要把修改 `+0x12` 或 `+0x14` 的版本号当作无害演练：它可能影响选择、降级或恢复条件。

【静态确认】一个具体的候选文本位于 `jlaunch3` file `0x7A2F8`、VMA `0x200C50F8`：`RICOH GR LENS A12 50mm F2.5 MACRO`。末尾 `O` 位于 file `0x7A318`、VMA `0x200C5118`。见 [数据摘录](evidence/13-data-and-labels.txt)。

【推断（设计）】可研究把该 `O` 的 `0x4F` 换成 `0x30`，让标签变为 `MACR0`。该候选只变一个字符，既不改代码指令，也不改数字版本；若它只用于输出镜头名称，就能从版本信息或照片元数据观察标记。

【未知】该结构的全部消费者、名称是否参与识别或查表、以及机身实际显示或写出此文本的位置未查明。有限 xref 没有找到直接消费者，不能代替数据流审计。因此这是有精确位置的候选，不是已证明无害的 patch；目前不能承诺版本页或照片中一定可见。

【推断（设计）】该演练需要依次满足以下条件，才有完整的恢复论证：

1. 【推断（设计）】先只读证明文本全部消费者都属于显示或元数据输出，并指定一个确定的相机观察位置。若无法证明，放弃该位置，继续找专用显示字符串。
2. 【推断（设计）】证明同版本 MAIN 确实会被写入，且官方 `0x0151/0x0000` 能覆盖演练后的相同版本；仅在更新页看到该版本不够。
3. 【推断（设计）】证明 MAIN 不运行时仍能进入恢复环境，并证明重写 MAIN 不破坏这份环境。普通显示修改成功后再刷回，并不能覆盖早期启动崩溃。
4. 【推断（设计）】在另行批准的实机任务中，才开展“修改 → 写入 → 冷启动观察标记 → 刷回官方 → 冷启动确认标记消失”，保存单元写入证据、版本、观察结果和官方恢复证据。本任务没有执行这些动作。

【未知】当前第 1–3 项均未闭合。若今后该演练成功，最多先证明这个特定文本修改可逆，不能外推到任意 MAIN hook、启动故障或 ADJCOM 修改。

### 8.2 ADJCOM：注释变体与版本字段变体

【静态确认】官方脚本已有一个 `#` 注释，解释器会跳过这种行。纯注释内的同长度 ASCII 标记替换不需要改变后续命令含义，但仍改变文件加权和。

【推断（设计）】注释内标记可以作为“文件校验与传送”研究的控制变体；若以后具有可信的单元暂存文件读回证据，可比较原始文件与带标记文件。但它不会改变相机界面，也没有证据表明该注释会持久保存到重启之后，不能满足用户要求的可见演练，更不能单独证明单元实际重刷。

【推断（设计）】可见的 ADJCOM 变体必须先定位一个仅用于显示、可完整恢复的持久字段，解出写入该字段的精确命令和官方反向覆盖行为，再只改该字段。不能直接把开头的 `W0151` 改成另一个版本数值，也不能凭 `V0002` 猜测地址或用途。

【未知】目前没有达到上述条件的字段或命令，因此没有可交给构建者的“更安全、可见、可恢复” `jlaunch8` 方案。该设计保持阻塞，不能以“数据文件风险低”为由先刷。

## 10. 证据重跑入口与分析局限

【静态确认】本目录新增的 [inspect.py](inspect.py)、[query.py](query.py)、[collect_evidence.py](collect_evidence.py)只用于读字节、复算加权和、调用 objdump 和生成证据。官方文件没有作为输出目标。主要结果包括头部解码、带 VMA 和 file offset 的 14 个摘录、命令统计、分派表和前后哈希。[verify_report.py](verify_report.py)核对文档链接、声明标签、脚本语法、校验结果及输入身份，结果见 [verification.json](verification.json)。

【静态确认】以下命令重跑分析结果，不构建固件；它们只运行本任务新增的脚本。

```sh
python3 -I research/unit_recovery/inspect.py inventory
python3 -I research/unit_recovery/collect_evidence.py
python3 -I research/unit_recovery/inspect.py after
python3 -I research/unit_recovery/verify_report.py
```

【静态确认】新反汇编位于 [disasm/](disasm/)。每份文件保存官方 SHA-256、切片 SHA-256、VMA 与文件范围、换算公式和实际 objdump 命令。重建全部反汇编的命令清单见 [disassembly-commands.json](disassembly-commands.json)。工具参数是 `-D -b binary -m m32r -EB --adjust-vma=...`，没有运行目标指令。

【未知】线性反汇编不能自动区分全部代码与数据，也不证明完整调用图、动态寄存器目标、运行时分支、硬件 watchdog 或掉电行为。有限常量搜索的无命中不能证明不可达；上述限制已纳入结论。
